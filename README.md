# Платформа партнерских сайтов провайдеров

Монорепозиторий локального прототипа платформы для партнерских сайтов интернет-провайдеров. В коде реализован первый вертикальный срез для Дом.ру: статическая публичная витрина Release 1 с общей главной, единой блочной HOME каждого города импортированного каталога, картой покрытия, региональным каталогом городов с поиском и тремя legal-страницами, API, PostgreSQL-модель, импорт городов и тарифов, управляемый sitemap index, одношаговые HTTP 301, прием заявок, журнал заявок, история изменений CMS и фоновые задачи.

Текущий статус на 15 сентября 2026 года: **прототип с защищенным внешним test-контуром**. Решение о допуске реального трафика принимает только владелец; технические и юридические проверки в документации дают ему evidence, но не подменяют это решение. Код формирует точный набор маршрутов Release 1, а миграция публикует полный импортированный каталог городов и пять обязательных общих страниц. Три legal-текста адаптированы для `tv-internet-dom.ru`; реквизиты оператора и получателей нужно подтвердить до снятия парольной защиты. Состояние внешнего test-контура подтверждается отдельно и не выводится из локального кода. Точная граница между работающими возможностями, демонстрационными интерфейсами и планом находится в [состоянии проекта](docs/current-state.md).

Раздел `/seo/templates` в админке управляет обязательными Title, Description и индексируемостью восьми типов страниц Release 1; необязательные Open Graph Title/Description/image получают явный fallback. Новая публикация разрешает переменные по каждому URL, а `noindex` сохраняет HTML, но убирает URL из sitemap. Исторические Page/Tariff SEO JSON пока сохранены для отдельной сверки и очистки. Миграция `0047_seo_templates` подтверждена живым admin API; дополнение `0048_seo_open_graph` пока требует отдельного deployment.

## Локальный запуск

Нужны Node.js 22.23.2, Corepack, Docker Engine с Compose и pnpm 11.19.0. Другие совместимые Node 22 могут работать, но проверяемый baseline закреплен в [технологической базе](docs/technology-baseline.md).

```powershell
Copy-Item .env.example .env
docker compose up -d postgres redis
pnpm install --frozen-lockfile
pnpm db:generate
pnpm --filter @provider/database migrate:deploy
pnpm --filter @provider/database seed
```

Затем запускайте приложения в отдельных терминалах:

```powershell
pnpm dev:api
pnpm dev:web
pnpm --filter @provider/admin dev
pnpm dev:worker
```

Seed создаст опубликованный сайт `domru-site` с видимым названием «Дом.ру» и demo-город `kazan`, одну городскую страницу `HOME` с канонической композицией из семи управляемых блоков и, только если каталог города пуст, два демонстрационных тарифа без цен. Пять обязательных общих страниц создаются отдельно от города в `PUBLISHED`; legal-страницы используют версионированные тексты public web. Повторный запуск не перезаписывает найденные global pages и не возвращает demo-тарифы после полного импорта. Production-каталог формируется XLSX-импортом, который публикует все 207 городов и создает для каждого нового города такую же единственную `HOME`; `/kazan` в seed остается только локальным примером. Локальная команда сначала собирает API, затем запускает тот же CommonJS entrypoint `apps/api/dist/seed.js`, который используется production bootstrap, и сама загружает корневой `.env`; для входа в API seed требует в нем непустые `ADMIN_EMAIL` и `ADMIN_PASSWORD`.

После запуска API полный справочник из 207 городов можно сначала проверить, а затем применить через административный HTTP API:

```powershell
pnpm cities:import
pnpm cities:import -- --apply --actions=data/imports/city-actions.json
```

Команда использует [data/imports/cities.xlsx](data/imports/cities.xlsx), переводит примененные города во внутренний статус `PUBLISHED`, а для нового города создает `HOME` с каноническими блоками. Это сохраняет рабочую версию CMS, но не меняет уже опубликованный сайт до отдельной успешной публикации. Нужен тот же `ADMIN_API_TOKEN`, с которым запущен API; подробности — в [описании источника](data/imports/README.md).
Перед применением admin `/cities/import` показывает каждую валидную строку, старые и новые значения и требует выбрать `update`/`skip` для существующего slug либо `create`/`skip` для нового. Apply и guarded undo сохраняют только рабочую версию, а общий publication control отдельно запускает публикацию точного снимка сайта. Undo доступен, пока затронутые записи не менялись позже и у созданных городов не появились страницы, тарифы, заявки, проверки адреса или редиректы. Каталог, поиск и боковая форма управления названием и статусом города находятся на `/cities`; глобальные телефоны подключения и техподдержки редактируются на вкладке «Значения сайта» в `/variables` и попадают на сайт только после общей публикации. Вторая вкладка показывает read-only каталог системных кодов, контекстные рабочие и опубликованные значения и места использования. Аналогично `/tariffs` содержит каталог, быстрый просмотр и переход в длинную форму `/tariffs/edit?id=...`, а XLSX-preview, применение, история и явная публикация вынесены на `/tariffs/import`. Канонический тарифный XLSX и редактор не принимают `show_on_site`; быстрый просмотр до отдельной очистки legacy-данных может показать только ранее сохраненную рекомендацию, которая не управляет публикацией. Full-snapshot импорт не удаляет отсутствующие тарифы: он архивирует их с причиной, временем и ссылкой на import run, сохраняет связи заявок, а preview показывает `create/update/archive/unchanged` и измененные поля. Guarded undo возвращает точное предыдущее lifecycle-состояние, если после apply не было конфликтующих изменений. На публичных карточках и странице тарифа `connection_cost = 0` выводится как «Бесплатное подключение», положительное значение — как стоимость, а пустое поле не создает строку. API принимает только полный action map текущего validation report и отклоняет устаревший preview. CLI не подставляет решения автоматически: с `--apply` обязателен `--actions=<path>` к JSON-объекту вида `{ "kazan": "update", "innopolis": "skip" }`, содержащему действие для каждого кандидата.

## Проверка рабочего дерева

```powershell
pnpm check
```

Один скрипт, который делает `lint` → `db:validate` → `ALLOW_DEMO_DATA=true build` → `test` в этом порядке — тот же, что использует CI (`.github/workflows/ci.yml` на каждый push/PR в `master`). По отдельности:

```powershell
pnpm lint
pnpm db:validate
$env:ALLOW_DEMO_DATA = "true"; pnpm build
pnpm test
```

`apps/web` получает build-time каталог опубликованных городов, их регионов, общих страниц, тарифных предложений, точный `routes` inventory и редиректы из API через server-only `SITE_DATA_API_URL`; при его отсутствии для обратной совместимости используется `PUBLIC_API_URL`, который отдельно встраивается в browser-формы. В целевом Coolify-контуре publisher запрашивает отдельный защищенный build-каталог из неизменяемого снимка одной рабочей ревизии, а публичные API и redirect resolver продолжают читать последний успешно опубликованный снимок. Все текущие content mutators — ручные изменения сайта, региона, города, страницы, блока, тарифа и редиректа, изменение провайдера, программный import тарифов и apply/undo обоих XLSX-импортов — только сохраняют рабочую версию с before/after audit; отдельный admin API фиксирует ожидаемую ревизию и запускает ее публикацию. Личный `/preview` читает текущий рабочий catalog через cookie-auth API, показывает любой URL Release 1 в изолированном desktop/tablet/mobile iframe и не создает publication snapshot; неполная HOME или конфликт маршрутов блокируют отображение теми же catalog-проверками. На `/audit` оператор фильтрует журнал одного сайта по сущности, действию, ID, источнику или автору и открывает значения полей до/после без загрузки тяжелого diff в общий список. `/trash` объединяет архивные города, страницы, тарифы, редиректы и блоки; восстановление требует подтверждения, возвращает статусные сущности как `DRAFT` и также остается рабочей правкой до публикации. На экранах тарифов, городов и редиректов и в обоих XLSX-импортах общий блок показывает рабочую и опубликованную версии, позволяет запустить публикацию сразу либо запланировать точный неизменяемый снимок и отменить его до наступления срока. Следующие сохранения не входят в уже запланированный снимок; worker каждую минуту передает наступившие расписания в тот же rebuild-flow. При ожидании или ошибке сайт продолжает показывать предыдущую опубликованную версию. Release 1 всегда содержит `/`, пять общих маршрутов, `/{location}` каждого опубликованного города и `/{location}/{tariffSlug}` каждого опубликованного тарифа этого города: всего `N + T + 6` HTML-страниц (индексируемых может быть меньше при `noindex`) и общую 404. Страница тарифа собирается одним типизированным программным шаблоном для `INTERNET` и `INTERNET_TV`: он разделяет текущую и обычную промо-цену, явно показывает отсутствие ТВ у интернет-тарифа и условно добавляет кинотеатры, оборудование, игру и дополнительные сервисы только из валидных структурированных значений. Неизвестный атрибут или системный код блокирует сборку вместо вывода догадки; карточка города ведёт как на detail, так и к быстрой проверке адреса. Service detail остаются вне Release 1. Каждый опубликованный город обязан иметь ровно одну HOME с пустым slug и канонической последовательностью из семи блоков: DB/admin не допускают повторную HOME, а API и web fail-closed отклоняют отсутствующую, повторную, неканоническую или неполную HOME. Несовпадающий inventory и коллизии URL блокируются вместо вывода fallback-шаблона. Все публичные HTML-URL, кроме корня `/`, канонизируются без завершающего слэша; slash-вариант получает один HTTP 301 с сохранением query string, а API и asset namespaces не затрагиваются. Production build требует `PUBLIC_SITE_URL` в виде чистого HTTPS origin, а `PUBLIC_API_URL` — в виде внешнего HTTPS base URL с точным path `/api/v1`; отсутствие любой обязательной опубликованной общей страницы, лишний или конфликтующий маршрут, неполная городская HOME, пустые/небезопасные origin либо цепочка redirects осознанно блокируют сборку. После `astro build` pre-publication SEO gate сверяет sitemap с готовыми `*/index.html`, canonical, title, description, H1, robots, loopback-утечки и неиндексируемую 404. `ALLOW_DEMO_DATA=true` явно разрешает демонстрационный Release 1 и loopback URL только для разработки и локальной проверки без поднятого API.

Прямой `docker-compose.prod.yml` принимает `SITE_DATA_API_URL` отдельно от browser API и требует уже доступный источник каталога на стадии image build. Для целевого Coolify-контура это ограничение снято отдельным `docker-compose.coolify.yml`: images собираются без обращения к каталогу, затем runtime-цепочка `migrate → api → bootstrap-seed → web-publish → web` создает проверенную static-публикацию из внутреннего API. API использует отдельные кешируемые dependency stages: облегченный production runtime и migration image с Prisma CLI; migration target переиспользует уже установленный build dependency tree, а `api` и `bootstrap-seed` разделяют один runtime image без повторного build target. Для совместимости с pre-stop pull Coolify 4.3.19 `bootstrap-seed` задает `pull_policy: never`, поэтому общий локально собранный API image не запрашивается из Docker Hub. Все Docker install stages используют общий BuildKit pnpm-store cache, повторяют transiently failed install с уже заполненным store и доверяют frozen lockfile только внутри production image build; обычный CI install продолжает независимо проверять supply-chain policy. Publisher устанавливает только зависимости `apps/web`, admin — только `apps/admin`, worker — только свои production-зависимости, поэтому повторный export не переносит весь monorepo `node_modules`. Publication symlink заменяется атомарным `mv -fT`: команда не следует уже существующей ссылке на каталог и не оставляет `current` битой после очистки предыдущего release. Завершенные one-shot services явно исключены из Coolify health-оценки, а API, worker, web и admin имеют собственные healthchecks. Точные датированные deployment-доказательства хранятся в [эксплуатационной документации](docs/deployment.md), а не используются здесь как текущий status cache.

Целевой внешний test-контур развертывается из GitHub через Coolify на `tv-internet-dom.ru`, без дополнительного `stage`-контура. `web` (`tv-internet-dom.ru`) и `admin` (`admin.tv-internet-dom.ru`) публикуются через Coolify proxy; browser security middleware стоит перед общим Basic Auth, поэтому HSTS, `nosniff`, Referrer/Permissions Policy и frame policy применяются также к неавторизованному `401`. API остается внутренним и доступен браузеру через same-origin `/api/*`. Astro добавляет к каждому HTML hash-based CSP: public разрешает только необходимые endpoints Яндекс Метрики при включенном счетчике, admin — свой API origin; единственное `unsafe-inline` ограничено `style-src-attr` админки для используемых Radix checkbox. Public framing разрешен только себе и официальным Webvisor origins без конфликтующего `X-Frame-Options`, admin запрещает framing через `frame-ancestors 'none'` и `X-Frame-Options: DENY`. Для Compose bcrypt verifier хранится в Coolify как `Literal`, доступный на Buildtime и Runtime, а `Escape special characters in labels` выключен: иначе `$` экранируется до `$${...}` либо переменная отсутствует во время `docker compose build`. Админка намеренно вынесена на поддомен и получает явный `X-Robots-Tag: noindex, nofollow, noarchive`.

Для автоматических пересборок worker поддерживает два явных provider-режима. Legacy `webhook` по-прежнему требует синхронный финальный `SUCCEEDED`; целевой `coolify` запускает resource через API, сохраняет `deployment_uuid` в `SiteRebuild`, ограниченно опрашивает статус и публикует ревизию только после `finished`. `queued`/`in_progress`, timeout и повтор worker не создают ложный success; незавершенный deployment возобновляется по сохраненному UUID. Реализация #57 подтверждена реальным Coolify polling rehearsal.

В production Compose отдельный one-shot сервис `migrate` применяет Prisma migrations после готовности PostgreSQL и до старта API. `/api/v1/health/live` проверяет процесс, а `/api/v1/health/ready` и совместимый `/api/v1/health` требуют доступных PostgreSQL и Redis. В Coolify worker отдельно проверяет Redis, а web/admin — ответ своего локального Caddy. Seed остается явным одноразовым шагом: его нельзя безопасно выполнять при каждом деплое.

Защищенный `GET /api/v1/admin/readiness` показывает, какие интеграции DaData, проверки провайдеров Tarifnik, общего endpoint проверки действующего абонента Дом.ру, доставки в CRM Tarifnik, email/rebuild и PII retention policy сконфигурированы, и остается `blocked`, пока обязательные переменные пусты. Городские профили Дом.ру находятся в версионированном несекретном справочнике API, а не в environment. Endpoint никогда не возвращает значения секретов и не заменяет проверку реальных договоров, legal decision или sandbox-вызовы.

Публичные write-routes и login проходят строгую DTO-валидацию; лишние поля и заполненный скрытый honeypot отклоняются. Redis-backed rate limiting разделяет login, публичные формы и остальные маршруты; в production Compose доверие proxy headers включено только у API за Caddy. Worker ежедневно запускает bounded hard-delete просроченных лидов и связанных payloads через worker-only API, но только при явно заданном валидном `PII_RETENTION_DAYS`. Сам срок код не выбирает: legal decision остается блокером production.

В `/leads` оператор видит evidence каждого шага фонового решения и историю попыток. После исчерпанной технической ошибки DaData Phone он может запросить новую проверку без обхода правил доставки; переанализ комментария доступен только при новой версии правил и сохраняет прежний результат с автором. Эти действия не изменяют исходную причину заявки.

На дату документации release gate зеленый. Актуальный числовой baseline и состав сценариев, включая глобальный DaData suggest/clean, мягкое ранжирование через IPLocate с безопасным fallback, межгородскую проверку адреса с сохранением source-контекста страницы, официальный Tarifnik address/delivery contract, BullMQ-safe постановку и восстановление доставки, полный регионально однозначный справочник профилей Дом.ру, безопасную retry-политику, API input security, PII retention, infrastructure/release readiness, browser security headers и hash-based CSP, migration dependency, Docker dependency-layer caching, filtered runtime images и Compose health policy, Node 24 runtime GitHub Actions, русские статусы и безопасный retry заявок в админке, экраны тарифов, городов, редиректов, рабочего preview, журнала изменений, корзины и расписания публикаций, browser CORS, отсутствие выведенного из эксплуатации CRM-workspace, канонический справочник, full-snapshot импорт, одношаговые 301, Coolify polling/retry, production origin и pre-publication SEO gate public web, ведутся только в [docs/TEST_COVERAGE.md](docs/TEST_COVERAGE.md).

Тарифная detail-страница с известной базовой ценой показывает предварительный конфигуратор. Варианты и суммы вычисляет публичный API только из последнего успешно опубликованного снимка; неизвестные цены не заменяются нулём. Форма передаёт выбор и отпечаток расчёта; API повторно проверяет их по опубликованному снимку и сохраняет неизменяемые строки и итоги в заявке. Окончательные условия подтверждает оператор.

Системные текстовые подстановки V1 разрешаются сервером при построении рабочего каталога и сохраняются как готовый текст в снимке публикации. Фиксированный реестр охватывает телефоны Site, имя Provider, формы City, имя/скорость/цену/каналы Tariff и год; неизвестный код или подстановка в URL блокирует снимок, известное пустое значение сопровождается предупреждением с путем к полю. Экран каталога кодов и статистика использования пока не реализованы.

## Безопасность и данные

Не добавляйте `.env`, токены внешних API, пароли или реальные данные заявок в Git. Единый локальный источник секретных значений — корневой `.env`, production-источник — Coolify Environment Variables; `.env.example` содержит только имена и безопасные шаблоны. В новом окружении DaData, проверка провайдеров, проверка договора, Tarifnik и email отключены, пока для них не заданы обязательные переменные. Sales-заявка сначала сохраняется, затем фоново проходит DaData Phone и проверку договора; без необходимых credentials она остается оператору после технических попыток, но не считается переданной в кол-центр.
