## Локальный запуск

Нужны Node.js 22.23.2, Corepack, Docker Engine с Compose и pnpm 11.19.0. Другие совместимые Node 22 могут работать, но проверяемый baseline закреплен в [технологической базе](docs/technology-baseline.md).

```powershell
Copy-Item .env.example .env
docker compose up -d postgres redis
pnpm install --frozen-lockfile
pnpm db:generate
pnpm --filter @provider/database migrate:deploy
pnpm --filter @provider/database seed
```

Затем запускайте приложения в отдельных терминалах:

```powershell
pnpm dev:api
pnpm dev:web
pnpm --filter @provider/admin dev
pnpm dev:worker
```

Seed создаёт опубликованный сайт `domru-site` с видимым названием «Дом.ру» и demo-город `kazan`, одну городскую HOME-shell со ссылкой на site-scoped `PageTemplate(CITY_HOME)` с двумя общими блоками (Hero и тарифы) и, только если каталог города пуст, два демонстрационных тарифа без цен в DRAFT. Создаются также HOME Hero и восемь SEO-шаблонов; новый каталог проходит публикационный preflight без публикации неподтверждённых тарифов. Пять обязательных общих страниц создаются отдельно от города в `PUBLISHED`; legal-страницы используют версионированные тексты public web. Весь bootstrap выполняется одной транзакцией и требует credentials до записи. Повторный запуск сохраняет существующие страницы, шаблоны, SEO, телефоны и пароль администратора и не возвращает demo-тарифы в непустой каталог. Seed не создаёт публикацию или rebuild. Production-каталог формируется XLSX-импортом, который публикует все 207 городов и создает для каждого нового города только HOME-shell со ссылкой на тот же site-scoped шаблон; `/kazan` в seed остается только локальным примером. Локальная команда сначала собирает API, затем запускает тот же CommonJS entrypoint `apps/api/dist/seed.js`, который используется production bootstrap, и сама загружает корневой `.env`; для входа в API seed требует в нем непустые `ADMIN_EMAIL` и `ADMIN_PASSWORD`.

После запуска API полный справочник из 207 городов можно сначала проверить, а затем применить через административный HTTP API:

```powershell
pnpm cities:import
pnpm cities:import -- --apply --actions=data/imports/city-actions.json
```

Команда использует [data/imports/cities.xlsx](data/imports/cities.xlsx), переводит примененные города во внутренний статус `PUBLISHED`, а для нового города создает `HOME` с каноническими блоками. Это сохраняет рабочую версию CMS, но не меняет уже опубликованный сайт до отдельной успешной публикации. Нужен тот же `ADMIN_API_TOKEN`, с которым запущен API; подробности — в [описании источника](data/imports/README.md).
Перед применением admin `/cities/import` показывает каждую валидную строку, старые и новые значения и требует выбрать `update`/`skip` для существующего slug либо `create`/`skip` для нового. Apply и guarded undo сохраняют только рабочую версию, а общий publication control отдельно запускает публикацию точного снимка сайта. Undo доступен, пока затронутые записи не менялись позже и у созданных городов не появились страницы, тарифы, заявки, проверки адреса или редиректы. Каталог, поиск и боковая форма управления названием и статусом города находятся на `/cities`; глобальные телефоны подключения и техподдержки редактируются на вкладке «Значения сайта» в `/variables` и попадают на сайт только после общей публикации. Вторая вкладка показывает read-only каталог системных кодов, контекстные рабочие и опубликованные значения и места использования, включая исходные SEO/OG-шаблоны со ссылками на их редактор. Аналогично `/tariffs` содержит каталог, быстрый просмотр и переход в длинную форму `/tariffs/edit?id=...`, а XLSX-preview, применение, история и явная публикация вынесены на `/tariffs/import`. Канонический тарифный XLSX и редактор не принимают `show_on_site`; быстрый просмотр до отдельной очистки legacy-данных может показать только ранее сохраненную рекомендацию, которая не управляет публикацией. Full-snapshot импорт не удаляет отсутствующие тарифы: он архивирует их с причиной, временем и ссылкой на import run, сохраняет связи заявок, а preview показывает `create/update/archive/unchanged` и измененные поля. Guarded undo возвращает точное предыдущее lifecycle-состояние, если после apply не было конфликтующих изменений. На публичных карточках и странице тарифа `connection_cost = 0` выводится как «Бесплатное подключение», положительное значение — как стоимость, а пустое поле не создает строку. API принимает только полный action map текущего validation report и отклоняет устаревший preview. CLI не подставляет решения автоматически: с `--apply` обязателен `--actions=<path>` к JSON-объекту вида `{ "kazan": "update", "innopolis": "skip" }`, содержащему действие для каждого кандидата.

В редакторах SEO-шаблонов и тарифов доступна контекстная вставка системных кодов в текстовые поля; сохранение SEO/OG-текстов и промотекста тарифа проверяет коды до записи. Локальные SEO-значения страниц и тарифов нельзя изменить через admin API: метаданные маршрутов задаются SEO-шаблонами сайта. Существующая публикация от этого не меняется — её запуск остаётся отдельным действием.

## Проверки перед коммитом и push

```powershell
pnpm check
```

`pnpm check` делает `lint` → `db:validate` → `ALLOW_DEMO_DATA=true build` → `test` в этом порядке; CI выполняет его на каждый push/PR в `master`. Локально полный gate запускают один раз перед push кода, а также перед коммитом изменений миграций, заявок, аутентификации, тарифного импорта/расчетов, публикации, публичных маршрутов, инфраструктуры или CI. Для обычной разработки достаточно проверок затронутого workspace и связанных тестов; для изменений только документации — `git diff --check` и сверки измененных ссылок и фактов. Точные правила и исключение повторного gate для неизменного состояния — в [AGENTS.md](AGENTS.md). По отдельности:

```powershell
pnpm lint
pnpm db:validate
$env:ALLOW_DEMO_DATA = "true"; pnpm build
pnpm test
```

Публичная сборка включает согласованный вариант 1 иконок с tarify-dom.ru: ICO 16/32/48, PNG 96, непрозрачный Apple Touch Icon 180 и манифест с PNG 192/512 (512 также maskable). PNG 96 и манифест имеют стабильные URL с перепроверкой кеша; ICO, Apple icon и изображения манифеста поддерживают версионирование публикации. Сборка проверяет набор ссылок на всех HTML-страницах, форматы/размеры файлов и манифест. [Контракт и источники](docs/research/2026-11-06-site-icons.md).

`apps/web` получает build-time каталог опубликованных городов, их регионов, общих страниц, тарифных предложений, точный `routes` inventory и редиректы из API через server-only `SITE_DATA_API_URL`; при его отсутствии для обратной совместимости используется `PUBLIC_API_URL`, который отдельно встраивается в browser-формы. В Coolify-контуре закрытый builder запрашивает exact неизменяемый publication snapshot; публичные API и redirect resolver читают снимок, который Caddy фактически обслуживает, включая восстановление SQL acknowledgment после активации. Все текущие content mutators — ручные изменения сайта, региона, города, страницы, блока, общего PageTemplate, тарифа и редиректа, изменение провайдера, программный import тарифов и apply/undo обоих XLSX-импортов — только сохраняют рабочую версию с before/after audit; отдельный admin API фиксирует ожидаемую ревизию и запускает ее публикацию. Личный `/preview` читает текущий рабочий catalog через cookie-auth API, показывает любой URL Release 1 в изолированном desktop/tablet/mobile iframe и не создает publication snapshot; неполная HOME или конфликт маршрутов блокируют отображение теми же catalog-проверками. На `/audit` оператор фильтрует журнал одного сайта по сущности, действию, ID, источнику или автору и открывает значения полей до/после без загрузки тяжелого diff в общий список. `/trash` объединяет архивные города, страницы, тарифы, редиректы и блоки; восстановление требует подтверждения, возвращает статусные сущности как `DRAFT` и также остается рабочей правкой до публикации. Для архивных тарифов доступна отдельная пакетная физическая очистка после постраничного предпросмотра, повторной проверки связей и подтверждения; связанные с заявками или историей записи сохраняются. На экранах тарифов, городов и редиректов и в обоих XLSX-импортах общий блок показывает рабочую и опубликованную версии, ведёт на общий `/publication` для проверки всех сохранённых изменений и ручного запуска точного снимка. Выбора даты и времени нет. При ожидании или ошибке сайт продолжает показывать предыдущую опубликованную версию. Release 1 всегда содержит `/`, пять общих маршрутов, `/{location}` каждого опубликованного города и `/{location}/{tariffSlug}` каждого опубликованного тарифа этого города: всего `N + T + 6` HTML-страниц (индексируемых может быть меньше при `noindex`) и общую 404. Страница тарифа собирается одним типизированным программным шаблоном для `INTERNET` и `INTERNET_TV`: он разделяет текущую и обычную промо-цену, явно показывает отсутствие ТВ у интернет-тарифа и условно добавляет кинотеатры, оборудование, игру и дополнительные сервисы только из валидных структурированных значений. Неизвестный атрибут или системный код блокирует сборку вместо вывода догадки; карточка города ведёт как на detail, так и к быстрой проверке адреса. Service detail остаются вне Release 1. Каждый опубликованный город обязан иметь ровно одну HOME с пустым slug и канонической последовательностью версии 3.0.0 из десяти блоков: DB/admin не допускают повторную HOME, а API и web fail-closed отклоняют отсутствующую, повторную, неканоническую или неполную HOME. Несовпадающий inventory и коллизии URL блокируются вместо вывода fallback-шаблона. Все публичные HTML-URL, кроме корня `/`, канонизируются без завершающего слэша; slash-вариант получает один HTTP 301 с сохранением query string, а API и asset namespaces не затрагиваются. Production build требует `PUBLIC_SITE_URL` в виде чистого HTTPS origin, а `PUBLIC_API_URL` — в виде внешнего HTTPS base URL с точным path `/api/v1`; отсутствие любой обязательной опубликованной общей страницы, лишний или конфликтующий маршрут, неполная городская HOME, пустые/небезопасные origin либо цепочка redirects осознанно блокируют сборку. После `astro build` pre-publication SEO gate сверяет sitemap с готовыми `*/index.html`, canonical, title, description, H1, robots, loopback-утечки и неиндексируемую 404. `ALLOW_DEMO_DATA=true` явно разрешает демонстрационный Release 1 и loopback URL только для разработки и локальной проверки без поднятого API.

Прямой `docker-compose.prod.yml` требует доступного каталога на стадии image build и сохраняет прежний внешний provider. В Coolify images собираются без каталога: `migrate → api → bootstrap-seed → web` запускает постоянный controller/Caddy на прежнем `web_publication` volume. API и worker принудительно используют `REBUILD_PROVIDER=static` и private `http://web:8081`; наружу открыт только web 80. Первый переход проверяет полный HTML fingerprint и exact published snapshot, сохраняет старые байты и assets, затем CODE после terminal deployment выпускает renderer. Runtime-only Coolify token и одноразовый migration proof читаются из `.env`, не требуют build scope. API migration/runtime разделяют кешируемые dependency stages, `bootstrap-seed` использует `pull_policy: never`; все Docker installs сохраняют frozen lockfile и общий pnpm-store. Seed после первого запуска явно выключен. Исторические deployment-доказательства — в [эксплуатационной документации](docs/deployment.md).

Целевой внешний test-контур развертывается из GitHub через Coolify на `tv-internet-dom.ru`, без дополнительного `stage`-контура. `web` (`tv-internet-dom.ru`) и `admin` (`admin.tv-internet-dom.ru`) публикуются через Coolify proxy; browser security middleware стоит перед общим Basic Auth, поэтому HSTS, `nosniff`, Referrer/Permissions Policy и frame policy применяются также к неавторизованному `401`. API остается внутренним и доступен браузеру через same-origin `/api/*`. Astro добавляет к каждому HTML hash-based CSP: public разрешает только необходимые endpoints Яндекс Метрики при включенном счетчике, admin — свой API origin; единственное `unsafe-inline` ограничено `style-src-attr` админки для скрытого input React Aria checkbox. Public framing разрешен только себе и официальным Webvisor origins без конфликтующего `X-Frame-Options`, admin запрещает framing через `frame-ancestors 'none'` и `X-Frame-Options: DENY`. Для Compose bcrypt verifier хранится в Coolify как `Literal`, доступный на Buildtime и Runtime, а `Escape special characters in labels` выключен: иначе `$` экранируется до `$${...}` либо переменная отсутствует во время `docker compose build`. Админка намеренно вынесена на поддомен и получает явный `X-Robots-Tag: noindex, nofollow, noarchive`.

Worker поддерживает три provider-режима. Coolify Compose закрепляет `static`: Astro build и атомарная Caddy-активация контента не создают deployment; неопределённый исход восстанавливается по receipt. После deployment runtime автоматически согласует renderer по runtime `SOURCE_COMMIT`, latest exact finished deployment и healthy resource, пересобирая только уже обслуживаемый snapshot. Рабочие изменения публикуются по ручному нажатию. Машинный `POST /internal/site-publications/:siteSlug/release-code` остаётся для диагностики/восстановления. Legacy `webhook` требует синхронного финального `SUCCEEDED`; legacy `coolify` сохраняет deployment UUID и принимает только `finished`.

Админка показывает этапы подготовки, сборки страниц, проверки, переключения сайта и подтверждения. Счётчики измеряются в реальном pipeline, время восстанавливается после reload. Приблизительный диапазон оставшегося времени доступен после трёх сопоставимых успешных запусков; ожидание CODE, повторная попытка и недоступность данных объясняются отдельно. Прогресс сам по себе не подтверждает публикацию.

В production Compose отдельный one-shot сервис `migrate` применяет Prisma migrations после готовности PostgreSQL и до старта API. `/api/v1/health/live` проверяет процесс, а `/api/v1/health/ready` и совместимый `/api/v1/health` требуют доступных PostgreSQL и Redis. В Coolify worker отдельно проверяет Redis, а web/admin — ответ своего локального Caddy. Seed остается явным одноразовым шагом: его нельзя безопасно выполнять при каждом деплое.

Защищенный `GET /api/v1/admin/readiness` показывает, какие интеграции DaData, проверки провайдеров Tarifnik, общего endpoint проверки действующего абонента Дом.ру, доставки в CRM Tarifnik, email/rebuild и PII retention policy сконфигурированы, и остается `blocked`, пока обязательные переменные пусты. Городские профили Дом.ру находятся в версионированном несекретном справочнике API, а не в environment. Endpoint никогда не возвращает значения секретов и не заменяет проверку реальных договоров, legal decision или sandbox-вызовы.

Публичные write-routes и login проходят строгую DTO-валидацию; лишние поля и заполненный скрытый honeypot отклоняются. Redis-backed rate limiting разделяет login, публичные формы и остальные маршруты; в production Compose доверие proxy headers включено только у API за Caddy. Worker ежедневно запускает bounded hard-delete просроченных лидов и связанных payloads через worker-only API, но только при явно заданном валидном `PII_RETENTION_DAYS`. Сам срок код не выбирает: legal decision остается блокером production.

В `/leads` оператор видит evidence каждого шага фонового решения и историю попыток. После исчерпанной технической ошибки DaData Phone он может запросить новую проверку без обхода правил доставки; переанализ комментария доступен только при новой версии правил и сохраняет прежний результат с автором. Эти действия не изменяют исходную причину заявки.

На дату документации release gate зеленый. Актуальный числовой baseline и состав сценариев, включая глобальный DaData suggest/clean, мягкое ранжирование через IPLocate с безопасным fallback, межгородскую проверку адреса с сохранением source-контекста страницы, официальный Tarifnik address/delivery contract, BullMQ-safe постановку и восстановление доставки, полный регионально однозначный справочник профилей Дом.ру, безопасную retry-политику, API input security, PII retention, infrastructure/release readiness, browser security headers и hash-based CSP, migration dependency, Docker dependency-layer caching, filtered runtime images и Compose health policy, Node 24 runtime GitHub Actions, русские статусы и безопасный retry заявок в админке, экраны тарифов, городов, редиректов, рабочего preview, журнала изменений, корзины, обзора ручной публикации и безопасного удаления прежней функции расписания, browser CORS, отсутствие выведенного из эксплуатации CRM-workspace, канонический справочник, full-snapshot импорт, одношаговые 301, Coolify polling/retry, production origin и pre-publication SEO gate public web, ведутся только в [docs/TEST_COVERAGE.md](docs/TEST_COVERAGE.md).

Тарифная detail-страница с известной базовой ценой показывает предварительный конфигуратор. Варианты и суммы вычисляет публичный API только из последнего успешно опубликованного снимка; неизвестные цены не заменяются нулём. Форма передаёт выбор и отпечаток расчёта; API повторно проверяет их по опубликованному снимку и сохраняет неизменяемые строки и итоги в заявке. Окончательные условия подтверждает оператор.

Системные текстовые подстановки V1 разрешаются сервером при построении рабочего каталога и сохраняются как готовый текст в снимке публикации. Фиксированный реестр охватывает телефоны Site, имя Provider, формы City, имя/скорость/цену/каналы Tariff и год; неизвестный код или подстановка в URL блокирует снимок, известное пустое значение сопровождается предупреждением с путем к полю. В `/variables` уже работают каталог кодов, контекстные значения и учет рабочих/опубликованных мест использования. ## Безопасность и данные

Не добавляйте `.env`, токены внешних API, пароли или реальные данные заявок в Git. Единый локальный источник секретных значений — корневой `.env`, production-источник — Coolify Environment Variables; `.env.example` содержит только имена и безопасные шаблоны. В новом окружении DaData, проверка провайдеров, проверка договора, Tarifnik и email отключены, пока для них не заданы обязательные переменные. ## Навигация админки

Рабочие разделы админки используют общий сохраняемый AdminWorkspace React-root. Меню, шапка и publication polling сохраняются, экраны монтируются заново по pathname/query; код выбранного раздела предварительно загружается по hover/focus ссылки. Совпадающие одновременные GET объединяются. Для быстрого возврата списки городов/тарифов, справочники, паспорта и read-only каталог подстановок используют ограниченный кэш в памяти сессии (до 30 секунд, до 32 ответов) с обязательной проверкой в фоне и явным состоянием обновления. Доступ проверяется на сервере при каждом запросе; смена пользователя/logout/401 сбрасывают данные. Любая мутация сбрасывает кэш при начале и завершении, завершение публикации — при смене publishedRevision. Поздние ответы прежнего поколения не восстанавливают кэш. Редакторы получают свежие данные и сохраняют expectedWorkingRevision; городская форма фиксирует ревизию прочитанной строки при открытии и недоступна до завершения проверки каталога. Несохранённые формы защищены при внутренних переходах и Back/Forward. `/preview`, login и lead-access сохраняют отдельные документы. [Измерения и границы проверки](docs/research/2026-10-08-admin-navigation-cache.md).
