> Архив исходного этапа. Все задачи #24–31 закрыты; закрытие #31 по решению владельца не означает выполнение дополнительной проверки #144. Действующие границы и следующая очередь — в [плане релизов](../../release-plan.md).

Статус: с 8 сентября 2026 этот файл — только историческое обоснование исходного состава и порядка задач. Пошаговые статусы, чек-листы и текущий прогресс ведутся в GitHub Issues (label `task`, milestone «Release 1: минимальный публичный запуск»). Каноническая структура релиза изменена 14 сентября и находится в [site-structure.md](../../site-structure.md); план перехода — в [2026-09-14-release-1-site-structure-transition.md](2026-09-14-release-1-site-structure-transition.md). Как устроена вся система — [docs/task-management.md](../../task-management.md). Не вести здесь чек-листы заново — это и была причина рассинхронизации, которую система из `task-management.md` устраняет.

**Goal:** довести локальный прототип до проверяемого первого MVP для одного сайта Дом.ру в Казани без публикации демо-данных, недостоверных статусов и незащищенных ссылок.

**Architecture:** сначала стабилизируется release gate и надежный контур данных. Затем единый outbox на BullMQ делает доставку лидов и пересборку наблюдаемыми. Публичный Astro-сайт получает build-time контракт, который блокирует production-сборку при недоступных данных, после чего расширяется от фиксированной Казани к опубликованным городам и страницам.

**Tech Stack:** pnpm 11, Node.js 22, TypeScript, Astro 7 static output, NestJS 12/Fastify, PostgreSQL 18, Prisma 7, Redis 8, BullMQ 6, Caddy, Docker Compose.

## Порядок и критерии остановки

[Task #31](https://github.com/Celtoman/astro-telekom/issues/31) закрыта 15 сентября 2026 года по прямому решению владельца и больше не используется как механический gate публикации или трафика. Незавершенные external API/legal вопросы, включая [#144](https://github.com/Celtoman/astro-telekom/issues/144), сохраняют собственные статусы; configuration gate TD-10 подтверждает только наличие переменных и не заменяет договоры, sandbox или SLA. Решение о готовности к трафику принимает только владелец. Каждая задача завершается тестом, документацией и проверкой реального результата, а не только компиляцией — это правило действует независимо от конкретного issue-трекера.

## Приемка MVP

Техническая приемка Release 1 требует, чтобы чистый production-like контур прошел `pnpm check`, миграции, build без demo fallback, raw HTML audit, endpoint health с БД, импорт полного тарифного снимка, наблюдаемую пересборку, проверку адреса, безопасную обработку заявки и sandbox-доставку. Отдельно фиксируются состояние реального контракта Tarifnik и правил работы с персональными данными. Точный состав HTML задает [site-structure.md](../../site-structure.md), а механическая проверка прогресса ведется в [milestone «Release 1: минимальный публичный запуск»](https://github.com/Celtoman/astro-telekom/milestone/1). Итоговое решение о допуске трафика принимает владелец, а не план или статус issue.
