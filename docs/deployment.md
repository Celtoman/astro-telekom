## Хранение публикаций

Старый HTML обслуживается отдельной [архивной retention](runbooks/publication-retention.md), не Docker prune. Host helper использует существующее S3-хранилище Coolify без передачи credentials в web; полное скачивание/восстановление архива обязательно до удаления. Приватный controller разделяет очередь с CMS/CODE и защищает active/baseline/две rollback/незавершённые операции и закреплённые восстановленные версии. До двух дополнительных подтверждённых версий за 24 часа сохраняются в бюджете 8 ГиБ всего тома; обязательная защита имеет приоритет. Перед новой static-сборкой требуется 8 ГиБ свободного места. Новые архивы предназначены для существующего Backblaze B2 storage 2; ранее подтверждённые объекты читаются в исходном storage 1 или 2. Versioned assets и immutable metadata сохраняются. Systemd timer/path включаются только после exact-SHA выпуска и первой успешной очистки; факт включения фиксируется отдельно.

## Обязательная подготовка

1. Скопировать `.env.example` в `.env` и заменить все placeholders секретов и доменов.
2. Задать `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `DATABASE_URL` с host `postgres` для контейнерного API.
3. Для direct Compose задать `PUBLIC_DOMAIN`, `ADMIN_DOMAIN`, `API_DOMAIN` и `SITE_DATA_API_URL`, доступный из Docker builder. Для Coolify задать `PUBLIC_DOMAIN=tv-internet-dom.ru`, `ADMIN_DOMAIN=admin.tv-internet-dom.ru`; `SITE_DATA_API_URL=http://api:3000/api/v1` и browser API URLs формируются самим Compose. API не получает внешний домен.
4. Задать случайные непустые `ADMIN_API_TOKEN`, `SUBSCRIBER_COOKIE_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`.
5. Проверить rate-limit policy: `RATE_LIMIT_WINDOW_MS`, `RATE_LIMIT_LOGIN_MAX`, `RATE_LIMIT_SUGGESTIONS_MAX`, `RATE_LIMIT_PUBLIC_WRITE_MAX`, `RATE_LIMIT_DEFAULT_MAX`. Подсказки имеют отдельный bucket и по умолчанию допускают 60 запросов за окно; создание заявки и проверка адреса сохраняют строгий лимит 10. Production Compose принудительно задает API `TRUST_PROXY=true`, потому что API не публикует порт и получает внешний трафик только от Caddy; при прямой публикации API доверие proxy headers нужно пересмотреть.

Для Coolify public/admin Caddy доверяет только прямому private-range proxy-пиру, определяет `{client_ip}` по `trusted_proxies_strict` справа налево и передаёт API один очищенный `X-Forwarded-For`. Fastify с `TRUST_PROXY=true` использует это значение для rate limit и серверного IP в снимке заявки. Локальный Caddy 2.11.4 подтвердил синтаксис обоих конфигов; в изолированном HTTP-прогоне заголовок `203.0.113.44, 198.51.100.77` дошёл до upstream как единственный `198.51.100.77`. Перед объявлением live IP подтверждённым нужен отдельный smoke на deployed SHA; прямой доступ к внутреннему Caddy или API вне доверенной сети не предусмотрен.
6. Задать согласованный срок хранения сырых заявок `PII_RETENTION_DAYS=180`. Без валидного значения scheduler отключен и readiness заблокирован. Размер batch и UTC cron настраиваются отдельно. Юридическое основание обработки и текст согласия фиксируются отдельными проверяемыми фактами для решения владельца; дополнительная перепроверка ведется в низкоприоритетной #144.
7. До включения заявок подтвердить договоры и задать coverage, contract, Tarifnik, email и rebuild variables. Проверить защищенный `/api/v1/admin/readiness`: `status` должен быть `configured`. Это подтверждает только наличие конфигурации — затем обязательны sandbox-вызовы и согласованные legal/SLA decisions.
8. Направить DNS A/AAAA для `tv-internet-dom.ru` и `admin.tv-internet-dom.ru` на Coolify-сервер; 80/443 должны быть доступны Coolify edge proxy.
9. Сгенерировать bcrypt credential строкой `htpasswd -nbB <username> <password>` и сохранить результат только в Coolify как `TEST_BASIC_AUTH_USERS`. Включить `Literal`, `Buildtime` и `Runtime`, выключить `Multiline`; в Advanced обязательно выключить `Escape special characters in labels`. Compose интерполирует label уже во время `docker compose build`: runtime-only значение отсутствует в `build-time.env`, а label escaping превращает `${TEST_BASIC_AUTH_USERS...}` в неинтерполируемый `$${TEST_BASIC_AUTH_USERS...}`. Открытый пароль и готовый credential не коммитить.
10. Явно выбрать RUN_BOOTSTRAP_SEED. Для существующего контура — false. Значение true предназначено только для первого bootstrap; повторный запуск проверен отдельно и не заменяет импорт реального каталога.

Секретные значения не дублируются в документации или отдельных временных файлах. Для локальной разработки их единый источник — исключенный из Git корневой `.env`; для production — Coolify Environment Variables. `.env.example` остается только реестром имен, безопасных URL и пустых placeholders.

10 сентября 2026 года заполненные P0-переменные интеграций, rebuild и retention перенесены из локального `.env` в основной production-контур Coolify через официальный API. Перенос создавал только отсутствующие имена, не перезаписывал существующие значения и не затрагивал preview. Городские `origin/providerid/referer` теперь поставляются вместе с API в проверяемом справочнике, поэтому прежние одногородские environment values больше не используются. Позднее в тот же день владелец добавил `RESEND_API_KEY`; он перенесен отдельной production runtime/literal/shown-once переменной. Синтетическое письмо без PII с настроенными `LEADS_EMAIL_FROM`/`LEADS_EMAIL` принято Resend с HTTP 200 и получено владельцем. 15 сентября пустое production-значение `ADMIN_API_TOKEN` было заменено случайным 64-символьным токеном с флагами Literal + Buildtime + Runtime: без build scope Coolify не может интерполировать обязательный `SITE_DATA_API_TOKEN` в Compose до запуска контейнеров.

## Работа агента с Coolify через MCP

По решению владельца от 28 октября 2026 года **штатные операции агента с Coolify выполняются через подключённый `coolify` MCP**: диагностика, чтение состояния и логов, настройка приложения, деплой/редеплой, перезапуск, отмена и восстановление. Рабочий ресурс — приложение `astro-telekom`. Оно получает Compose из `Celtoman/astro-telekom-release`. В `Celtoman/astro-telekom` находятся код и Dockerfiles.

1. Проверить, что инструменты `coolify` доступны в текущем сеансе агента, и выполнить безопасное чтение, например `get_current_team`. Запись подключения в конфигурацию или отдельный HTTP-запрос к `/mcp` ещё не подтверждают доступность инструментов из чата. Если подключение не загрузилось, обновить подключения или перезапустить клиент и повторить проверку.
2. Найти приложение через `search_resources` и прочитать `get_application`. Сверить имя, репозиторий, ветку и UUID с целевым контуром; для существующего ресурса использовать `COOLIFY_RESOURCE_UUID` как дополнительную проверку. Все последующие операции адресовать проверенному приложению или его deployment UUID.
3. Для диагностики использовать `list_deployments`, `get_deployment` и доступные инструменты логов. Права токена и ограничения ответов MCP определяют доступные данные; отсутствие доступа к логам фиксировать как непроверенный участок.
4. Для выпуска кода дождаться зелёного CI точного SHA исходников, собрать образы и опубликовать соответствующий Compose по [runbook GHCR](runbooks/ghcr-release.md). Закрепить SHA Compose в приложении через `manage_application`, сверить репозиторий, ветку и SHA и вызвать `deploy` с UUID приложения. Сохранить deployment UUID и проверять именно его через `get_deployment` до конечного состояния. После сетевого сбоя сначала прочитать историю, чтобы установить, был ли deployment создан, и только затем решать вопрос о повторе.
5. Успех выпуска подтвердить по `finished`, совпадению deployment `commit` с SHA Compose, состоянию `running:healthy`, digest образов и SHA кода в OCI-метках. Сверить тома, обслуживаемый снимок, готовность CODE и внешний HTTP. Перезапуск через `control` и новый deployment через `deploy` — разные операции. Выбирать ту, которую требует задача.

API/CLI — резервный путь, когда MCP недоступен или не предоставляет необходимую операцию, включая закрепление требуемого SHA. Перед переходом агент явно сообщает конкретное ограничение MCP и выбранный способ выполнения уже согласованной задачи; проверки результата остаются теми же. Рабочий процесс агента через MCP и эти исключения обязательны также для действий из раздела «Настройка Coolify» ниже.

Локальный токен подключения хранится только в исключённом из Git корневом `.env` под именем `COOLIFY_MCP_TOKEN`. Конфигурация клиента читает его при подключении; значение токена не включается в документацию, команды в отчёте или Git. Состав доступных инструментов проверяется в текущем сеансе, а не по сохранённому числу или списку из прежней проверки.

Это правило задаёт интерфейс работы агента. Программные обращения publication controller и legacy worker provider к Coolify REST API продолжают использовать `COOLIFY_API_URL`, `COOLIFY_API_TOKEN` и `COOLIFY_RESOURCE_UUID` по существующему контракту. В действующем Coolify Compose CMS-публикация по-прежнему выполняется через private static controller без redeploy приложений; MCP используется агентом для эксплуатационных операций и выпуска кода.

## Настройка Coolify

1. Для действующего `astro-telekom` использовать существующее Git-based application и GitHub App `astro-domru` с доступом к `Celtoman/astro-telekom-release`. На целевом сервере нужен GHCR login с доступом на чтение пакетов выпуска. Новый ресурс создавать для изолированного контура с собственными доменами и томами.
2. Выбрать build pack `Docker Compose`, base directory `/`, Compose location `/docker-compose.coolify.yml`; Raw Compose не включать.
3. В карточке сервиса `web` назначить домен `https://tv-internet-dom.ru`, в `admin` — `https://admin.tv-internet-dom.ru`. Оба контейнера слушают внутренний порт 80, поэтому в актуальном Coolify суффикс порта не нужен. Поле `noindex_domains` оставить пустым: индексационная политика задана явными Compose labels (`noindex, nofollow` для public и дополнительно `noarchive` для admin), а generated middleware Coolify иначе перезаписывает более строгий admin-заголовок.
4. Заполнить обязательные environment values. `TEST_BASIC_AUTH_USERS` хранить как Literal + Buildtime + Runtime: это bcrypt verifier, а не открытый пароль. Для существующего контура оставить RUN_BOOTSTRAP_SEED=false; новый bootstrap проверен на свежей PostgreSQL и повторном запуске.
5. Coolify Compose принудительно использует `REBUILD_PROVIDER=static` для CMS. `COOLIFY_API_URL`, `COOLIFY_RESOURCE_UUID` и runtime-only `COOLIFY_API_TOKEN` нужны controller для проверки CODE-release, а не для запуска CMS deployment. Token сохраняет Runtime/Literal scope без Build и Multiline; web получает его через runtime `.env`, без Compose interpolation/build args. Одноразовые `PUBLICATION_LEGACY_*` proof-переменные также Runtime/Literal, без Build scope. После terminal deployment runtime автоматически согласует renderer с runtime `SOURCE_COMMIT`: сохраняет обслуживаемый snapshot, перепроверяет deployment перед activation и восстанавливает ту же операцию при недоступности provider. CMS ожидает эту подготовку и продолжается автоматически. При отсутствии/невалидности deployed commit система сохраняет предыдущий сайт и сообщает о недоступной подготовке; диагностика/восстановление доступны через машинный `/internal/site-publications/:siteSlug/release-code` с exact deployment ID/SHA. HTTP 202 требует повторить ту же команду. Legacy внешний provider остаётся доступен в прямом prod Compose.
6. Оставить выключенными `Inject Build Args to Dockerfile` и GitHub Auto Deploy. Закрепить ветку и полный SHA Compose с готовыми образами, затем явно запустить deployment через Coolify MCP по [runbook GHCR](runbooks/ghcr-release.md). `REBUILD_WEBHOOK_URL` в Coolify-режиме оставить пустым. Программный legacy provider сохраняет API start/status, а действующий static provider обращается к private controller.
7. Проверить TLS и Basic Auth на `/`, `/robots.txt`, `/sitemap.xml`, `/kazan/`, `/api/v1/health/live`, а также на всех admin routes. Без credentials каждый внешний URL должен возвращать `401`; после входа формы и admin API должны обращаться к same-origin `/api/v1` без второго HTTP-auth prompt. И на `401`, и на авторизованном `200` обязательны HSTS `max-age=31536000` без preload/includeSubDomains, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` и ограничивающий `Permissions-Policy`. Public CSP должен разрешать framing только себе и официальным Webvisor origins без `X-Frame-Options`; admin — содержать `frame-ancestors 'none'`, `X-Frame-Options: DENY` и `X-Robots-Tag: noindex, nofollow, noarchive`. В браузере отдельно проверить отсутствие CSP violations, работу public формы/API/Метрики и admin routes.
8. После первого успешного seed оставить RUN_BOOTSTRAP_SEED=false. Code deployment должен сохранить publication ID/revision/catalog уже обслуживаемого снимка. Для проверки контента выполнить save → review → publish и проверить реальные фазы, durable receipt/SQL acknowledgment, итоговый HTML и отсутствие нового deployment.

## Порядок первого запуска

Direct Compose по-прежнему рассчитан на повторное развертывание с уже доступным `SITE_DATA_API_URL`:

```powershell
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml exec api node /workspace/apps/api/dist/seed.js
```

Образ `publication-runtime` собирается в GitHub Actions без доступа к каталогу. PostgreSQL/Redis, migrations, API и явный bootstrap seed запускаются до web runtime; циклической зависимости API/worker от web нет. Startup принимает verified legacy baseline либо protocol autosave, сохраняя фактически опубликованную версию. CMS job строит конкретный immutable snapshot через закрытый endpoint и активирует Caddy только после Astro/SEO gates. CODE использует уже обслуживаемый snapshot и ждёт terminal deployment. Внешний test-контур переведён на static runtime; baseline/CODE и две CMS-публикации подтверждены в [приёмке](research/2026-10-06-static-publication-live-acceptance.md). Исторические проверки ниже относятся к указанным SHA. Автоматическое CODE и telemetry доработки #256 проверены на exact deployment `215cf65`: [приёмка](research/2026-10-06-publication-progress-and-recovery.md).

Образ `publication-runtime` наследует слой зависимостей `web-deps` и копирует исходники `apps/web`, `apps/api/src`, общие `scripts`, `.npmrc` и `deploy/coolify-web.Caddyfile`. Манифесты и lockfile уже находятся в слое зависимостей. Полная копия репозитория нужна целям `publisher` и `build`. Если у рендерера появится зависимость за пределами этого списка, обновите Dockerfile и проверку состава образа. Перед выпуском сравните идентификатор рендерера при одинаковых исходниках и окружении и прогоните проверку CODE, CMS и перезапуска на собранном образе.

В Dockerfiles образов основного стека dependency layer строится до копирования исходников: сначала root/workspace manifests, `pnpm-lock.yaml` и единый `scripts/pnpm-install-retry.sh`, затем install, затем исходники. Все install stages используют один BuildKit cache mount `pnpm-store`, поэтому загруженные пакеты переиспользуются между targets и следующими сборками; transient failure повторяет install до трех раз в том же заполненном store. Production Docker install передает `--trust-lockfile`: это убирает многократную сетевую перепроверку всех записей уже зафиксированного lockfile, но не отключает `--frozen-lockfile`; обычный CI/local install без флага по-прежнему выполняет supply-chain verification. Поэтому образы для выпуска собираются из прошедшего CI SHA в `master`. API Dockerfile разделяет filtered build и production runtime dependencies, а migration target с Prisma CLI переиспользует build dependency tree вместо второго одинакового install. `api` и `bootstrap-seed` используют один runtime image. В исходном Compose для локальной сборки seed использует `pull_policy: never`. Compose выпуска из GHCR указывает один digest для обоих сервисов. Publisher устанавливает только workspace `@provider/web`, admin — только `@provider/admin`, а worker — только production-зависимости `@provider/worker`, чтобы final images не экспортировали весь monorepo dependency tree. Повторный live deployment v4.3.18 завершился за 85 секунд: в логе отмечены 54 кешированных шага, без install retry, network timeout и build error.

Локальная production-подобная проверка 9 сентября 2026 года использовала отдельный пустой BuildKit builder. До bounded retry холодный прогон воспроизвел сетевой timeout через 375,52 с; после исправления полный cold build завершился за 343,15 с, повторный — за 81,85 с без install/network work (`CACHED`). Compose затем применил все 12 migrations, существовавшие в той ревизии, выполнил bootstrap seed, собрал и атомарно опубликовал 10 HTML-файлов, оставил API/worker/web/admin/PostgreSQL/Redis healthy с restart count 0, а `migrate`/`bootstrap-seed`/`web-publish` завершил с exit code 0. Тестовый stack и его volumes после проверки удалены.

Seed не становится автоматической операцией каждого deploy: Coolify не начнет работу, пока оператор явно не выберет `true` или `false`; после первого запуска значение должно быть `false`. Seed проверен на свежей PostgreSQL 18 после всех migrations: создаёт одну demo-городскую `HOME` со ссылкой на общий CITY_HOME3 из десяти блоков, полную HOME с пустым FAQ, четырнадцать SEO-шаблонов, пять обязательных site-global страниц, общие ACCOUNT/OFFICIAL_SITE/SPEED_TEST/EQUIPMENT_ROUTER и городской CITY_SUPPORT в `PUBLISHED` и DRAFT примеры тарифов без цен только для пустого каталога. Credentials обязательны до записи; все изменения атомарны. Повторный запуск сохраняет существующие content/templates/SEO/phones/password и импортированный каталог; seed не создаёт публикацию или rebuild. `node scripts/rehearse-seed.mjs` воспроизводит этот контракт в собственном временном Docker PostgreSQL, включая publication preflight и rollback. Production использует полный примененный импорт городов и тарифов. Три legal-текста версионированы в public web для домена `tv-internet-dom.ru`; их дополнительная сверка ведется как низкоприоритетная #144 и не является deployment- или traffic-gate. Web и admin в Coolify встраивают соответственно `https://tv-internet-dom.ru/api/v1` и `https://admin.tv-internet-dom.ru/api/v1`; их Caddy проксирует `/api/*` во внутренний `api:3000`. Astro build добавляет HTML CSP с hashes всех inline scripts/styles; admin `frame-src 'self'` нужен только для локального sandboxed `srcdoc` на `/preview`, тогда как `frame-ancestors` и `X-Frame-Options: DENY` по-прежнему запрещают внешнее встраивание самой админки. Админка остается на отдельном поддомене; production cookie остается `Secure` и требует HTTPS.

Для первоначальной загрузки географии после запуска API выполнить `pnpm cities:import`, проверить счетчики validation report и затем `pnpm cities:import -- --apply --actions=<path>`. Команда пишет только через административный API, сохраняет статус существующего города, а новый создаёт в `DRAFT`. Атомарно создаёт новому городу единственную `PUBLISHED` HOME-shell со ссылкой на общий CITY_HOME3 без локальных блоков; при существующем ADDRESS-шаблоне добавляет связанную ADDRESS-shell. Статус shell не публикует сам город или сайт: включение города в public inventory требует опубликованного города и отдельной публикации snapshot. Целевой полный каталог Release 1 остаётся продуктовым решением; пропущенные оператором строки не изменяются. Исходник и детали находятся в [data/imports/README.md](../data/imports/README.md).

## Требуемые проверки до публикации

Новая публикация и повтор `FAILED`/`CANCELLED` сначала сохраняют воспроизводимый отчет по всем URL Release 1. `BLOCKED` отвечает 409 с ID отчета, не создает новый publication/rebuild и сохраняет прежний public snapshot. Оператор смотрит последний отчет в общем блоке публикации либо получает историю через защищенные `/admin/sites/:siteId/publication-validations`; JSON включает точный source snapshot для воспроизведения. Успешный preflight не подменяет post-build проверку Astro HTML/SEO: ошибка сборки остается в статусе публикации/rebuild. Исторические снимки до `0050` имеют пустой `validationId`. ### Автоматическая подготовка проекций опубликованных каталогов

В Coolify отдельная роль `serving-projection-warmer` использует тот же закреплённый runtime-образ, что API. Она запускается после миграций, получает runtime `env_file`, обращается к приватному контроллеру на `http://web:8081` и работает без портов и томов. Начальные пределы составляют 0,5 CPU и 512 МиБ. При выключенном флаге процесс завершается с кодом 0. Состояние этой роли и событие `projection_ready` проверяются отдельно при включении.

Внешнее включение выполняется по шагам.

1. Применить `0080_serving_catalog_projection` с `SERVING_CATALOG_PROJECTIONS_ENABLED=false`. Убедиться, что активный ID, последовательность выпуска, дайджест каталога и все прежние тома сохранились.
2. Включить `SERVING_CATALOG_PROJECTION_WARMER_ENABLED=true`. Проверить, что роль использует тот же API digest и опубликовала `projection_ready` для текущего ID с дайджестом из приватного `/active`. При повторном старте готовая проекция может уже существовать. В таком случае однократная команда проверки возвращает её точные `publicationId`, `generation` и `catalogDigest`.
3. Включить `SERVING_CATALOG_PROJECTIONS_ENABLED=true` после проверки доказательства. Повторить read-only HTTP для каталога, новости и активного снимка. Отдельно проверить задержку и штатный fallback по exact ID. Для отката выключить чтение первым.

После миграции 0080 запустите отдельный процесс на той же версии API и с тем же PostgreSQL. Для static-провайдера процессу нужны `DATABASE_URL`, `REBUILD_PROVIDER=static`, внутренний `STATIC_PUBLICATION_URL` и `ADMIN_API_TOKEN`. Роль подключения использует текущие разрешения API на публикации и проекции и право `TEMP` для промежуточных строк. HTTP-порт и Redis ему не требуются.

```sh
SERVING_CATALOG_PROJECTION_WARMER_ENABLED=true node --env-file=.env apps/api/dist/serving-projection-warmer-main.js
```

Наблюдайте `projection_ready` с ID, поколением, digest, числом городов и временем подготовки. `lockMs` измеряет от запроса `FOR UPDATE NOWAIT` до окончания записей в транзакции. Задержка commit в это поле не включена. Перед включением `SERVING_CATALOG_PROJECTIONS_ENABLED=true` подтвердите готовность проекции точного текущего ID и проверьте ответы нужных публичных маршрутов. Разовый запуск `node apps/api/dist/warm-serving-catalog-projection.js <publicationId>` остаётся доступен из окружения API с настроенным `DATABASE_URL`.

Процесс использует уже сохранённые задания пересборки, включая ещё не обработанные запросы и retry. Точный `/active` позволяет подготовить исторический снимок после rollback. Ошибка прогрева оставляет точное полное чтение и не останавливает активацию или SQL acknowledgment. Можно выключить чтения флагом API и независимо остановить процесс. Отключение сохраняет подготовленные проекции и исходные каталоги.

## Известные эксплуатационные ограничения

- Astro CSP meta защищает HTML document resources, а не HTTP framing policy; поэтому `frame-ancestors` и общие response headers дублируются на Traefik/Caddy edge. При изменении Coolify routing нужно повторно проверить порядок middleware на processed Compose и заголовки неавторизованного `401`.
- Нет общего мониторинга, alerting и лог-агрегации. Решение 15 сентября об отмене общей #145 сохранено. Оно не отменяет позднее отдельно реализованные editorial DB/media backup #546 и publication retention #440/#438; их область, внешние проверки и восстановление описаны в профильных runbooks выше.
- Автоматическое hard-delete PII реализовано, срок 180 дней согласован и указан в `.env.example`; юридические сведения и isolated rehearsal production retention фиксируются как отдельные результаты для решения владельца.
- Исторический срез 4 ноября 2026: дерево содержало 65 миграций до `0065_tvbox_availability` (0065 применена, тарифный snapshot 28 опубликован; 0063/0064 ранее выпущены с ADDRESS snapshot 27; прежняя 0062 выпущена со снимком 24; для прежней `0060_home_hero_city_search` 13 октября read-only SQL подтвердил finished без rollback на внешнем контуре); ранее deployment `k1osuggjvvr9qpx8cyv68lnk` exact-SHA `cde74bf00580e63f3708ad6d77aed52c45def35b` завершился с успешным one-shot `migrate` перед здоровым API (Compose требует `service_completed_successfully`), что подтверждает применение `0049`; через live admin API после deployment `ffll1n82r7ewxetctru1p358` exact-SHA `fa472ed83df38120c277d7d7d8195e61aa462fcd` подтверждена доступность новых OG-полей в схеме. Перечисленные общие legacy CMS mutators — ручные изменения сайта, региона, города, страницы, блока, тарифа и редиректа, изменение провайдера, программный import тарифов и apply/undo обоих XLSX-импортов — сохраняют рабочую ревизию и не меняют public API/redirect resolver до отдельной успешной публикации. - Direct `docker-compose.prod.yml` по-прежнему требует заранее доступный `SITE_DATA_API_URL`; исторический bootstrap Coolify подтверждался отдельно; текущий seed дополнительно проверен на свежей schema и повторном запуске.
- Исторические live rehearsals 9–11 сентября 2026 года подтвердили DNS/TLS, persistent volumes, 401/200 password boundary, same-origin API, `www → non-www`, повторную web-публикацию и устойчивый `running:healthy`. Точные commit/deployment-пары сохранены в вводном снимке; их нельзя переносить на более новую ревизию без нового probe.
- Coolify adapter покрыт UUID/polling/retry/timeout tests и подтвержден против реального control plane: [#57](https://github.com/Celtoman/astro-telekom/issues/57) закрыта после polling rehearsal до `finished` на точном deployment commit.
- Rebuild требует одновременно PostgreSQL, Redis, worker, API и доступный выбранный provider; наличие URL/token без успешного финального rehearsal не доказывает публикацию.
- Для применения persistent rebuild-job нужна миграция `0010_site_rebuild_jobs`.
- Fallback email link требует примененной миграции `0009_lead_access_tokens`; ссылка одноразовая, действует 24 часа и проверяется API. Raw token передается во fragment и не попадает в HTTP request к static admin.
- Retention query требует миграцию `0012_pii_retention_indexes`; она добавляет индексы `Lead.createdAt` и `AddressCheck.createdAt`, не выбирая срок хранения.
- Persistent обычное оповещение требует миграцию `0015_lead_notification_outbox`, Redis и работающий `lead-notifications` consumer; ручной повтор создает новый revision, а не новую PII-запись. Live-проверка после исправления sender перевела сохраненную запись из `revision 1 / FAILED / HTTP 403` в `revision 2 / SUCCEEDED`; Resend вернул provider ID. Все автоматические попытки одной revision сохраняют общий idempotency key, новый ручной цикл получает новый key.

## Обновление при удалении публикаций по времени

Миграция `0057_remove_publication_schedule` отменяет ещё ожидавшие снимки без их публикации и без продвижения Site.publishedRevision. Даты прежней функции сохраняются только как историческое evidence в providerResponse.retiredSchedule; поля и индекс удаляются, SCHEDULED исключается из текущего enum. Перед применением остановить legacy worker и дождаться завершения уже переданных в rebuild отложенных публикаций. При наличии такого PENDING/RUNNING snapshot либо активного rebuild на ожидающий снимок миграция завершается ошибкой и откатывается целиком. Новый worker удаляет сохранённый scheduler в Redis; остаточные задания прежней функции не вызывают API публикации. Отмена прежних ожиданий и cleanup проверены в изолированном PostgreSQL/Redis rehearsal. Внешний rollout exact SHA `d440ec4` завершился успешно: one-shot migrate перед healthy API, удалённые routes дают 404, published revision/catalog сохранились. На внешнем preflight ожиданий не было; прямого SQL/Redis-аудита не выполняли. См. [приёмку 6 октября](research/2026-10-06-manual-publication-rollout.md).
