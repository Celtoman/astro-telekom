# Развертывание и эксплуатационный контур

Сверка процедур: 6 октября 2026 года. Coolify использует постоянный publication runtime; CMS publish не запускает redeploy, code deployment выпускает renderer обслуживаемого snapshot. Контракт и восстановление — в [publication.md](publication.md), доказательства — в [research/README.md](research/README.md).

Direct prod Compose использует migration target с Prisma CLI; отдельный Docker/PostgreSQL 18 rehearsal (#236) проверяет применение всех миграций и точную идемпотентность. Запуск: `node scripts/rehearse-direct-migration.mjs`. Эта проверка не подтверждает полный запуск direct stack: web по-прежнему требует уже доступный `SITE_DATA_API_URL`. Seed соответствует текущей schema и прошёл отдельный свежий PostgreSQL rehearsal. Действующий Coolify-контур использует RUN_BOOTSTRAP_SEED=false. Только владелец определяет готовность к реальному трафику.

## Контуры

| Контур | Команда | Состав |
| --- | --- | --- |
| Локальная инфраструктура | `docker compose up -d postgres redis` | Только PostgreSQL и Redis с опубликованными портами 5432/6379. |
| Локальные приложения | pnpm-команды из README | API, web, admin, worker в процессах хоста. |
| Альтернативный direct-контур | `docker compose -f docker-compose.prod.yml up -d --build` | Повторное развертывание при уже доступном `SITE_DATA_API_URL`: PostgreSQL, Redis, one-shot Prisma migrate, API, worker, web, admin, внешний Caddy. |
| Coolify test, действующий внешний контур | Git-based Docker Compose resource, docker-compose.coolify.yml | Защищённые public/admin origins, внутренний API, отдельный migration target, постоянный publication runtime и атомарная Caddy activation. Точные rollout-доказательства — в research/README.md. |

PostgreSQL 18 хранит major-specific data directory внутри volume, смонтированного в `/var/lib/postgresql`. Не возвращать старый mount `/var/lib/postgresql/data`: официальный PG18 image отказывается запускаться с таким layout.

## Обязательная подготовка

1. Скопировать `.env.example` в `.env` и заменить все placeholders секретов и доменов.
2. Задать `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `DATABASE_URL` с host `postgres` для контейнерного API.
3. Для direct Compose задать `PUBLIC_DOMAIN`, `ADMIN_DOMAIN`, `API_DOMAIN` и `SITE_DATA_API_URL`, доступный из Docker builder. Для Coolify задать `PUBLIC_DOMAIN=tv-internet-dom.ru`, `ADMIN_DOMAIN=admin.tv-internet-dom.ru`; `SITE_DATA_API_URL=http://api:3000/api/v1` и browser API URLs формируются самим Compose. API не получает внешний домен.
4. Задать случайные непустые `ADMIN_API_TOKEN`, `SUBSCRIBER_COOKIE_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`.
5. Проверить rate-limit policy: `RATE_LIMIT_WINDOW_MS`, `RATE_LIMIT_LOGIN_MAX`, `RATE_LIMIT_SUGGESTIONS_MAX`, `RATE_LIMIT_PUBLIC_WRITE_MAX`, `RATE_LIMIT_DEFAULT_MAX`. Подсказки имеют отдельный bucket и по умолчанию допускают 60 запросов за окно; создание заявки и проверка адреса сохраняют строгий лимит 10. Production Compose принудительно задает API `TRUST_PROXY=true`, потому что API не публикует порт и получает внешний трафик только от Caddy; при прямой публикации API доверие proxy headers нужно пересмотреть.

Для Coolify public/admin Caddy доверяет только прямому private-range proxy-пиру, определяет `{client_ip}` по `trusted_proxies_strict` справа налево и передаёт API один очищенный `X-Forwarded-For`. Fastify с `TRUST_PROXY=true` использует это значение для rate limit и серверного IP в снимке заявки. Локальный Caddy 2.11.4 подтвердил синтаксис обоих конфигов; в изолированном HTTP-прогоне заголовок `203.0.113.44, 198.51.100.77` дошёл до upstream как единственный `198.51.100.77`. Перед объявлением live IP подтверждённым нужен отдельный smoke на deployed SHA; прямой доступ к внутреннему Caddy или API вне доверенной сети не предусмотрен.
6. Задать согласованный срок хранения сырых заявок `PII_RETENTION_DAYS=180`. Без валидного значения scheduler отключен и readiness заблокирован. Размер batch и UTC cron настраиваются отдельно. Юридическое основание обработки и текст согласия фиксируются отдельными проверяемыми фактами для решения владельца; дополнительная перепроверка ведется в низкоприоритетной #144.
7. До включения заявок подтвердить договоры и задать coverage, contract, Tarifnik, email и rebuild variables. Проверить защищенный `/api/v1/admin/readiness`: `status` должен быть `configured`. Это подтверждает только наличие конфигурации — затем обязательны sandbox-вызовы и согласованные legal/SLA decisions.
8. Направить DNS A/AAAA для `tv-internet-dom.ru` и `admin.tv-internet-dom.ru` на Coolify-сервер; 80/443 должны быть доступны Coolify edge proxy.
9. Сгенерировать bcrypt credential строкой `htpasswd -nbB <username> <password>` и сохранить результат только в Coolify как `TEST_BASIC_AUTH_USERS`. Включить `Literal`, `Buildtime` и `Runtime`, выключить `Multiline`; в Advanced обязательно выключить `Escape special characters in labels`. Compose интерполирует label уже во время `docker compose build`: runtime-only значение отсутствует в `build-time.env`, а label escaping превращает `${TEST_BASIC_AUTH_USERS...}` в неинтерполируемый `$${TEST_BASIC_AUTH_USERS...}`. Открытый пароль и готовый credential не коммитить.
10. Явно выбрать RUN_BOOTSTRAP_SEED. Для существующего контура — false. Значение true предназначено только для первого bootstrap; повторный запуск проверен отдельно и не заменяет импорт реального каталога.

Секретные значения не дублируются в документации или отдельных временных файлах. Для локальной разработки их единый источник — исключенный из Git корневой `.env`; для production — Coolify Environment Variables. `.env.example` остается только реестром имен, безопасных URL и пустых placeholders.

10 сентября 2026 года заполненные P0-переменные интеграций, rebuild и retention перенесены из локального `.env` в основной production-контур Coolify через официальный API. Перенос создавал только отсутствующие имена, не перезаписывал существующие значения и не затрагивал preview. Городские `origin/providerid/referer` теперь поставляются вместе с API в проверяемом справочнике, поэтому прежние одногородские environment values больше не используются. Позднее в тот же день владелец добавил `RESEND_API_KEY`; он перенесен отдельной production runtime/literal/shown-once переменной. Синтетическое письмо без PII с настроенными `LEADS_EMAIL_FROM`/`LEADS_EMAIL` принято Resend с HTTP 200 и получено владельцем. 15 сентября пустое production-значение `ADMIN_API_TOKEN` было заменено случайным 64-символьным токеном с флагами Literal + Buildtime + Runtime: без build scope Coolify не может интерполировать обязательный `SITE_DATA_API_TOKEN` в Compose до запуска контейнеров.

## Настройка Coolify

1. Создать Git-based application из приватного GitHub-репозитория через GitHub App или Deploy Key.
2. Выбрать build pack `Docker Compose`, base directory `/`, Compose location `/docker-compose.coolify.yml`; Raw Compose не включать.
3. В карточке сервиса `web` назначить домен `https://tv-internet-dom.ru`, в `admin` — `https://admin.tv-internet-dom.ru`. Оба контейнера слушают внутренний порт 80, поэтому в актуальном Coolify суффикс порта не нужен. Поле `noindex_domains` оставить пустым: индексационная политика задана явными Compose labels (`noindex, nofollow` для public и дополнительно `noarchive` для admin), а generated middleware Coolify иначе перезаписывает более строгий admin-заголовок.
4. Заполнить обязательные environment values. `TEST_BASIC_AUTH_USERS` хранить как Literal + Buildtime + Runtime: это bcrypt verifier, а не открытый пароль. Для существующего контура оставить RUN_BOOTSTRAP_SEED=false; новый bootstrap проверен на свежей PostgreSQL и повторном запуске.
5. Coolify Compose принудительно использует `REBUILD_PROVIDER=static` для CMS. `COOLIFY_API_URL`, `COOLIFY_RESOURCE_UUID` и runtime-only `COOLIFY_API_TOKEN` нужны controller для проверки CODE-release, а не для запуска CMS deployment. Token сохраняет Runtime/Literal scope без Build и Multiline; web получает его через runtime `.env`, без Compose interpolation/build args. Одноразовые `PUBLICATION_LEGACY_*` proof-переменные также Runtime/Literal, без Build scope. После terminal deployment runtime автоматически согласует renderer с runtime `SOURCE_COMMIT`: сохраняет обслуживаемый snapshot, перепроверяет deployment перед activation и восстанавливает ту же операцию при недоступности provider. CMS ожидает эту подготовку и продолжается автоматически. При отсутствии/невалидности deployed commit система сохраняет предыдущий сайт и сообщает о недоступной подготовке; диагностика/восстановление доступны через машинный `/internal/site-publications/:siteSlug/release-code` с exact deployment ID/SHA. HTTP 202 требует повторить ту же команду. Legacy внешний provider остаётся доступен в прямом prod Compose.
6. Отключить `Inject Build Args to Dockerfile`, чтобы Coolify не добавлял environment variables и secrets как Docker `ARG`. Затем запустить выбранный commit вручную. В текущем ресурсе GitHub Auto Deploy выключен: push сам по себе deployment не запускает, поэтому после зеленого CI нужно отдельно вручную запустить выбранный exact SHA. `REBUILD_WEBHOOK_URL` в Coolify-режиме оставить пустым: worker использует API start/status, а не webhook.
7. Проверить TLS и Basic Auth на `/`, `/robots.txt`, `/sitemap.xml`, `/kazan/`, `/api/v1/health/live`, а также на всех admin routes. Без credentials каждый внешний URL должен возвращать `401`; после входа формы и admin API должны обращаться к same-origin `/api/v1` без второго HTTP-auth prompt. И на `401`, и на авторизованном `200` обязательны HSTS `max-age=31536000` без preload/includeSubDomains, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` и ограничивающий `Permissions-Policy`. Public CSP должен разрешать framing только себе и официальным Webvisor origins без `X-Frame-Options`; admin — содержать `frame-ancestors 'none'`, `X-Frame-Options: DENY` и `X-Robots-Tag: noindex, nofollow, noarchive`. В браузере отдельно проверить отсутствие CSP violations, работу public формы/API/Метрики и admin routes.
8. После первого успешного seed оставить RUN_BOOTSTRAP_SEED=false. Code deployment должен сохранить publication ID/revision/catalog уже обслуживаемого снимка. Для проверки контента выполнить save → review → publish и проверить реальные фазы, durable receipt/SQL acknowledgment, итоговый HTML и отсутствие нового deployment.

## Порядок первого запуска

Direct Compose по-прежнему рассчитан на повторное развертывание с уже доступным `SITE_DATA_API_URL`:

```powershell
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml exec api node /workspace/apps/api/dist/seed.js
```

Coolify Compose не читает каталог при image build. PostgreSQL/Redis, migrations, API и явный bootstrap seed запускаются до web runtime; циклической зависимости API/worker от web нет. Startup принимает verified legacy baseline либо protocol autosave, сохраняя фактически опубликованную версию. CMS job строит конкретный immutable snapshot через закрытый endpoint и активирует Caddy только после Astro/SEO gates. CODE использует уже обслуживаемый snapshot и ждёт terminal deployment. Внешний test-контур переведён на static runtime; baseline/CODE и две CMS-публикации подтверждены в [приёмке](research/2026-10-06-static-publication-live-acceptance.md). Исторические проверки ниже относятся к указанным SHA. Автоматическое CODE и telemetry доработки #256 проверены на exact deployment `215cf65`: [приёмка](research/2026-10-06-publication-progress-and-recovery.md).

Во всех четырех Dockerfile dependency layer строится до копирования исходников: сначала root/workspace manifests, `pnpm-lock.yaml` и единый `scripts/pnpm-install-retry.sh`, затем install, затем исходники. Все install stages используют один BuildKit cache mount `pnpm-store`, поэтому загруженные пакеты переиспользуются между targets и следующими сборками; transient failure повторяет install до трех раз в том же заполненном store. Production Docker install передает `--trust-lockfile`: это убирает многократную сетевую перепроверку всех записей уже зафиксированного lockfile, но не отключает `--frozen-lockfile`; обычный CI/local install без флага по-прежнему выполняет supply-chain verification. Поэтому deployment разрешен только из прошедшего CI `master`. API Dockerfile разделяет filtered build и production runtime dependencies, а migration target с Prisma CLI переиспользует build dependency tree вместо второго одинакового install. `api` и `bootstrap-seed` используют один именованный runtime image: one-shot seed не объявляет второй одинаковый build target и запрещает registry pull этого локального image через `pull_policy: never`. Publisher устанавливает только workspace `@provider/web`, admin — только `@provider/admin`, а worker — только production-зависимости `@provider/worker`, чтобы final images не экспортировали весь monorepo dependency tree. Повторный live deployment v4.3.18 завершился за 85 секунд: в логе отмечены 54 кешированных шага, без install retry, network timeout и build error.

Локальная production-подобная проверка 9 сентября 2026 года использовала отдельный пустой BuildKit builder. До bounded retry холодный прогон воспроизвел сетевой timeout через 375,52 с; после исправления полный cold build завершился за 343,15 с, повторный — за 81,85 с без install/network work (`CACHED`). Compose затем применил все 12 migrations, существовавшие в той ревизии, выполнил bootstrap seed, собрал и атомарно опубликовал 10 HTML-файлов, оставил API/worker/web/admin/PostgreSQL/Redis healthy с restart count 0, а `migrate`/`bootstrap-seed`/`web-publish` завершил с exit code 0. Тестовый stack и его volumes после проверки удалены.

Seed не становится автоматической операцией каждого deploy: Coolify не начнет работу, пока оператор явно не выберет `true` или `false`; после первого запуска значение должно быть `false`. Seed проверен на свежей PostgreSQL 18 после всех migrations: создаёт одну demo-городскую `HOME` со ссылкой на общий CITY_HOME (Hero и тарифы), HOME Hero, восемь SEO-шаблонов, пять site-global страниц в `PUBLISHED` и DRAFT примеры тарифов без цен только для пустого каталога. Credentials обязательны до записи; все изменения атомарны. Повторный запуск сохраняет существующие content/templates/SEO/phones/password и импортированный каталог; seed не создаёт публикацию или rebuild. `node scripts/rehearse-seed.mjs` воспроизводит этот контракт в собственном временном Docker PostgreSQL, включая publication preflight и rollback. Production использует полный примененный импорт городов и тарифов. Три legal-текста версионированы в public web для домена `tv-internet-dom.ru`; их дополнительная сверка ведется как низкоприоритетная #144 и не является deployment- или traffic-gate. Web и admin в Coolify встраивают соответственно `https://tv-internet-dom.ru/api/v1` и `https://admin.tv-internet-dom.ru/api/v1`; их Caddy проксирует `/api/*` во внутренний `api:3000`. Astro build добавляет HTML CSP с hashes всех inline scripts/styles; admin `frame-src 'self'` нужен только для локального sandboxed `srcdoc` на `/preview`, тогда как `frame-ancestors` и `X-Frame-Options: DENY` по-прежнему запрещают внешнее встраивание самой админки. Админка остается на отдельном поддомене; production cookie остается `Secure` и требует HTTPS.

Для первоначальной загрузки географии после запуска API выполнить `pnpm cities:import`, проверить счетчики validation report и затем `pnpm cities:import -- --apply --actions=<path>`. Команда пишет только через административный API, переводит каждый примененный город в `PUBLISHED` и атомарно создает новому городу единственную `PUBLISHED` страницу `HOME` со ссылкой на общий CITY_HOME (Hero и тарифы). Это закрепляет решение Release 1 публиковать полный примененный каталог городов; пропущенные оператором строки не изменяются. Исходник и детали находятся в [data/imports/README.md](../data/imports/README.md).

## Требуемые проверки до публикации

Новая публикация и повтор `FAILED`/`CANCELLED` сначала сохраняют воспроизводимый отчет по всем URL Release 1. `BLOCKED` отвечает 409 с ID отчета, не создает новый publication/rebuild и сохраняет прежний public snapshot. Оператор смотрит последний отчет в общем блоке публикации либо получает историю через защищенные `/admin/sites/:siteId/publication-validations`; JSON включает точный source snapshot для воспроизведения. Успешный preflight не подменяет post-build проверку Astro HTML/SEO: ошибка сборки остается в статусе публикации/rebuild. Исторические снимки до `0050` имеют пустой `validationId`. Локально подтверждены все 50 миграций на PostgreSQL 18 и блокирующий/успешный сценарии. CI `35991425487` для SHA `71fac3e5cee30906bc4e1171d7244cc6feb4d657` прошел; Coolify deployment `tuszecyovtkywimzjebxajwo` завершился `finished`, приложение `running:healthy`, public/admin/readiness без Basic Auth дали ожидаемый 401. Compose зависимость `service_completed_successfully` подтверждает успешный one-shot `migrate` перед API, но отдельный SQL-аудит таблицы миграций и live создание отчета не проводились.

Первый переход внешней БД на Release 1 и применение `0032_canonical_city_home` выполнять только по [runbook безопасной миграции данных](runbooks/release-one-data-migration.md): подтвержденная внешняя точка восстановления, сопоставимые pre/post read-only audits, явная публикация новой рабочей ревизии, production-like build и exact-SHA smoke. Канонический SQL-инвентаризатор — [`scripts/release-one-database-audit.sql`](../scripts/release-one-database-audit.sql); он не выполняет операций записи.

Для `0052_page_template_schema`/`0053_page_template_home_backfill` перед deploy сверить число опубликованных HOME и получить внешнюю точку восстановления БД. Backfill внутри транзакции блокирует параллельные CMS-записи, сравнивает редакционный payload после замены формы города и останавливается при любом отличии либо неполной семиблочной HOME. После deploy проверить: по одному `PageTemplate(CITY_HOME)` и семь `PageTemplateBlock` на затронутый сайт, ровно столько связанных опубликованных HOME, сколько было до миграции, одну новую рабочую ревизию/аудит и отсутствие автоматического `SitePublication`. Если backfill остановился, сначала исправить источник расхождения и повторить migration deploy; старая схема не переходит к чтению шаблона. Если ошибка выявлена уже после успешного применения, оставить прежний публичный snapshot и восстановить согласованный снимок БД внешним механизмом владельца либо выполнить отдельную проверенную forward-миграцию; удаление legacy Page/PageBlock в этом шаге запрещено. Отдельно подтвердить эквивалентность построенного рабочего каталога и только затем публиковать новую ревизию.

## Известные эксплуатационные ограничения

- Astro CSP meta защищает HTML document resources, а не HTTP framing policy; поэтому `frame-ancestors` и общие response headers дублируются на Traefik/Caddy edge. При изменении Coolify routing нужно повторно проверить порядок middleware на processed Compose и заголовки неавторизованного `401`.
- Нет общего мониторинга, alerting и лог-агрегации. По решению владельца от 15 сентября 2026 года PostgreSQL backup/restore обеспечивает другое внешнее решение: репозиторий не содержит backup workflow/runner, не задает его credentials или policy и не отслеживает эту работу в #145.
- Автоматическое hard-delete PII реализовано, срок 180 дней согласован и указан в `.env.example`; юридические сведения и isolated rehearsal production retention фиксируются как отдельные результаты для решения владельца.
- Текущее дерево содержит 60 миграций до `0060_home_hero_city_search` (применение последней на внешнем контуре пока не подтверждено); ранее deployment `k1osuggjvvr9qpx8cyv68lnk` exact-SHA `cde74bf00580e63f3708ad6d77aed52c45def35b` завершился с успешным one-shot `migrate` перед здоровым API (Compose требует `service_completed_successfully`), что подтверждает применение `0049`; через live admin API после deployment `ffll1n82r7ewxetctru1p358` exact-SHA `fa472ed83df38120c277d7d7d8195e61aa462fcd` подтверждена доступность новых OG-полей в схеме. Изолированный PostgreSQL 18 rehearsal подтвердил repair `0039`; deployment `0zrpw6x8nvwjqqb2k5e4wcbq` exact-SHA `3f47b2b823b49ecf6788be6007e3d3323d35c440` затем применил additive `0040`, добавив nullable idempotency/consent evidence к `Lead` без переписывания исторических заявок. `0041` добавляет nullable JSONB `Lead.configurationSnapshot`; после exact-SHA rollout историческая карточка заявки прочитана через Prisma с `configurationSnapshot: null`. `0042` добавляет enum-значение для неопределённого исхода резервного письма, `0043` — nullable снимок причины и индекс фильтра, `0044` — nullable текст и анализ комментария, `0045` — nullable evidence проверки телефона и статусы фонового решения, `0046` — nullable номер активной попытки и append-only историю решений без backfill исторических заявок. `0047` добавляет типизированные site-scoped SEO-шаблоны для восьми типов маршрутов и backfill без удаления legacy Page/Tariff SEO JSON; `0048` аддитивно добавляет nullable OG-поля, а `0049` — статусы неопределенного исхода API-доставки для лида и попытки без backfill. При следующих изменениях сравнивать Prisma migrations с exact SHA, а не с ручным числом в документе.
- Static web получает изменения только после явной публикации соответствующего снимка; Coolify выполняет её внутри publication runtime без внешнего redeploy. Все текущие content mutators — ручные изменения сайта, региона, города, страницы, блока, тарифа и редиректа, изменение провайдера, программный import тарифов и apply/undo обоих XLSX-импортов — сохраняют рабочую ревизию и не меняют public API/redirect resolver до отдельной успешной публикации. Дальнейшее развитие CMS отслеживается в #151.
- Direct `docker-compose.prod.yml` по-прежнему требует заранее доступный `SITE_DATA_API_URL`; исторический bootstrap Coolify подтверждался отдельно; текущий seed дополнительно проверен на свежей schema и повторном запуске.
- Исторические live rehearsals 9–11 сентября 2026 года подтвердили DNS/TLS, persistent volumes, 401/200 password boundary, same-origin API, `www → non-www`, повторную web-публикацию и устойчивый `running:healthy`. Точные commit/deployment-пары сохранены в вводном снимке; их нельзя переносить на более новую ревизию без нового probe.
- Coolify adapter покрыт UUID/polling/retry/timeout tests и подтвержден против реального control plane: [#57](https://github.com/Celtoman/astro-telekom/issues/57) закрыта после polling rehearsal до `finished` на точном deployment commit.
- Rebuild требует одновременно PostgreSQL, Redis, worker, API и доступный выбранный provider; наличие URL/token без успешного финального rehearsal не доказывает публикацию.
- Для применения persistent rebuild-job нужна миграция `0010_site_rebuild_jobs`.
- Fallback email link требует примененной миграции `0009_lead_access_tokens`; ссылка одноразовая, действует 24 часа и проверяется API. Raw token передается во fragment и не попадает в HTTP request к static admin.
- Retention query требует миграцию `0012_pii_retention_indexes`; она добавляет индексы `Lead.createdAt` и `AddressCheck.createdAt`, не выбирая срок хранения.
- Persistent обычное оповещение требует миграцию `0015_lead_notification_outbox`, Redis и работающий `lead-notifications` consumer; ручной повтор создает новый revision, а не новую PII-запись. Live-проверка после исправления sender перевела сохраненную запись из `revision 1 / FAILED / HTTP 403` в `revision 2 / SUCCEEDED`; Resend вернул provider ID. Все автоматические попытки одной revision сохраняют общий idempotency key, новый ручной цикл получает новый key.

Полный список рисков и работа по закрытию — в [technical-debt.md](technical-debt.md).

## Обновление при удалении публикаций по времени

Миграция `0057_remove_publication_schedule` отменяет ещё ожидавшие снимки без их публикации и без продвижения Site.publishedRevision. Даты прежней функции сохраняются только как историческое evidence в providerResponse.retiredSchedule; поля и индекс удаляются, SCHEDULED исключается из текущего enum. Перед применением остановить legacy worker и дождаться завершения уже переданных в rebuild отложенных публикаций. При наличии такого PENDING/RUNNING snapshot либо активного rebuild на ожидающий снимок миграция завершается ошибкой и откатывается целиком. После устранения причины отметить неуспешную migration как rolled-back командой `pnpm --filter @provider/database exec prisma migrate resolve --rolled-back 0057_remove_publication_schedule --config ../../prisma.config.ts`, затем повторить migrate:deploy. Новый worker удаляет сохранённый scheduler в Redis; остаточные задания прежней функции не вызывают API публикации. Отмена прежних ожиданий и cleanup проверены в изолированном PostgreSQL/Redis rehearsal. Внешний rollout exact SHA `d440ec4` завершился успешно: one-shot migrate перед healthy API, удалённые routes дают 404, published revision/catalog сохранились. На внешнем preflight ожиданий не было; прямого SQL/Redis-аудита не выполняли. См. [приёмку 6 октября](research/2026-10-06-manual-publication-rollout.md).
