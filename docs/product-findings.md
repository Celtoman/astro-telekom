# Продуктовые и UX/UI-находки

Этот документ — постоянный входящий реестр наблюдений и идей, обнаруженных во время любых задач проекта. Здесь сразу фиксируются продуктовые гипотезы, идеи реализации, интерфейсные и UX/UI-находки, предложения по удобству использования, структуре и управлению админкой, рабочим процессам и другим улучшениям до отдельного обсуждения с владельцем продукта. Отдельное разрешение на добавление новой записи не требуется.

Запись в этом файле не означает согласованного решения и не подтверждает наличие дефекта в коде:

- подтвержденная техническая проблема оформляется GitHub Issue с label `tech-debt`;
- согласованное продуктовое решение переносится в [decisions.md](decisions.md);
- согласованная работа оформляется отдельным GitHub Issue с label `task`;
- после переноса исходная находка остается в реестре со ссылкой и итоговым статусом.

Находка не реализуется попутно в задаче, в которой была обнаружена. Сначала она проходит отдельное обсуждение и критическую проверку; только согласованный итог становится решением или исполнимой задачей.

## Статусы

- `NEW` — находка зафиксирована и ожидает обсуждения;
- `DISCUSSED` — обсуждена, но решение не принято;
- `ACCEPTED` — направление согласовано, требуется оформить решение или задачу;
- `REJECTED` — осознанно отклонена с зафиксированной причиной;
- `CONVERTED` — перенесена в `decisions.md` и/или GitHub Issue.

### PF-001 — Выбрать доменный контур первого внешнего rehearsal

- Дата: 2026-09-09
- Область: product / operations
- Статус: CONVERTED
- Контекст: подготовка первого публичного production-like rehearsal и проверка необходимости покупки домена.
- Наблюдение: TLS, DNS, CORS/cookie и canonical нельзя полноценно проверить только на localhost, но публикация незрелого прототипа сразу на основном домене создает риск случайной индексации и смешения тестовых данных с будущим production-контуром.
- Возможное влияние: преждевременное появление тестовых URL в поиске, неверные canonical и cookies, усложнение переноса на основной домен.
- Идея или гипотеза улучшения: обсуждение завершено — проект разворачивается из GitHub через Coolify на купленном тестовом домене `tv-internet-dom.ru`, без дополнительного `stage`-контура; все human-facing страницы до публичного запуска закрываются паролем.
- Вопросы для обсуждения: техническая реализация same-origin browser API под общей парольной защитой уточняется при выполнении deployment-задач; финальный production-домен будет выбран отдельно.

### PF-002 — Показывать готовность интеграционного профиля города перед публикацией

- Дата: 2026-09-10
- Область: product / UX / operations
- Статус: NEW
- Контекст: перенос многогородской схемы проверки действующего договора Дом.ру из рабочего бота в платформу партнерских сайтов.
- Наблюдение: для запроса Дом.ру каждому городу нужны свои `origin`, `providerid` и `referer`; отсутствие или неверный профиль переводит заявку в ручную проверку либо создает риск запроса с параметрами другого города.
- Возможное влияние: администратор может опубликовать город, не зная, готова ли для него критичная интеграция приема заявок.
- Идея или гипотеза улучшения: в карточке города и общем release-readiness показывать отдельный статус профиля проверки договора: найден, используется региональный fallback, отсутствует или конфликтует; публикацию без профиля разрешать только после явного подтверждения последствий.
- Вопросы для обсуждения: должен ли отсутствующий профиль полностью блокировать публикацию города; где управлять профилями — через импортируемый справочник, отдельный экран или настройки провайдера; кто подтверждает региональный fallback.

### PF-003 — Хранить фактическую географию заявки отдельными структурированными полями

- Дата: 2026-09-10
- Область: product / data model / admin UX
- Статус: NEW
- Контекст: после разрешения адресов любого города `Lead.cityId` и `AddressCheck.cityId` сохраняют город страницы-источника, а фактические город, населенный пункт и регион остаются внутри нормализованного DaData snapshot и строки адреса.
- Наблюдение: текущего разделения достаточно для корректной маршрутизации и чтения единичной заявки, но будущие фильтры и отчеты по фактической географии потребуют разбора JSON либо отдельной денормализации.
- Возможное влияние: аналитика может смешать город привлечения и город подключения, если новый отчет без уточнения использует только `cityId`.
- Идея или гипотеза улучшения: отдельно хранить `addressCity`, `addressSettlement` и `addressRegion`, не меняя source-семантику `cityId`, и явно предлагать в фильтрах выбор между географией страницы и адреса подключения.
- Вопросы для обсуждения: нужны ли структурированные поля уже в первом релизе; какие отчеты строятся по фактической географии; нужно ли переносить значения из существующих DaData snapshots.
- Связанные решения/issues: [решение](decisions.md#5-заявки-кол-центр-и-аналитика), [#87](https://github.com/Celtoman/astro-telekom/issues/87)

### PF-004 — Подсказки адреса должны выглядеть как часть формы, а не как системные кнопки

- Дата: 2026-09-10
- Область: public UX/UI / forms / accessibility
- Статус: CONVERTED
- Контекст: строки DaData создаются в браузере после загрузки страницы. Scoped CSS Astro не попадал на динамические элементы, поэтому браузер показывал мелкие серые системные кнопки вместо спроектированного списка.
- Наблюдение: визуальная проблема совпала с функциональной — общий низкий rate limit периодически заменял список неинформативным сообщением о недоступности.
- Возможное влияние: пользователь хуже различает варианты адреса, не понимает причину сбоя и может не завершить ключевой путь заявки.
- Согласованное улучшение: белый компактный dropdown с основной и уточняющей строками, контрастным active-state, высотой строки не менее 44 px, клавиатурным управлением и честными состояниями ошибки; подсказки используют отдельный лимит, debounce и локальный cache.
- Вопросы для обсуждения: отсутствуют — направление явно согласовано владельцем и реализовано в рамках issue.
- Связанные решения/issues: [#88](https://github.com/Celtoman/astro-telekom/issues/88)

### PF-005 — Ранжировать подсказки с мягким приоритетом города и подсвечивать совпадения

- Дата: 2026-09-10
- Область: public UX/UI / forms / address search
- Статус: CONVERTED
- Контекст: сравнительная проверка формы `mts-tv-internet.ru` и production-формы Дом.ру на запросе «Челны Тукая 49».
- Наблюдение: без `locations_boost` DaData ставит первым реальный, но неверный для намерения пользователя адрес в селе Козяково-Челны; форма МТС использует мягкий приоритет города через КЛАДР-код и выводит адрес Набережных Челнов первым. Ее dropdown дополнительно показывает короткую инструкцию, ограничивает первичную выдачу тремя вариантами и выделяет совпавшие фрагменты запроса.
- Возможное влияние: неверный первый вариант повышает риск выбора другого населенного пункта и ошибочной проверки подключения; отсутствие подсветки замедляет сравнение похожих длинных адресов.
- Согласованное улучшение: использовать мягкий `locations_boost`, сохранив глобальный поиск без `locations`; показывать до пяти двухстрочных вариантов с безопасной подсветкой совпадений и строкой «Выберите адрес».
- Вопросы для обсуждения: закрыты — КЛАДР-код дает IPLocate без изменения модели `City`, а при недоступной геолокации используется однозначная пара «регион + город страницы»; для UI выбраны пять двухстрочных вариантов.
- Связанные решения/issues: [решение о межгородских адресах](decisions.md#5-заявки-кол-центр-и-аналитика), [#89](https://github.com/Celtoman/astro-telekom/issues/89), [задача #91](https://github.com/Celtoman/astro-telekom/issues/91)

### PF-006 — Использовать город по IP как необязательный сигнал ранжирования адресов

- Дата: 2026-09-10
- Область: public UX / forms / address search / privacy
- Статус: CONVERTED
- Контекст: официальный API DaData предлагает связать `iplocate/address` с адресными подсказками: определить КЛАДР-код города посетителя и передать его в `locations_boost` при `suggest/address`.
- Наблюдение: сигнал по IP может улучшить неоднозначные запросы пользователя с любой страницы партнерского сайта, однако DaData оценивает точность определения города лишь в 60–80%; результат также искажают VPN, мобильные сети и корпоративные прокси. Повторный вызов при каждом вводимом символе быстро расходует суточный лимит, а передача IP в DaData добавляет отдельный аспект обработки пользовательских данных.
- Возможное влияние: более релевантный первый адрес для посетителей не из города страницы; при использовании результата как ограничения — риск скрыть правильный адрес, при частых вызовах — исчерпать лимит, при неописанной передаче IP — создать правовой и privacy-пробел.
- Идея или гипотеза улучшения: использовать определенный по IP город только как мягкий `locations_boost`, никогда не как `locations`, не менять им выбранный пользователем адрес и не считать его подтвержденной географией. Выполнять определение один раз на короткоживущую сессию или кешировать ограниченное время; при `location: null`, ошибке или таймауте незаметно переходить к контексту города страницы. Не сохранять результат в заявке и отдельно учесть передачу IP в документах о персональных данных.
- Вопросы для обсуждения: закрыты — явный запрос и выбор пользователя определяют фактический адрес; IP используется только для soft boost, КЛАДР-код/none хранится 24 часа в HttpOnly-cookie без сохранения IP на сервере, а передача IP в DaData отдельно учитывается в будущей legal-документации.
- Связанные решения/issues: [решение](decisions.md#5-заявки-кол-центр-и-аналитика), [#89](https://github.com/Celtoman/astro-telekom/issues/89), [задача #91](https://github.com/Celtoman/astro-telekom/issues/91)

### PF-007 — Показывать оператору этап обработки заявки и требуемое действие

- Дата: 2026-09-10
- Область: admin UX / заявки / наблюдаемость доставки
- Статус: CONVERTED — принцип согласован владельцем; реализация отслеживается в [#92](https://github.com/Celtoman/astro-telekom/issues/92) и [#93](https://github.com/Celtoman/astro-telekom/issues/93)
- Контекст: при разборе production-заявки со статусом `PENDING` выяснилось, что карточка не показывает ошибку постановки в очередь, выводит внутренние коды `AVAILABLE`, `NOT_FOUND`, `API`, `FAILED` и читает идентификатор внешней заявки не из фактического поля DTO.
- Наблюдение: одного общего статуса недостаточно, если заявка может остановиться между проверкой адреса, проверкой договора, очередью и внешней доставкой. Оператору нужно видеть понятный текущий этап, итог каждого завершенного шага и следующее требуемое действие.
- Возможное влияние: зависшие заявки незаметны без чтения логов, а оператор вынужден расшифровывать технические enum-коды и не видит, требуется ли ручное действие.
- Согласованное улучшение: все пользовательские статусы выводить по-русски с коротким объяснением; неизвестный код не показывать как готовый текст интерфейса; отдельно показывать постановку в очередь, попытку Tarifnik, резервную email-доставку и возможность безопасного повтора, когда она допустима.
- Вопросы для обсуждения: точные формулировки статусов и уровень показа технических деталей согласовать при реализации экрана; исходный код ошибки оставить доступным только как дополнительную диагностическую информацию.
- Связанные решения/issues: [#92](https://github.com/Celtoman/astro-telekom/issues/92), [#93](https://github.com/Celtoman/astro-telekom/issues/93)

### PF-010 — Публиковать публичные URL без завершающего слэша

- Дата: 2026-09-11
- Область: public SEO / routing / URL contract
- Статус: CONVERTED — требование явно согласовано владельцем и оформлено в [#105](https://github.com/Celtoman/astro-telekom/issues/105)
- Контекст: владелец зафиксировал единый формат URL сайта без слэша в конце.
- Наблюдение: формат должен применяться не только к видимой строке URL, но и согласованно к генерации маршрутов, `canonical`, `sitemap.xml`, внутренним ссылкам и edge-редиректам.
- Возможное влияние: одновременная доступность slash- и no-slash-вариантов создает дубли, размывает SEO-сигналы и может приводить к цепочкам редиректов.
- Согласованное улучшение: все публичные HTML-URL, кроме корня `/`, публиковать без завершающего `/`; slash-варианты одним HTTP 301 приводить к каноническому адресу с сохранением query string. Assets, файлы и API-маршруты не включать в это правило.
- Вопросы для обсуждения: отсутствуют; детали реализации и regression-покрытие зафиксированы в задаче.
- Связанные решения/issues: [#105](https://github.com/Celtoman/astro-telekom/issues/105)

### PF-012 — Защищать рабочие экраны от запоздалых ответов и рассинхронизации DOM

Будущие маршруты и категории без соответствующих страниц или фильтров не включать.
- Вопросы для обсуждения: оставить ли подпись «Карта покрытия» или использовать «Проверить адрес»; нужен ли пункт «Тарифы» на общей главной с переходом к выбору города; добавлять ли в футер контекстные переходы к тарифам и форме.

- Идея или гипотеза улучшения: компактный список этапов «Подготовка → Сборка страниц → Проверка → Переключение сайта → Подтверждение». Завершённые этапы отмечены, текущий выделен, будущие нейтральны. Показывать прошедшее время, реальные счётчики страниц при наличии измерений и приблизительное оставшееся время диапазоном по сопоставимым успешным запускам. При недостатке данных сообщать, что оценка пока недоступна. В шапке — краткий текущий этап и переход к общему экрану.
- Состояния и границы: прогресс относится к точным publication/rebuild/revision/attempt и восстанавливается после обновления страницы. Очередь, повторная попытка, недоступные данные и неизвестный activation outcome отображаются отдельно от terminal failure. Успех появляется только после подтверждения activation и SQL acknowledgment; искусственно растущий процент и отсчёт без измерений не используются. Технические логи остаются в раскрываемых подробностях. Паттерны берутся из действующей shadcn/React Aria дизайн-системы; при проработке применён навык `ux-feedback`.
- Вопросы для обсуждения: утвердить состав карточки и политику приблизительной оценки времени. Планировщик, отмена публикации и новые способы запуска не предлагаются.
- Связанные решения/issues: [#255](https://github.com/Celtoman/astro-telekom/issues/255), [PF-030](#pf-030--дать-явный-глобальный-путь-к-публикации-изменений), [admin-design-system](admin-design-system.md).

### PF-034 — Автоматически завершать подготовку публикации после deployment

- Дата: 6 октября 2026 года.
- Область: надёжность публикации / эксплуатация / admin UX.
- Статус: CONVERTED — владелец поручил устранить проблемы публикации вместе с визуальным контролем; задача [#256](https://github.com/Celtoman/astro-telekom/issues/256), дефект [#257](https://github.com/Celtoman/astro-telekom/issues/257).
- Наблюдение: после ручного deployment новая CMS-публикация 14 ожидала согласования renderer с обслуживаемой версией 13. Отдельный технический CODE release не был виден оператору.
- Решение: runtime автоматически проверяет точный deployed commit, последний finished deployment и здоровье приложения; пересобирает только уже обслуживаемый snapshot. CMS-публикация ожидает подготовки, объясняет ожидание и продолжается без нового нажатия. Сохранённые рабочие изменения по-прежнему публикуются только вручную.
- Границы: подтверждение activation и SQL acknowledgment остаётся обязательным; неопределённый результат восстанавливается по прежней durable job. Состояния подготовки/недоступного provider показываются отдельно, новые deployment и расписание публикации не создаются.

### PF-194 — Полный набор иконок сайта для браузеров и устройств

- Дата: 2026-11-06.

Все ссылки должны учитывать immutable asset prefix публикации; manifest должен ссылаться на assets своего артефакта. Текущий verify-publication.mjs допускает ровно один rel=icon, поэтому расширение требует обновления verifier и связанных тестов, а не только новых link-тегов. SVG имеет смысл только при наличии настоящего векторного исходника.
- Источники: [Google Search Central](https://developers.google.com/search/docs/appearance/favicon-in-search), [web.dev: HTML icons](https://web.dev/learn/html/document-structure/), [web.dev: manifest](https://web.dev/articles/add-manifest).

### PF-244 — Что происходит после выбора роутера

- 24 ноября 2026. Статус OBSERVED. На защищённом стенде кнопка «Выбрать модель» открывает блок консультации со сводкой модели и цены. По согласованному плану модель остаётся в интерфейсе, а оператор получает запрос на обратный звонок по общему контракту. После отправки форма говорит о вопросах подключения. Из сочетания этих элементов трудно понять, известна ли оператору модель и что обсудят при звонке. [Согласованный сценарий](plans/2026-11-23-router-implementation-plan.md)
- Вариант в рамках текущего контракта — назвать действие «Обсудить модель», подсказать посетителю, что модель можно назвать при звонке, и показать подтверждение с темой консультации по роутеру. Если оператор должен заранее видеть выбранную модель, нужно отдельно согласовать передачу выбора в заявку и уведомление.
- Владелец согласовал FLOW 1 по кнопке «Оставить заявку» во всех трёх карточках. Решение — показать выбранную модель в общей модалке, открыть форму сразу для любого посетителя и использовать тексты о покупке роутера. После ввода телефона и согласия посетитель отправляет запрос на обратный звонок по существующему контракту.
