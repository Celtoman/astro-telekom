# Личный кабинет: минимальная CMS и план переноса в код

5 ноября 2026. [Подготовка #510](https://github.com/Celtoman/astro-telekom/issues/510). Основной комплект: **[паспорта всех17 размещений](2026-11-05-account-block-passports.md)** → этот план → [итоговый Figma-эталон](../research/2026-11-05-account-cleanup-screens.md).

**План принят владельцем; реализация разрешена отдельным сообщением и выполняется в задаче [#511](https://github.com/Celtoman/astro-telekom/issues/511).** Код и локальные проверки описаны в [отчёте внедрения](../research/2026-11-05-account-implementation.md). Внешний push/deployment и активация нового CMS snapshot остаются отдельными действиями; публичный выпуск и недостающие страницы не входят в этот объём.

## 1. Что согласовано после прожарки

| Решение | Зафиксированный результат |
| --- | --- |
| Достаточный минимум | Одна небольшая форма страницы, без поблочного конструктора |
| Тексты | H1 и введение редактируются; длинные инструкции, условия услуг, суммы, сроки и пояснения — в коде |
| Изображения | Редактор заменяет изображения в14 именованных местах; компоновкой не управляет |
| FAQ | Редактор меняет тексты, добавляет, удаляет и переставляет вопросы; стартовые6 пар сохраняются |
| Контакты | Общие connection/support телефоны из существующих настроек; локальных дубликатов ACCOUNT нет |
| Первый этап | ACCOUNT отдельно в защищённом тестовом контуре; недостающие страницы/переходы — зависимости публичного выпуска |
| Собственная авторизация | Не нужна; страница ведёт в кабинет провайдера |
| Дизайн | Выбранные оригиналы и четыре экрана Screens, без новой сборки вариантов или изменения D/T |

Никаких CMS-полей `dailyPrice`, `maxDays`, `suspensionPrice`, текстов условий, числа карточек, порядка секций, цветов, CSS/HTML/JS или mobile carousel controls. Прежнее предложение редактировать условия отменено прямым решением владельца.

## 2. Почему нужен отдельный контракт, хотя форма небольшая

В текущем коде есть `Page.content Json?`, каталог умеет проецировать это содержимое, есть SEO-редактор и общая публикация. Но нет типа ACCOUNT, предметного редактора, renderer согласованной композиции и разрешения этого URL во всех route guards. Generic rich_text не воспроизведёт дизайн.

Проверенные точки интеграции:

Дополнительная PageTemplate-архитектура не даёт здесь нужной редакторской возможности и увеличивает объём.

## 3. Предлагаемый контракт данных и редактора

Версия `account.v1`, поле `content.version='1.0.0'`; это предлагаемая версия новой схемы, не текущая версия всего репозитория. Верифицируется API, применяется к working draft и сохраняется в immutable snapshot. Неизвестные ключи/неверные типы отклоняются, а не теряются при save.

| Поле | Тип/контрол | Валидация и поведение |
| --- | --- | --- |
| SEO | Существующий редактор/SEO API | Title, description, OG и индексация по действующему контракту; canonical системно вычисляется из канонического маршрута, не новое редактируемое поле; не копировать SEO в content |
| `hero.h1` | string/input | Предлагаемый предел200 символов, непустое при публикации; plain text, без ручного HTML |
| `hero.intro` | string/textarea | Предлагаемый предел5000 символов; начальные4 абзаца разделены пустыми строками; непустое при публикации |
| `loginUrl` | string/URL | ≤2048, HTTPS без credentials; начальное `https://dom.ru/user/login`; предлагаемая системная allowlist `dom.ru`/`lk.dom.ru`; новый хост через обновление этой политики |
| `images.<slot>.src` | asset URL/input | Локальный `/images/…` либо статический HTTPS-ресурс по правилам ниже; ровно14 смысловых ключей, не массив произвольной длины |
| `images.<slot>.alt` | string/input | Предлагаемый предел500 символов; содержательная непустая альтернатива; исключение декоративной бизнес-картинки допускается лишь после подтверждения её полной эквивалентности тексту в реализации |
| `images.<slot>.caption` | string/input | Только13 слотов с существующей подписью, предлагаемый предел500; не создавать новую подпись приложения. Начальные подписи сохраняются, меняются при необходимости вместе с заменой изображения |
| `faq.items[]` | list с question/answer | draft0–50, публикация1–50 полных пар; question≤2000, answer≤20000 как в текущей схеме FAQ |
| Служебные метаданные | read_only | id страницы, version, working/published revision, технические ключи слотов; не редактор раскладки |

Пределы200/5000/500/2048 — предложения API-контракта для реализации, не уже действующая ACCOUNT-схема. На допустимом максимуме контент переносится, а не обрезается. H1/intro не интерпретируются как HTML или шаблоны. FAQ может использовать существующие SITE-подстановки по текущему валидатору; городские/тарифные переменные на общей ACCOUNT запрещены.

Форма в разделе «Страницы → Личный кабинет» (предлагаемая навигация, ещё не существующий путь): «Основное» → «Иллюстрации» → «FAQ», ссылка в существующий SEO-редактор. Слоты имеют понятные названия/миниатюры, фиксированы и упорядочены по странице. Редактор не видит raw JSON, не выбирает брейкпоинт для отдельных текстов и не настраивает число колонок.

Для reorder FAQ нужны команды «Выше/Ниже» с клавиатуры, а не только drag. После добавления фокус на новом вопросе; после удаления — на следующей паре/кнопке добавления. Несохранённый ввод защищён при внутренних переходах, Back/Forward и обновлении. Save сообщает фактический результат API и новую рабочую ревизию, не «опубликовано».

### Сохранение и публикация

- Guarded save атомарно проверяет site-scoped доступ и `expectedWorkingRevision`, сохраняет content и ContentRevision. 409 не перезаписывает чужую версию; введённое сохраняется для сравнения/повтора. При401/403 нет частичного сохранения и ложного успеха. Generic Page PATCH не должен обходить типизированную ACCOUNT-валидацию или revision guard.
- `Page.cityId=null` сам по себе не гарантирует единственность: текущий unique по nullable cityId не защищает от дублей общей страницы. ACCOUNT должна быть одна на сайт с каноническим slug; способ обеспечения уникальности выбрать и проверить миграцией/транзакцией с конкурентным тестом.
- Безопасный неполный draft сохраняется. Missing required поля, пустые FAQ-пары, неизвестные переменные и обязательные сломанные изображения блокируют готовность к публикации с путём поля. Нельзя скрывать их и объявлять страницу готовой.
- SEO остаётся отдельной операцией существующего редактора, учитывающей общий working revision. Форма ACCOUNT перечитывает актуальную ревизию после SEO save; устаревшие вкладки дают409.
- Preview строится из working данных через ту же проекцию/композицию, сайт — из конкретного serving snapshot. В preview нет реальных переходов, отправок и звонков; безопасные локальные раскрытия FAQ доступны, чтобы проверить ответы. Не использовать режим, который при `interactive=false` вообще выбрасывает текст всех закрытых ответов из preview.
- Публикация захватывает **весь working site**, не только ACCOUNT. Перед активацией предъявляется полный diff, включая чужие неопубликованные изменения. Их наличие не является разрешением выпустить их вместе с ACCOUNT.

### Иллюстрации: минимальная механика замены

V1 предлагается на существующем паттерне **замены URL источника** и метаданных в фиксированном слоте. Это выполняет согласованную редактируемость изображений; файловый upload, медиатека, папки и обработчик произвольных загрузок в минимум не добавляются. В CMS следует прямо назвать контрол «Источник изображения», не рисовать неработающую кнопку загрузки. Если необходима именно загрузка локального файла целиком через CMS, это отдельное изменение технического объёма перед реализацией, а не уже имеющаяся возможность.

Для начального набора при реализации экспортировать именно исходные пиксели/векторы принятого дизайна, а не full-page PNG. Разместить в версионированных проектных assets; сохранить provenance, размеры и digest. Поддерживаемые контентные форматы V1 — PNG/WebP/JPEG; рамки, иконки и store badges — системные ресурсы. Пример технического лимита ресурса для реализации: до10MiB и20MP; отказ не должен портить прежний слот. Сравнение с новым реальным изображением перед фиксацией этих пределов обязательно.

HTTPS-источник должен быть стабильным, версионированным, принадлежать разрешённому статическому хостингу; не signed URL с истекающим сроком, не data/blob URI, не credentials и не исполняемый SVG/HTML. Нельзя обещать воспроизводимость старого snapshot при перезаписи файла по тому же URL. Изменение картинки означает **новый URL**, прежний ресурс сохраняется. Размер/пропорции, доступность и тип проверяются до публикации; при отсутствии возможности подтвердить стабильность использовать проектный versioned asset.

Если проверка ресурсов выполняется сервером, запретить произвольный URL fetch: allowlist хостов, запрет private/loopback/link-local адресов и небезопасных redirects, ограничение времени/размера/MIME и проверка каждого redirect. Повтор сборки/CODE не должен незаметно менять пиксели старого serving snapshot. Конкретный перечень собственных media-хостов и способ проверки — технический gate до реализации media-части; кодовую/контентную структуру страницы ради него менять не нужно.

## 5. Последовательность внедрения после отдельного разрешения

### Этап1 — зафиксировать исходники и закрыть технические prerequisites

**Ответственные:** разработчик + владелец контента по спорным фактам. Прочитать актуальные Figma design context/screenshots перед кодом; зафиксировать keys/asset provenance всех13 семейств,17 размещений и14 слотов. Сопоставить тексты финального Screens с исходным сохранённым контентом: исключить разрешённые удаления, сохранить все остальные смыслы, списки, предупреждения и6FAQ. Не восстанавливать отклонённый дизайн статьи.

Уточнить существующие собственные static media-хосты/ресурсы для замены URL и способ стабильного хранения начальных assets. На этом этапе согласовать спецификацию расширения source-контракта общего FLOW2: глобальная страница в site scope, фактический город/структурированный дом, проверка по serving snapshot. **Выход:** content/action/asset manifests, безопасный source DTO и обратная совместимость городских форм, карта нерешённых destinations. Если данные требуют редакционной правки — предъявить конкретный before/after, не исправлять заранее неизвестный текст по общему разрешению на перенос.

### Этап2 — модель, route inventory и рабочие данные

Добавить ACCOUNT в необходимые Page/SEO/public route типы, строгий schema/defaults/валидатор, программные паспорта и кодовый контент. Одно каноническое глобальное размещение. Не входит в разрешение этой задачи. После реализации недостающих маршрутов — полная функциональная приёмка всех переходов, подтверждение актуальности условий/контактов/инструкций, проверка реальных браузеров и решение владельца о публичном запуске. Новые страницы не добавляются в этап1–5 «заодно».

## 8. Короткий протокол будущей пользовательской проверки

**Статус:** подготовка, реальных участников/сессий/результатов нет. По Figma-регламенту протокол входит в передачу полной страницы; рекрутинг и проведение требуют отдельного поручения и не блокируют саму документальную поставку.

**Решение исследования:** достаточно ли понятны оглавление, горизонтальные карточки и разделение «инструкция партнёра → действие у провайдера», чтобы принять реализацию без дополнительной перегруппировки.

**Вопросы:** находят ли нужный раздел без боковой панели; обнаруживают ли содержимое за первым элементом мобильной ленты; различают ли восстановление/вход и прекращение/временную паузу; понимают ли куда ведёт основной переход; может ли редактор обновить снимок и FAQ, сохранив раскладку.

**Участники для будущего заказа:** действующие/недавние абоненты, знакомые с оплатой интернета, с разным опытом кабинета и мобильными устройствами; отдельно редактор контента для CMS-задач. Не сотрудники текущего дизайна как замена абонентам. Размер выборки согласовать под конкретные риски/устройства; универсальную статистическую гарантию не назначать. Браузеры/AT — те, которыми реально пользуются участники, без сбора абонентских паролей/платежей.

| Нейтральное задание участнику | Успех / что фиксировать |
| --- | --- |
| «Вы сменили телефон и не помните данные, которыми пользовались раньше. Найдите, как снова получить доступ к управлению услугами» | Находит нужную инструкцию без подсказки; отмечаем ошибочные переходы/возврат |

Модератор сообщает: «Проверяем страницу, не вас; рассказывайте, что ищете и чего ожидаете». Не подсказывать названия чипов/направление жеста; после затруднения сначала «Что попробовали бы дальше?». Отметить помощь модератора как assisted, не успех без помощи. Для каждой задачи записывать complete/partial/fail, время описательно, ошибки/восстановление и оценку понятности; критерий полного успеха — достигнутая задача без подсказки, а не заданный без основания процент.

Строка наблюдения: `participant pseudonym | device/browser/AT | task | timestamp | observed action/quote | interpretation separately | outcome | assistance | severity | evidence`. Приоритет находки объяснять влиянием на задачу и повторяемостью в этой выборке, без заявлений о всей аудитории. Запись экрана/голоса — только с добровольным согласием; срок хранения, доступ и контакт организатора определить перед сессиями. Реальные договоры, баланс, пароли и платежи в заданиях не используются.
