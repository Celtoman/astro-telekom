Author — фактический Person либо Organization с необязательной достоверной ссылкой; отсутствие автора допустимо. Издатель берётся из проверенных настроек партнёрского сайта. Не создавать автора «Дом.ру» из темы новости. Источник включает исходный URL/название при наличии и сохраняется при переносе.

**Body schema:** версионированное дерево с разрешёнными paragraph/text, H2/H3, bold/italic, списками, ссылками, цитатой и изображениями/подписями. H1 создаёт шаблон. Произвольные HTML, script, iframe, style, шрифты/цвета/колонки не принимаются. Текст и URL валидирует сервер; неизвестный узел не исполняется и не теряется молча при импорте. Фронтенд и preview используют один serializer/render contract.

**URL:** normalize по [public-url.ts](../../apps/web/src/data/public-url.ts), без завершающего slash; уникальность news slug в пределах сайта. Реестр маршрутов проверяет коллизии `/news`, `/news/page/*`, `/news/category/*`, городов, действующих страниц и 301 до сохранения/выпуска. Коллизии старых слагов в импорте выводятся для разрешения, не исправляются незаметным добавлением суффиксов. Переименование заголовка не меняет slug.

**Даты:** дата первой публикации для читателя отделена от времени операции CMS/импорта; перенос сохраняет исходную дату и timezone, если известна. Неизвестную точность отметить в реестре. dateModified обновляет только изменение выпущенной редакции, не autosave, preview или CODE rebuild. Равные даты сортируются дополнительным стабильным id. Расписание не реализуется; будущая дата не должна молча включать отложенную публикацию.

## 5. Независимая публикация — обязательный отдельный этап

**Выбранный подход:** один действующий статический pipeline и полный атомарный артефакт, но композитный source из live baseline плюс выбранный change set. Не добавлять второй независимый deploy/copy HTML поверх текущего релиза. Не рендерить публичные новости запросами в рабочую БД при каждом просмотре.

Последовательность:

1. Определить **фактически обслуживаемый** publication ID штатным serving context. «Последний SUCCEEDED» не подменяет его при неопределённости. Если baseline недоступен, review сообщает об этом и не берёт рабочий каталог как замену.
2. Захватить исходный source baseline из связанного validation snapshot и выбранные immutable editorial revisions. Для старых снимков без нужного source выполнить явную проверяемую bootstrap-процедуру; не синтезировать источник из всех текущих рабочих данных.
3. Сформировать change set: выбранная статья/настройка, точные медиа, новая категория при необходимости, нужные 301. Настройки уже существующей категории с посторонним черновиком не выпускаются автоматически. Зависимости показаны до запуска.
4. Наложить только этот change set. Пересчитать производные списки/категории, pagination, главную и related из **смешанного опубликованного источника**, а не из рабочих news rows.
5. Сохранить полноценные sourceSnapshot/catalog и manifest выбранных редакций. Валидировать весь результат, включая неизменённые существующие маршруты; посторонние невалидные черновики не должны блокировать scoped release, поскольку их нет в candidate source.
6. Review привязан к basePublicationId, revisions и digest. Изменение выбранной записи/зависимости либо активация другой публикации делает review устаревшим. Нельзя незаметно заменить его новым составом.
7. Создать/повторно получить операцию по idempotency key; очередь сайта сериализует активации. При изменившемся baseline — новый review/rebase до запуска, без потери чужой уже опубликованной новости.
8. Штатные builder, manifest, Caddy If-Match, durable receipt и SQL acknowledgment активируют HTML, assets, redirects и public catalog вместе.
9. После подтверждения отметить опубликованными **только захваченные entity revisions**. Если во время сборки появился новый autosave, он остаётся отдельным черновиком: «На сайте · есть изменения».
10. При timeout/poll failure проверить прежний operationId и receipt. Отказ до activation оставляет baseline; uncertain outcome восстанавливается штатно, без повторного слепого запуска.

### 5.1. Ревизии, совместимость и регрессии

Текущие `Site.workingRevision/publishedRevision` и unique `(siteId, siteRevision)` не выражают частичный выпуск. **Нельзя** объявить все сохранения опубликованными, просто выставив global publishedRevision в номер scoped release.

В T1 зафиксировать additive migration/ADR: отдельная монотонная последовательность публикаций/operation identity и ledger выбранных entity revisions; `siteRevision` сохраняется как provenance захваченного legacy-среза. Unique/dedup/order queries, controller/worker receipts и readers должны различать номер выпуска и номер working source. Перенос существующих записей детерминированный, их immutable JSON не переписывается. Контрольная точка T4 запрещает продолжать интеграцию до регрессионного доказательства этих правил.

Обычный выпуск legacy CMS продолжает выбирать свой прежний scope и сохраняет уже опубликованную редакционную часть из live baseline. Он не должен автоматически выпускать все draft-новости. CODE rebuild пересобирает точный обслуживаемый snapshot, не захватывает рабочие редакции.

**Категория:** rename/meta/slug — отдельный scope. Изменение отражается во всех публичных карточках/статьях категории, но не выпускает их неготовые body/cover drafts. При переносе материалов/удалении категории используются field-level изменения опубликованных редакций; конфликтующие draft-планы видны отдельно. Смена slug категории создаёт 301 старого category path и корректно обрабатывает существовавшие страницы её пагинации.

**Снятие:** удаляет статью из candidate catalog и всех производных представлений; публичный маршрут удалён, noindex404; история остаётся. Исходные aliases не ведут на несуществующее назначение: их деактивация/замена входит в change set. Повторный выпуск проверяет slug/redirect conflicts заново. Если вручную выбранная related-новость снята, публичная подборка исключает её и дополняется автоалгоритмом; чужой draft списка related не публикуется.

## 6. UX/UI админки

### 6.1. Навигация и экран списка

- Sidebar: «Новости → Все новости / Категории»; «Страницы → Новости» для общих настроек и «Страницы →404». В списке есть прямой вход в настройки раздела, без необходимости помнить их размещение.
- Заголовок, счётчик, «Создать новость», поиск, категория и состояние. Таблица: заголовок, категория, публичная дата, состояние, действия. На Mobile сохраняются заголовок/статус/дата и доступные действия, а не широкая горизонтальная таблица.
- Состояния: «Черновик», «На сайте», «На сайте · есть изменения», «Снята с публикации». «Проверяем… / Публикуем… / Ошибка выпуска» — отдельное состояние операции, не подмена жизненного цикла.
- Loading, initial empty, no matches, error/retry и stale refreshing различимы. Нулевой результат поиска не предлагает ошибочно создавать первую новость; есть сброс фильтров.
- URL/query хранят фильтры/страницу списка; возврат из редактора восстанавливает их и положение. Клик заголовка — обычная ссылка; меню доступно без hover. Bulk publish отсутствует.

### 6.2. Редактор новости

**Верхняя панель:** «К списку», точный статус сохранения/время, «Предпросмотр», «Опубликовать»/«Опубликовать изменения». Верхняя панель не закрывает фокус/поле при zoom. Снятие и история — вторичные действия с ясными подписями, не рядом с основной кнопкой как равнозначные.

**Основная область:** заголовок → короткий анонс карточки → обложка → rich-text. **Справа:** состояние/live-ссылка → категория и дата → адрес → автор/источник → related → SEO → социальные сети. Редкие группы раскрываются; наличие ошибок внутри закрытой группы видно. На узком экране основная область первая, настройки после неё, действия остаются достижимыми.

Обязательные для выпуска поля: title, slug, category, дата и непустой body; анонс нужен для принятой карточки. Обложка/автор/источник/индивидуальное SEO необязательны. Draft сохраняется с missingFields. Ограничения длины/размера сообщаются до ошибки; длины SEO — рекомендации, не произвольные жёсткие SEO-блокировки. Длинные заголовки проверяются без обрезания публичного текста.

Слаг предлагается из заголовка только до явного выбора адреса; после первой публикации он меняется отдельным действием с показом 301. Рядом виден полный нормализованный адрес. Время/дата имеют ясную часовую зону. Авто-related показывает реальные выбранные системой материалы; manual позволяет до 3 уникальных опубликованных, без self-reference и дублей.

**Микротексты:** «Черновик сохранён. На сайте прежняя версия», «Не удалось сохранить. Текст остаётся в редакторе», «Материал изменён в другой вкладке», «Публикация проверяется — повторный запуск пока не нужен», «Опубликовано» только после подтверждения.

### 6.3. Автосохранение, конфликт и история

- Предлагаемый технический режим: autosave после паузы 1s, принудительный flush перед preview/review и при безопасном уходе. Не сохранять каждый keystroke отдельной исторической редакцией. Не отправлять незавершённую IME-композицию.
- Очередь сохраняет порядок, объединяет новые правки; ответ старого запроса не перезаполняет более новый ввод. CAS по entityRevision; глобальный чужой autosave не создаёт ложный конфликт новости.
- Локальная recovery-копия содержит поля текущего draft, user/site/entity/base revision и digest, без session token. Предлагаемый срок 7 суток — параметр технического контракта; explicit logout очищает данные пользователя. При повторном входе показывать восстановление только тому же аккаунту/сайту.
- Копию удалять лишь когда сервер подтвердил **именно её** digest; новый ввод, набранный во время запроса, не удалять. Нельзя обещать сохранность после закрытия вкладки только по отправленному, но не подтверждённому запросу.
-409: приостановить autosave, сохранить оба варианта, предложить сравнение/копирование и явное сохранение выбранного варианта с новой revision. Кнопка «Обновить» не стирает ввод без решения пользователя.
- История: публикации и последние 20 контрольных черновых snapshots. Checkpoint по значимому изменению/выходу из редактирования и перед восстановлением; точный механизм группировки закрепить тестом. Undo/redo ввода и история серверных редакций — разные функции.
- «Восстановить в черновик» создаёт новую рабочую редакцию с CAS и сохраняет текущую в истории; не изменяет live и не очищает опубликованные версии.

### 6.4. Категории, настройки и 404

- Таблица категорий: название, slug, отдельно публичное/общее число материалов, состояние изменений; число — переход в отфильтрованный список. Создание доступно и из combobox редактора без потери текста.
- Редактор категории: название, slug, описание, SEO/OG, preview, список затрагиваемых публикаций. Запрет удаления используемой категории объясняется количеством/ссылкой; действие переноса показывает точный состав.
- Настройки списка: title/intro и согласованные подписи. Размер сетки, цвет чипов,12 записей, число колонок и сортировка не предлагаются как свободные дизайнерские настройки.
-404: только предусмотренные поля принятого макета и разрешённые внутренние destinations. Ошибочная ссылка недоступна для выпуска; назначение не вводится произвольным небезопасным URL. Кнопки/шапка/футер сохраняют принятые размеры и компоненты.
- Для каждого scope — самостоятельные draft/live, preview и publish review. Category/list/404 не используют кнопку, которая фактически выпускает все остальные изменения сайта.

### 6.5. Доступность и дизайн-проверка

Использовать существующие Card/Table/Field/Input/Badge/Alert/Button/Dialog/Progress и React Aria. Специальные editor/uploader/cropper — композиции в стиле референса, с документированным отсутствием готового блока. Не переносить публичный розовый дизайн целиком в рабочую админку.

Проверить keyboard, видимый/неперекрытый фокус, имена/описания полей, возврат фокуса из диалогов, ошибки не только цветом, live-статусы без перехвата фокуса. Для загрузки и кадрирования есть альтернатива drag, для текста — доступная toolbar с undo/redo/links. Светлая/тёмная темы,1440/834/390/320,200% zoom и reflow400% — отдельные проверяемые сценарии. Автоматический scan не заменяет keyboard/AT.

## 7. Медиа, хранение и зависимости

1. Multipart upload через API, контроль auth/site, signature/MIME, размера и разрешения изображения, лимиты декодирования. Первый выпуск: JPEG/PNG/WebP; исходные ссылки и неподдержанные форматы импорта отмечаются в отчёте. Не принимать произвольный SVG/HTML как editorial image.
2. Сохранять оригинал и производные под неизменяемыми content-addressed/asset-versioned ключами. Crop обложки 16:9 не разрушает исходник; социальное изображение может иметь собственный crop. Alt и подпись редактируются отдельно от файла.
3. Для действующего контейнерного контура предусмотреть persistent media volume, API write и приватный доступ builder/read-only. Точная mount/backup-схема входит в T3; не полагаться на эфемерный слой контейнера.
4. Draft media доступны авторизованному preview; не размещать неопубликованные файлы в общедоступной папке. Preview получает assets через защищённый endpoint/подготовленные blob URLs, не передавая токены в публичный URL.
5. В immutable release копируются точные нужные derivatives и hashes через существующий artifact manifest/publicAsset contract. Публичное изображение работает при недоступном API и не меняется из-за draft replacement.
6. Удаление проверяет ссылки current draft,20 контрольных редакций, всех published revisions, pending releases и retention. Автоматическую физическую очистку опубликованных assets не включать в первый этап; согласовать с существующим [retention runbook](../runbooks/publication-retention.md).
7. Backup должен включать оригиналы/метаданные и проверяемую связность с revisions; будущая пробная процедура восстановления на изолированном стенде — часть приёмки T3/T10.

Предложение rich text: [OSS Tiptap React](https://tiptap.dev/docs/editor/getting-started/install/react) с минимальными разрешёнными extensions и своей server-side валидацией AST. Платные version/AI/collaboration extensions не нужны: история хранится нашим API. Upload — [официальный fastify-multipart](https://github.com/fastify/fastify-multipart); sharp уже имеется у web, но API-зависимость/контейнерные библиотеки должны быть объявлены явно. До установки проверить совместимость, лицензию и audit; manifests и pnpm-lock меняются вместе.

## 8. Публичные страницы, метаданные и preview

### 8.1. Маршруты и представления

| Путь | Условие/поведение |
| --- | --- |
| `/news` | Общий список,200 даже при отсутствии публикаций, аккуратное пустое состояние. |
| `/news/page/{n}` | Целое n≥2 в существующем диапазоне; по 12 записей. `/page/1` →301 базового списка. |
| `/news/{slug}` | Только выпущенная редакция, иначе 404. |
| `/news/category/{slug}` | Опубликованная категория с публичными материалами; пустая не предлагается в навигации. |
| `/news/category/{slug}/page/{n}` | Та же пагинация внутри категории; page/1 → базовый category path. |
| Любой неизвестный URL | Полный принятый 404 с реальным HTTP404, без авто-перехода на главную; не индексируется. |

Некорректный/нулевой/отрицательный/слишком большой номер возвращает 404, не пустую 200 и не маскирующий редирект. Для прямого адреса категории без публичных материалов технический default плана —404; при восстановлении материала её route возвращается. Обработчик 404 не должен подменять ошибки API/приватного медиа; отсутствующий файл не получает ложный ответ 200.

Карточка — одна ссылка с одним Tab-stop; category chip внутри неё не отдельная ссылка. Без «Читать новость». Hover без сдвига, focus-visible, pressed и touch по принятому контракту. Роли title/summary/media выравниваются внутри строки Desktop/Tablet без обрезания; на Mobile естественная высота. Смешанные ряды с/без фото используют принятый системный fallback; чисто текстовый ряд не резервирует лишнюю картинку.

Статья A: Tablet-контейнер 720px по оси Header/Related, ширина чтения Desktop по принятому макету, Mobile без горизонтального scroll. Внизу до 3 связанных и готовая голубоватая «Все новости». Крошки статьи: D/T «Главная → Новости → Заголовок», M «Главная → Новости». Категория статьи отдельно ведёт в свой список. Крошки категории: «Главная → Новости → Категория», мобильное сокращение следует принятому библиотечному контракту без изобретения нового компонента.

Пагинация справа: Wide≤7/Mobile≤5 позиций с многоточиями, отсутствующие крайние действия схлопываются, Mobile действия второй строкой; минимум 44px по принятому дизайну. При 0/1 странице навигация скрыта. Многоточие скрывает минимум 2 страницы и не получает Tab-focus. `aria-current=page`, русские доступные имена и работа безJS. Состав 12 одинаков на всех устройствах. При смене category открывается первая страница, Back возвращает прежний контекст.

Блок главной размещается после «Больше возможностей», перед помощью с подключением; три последние из публичного news projection, без DEMO. При 0 скрыт; при 1/2 показывает доступное число. Не добавлять акции или менять соседние блоки. [#341](https://github.com/Celtoman/astro-telekom/issues/341) остаётся открытым до фактического выполнения и проверки своего Figma-объёма.

### 8.2. SEO, OG, Schema

- Сохранить общие SEO-шаблоны. Новые виды NEWS/NEWS_CATEGORY/NEWS_DETAIL имеют свои defaults; индивидуальный override разрешён только для новостей/категорий по согласованному исключению, а не возврат удалённых SEO JSON всех Page/Tariff.
- Title/Description формируются из типизированных полей; начиная со второй страницы Title имеет суффикс «Страница N». У каждой страницы собственные canonical/og:url; `/page/1` не создаёт дубль. Опубликованные INDEX-маршруты входят в sitemap; draft/withdrawn/404 и redirect sources не входят.
- OG: article для материала, website для list/category; title/description/url/image, размеры/alt, site_name/locale; применимые article dates/section. Fallback: OG override → SEO → title/summary; image override → cover → штатная social-картинка сайта. В sidebar видны итог и источник fallback, есть сброс override. Общий fallback не выдаётся за фото события в NewsArticle.
- Schema из той же выпущенной projection: WebPage+NewsArticle и BreadcrumbList; list/category — CollectionPage+ItemList видимых материалов. `articleSection`, фактические автор/издатель, dates с timezone, применимое изображение. Если импортированный текст не является новостью, тип Article выбирается по содержимому и отражается в реестре, без выдачи всех материалов за news.
- Один связанный JSON-LD graph со стабильными@id; расширить BaseLayout вместо дублирующего WebPage. JSON сериализуется безопасно для script, CSP hash формируется штатно. У 404 не появляется разметка несуществующей статьи.
- Социальное preview приблизительное; не обещает очистку кеша Telegram/другого сервиса. X Cards не считаются уже согласованной отдельной функцией: OG обязателен, дополнительные теги допустимы только без новых пользовательских полей/сервисов и после проверки нужности.
- Проверки: собственные инварианты/Schema.org Validator и применимые Google Rich Results Test. Валидный тест не обещает расширенное отображение. Первичные источники: [Article](https://developers.google.com/search/docs/appearance/structured-data/article), [Breadcrumb](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb), [Pagination](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading), [Open Graph](https://ogp.me/).

### 8.3. Общий preview

Использовать те же content model, renderer/helpers, CSS, шрифты и media projection, что в итоговой Astro-сборке. Не поддерживать вторую вручную похожую верстку админки. Представления: статья, list/home card, общий/category list и 404;1440/834/390/320; переключатель «Черновик / На сайте» с точной revision/publication identity.

Обычный draft-preview показывает выбранную сохранённую редакцию в опубликованном окружении; зависимые черновые поля показываются только если явно входят в выбранный candidate scope. «На сайте» читает serving snapshot; если версия недоступна, показывает ошибку, не подменяет её рабочей. Preview не публикует, не выполняет формы/заявки и не выдаёт sandbox-нажатия за доказательство public navigation.

## 11. Команды проверок и документы

Во время будущей разработки запускать только профильные suites, затем общий gate на рискованных этапах/перед push. После изменения API сначала `pnpm --filter @provider/api run build`, поскольку CJS-тесты читают dist. Примеры для уже названных новых suites:

pnpm --filter @provider/api run build
node --test tests/news-contract.test.cjs tests/editorial-revisions.test.cjs tests/editorial-publication-model.test.cjs

Новые suites запускать после их появления; отсутствие теста сейчас не считается падением baseline. `ALLOW_DEMO_DATA=true` допустим для локального build gate, но приёмка миграции/live-release использует точный реальный снимок. Внешний выпуск требует CI/deployment/receipt/live evidence, а не только `pnpm check`.

При реализации обновлять в том же коммите релевантные `current-state`, `architecture`, `data-model`, `api-contracts`, `publication`, `site-structure`, `admin-design-system`, `web-design-system`, `deployment`, `worker`, `TEST_COVERAGE`, профильные паспорта и README при изменении запуска/состава. **История:** подготовка плана завершилась документальными проверками. Последующим сообщением владелец разрешил реализацию, коммиты, push и deployment; проверки этапов ниже теперь выполняются по порядку. Архив по-прежнему исключён.
