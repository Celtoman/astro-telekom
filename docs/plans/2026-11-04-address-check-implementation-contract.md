# CITY_ADDRESS_CHECK: контракт внедрения и редакторов

4 ноября 2026. **Q1–Q20 согласованы владельцем.** Ответы Q11–Q20 подтверждены сообщением с вложенным текстом. Учёт полного внедрения: [#479](https://github.com/Celtoman/astro-telekom/issues/479). Полное внедрение для всех городов явно разрешено владельцем: код, CMS, preview, проверки, push, деплой, CMS-публикация и проверка сайта. Реализация выполняется по этому контракту; результаты выпуска фиксируются отдельно.

## Область и источники

- Страница создаётся для всех опубликованных городов. Особого пилотного города и отдельного локального состава нет. Проверки охватывают полный каталог и представительные граничные случаи.
- Тип: CITY_ADDRESS_CHECK; URL: `/{location}/proverka-podklyucheniya-k-domru-po-adresu`, без завершающего слеша.
- Единый шаблон ADDRESS с собственным редакционным содержимым, независимо от HOME/CITY_HOME; локальных текстовых override отдельных городов нет.
- Полная CMS, паспорта каждого блока, рабочая версия, preview и публикация входят в объём. Общие источники фактов и общие компоненты переиспользуются.
- Визуальный эталон — [итоговые Screens](../research/2026-11-03-address-final-assembly-applied.md): Desktop620:1549, Tablet620:1565, Mobile620:1581, Mobile320620:1597 в файле BdxNHlBVZWejREtOEIWDkI. Исходники результатов и подборки — SRC-0147/0148 файла pKN4YecfI2fZuMj822ud49.
- Последовательность: шапка → вводная → проверка адреса → объяснение результатов → популярные тарифы → этапы → преимущества → консультация → FAQ → футер.
- Белая страница; общий контейнер1360/720/358/288 px на эталонных ширинах1440/834/390/320. Длинный контент увеличивает высоту, горизонтальная лента допустима только внутри преимуществ.

## Данные, действия и навигация — Q1–Q10

### Тарифная подборка — Q3/Q6/Q7

1. Источник — опубликованные доступные предложения текущего города из authoritative snapshot, та же TariffView, что у городского каталога.
2. Находим минимальную текущую месячную цену в INTERNET, INTERNET_TV и среди тарифов с `game.status=INCLUDED`. Gaming является дополнительным признаком и может пересекаться с INTERNET/INTERNET_TV.
3. Объединяем результаты без повторов; добираем до3 оставшимися INTERNET/INTERNET_TV по возрастанию цены. Чистое TV в доборе не участвует.
4. Финальная подборка сортируется по возрастанию цены. При равенстве сохраняется порядок каталога. Закрепление isSticky не даёт преимущества перед более дешёвым предложением.
5. Цена — `promoPrice ?? standardPrice`, соответствующая текущей цене карточки, без разовых платежей и опциональных дополнений. Предложения без известной цены исключаются из отбора.
6. Если предложений1 или2 — показываем их; при3 и более выводим выбранные3. Владелец подтвердил, что опубликованных городов без тарифов не будет. Новый режим публикации города без тарифов не вводится.
7. Карточки используют стандартное городское представление. Кнопка «Подключить» — FLOW1 с названием тарифа и городом; «Подробнее» — действующая страница тарифа. «Все тарифы» — `/{location}#tariffs`.

### Общие сценарии — Q4/Q5/Q8

- Самостоятельная адресная проверка — существующий FLOW2. Три бизнес-результата отделены от ошибок сервиса. Сохраняются подсказки, выбор структурированного дома, повтор, согласие, юридические документы и существующая серверная атрибуция.
- Межгородской адрес разрешён действующим контрактом: результат относится к выбранному дому, source-контекст сохраняет страницу начала проверки. Это не переключение города страницы и не новый повод менять существующую бизнес-логику.
- Пункты Header/Footer проверки подключения ведут на ADDRESS текущего города. Встроенные адресные формы продолжают непосредственный FLOW2. Общие resolver и snapshot-aware назначения не должны создавать ссылку на ещё не выпущенный маршрут в историческом CODE-снимке.
- На ADDRESS выбор города переводит на ADDRESS выбранного города и сбрасывает ввод/результат проверки. Системный приоритет города маршрута и существующий fallback общих страниц сохраняются.
- Все обычные обращения — FLOW1; обычное открытие очищает прежний тарифный контекст. Заявка из тарифной карточки сохраняет только действующий разрешённый контекст тарифа/города.

### SEO — Q10

Отдельный SEO-шаблон типа ADDRESS: редактируемые Title/Description, городские подстановки, собственный canonical, INDEX/NOINDEX, существующий OG-fallback. Индексируемые опубликованные URL включаются в sitemap. Текущие Basic Auth и noindex внешнего test-контура сохраняются; допуск реального трафика остаётся решением владельца.

## Каждый блок: подтверждённый контракт Q11–Q20

Первоначальный сокращённый перечень Q9 не был принят как достаточное согласование страницы. По уточнению владельца он заменён полным рассмотрением всех десяти блоков Q11–Q20 ниже; каждый пункт подтверждён отдельно.

### 1. Шапка — Q11

Используется актуальная сквозная шапка сайта с текущим системным меню, логотипом и подписями. Город берётся из URL-контекста, список — из опубликованного каталога. Телефоны/графики редактируются в общих настройках Site; отдельного ADDRESS-редактора Header нет. Проверка → ADDRESS текущего города, callback → FLOW1, смена города на ADDRESS сохраняет тип страницы. Меню и общие источники соответствуют остальным страницам.

### 2. Вводная — Q12

Два ADDRESS-поля: H1 и пояснение. Оба допускают существующие городские подстановки. Крошки и их ссылки системные: главная → текущий город → проверка подключения. Одна семантическая H1; оформление и переносы соответствуют Screens.

### 3. Адресный блок с помощью — Q13

13 ADDRESS-полей:

- `eyebrow`, `title`, `intro` — надзаголовок, заголовок и пояснение адресной карточки;
- `addressLabel`, `addressPlaceholder`, `checkButtonText`, `reassuranceText` — подпись и подсказка адресного поля, подпись проверки, пояснение под формой;
- `image`, `imageAlt`, `imageBadgeText` — иллюстрация, alt и бейдж;
- `helpEyebrow`, `helpTitle`, `callbackButtonText` — надзаголовок/заголовок помощи и подпись звонка.

Телефон и срок callback — общие настройки. Адресная форма — существующий FLOW2, правая кнопка — FLOW1. Подсказки, ошибки, результаты, согласия и документы принадлежат общей логике форм; не редактируются отдельными копиями ADDRESS. Адаптация соответствует2g в Screens, включая скрытие декоративной иллюстрации на Mobile.

### 4. Объяснение результатов — Q14

16 ADDRESS-полей: заголовок/вступление; у каждого из трёх фиксированных результатов — заголовок, описание, подпись следующего шага и текст следующего шага; заголовок/текст нижнего пояснения.

Смысловые ключи фиксированы: доступен Дом.ру / найдены альтернативы / предложений нет. Нижнее пояснение относится к отсутствию адреса и техническим ошибкам. Голубые карточки, белые подложки, согласованные иконки и красноватое пояснение сохраняются. Это информационный блок, а не второй renderer состояния FLOW2.

### 5. Популярные тарифы — Q15

Пять ADDRESS-полей: заголовок, вступление, подписи подключения, подробностей и всех тарифов. Источник карточек и алгоритм фиксированы выше. Нет локального редактора тарифных цен/названий внутри блока. Desktop3 колонки, Tablet2, Mobile/320 одна; выводятся только выбранные1–3 карточки и ссылка каталога.

### 6. Этапы подключения — Q16

11 ADDRESS-полей: заголовок, вступление, четыре пары заголовок/описание, подпись обращения. Четыре фиксированных шага: заявка → согласование времени → установка → подтверждение подключения. Порядок, номера и иконки системные. Телефон общий, CTA первого шага — FLOW1. Тексты независимы от HOME/CITY. Принятый сквозной компонент, Desktop4 / Tablet2 / Mobile1 колонка.

### 7. Преимущества — Q17

13 ADDRESS-полей: заголовок блока и шесть пар заголовок/описание. Ключи, порядок и иконки speed/fiber/wifi6/movix/connection/support фиксированы.

Факты: скорость — максимум опубликованных тарифов текущего города; технологии/Wi-Fi/Movix/онлайн-заявка — существующие общие редактируемые поля Site.publicDisplay; режим поддержки — общие настройки. При неизвестной скорости скрывается только чип, карточка остаётся. На Mobile горизонтальная лента с доступностью всех шести карточек, на больших размерах сетка3/2 колонки. Константа макетного примера не становится городским значением.

### 8. Консультация — Q18

Шесть ADDRESS-полей: заголовок блока, пояснение, заголовок формы, подпись телефона, подсказка телефона, подпись отправки. Телефон отдела и срок callback общие. Встроенный FLOW1 отправляется непосредственно из блока; валидация, согласие, документы, повтор и успех общие. Сохранение данных при юридическом просмотре и ошибке остаётся обязательным. Второй пустой диалог вместо отправки не открывается.

### 9. FAQ — Q19

ADDRESS-поля: заголовок и упорядоченные пары вопрос/ответ. Добавление, удаление и перестановка разрешены, публикация1–50 полных пар. Поддерживаются действующие SITE/CITY-подстановки. Начальные шесть демопар переносятся дословно.

На ADDRESS первый видимый вопрос открыт, остальные закрыты; раскрытие независимо. Пара с отсутствующим необходимым значением скрывается по существующему правилу. Если после этого видимых пар нет, секция скрывается. Общий renderer поддерживает согласованное состояние ADDRESS без автоматического изменения исходного состояния других страниц. Preview показывает реальное содержание ответов и согласованное начальное состояние.

### 10. Футер — Q20

Текущий сквозной Footer. Информационно-юридический абзац и подпись обращения редактируются глобально; телефоны/графики общие. Структура ссылок, логотип и назначения системные. Проверка → ADDRESS текущего города, обращение → FLOW1, документы → действующие юридические страницы. Тексты самих документов принадлежат их существующим редакторам.

## Общие правила редакторов

Новые паспорта содержат назначение, допустимые страницы, все поля/источники, валидацию, preview и доступность. Реестр показывает контракт только для чтения; редактирование контента — предметными контролами. Для переиспользуемых полей сохраняются действующие типы и границы, SITE/CITY scope и правила безопасного неполного draft/строгой публикации. Не добавляются raw HTML, произвольный JSON/CSS/JS или индивидуальная структура города. Состав и порядок десяти секций фиксированы; системное скрытие отдельно описано выше. Все восемь контентных секций получают собственные ADDRESS-данные; Header/Footer используют общие источники.

## Подготовленное начальное наполнение — утверждено владельцем

- Редакционные тексты и изображения — из согласованных итоговых Screens, без новой редактуры, включая шесть исходных FAQ-пар. Для H1/городских упоминаний используются существующие подстановки; макетные тарифные цены/городские факты заменяются данными соответствующего города.
- Подключение тарифной карточки первоначально подписано «Подключить» по прямому решению владельца. Общая оболочка, контакты, сроки и реальные юридические документы — из существующих источников сайта.
- Предлагаемый исходный SEO Title: «Проверка подключения Дом.ру по адресу в {городе}». Description: «Проверьте, доступен ли Дом.ру по вашему адресу в {городе}. Выберите дом, узнайте результат проверки и посмотрите тарифы города». Здесь {городе} — обозначение существующей городской подстановки для обсуждения, не новая исполнимая синтаксическая форма. OG наследует SEO; редактор может менять SEO обычным способом.

## Конкретный план полного внедрения — утверждено владельцем

1. До кода получить живые Figma design context/screenshots принятых адаптивов и проверить прямые зависимости; использовать текущие компоненты/ассеты. Исторические Screens и библиотека не требуют новой редакции ради изменения runtime.
2. Реализовать версионированный ADDRESS model/validators/defaults/passports, общую проекцию каталога, selector популярных тарифов и служебный route kind. Зарезервировать slug от тарифных коллизий, обновить API/web inventory, SEO/redirect/publication validation и контекст формы. При N городах и T тарифах целевой обычный HTML output расширяется с N+T+6 до2N+T+6. Counts вычисляются из захваченного каталога, не зашиваются числом.
3. Добавить рабочую миграцию ADDRESS-шаблона/SEO и предметные редакторы восьми контентных секций, guarded save/подстановки/предпросмотр. Миграция сохраняет пользовательские данные и immutable snapshots, повышает рабочую ревизию атомарно; действующий seed не запускается. Изолированный PostgreSQL rehearsal проверяет повтор, сохранность и rollback/конкуренцию.
4. Собрать публичную страницу и sandbox preview на общей проекции/renderer; выделить общий renderer карточки без дублирования дизайна. Переиспользовать существующие FLOW1/FLOW2, legal, шаги, преимущества, консультацию и FAQ. Preview блокирует реальные отправки и внешние переходы.
5. Покрыть selector/1–2 тарифа/пересечение Gaming/равные цены/промо, маршруты/коллизии/SEO, редакторы/независимость контента/сохранение ревизии, preview/public parity и формы. Проверить четыре эталонных и промежуточные ширины, длинные города/тексты, клавиатуру/фокус, no-JS информационных секций, отсутствие общего горизонтального overflow. Все бизнес-исходы и ошибки/повторы проверять контролируемыми ответами; не отправлять реальные внешние заявки автоматически.
6. Выполнить профильные проверки по ходу, полный pnpm check на итоговом дереве, git diff --check, проверку ссылок и staged scope; после успешных проверок Conventional Commit. Обновить README и релевантные docs current-state/structure/passports/publication/API/architecture/design/TEST_COVERAGE; сохранить чужие незавершённые изменения.
7. После разрешения полного выпуска: push, зелёный exact-SHA CI, Coolify MCP deploy выбранного приложения и проверка finished/exact SHA/running:healthy/CODE/serving receipt. CODE сохраняет обслуживаемый snapshot и его корректные назначения до новой CMS-активации.
8. Проверить рабочую ревизию и состав общей публикации, затем активировать согласованный новый CMS snapshot; подтвердить durable receipt/SQL status, полный route inventory/sitemap, живые страницы и общий Header/Footer на существующих типах. Перепроверить все опубликованные города автоматически и представительные граничные страницы в браузере; CMS/preview/формы и тарифные ссылки. Зафиксировать фактические результаты и ограничения, затем закрыть задачу.

Общая CMS-публикация захватывает рабочую ревизию сайта целиком. При обнаружении посторонних неопубликованных изменений их состав предъявляется владельцу до активации; они не считаются разрешёнными данным контрактом автоматически.
