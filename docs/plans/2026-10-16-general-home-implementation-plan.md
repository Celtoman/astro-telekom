# Поэтапный план реализации общей главной

Дата: 16 октября 2026 года. Версия: 0.1. Статус: **APPROVED / IMPLEMENTATION_IN_PROGRESS**. Последующим поручением владелец разрешил автономно завершить все этапы с проверками, коммитами, push и deployment без промежуточных одобрений. Ранее указанная граница только этапа 1 больше не действует. Отложенные акции/новости и пользовательское соглашение сохраняют отдельный scope.

**Цель:** перенести собранную общую HOME `/` в код с управлением разрешённым контентом через админку, сохранив утверждённые дизайн, порядок и действия.

**Архитектура:** `PageTemplate(HOME)` и `PageTemplateBlock.data` → типизированные проверки API → неизменяемый опубликованный каталог → статический Astro-рендерер. Админка изменяет рабочую версию через HTTP; preview использует сохранённые данные. Версия состава общей HOME отделена от версии Hero и от CITY_HOME.

**Стек:** существующие NestJS/Fastify, Prisma/PostgreSQL, Astro, React, Tailwind/shadcn с React Aria. Новые инфраструктура, CMS-конструктор и загрузчик медиа не требуются.

**Порядок исполнения:** одна проверяемая задача за раз, с приёмкой результата этапа перед следующим. Чек-лист выполнения ведётся в GitHub task из раздела 11; ниже — обоснование, зависимости и критерии. Первоначальное поручение охватывало только план. После этапа 1 получено автономное поручение завершить весь план; текущие результаты и проверки фиксируются по этапам.

## 1. Источники и согласованный объём

Главный контракт — [утверждённые паспорта и карта действий 1.0](2026-10-16-general-home-passports-actions-draft.md), включая решения D1–D5. Дополнительно: [decisions](../decisions.md), [состав HOME](2026-10-12-general-home-block-agreement.md), [правила Figma](../figma-design-rules.md), [публичная дизайн-система](../web-design-system.md), [админка](../admin-design-system.md), [публикация](../publication.md), [структура сайта](../site-structure.md).

Состав: **Header → Hero1d → проверка адреса 2g → о провайдере B14 → преимущества B15 → как подключить B06b → Movix B17 → больше возможностей B16 → помощь 2e → города B13 → FAQ B19 → Footer**.

Это 12 секций: 10 контентных блоков, включая существующий Hero, и кодовые Header/Footer. Новых управляемых блоков — 9. Содержание паспортов повторно не пересогласовывается; технические имена новых файлов/метаданных и API ниже — предлагаемая реализация.

Вне объёма: недостающие страницы, Акции [#340](https://github.com/Celtoman/astro-telekom/issues/340), Новости [#341](https://github.com/Celtoman/astro-telekom/issues/341), пользовательское соглашение, миграция legal URL, редактор меню, media upload, аналитические изменения и автоматическая публикация. CITY_HOME и страницы тарифов сохраняют свой состав. Figma не редактируется.

## 2. Исходное состояние перед этапом 1 и причина декомпозиции

Проверено по локальному коду 16 октября; это не проверка внешнего контура и не повторная визуальная приёмка Figma.

| Область | Что есть сейчас | Что требуется |
| --- | --- | --- |
| Данные | `PageTemplate(HOME)`, JSON блоков, рабочая ревизия, аудит | Контракты и данные ещё девяти блоков; отдельная версия состава |
| API | `admin-page-templates.controller.ts` редактирует первые экраны и тарифы; `site-catalog.service.ts` выводит `homeHero` | Чтение/сохранение полного состава HOME и включение новых блоков в публичный каталог |
| Публикация | Проверки Hero, immutable snapshot, review и ручной publish | Проверки всех новых блоков с точной диагностикой; совместимость старых снимков |
| Админка | `/templates/home`, `HomeScreensApp.tsx`, редактор Hero, защита несохранённых данных | Отдельные секции девяти блоков на существующем экране HOME |
| Сайт | `pages/index.astro` выводит только Hero внутри `BaseLayout` | Девять компонентов и полная композиция; Footer пока упрощённый, основа layout серая |
| Формы | `AddressForm`, `CallbackDialog`, адресный FLOW2 и модальный FLOW1 | Подключить входы новой страницы; адаптировать отправку из встроенного 2e |
| Города | Опубликованный каталог, общий контекст и отдельная `CitiesDirectory` | Встроенный B13 без второго H1 и без фиктивного каталога |
| Preview | Отдельный HTML-renderer `preview-document.mjs`, список CSS/assets в `preview-public-styles.mjs` | Те же новые блоки, данные, оболочка и визуальное соответствие сайту |

Простая вёрстка с текстами в компонентах не выполнит утверждённый вариант с админкой. Предпочтителен перенос через существующую цепочку шаблонов и публикации. Новый универсальный конструктор увеличит объём без необходимости; повторное использование старых архивных типов не соответствует новым паспортам.

## 3. Этап 1 — контракты данных и проверок

**Результат:** единый исполнимый контракт HOME без изменения обслуживаемого сайта.

**Точки изменений:** новые `apps/api/src/general-home-model.ts`, `apps/api/src/general-home.ts`; существующие `apps/api/src/block-passports.ts`, `apps/api/src/content-validation-error.ts` и при необходимости `apps/api/src/block-validation.ts`. Новые имена файлов — предложение плана.

1. Описать типы девяти паспортов, фиксированные смысловые ключи карточек, разрешённые поля и лимиты строго по утверждённому документу.
2. Вынести фиксированный порядок десяти контентных блоков и собственные метаданные общей композиции. Предлагаются `generalHomeCompositionVersion=1.0.0` и отдельный implementation ID в `PageTemplate.content`; `firstScreenPassportVersion=2.0.0` Hero не менять. Не переиспользовать метаданные CITY_HOME по совпадению имени HOME.
3. Разделить безопасный черновик и готовность к публикации: черновик может иметь пустые обязательные строки/FAQ, но не неизвестные поля, HTML, опасные URL, подменённые ключи или неправильный состав фиксированных массивов.
4. Проверять SITE-переменные по разрешённым текстовым путям, включая вложенные карточки. CITY/TARIFF и переменные в URL/assets/ключах запрещены; `<red>` остаётся особенностью Hero.
5. Добавить девять паспортов в read-only реестр как APPROVED/1.0.0; `editorReadiness=PENDING` до появления и проверки редактора каждого блока. Новую композицию не помечать ACTIVE по факту добавления реестра.
6. Покрыть проверки содержательными сценариями в новом `tests/general-home.test.cjs`: фиксированные массивы, пропуски/дубли/неизвестные типы, лимиты, переменные, небезопасные ссылки, пустой FAQ и точный путь ошибки.

**Приёмка:** валидатор принимает согласованные данные всех девяти паспортов; безопасный неполный черновик возвращает список полей; публикационная проверка его блокирует. Неизвестная версия не включает новый renderer автоматически. Старые проверки Hero/CITY_HOME остаются зелёными.

## 4. Этап 2 — API, публичный каталог и публикационная диагностика

**Зависит от:** этапа 1.

**Точки изменений:** `apps/api/src/admin-page-templates.controller.ts`, `apps/api/src/site-catalog.service.ts`, `apps/api/src/catalog-variables.ts`, `apps/api/src/published-page-template-view.ts`, `apps/api/src/publication-validation.ts`; при необходимости `apps/api/src/publication-change-summary.ts` и `publication-workflow.service.ts` для проекции/представления новых данных. Существующий механизм публикации не заменять.

1. Добавить специализированное чтение HOME в существующий site-scoped API. Предлагаемый URL: `GET /api/v1/admin/sites/:siteId/page-templates/general-home`. Ответ: метаданные композиции, упорядоченные блоки, `missingFields`, рабочая/публичная ревизии и отдельно опубликованные данные либо их отсутствие.
2. Добавить `PATCH` того же ресурса: `expectedWorkingRevision` и полный список десяти `{blockType, data}`. Позиции, видимость, источники и системные действия определяет сервер. Это сохраняет весь экран атомарно; не создаёт редактор произвольного JSON.
3. Проверять site ownership, допустимые поля и контракт текущего заблокированного шаблона. Сохранять одной serializable-транзакцией, одной рабочей ревизией и before/after аудитом. При stale revision — 409 без частичной записи; ошибка не должна стирать клиентский ввод.
4. Сохранить совместимость существующего `first-screens/HOME`: изменение Hero через старый контракт не удаляет и не сбрасывает девять новых блоков. CITY_HOME остаётся независимым.
5. Расширить публичную проекцию типизированным составом HOME и его версией; разрешать текстовые SITE-переменные и учитывать usages. Служебные поля редактора не попадут в публичный каталог. Старые `homeHero/homeHeroVersion` поддерживать для исторических снимков.
6. Добавить общие системные значения графика «Ежедневно, 24/7» и срока «в течение 15 минут» без локальных CMS-копий и нового редактора глобальных контактов. Номера берутся из Site, города — из опубликованного каталога.
7. Подключить строгую проверку новых блоков к publication review/preflight. Ошибка должна иметь `template=HOME`, `block`, полный путь `field` и причину. Общая ошибка рендера не маскируется под пустой текстовый блок.
8. Расширить чтение опубликованной версии с учётом фактического формата сохранённых снимков; новые блоки нельзя подставлять из рабочей версии, если в опубликованном снимке их нет.

**Приёмка:** GET → PATCH → GET сохраняет разрешённые поля и ревизию; чужой site/неизвестные поля/конфликт не дают записи. Review видит каждую обязательную секцию. Новая проекция формируется из одного snapshot. Старые snapshots и API первого экрана читаются без потери данных.

## 5. Этап 3 — подготовка рабочей композиции и безопасный переход данных

**Зависит от:** этапов 1–2. На этом этапе готовятся и проверяются механизм и изолированные данные; внешний переход ещё не выполняется.

**Точки изменений:** новая следующая data migration в `prisma/migrations/` с именем `general_home_composition` (свободный номер проверить перед созданием), существующий `apps/api/src/seed.ts`, новый `scripts/rehearse-general-home.mjs`. Новые таблицы и Prisma enum для строковых blockType по текущей модели не нужны.

1. Подготовить переход известной прежней HOME к десяти блокам: сохранить существующие ID/контент Hero, добавить только девять согласованных типов, зафиксировать версию состава. При неизвестной или неоднозначной исходной композиции остановиться до записи.
2. Записывать только рабочий шаблон и его attributed revision/audit. Проверить повторное применение без дублей и дополнительной ревизии. `SitePublication`, `publishedRevision`, CITY_HOME и исторические записи не переписывать.
3. Переносить начальный контент и assets из утверждённых Screens после точной сверки во время реализации. Числа городов и контакты из картинки не копировать как данные сайта. Демопары FAQ не заносить в рабочую БД как реальный контент.
4. Для разработки/визуальных тестов подготовить отдельный fixture с демоFAQ. Рабочий пустой FAQ сохраняется черновиком, но блокирует готовность новой композиции. Не заполнять его автоматически примерными ответами.
5. Выполнить PostgreSQL rehearsal на изолированной БД: прежняя HOME, уже обновлённая HOME, неизвестный состав, чужой site, before/after история и неизменность опубликованного снимка.

**Приёмка:** переход повторяем, сохраняет Hero и историю, не публикует новый сайт и останавливается на неизвестных данных до частичного изменения.

**Условие внешнего перехода:** новая неполная HOME участвует в общей проверке рабочей ревизии и может заблокировать публикацию всего её snapshot. Поэтому подготовку/применение data migration на внешнем контуре планировать после готовности кода и контента либо в согласованное окно заполнения. Демоданные и ослабление валидатора для обхода блокировки не используются. В рамках текущего поручения миграции не запускаются.

**Точки изменений:** `apps/admin/src/components/HomeScreensApp.tsx`, `PageTemplatesApp.tsx`, `AdminWorkspace.tsx`, `BlockPassportsPanel.tsx`, `apps/admin/src/pages/templates/home.astro`; новые предметные компоненты в `apps/admin/src/components/general-home/` при необходимости. Переиспользовать `useUnsavedChanges`, `usePublicationFieldFocus`, `VariableInsertionPicker`, существующие React Aria/shadcn примитивы.

1. Расширить HOME на текущем маршруте `/templates/home?kind=HOME`, сохранив отдельный режим CITY_HOME. Перед сборкой сверить подходящий form/card-паттерн обязательного dashboard-референса; не переносить Next.js-специфичный код.
2. Показать Hero и девять отдельных секций в утверждённом порядке, без drag-and-drop и скрытия обязательных блоков. Разрешить только поля паспортов. Системные данные выводить для чтения с понятным источником.
3. Для B14/B15/B06b/Movix/B16 закрепить количество и смысл карточек. Для FAQ сделать добавление, удаление и порядок пар в пределах 0–50 черновика; порядок секций страницы от этого не меняется.
4. Связать общую форму с API этапа 2: атомарное сохранение, понятные `missingFields`, ошибки на точном поле, сохранение введённых значений при 409/сбое; отмена перезагрузки и ухода при несохранённых данных.
5. Показать рабочую и опубликованную версии раздельно; отсутствие опубликованных новых блоков обозначить явно. Переход к preview использует сохранённую ревизию, не несохранённый ввод.
6. Добавить ссылки на предметный редактор из паспортов и переходы к полю из publication issue. В `publication-issue-presentation.mjs` различать одинаковые имена `title`/`items` разных блоков через block/field, не угадывать по сообщению исключения.
7. Проверить loading/error/retry/empty/unauthorized, смену сайта/режима, фокус и клавиатуру. После подтверждения работающего редактора конкретного паспорта обновить его readiness на READY; остальные не отмечать готовыми за компанию.

**Приёмка:** оператор может изменить контент каждого нового блока без изменения дизайна, сохранить неполный безопасный черновик, найти ошибку и увидеть сохранённые данные. Городской Hero и прежние опубликованные данные не заменяются содержимым общей HOME.

## 10. Отдельные этапы и условия выпуска

| Отдельная работа | Как связана с главной |
| --- | --- |
| Недостающие страницы | `/movix`, `/faq`, `/contacts`, `/wifi-router`, три тематических URL каждого опубликованного города по согласованной структуре. Собственная постановка и приёмка; без выборочной подмены городов. До их готовности переходы отмечены как непроверенные зависимости |
| Реальный контент FAQ | Отдельная подготовка/согласование ответов. Блок и редактор входят в план, демотексты не становятся материалом для выпуска |
| Акции | Существующий бэклог #340, не создавать блок/данные/редактор/пустое место сейчас |
| Новости | Существующий бэклог #341, не создавать блок/данные/редактор/пустое место сейчас |
| Пользовательское соглашение | Отложено прямым поручением: не создавать документ/страницу и не менять существующий пункт или поведение |
| Внешний выпуск | Отдельное поручение после локальной приёмки; без автоматического deploy или CMS publish из разработки |

Готовность разработки главной можно принять локально с явным списком отсутствующих целевых страниц. **Полностью работоспособную внешнюю главную нельзя считать принятой до проверки этих переходов и согласованного реального FAQ.** Пользовательское соглашение не переоткрывается как обязательная задача этого этапа.

При выпуске по полученному автономному поручению: зелёный CI и проверенный exact SHA → контролируемое применение подготовленных рабочих данных → проверка редактора/preview и snapshot → ручная CMS-публикация конкретной ревизии → live readback страницы, assets и всех доступных действий. Порядок code deployment/миграции уточнить по реальной схеме запуска migrate до API: совместимый code-only выпуск обязан продолжать обслуживать прежний snapshot. Push и CI сами по себе не доказывают deployment или применение нового контента.
