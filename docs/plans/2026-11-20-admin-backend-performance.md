# План ускорения админки и бэкенда

**Цель.** Меню сразу показывает переход, рабочие разделы быстро загружают данные, а ревью и выпуск сайта выполняются без многосекундных пауз в обычных запросах.

**Архитектура.** Сохраняем Astro static и общую React-оболочку админки. В NestJS/Fastify даём экранам компактные чтения через Prisma и PostgreSQL. Тяжёлую проверку и рендер выполняем отдельным процессом. Отдельная короткая транзакция проверяет актуальность результата и разрешает передачу точного снимка в существующий контур сборки и активации.

**Статус.** План от 20 ноября 2026. На внешнем контуре выпущены #631/#632, пилотные переходы #627, каталог городов #628, списки новостей #629, общий опрос статуса #641 и пакетное чтение медиа из #637. Для каждого следующего этапа сверять текущий код, замеры и условия поставки. Чек-лист исполнения и связи с проблемами ведутся в [задаче #644](https://github.com/Celtoman/astro-telekom/issues/644). [Реализация и измерения первого пакета](../research/2026-11-20-admin-performance-first-package.md).

## Основания для порядка работ

| Сценарий | Проверенный факт | Решение |
| --- | --- | --- |
| Обычная навигация | На действующем коде React-оболочка сохраняется, но Astro ClientRouter ждёт HTML. В локальном сравнении клиентский путь на текущем стеке показал заголовок за 33–124 мс p95 на четырёх экранах | Заменить ожидание документа на клиентский переход внутри рабочего пространства |
| Каталог и ревью | Предпросмотр, SEO и Sitemap измерялись в районе 10–13 с до первого байта. Preview возвращает около 27,1 МБ JSON без сжатия | Начинать с узких API по назначению экрана и использованию выбранного объекта |
| Одновременный лёгкий запрос | При одном ревью liveness без SQL ответил за 14,6 с при статическом контроле 0,3 с | Убрать автоматическое ревью при входе, затем изолировать тяжёлый расчёт от HTTP |
| Стоимость вычислений | Локальная валидация на снимке с 4451 URL сократилась с 7,94–8,04 до 1,68–1,76 с при повторном использовании форматтеров и индекса переменных | Применить и проверить малорисковую оптимизацию отдельно от смены транзакций |
| Доступ к PostgreSQL | В коде полные снимки, выборки до пагинации, последовательные запросы и длительные транзакции. Доля SQL, ожидания пула и блокировок на проде пока не измерены | Снять тайминги и исправлять конкретные планы и запросы |

Подробности исходных проблем находятся в [подзадачах #644](https://github.com/Celtoman/astro-telekom/issues/644). Результаты повторной проверки с реализованным кодом приведены в [протоколе первого пакета](../research/2026-11-20-admin-performance-first-package.md). Базовый SHA аудита и удалённого master при подготовке плана — [ec7be550](https://github.com/Celtoman/astro-telekom/commit/ec7be550213fa1471490f8d818be00f9fd65e86a). Локальный master расходится с базой и содержит пользовательские изменения. Для реализации взять чистый изолированный checkout от проверенного актуального SHA. Перед началом проверить, что запланированные изменения можно внести без переноса не относящихся к задаче правок. При повторной сверке отметить уже выпущенные изменения и конфликты до разработки.

## Контракты, которые проверяем на каждом затронутом этапе

- Admin сохраняет текущие проверки ролей, сайта и cookie-сессии. Login, одноразовый доступ к заявкам и sandbox предпросмотра сохраняют собственные границы. Остатки пользовательских данных и запросов очищаются при выходе, 401 и смене пользователя. До подтверждения доступа показывается оболочка без защищённых данных.
- Сохранение, проверка кандидата, публикация и CODE остаются различными действиями. Кнопка «Проверить» готовит отчёт. Сборку запускает отдельное подтверждённое действие публикации. Основание для выпуска включает точный исходник, актуальную ревизию, обслуживаемую базу, выбранные редакционные версии, время вычисления переменных и версию правил.
- Редакционный выпуск включает выбранный набор и необходимые зависимости. Рабочие черновики вне набора сохраняются. История снимков, диагностические поля, блокирующие ошибки, inventory, noindex, SEO, 301, ресурсы, целостность и статус активации должны проходить действующие проверки.
- Действующая версия публикации определяется фактически обслуживаемым publication ID, в том числе в интервале между активацией Caddy и SQL ACK. При несовместимости или повреждении данных применяется текущий договор об ошибке или проверенный путь чтения той же версии.
- Для различающихся HTTP-контрактов добавляем совместимый маршрут или версию ответа. Поэтапный выпуск API и UI репетируется с предыдущей вкладкой в браузере. Все маршруты возвращают корректный статус и состояние ошибки.

Профильные документы в репозитории: `docs/admin-design-system.md`, `docs/api-contracts.md`, `docs/publication.md`, `docs/worker.md`, `docs/runbooks/ghcr-release.md`.

## Варианты и выбор

| Вариант | Ожидаемый эффект | Решение |
| --- | --- | --- |
| Настроить prefetch HTML для существующего ClientRouter | Часть повторных переходов станет быстрее. Первый визит всё ещё зависит от получения документа | Резервом служат нативные переходы на отдельные статические документы |
| Клиентский переход внутри существующего AdminWorkspace | Устраняет ожидание HTML при клике и сохраняет Astro URL для входа напрямую. В пилоте отзывчивость близка к варианту Next.js | Рекомендуемый вариант интерфейса |
| Миграция админки на Next.js | Меняет маршрутизацию, сборку, CSP и границы сессии. Понадобятся те же правки бэкенда | Вернуться к вопросу, если реализация на Astro не пройдёт приёмку |
| Только оптимизация синхронных функций | Даёт быстрое измеримое ускорение. Время работы всё ещё растёт с размером снимка и конкурентными запросами | Первое небольшое изменение бэкенда |
| Worker threads или отдельный процесс для проверки | Оба выносят CPU из основного event loop. Отдельный процесс даёт независимые лимиты, перезапуск и управление очередью | Предпочтителен отдельный процесс на коде API. Уточнить способ запуска и затраты на передачу снимка на изолированном прототипе |
| Узкие SQL-проекции или готовые записи по publication ID | JSONB-проекция уменьшает передачу в Node.js. Отдельные проекции убирают повторное чтение большого JSON для горячих запросов, но требуют совместимой записи и активации | Начинать с меньших выборок и измерения. Материализовать только подтверждённые горячие проекции |

**Готовность этапа.** Сравнения воспроизводятся. Для каждого сценария известно, какая часть времени относится к интерфейсу, API, SQL и CPU. Если внешняя детализация недоступна, отметить ограничение и использовать стенд для сравнительных решений.
