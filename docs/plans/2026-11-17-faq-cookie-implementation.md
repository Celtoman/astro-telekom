## 3. Контракт FAQ

### Данные и редактор

Одна глобальная страница `/faq` на сайт. Версионированное содержимое: H1/вводная, список групп со стабильными идентификаторами и порядком, список вопросов с постоянным идентификатором/ссылкой, обязательным `groupId`, заголовком и форматированным ответом; тексты нижней помощи. Идентификатор вопроса не меняется при редактировании заголовка, порядка или переносе между группами. Группировка и порядок одинаковы в HTML, оглавлении и Schema.

Редактор позволяет добавить/переименовать/переставить группы, назначить вопросу одну группу, добавить/изменить/переставить/удалить вопросы. Удаление непустой группы требует сначала разобрать её вопросы. Пустая именованная группа допустима в редакторе, но не выводится. Переключателей скрытия и отдельных статусов вопроса/группы нет. Создаваемые незаполненные поля могут находиться в несохранённой форме; API не сохраняет незаполненные добавленные вопросы/ответы или ссылки на отсутствующую группу. Для выпуска FAQ требуется хотя бы одна полноценная пара вопрос/ответ.

Ограниченный структурированный rich text: абзац, маркированный/нумерованный список, жирный текст, безопасная ссылка. Нет произвольного HTML, изображений, таблиц и пользовательского JS. Один нормализованный документ используется в preview, публичном HTML и JSON-LD. Ссылки валидируются; опасные схемы не исполняются. Существующие общие значения телефонов/графиков берутся из того же выпускаемого снимка; отдельные копии не создаются.

Ручное сохранение, защита несохранённого ввода, адресные ошибки, проверка рабочей ревизии/409 по действующему паттерну. SEO/OG/индексация — через существующую модель SEO. Preview использует тот же renderer и позволяет проверять раскрытия и размеры, без реальных заявок/звонков. Это не отдельный механизм автосохранения или истории из другой задачи.

### Публичное поведение и Schema

- Утверждённая композиция, белая основа, связанные визуальные роли и контакты без офиса. Переиспользуются общие header/footer/callback; «Раскрыть все» отсутствует.
- Семантические независимые раскрытия; содержимое ответов присутствует в итоговом HTML. Без JS вопросы доступны через native details, темы — обычными якорными ссылками.
- Постоянная ссылка на вопрос раскрывает его и прокручивает к нему с учётом шапки. Переименование вопроса или группы не ломает ссылку. Неизвестный hash не вызывает ошибку и не открывает случайный ответ. На мобильном выбор темы закрывает только оглавление.
- Одна сущность `FAQPage` и `BreadcrumbList` в общем JSON-LD; существующий default WebPage не дублируется. `Question`/`acceptedAnswer` создаются только из реально выводимых пар. Названия групп не превращаются в фиктивные вопросы. Данные не вводятся вручную вторым текстом.
- JSON-LD безопасно сериализуется, включая HTML-подобный текст и закрывающий script. Форматирование ответа преобразуется согласованным renderer, без потери текста списков/ссылок. Проверяется смысловое совпадение с HTML и отсутствие дублирующих сущностей/идентификаторов.
- Тип [FAQPage](https://schema.org/FAQPage) сохраняется в Schema.org. Google [прекратил показ FAQ rich results](https://developers.google.com/search/updates#removing-faq-rich-result); приёмка разметки проводится по валидности и соответствию странице, а не появлению расширенного результата в поиске.

## 4. Контракт cookie

Сквозное информационное уведомление OVL-0008, без механизма согласия и изменения принятой политики загрузки аналитики. Общие настройки сайта: включение, сообщение, подпись кнопки, две подписи ссылок и типы юридических документов. Адреса разрешаются по фактически опубликованным документам снимка. Ссылки открывают документы штатным способом; нажатие ссылки само по себе не запоминает закрытие уведомления.

Показ на всех публичных HTML-страницах, включая404 и legal; вне реальной оболочки admin/preview. Для настройки уведомления предусматривается изолированный визуальный preview без изменения закрытия в браузере редактора.

Оверлей закреплён снизу, не меняет поток страницы и не блокирует прокрутку/фокус. На D/T и Mobile соответствует принятым вариантам; на низком viewport его содержимое и действия остаются доступны. При открытом существующем публичном диалоге уведомление временно скрыто, после закрытия возвращается, если ещё не истёкло основание показа.

После «Понятно» хранится время закрытия для данного сайта/origin в браузере. Срок — ровно30×24часа после закрытия. Межстраничная навигация, повторный визит, обновление кода и изменение текстов/переключателя показа этот срок не сбрасывают. После истечения срока уведомление вновь появляется; новое закрытие начинает новый30-дневный срок. Нет ручного сброса, редакционной версии повторного показа и автоматического сброса от хеша текста. Версия схемы хранения остаётся технической характеристикой, а не командой повторного показа. При недоступном persistent storage закрытие действует в пределах текущего посещения без падения страницы. Изменение конфигурации действует после публикации.

## 5. Выборочная публикация и обратная совместимость

Два выбираемых scope: FAQ и COOKIE_NOTICE. Предпросмотр публикации показывает выбранные изменения, состав групп/вопросов, настройки cookie и результат валидации. Обрабатываются состояния до/после, отсутствие изменений и устаревшее подтверждение.

Выпуск накладывает только выбранное содержимое/метаданные на фактически обслуживаемый source snapshot, затем собирает и атомарно активирует артефакт штатным механизмом. Для FAQ берутся только его рабочая страница/SEO и необходимые зависимости; для cookie — только его namespace. Полная рабочая `Site.settings` не переносится вместе с cookie. Общие контактные значения, тарифы, новости, другие страницы и настройки остаются из serving baseline, если не включены отдельным разрешённым выпуском. Общие контакты FAQ используют значения именно полученного итогового снимка.

Публикация FAQ/cookie не помечает посторонние рабочие SITE/страничные правки выпущенными. Проверяются fingerprint/revision выбранного содержимого и serving baseline; при конфликте требуется свежий review, без overwrite. Валидация проводится над реально выпускаемым снимком, а не превращается в запрет из-за чужого незавершённого черновика.

Старые snapshots без FAQ не получают маршрут при CODE; без cookie-настроек не получают новое уведомление из текущего рабочего состояния или неявного demo default. Указатели общей навигации ведут на `/faq` только когда он есть в обслуживаемом inventory; до его первого выпуска сохраняется прежнее поведение. Невалидная присутствующая конфигурация не заменяется молча демоданными. Общая публикация сайта продолжает работать по своему контракту.

## 6. Этапы реализации

1. **Зафиксировать исходники.** Проверить текущее рабочее дерево и serving/working revisions без захвата чужих изменений; получить актуальный Figma context/screenshots FAQ/OVL и прямых зависимостей; составить карту к существующим компонентам/токенам/assets. Тематические переходы Figma проверены на четырёх адаптивах, [#610](https://github.com/Celtoman/astro-telekom/issues/610) закрыта. Для сайта проверить HTML-якоря, оглавление и прямые ссылки отдельными сценариями.
2. **Модель и API.** Добавить типизированные схемы FAQ/rich text/cookie, валидацию полных записей, стабильные IDs, глобальную классификацию FAQ, API редакторов, публичную проекцию, versioned snapshot/preflight и совместимость старых снимков. Подготовить только разрешённое демонаполнение, без перезаписи существующих пользовательских записей.
3. **Админка.** Собрать редактор FAQ из действующих React Aria/shadcn паттернов и карточку cookie в «Значения сайта». Добавить preview, SEO-навигацию, ревизии/ошибки и выборочный review/publication FAQ/cookie.
4. **Витрина.** Перенести утверждённый дизайн в Astro, общие контакты и действия, обновить конкретные ссылки шапки/футера, реализовать якоря/раскрытия/Schema, сквозной cookie и взаимодействие с диалогами. Связать маршрут с inventory, sitemap и SEO.
5. **Проверки и документация.** Выполнить профильные проверки, затем полный gate перед push, проверить сборку и визуальные/редакторские сценарии; обновить README по необходимости и фактические профильные документы в том же изменении.
6. **Защищённый test-выпуск.** Выбрать только подготовленные изменения кода, создать commits, push, дождаться зелёного CI выбранного SHA, выполнить Coolify deploy/CODE по процедуре. Затем сохранить/выпустить только выбранные FAQ/cookie-демоданные через новый review, подтвердить активацию и выполнить live-проверки. Если обнаружатся несовместимые посторонние изменения или требуется изменение согласованного плана, остановиться и описать конкретное расхождение.

## 7. Критерии проверки и завершения

- API/model: привязка к группе, уникальные IDs, перестановки, удаление непустой группы, отклонение неполных записей и небезопасных ссылок; SITE/page revision conflicts. Пустые группы не видны, у вопросов/групп отсутствуют переключатели скрытия.
- Rich text/Schema: абзацы, списки, выделения, ссылки, спецсимволы; один источник HTML/JSON-LD, совпадение пар, единая FAQPage, корректные breadcrumbs и canonical; проверка Schema.org validator и локальной структуры. Cookie не становится частью FAQ mainEntity.
- Публикация: FAQ отдельно, cookie отдельно, вместе, no-op/stale review; посторонние SITE/SEO/news/tariff/page drafts остаются рабочими и не меняют serving baseline. Старый snapshot/CODE не захватывает новые рабочие данные. Ошибка сборки не активирует артефакт.
- Browser: встроенный браузер Codex; FAQ1440/768/390/320 и cookie1440/834/390/320, промежуточные/низкие viewport по выявленным проблемам; длинные реальные тексты, клавиатура, фокус, scroll/hash/Back, мобильное оглавление, нативные раскрытия и существующие callback/city/legal flows. Телефоны/заявки не отправляются для проверки без отдельной необходимости/разрешения.
- Cookie: первый показ на разных публичных типах страниц, закрытие и повторные визиты до30дней, граница30дней с управляемым временем, отсутствие сброса после редактирования текста, выключение/включение, диалоги, storage failure; в админке нет сквозного реального уведомления. Срок не проверяется ожиданием реальных30дней.
- Профильные lint/typechecks и тесты; перед тестами на API dist пересобрать API. Полный `pnpm check` перед push кода, без необоснованных повторных полных запусков. При изменении зависимости — lockfile и `pnpm audit --audit-level=high`.
- Внешний результат: exact commit/finished deployment/running:healthy, CODE и выбранная CMS-активация SUCCEEDED; обслуживаемые HTML `/faq`, JSON-LD, assets, навигация и cookie подтверждены HTTP и встроенным браузером. Зафиксировать publication/artifact/revisions и оставшиеся ограничения.
- Документы: current-state, site-structure, block-passports, api-contracts, publication, TEST_COVERAGE, решения/PF и отчёт выпуска; README сверить, не менять без фактической причины. Проверить локальные ссылки и `git diff --check`.

## 8. Граница окончательного подтверждения

После подтверждения этого плана агент выполняет перечисленные этапы, включая commits/push, штатный test deploy и выбранную публикацию FAQ/cookie без повторных запросов на те же действия. Публикация посторонних данных, смена аналитической политики, редизайн, починка Figma-прототипа, добавление поиска, новые формы, скрытые вопросы/группы, неполные сохраняемые записи и механизм согласия cookie сюда не входят.
