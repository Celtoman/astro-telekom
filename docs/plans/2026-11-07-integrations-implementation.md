# Раздел «Интеграции»: подробный план реализации

**Дата:** 7 ноября 2026. **Задача:** [#577](https://github.com/Celtoman/astro-telekom/issues/577). **Источник:** PF-203 и прямое поручение владельца подготовить план.

**Статус:** продуктовые решения Q1–Q20 согласованы владельцем, план обновлён по итогам обсуждения. Разрешены подготовка и обновление документации; реализация, внешняя публикация, изменение действующего счётчика и подключение кода этим поручением не разрешены. Включение в milestone Release 1 отдельно не согласовано. Согласованный контракт также записан в [decisions.md](../decisions.md#7-ноября-2026--раздел-интеграции).

**Цель:** управлять одним счётчиком Яндекс Метрики и произвольными HTML/JS-вставками через общий список интеграций, с четырьмя готовыми событиями, ручным сохранением, историей и независимым пакетным выпуском раздела.

**Архитектура:** API хранит отдельную версионированную конфигурацию интеграций и её редакции. Выпуск накладывает выбранную редакцию на обслуживаемый source snapshot; статическая сборка получает согласованные настройки, вставки и CSP из этого снимка. Admin и обычный preview пользовательский код не выполняют. Цели создаются вручную в Метрике; API Метрики и OAuth отсутствуют.

**Стек:** действующие NestJS/Fastify, Prisma/PostgreSQL, Astro static, React/React Aria, Tailwind/shadcn, BullMQ и static publication controller. Для HTML-разбора переиспользовать подход `parse5`, уже присутствующий в root devDependencies; API должен объявить собственную runtime-зависимость, если разбирает HTML во время работы. Новый тяжёлый редактор кода не нужен для первого этапа.

## 2. Согласованные решения Q1–Q20 и границы первого этапа

В первый этап включены: общий список с одной готовой Метрикой и произвольными HTML/JS-вставками; четыре включённых готовых события с отдельными переключателями; три позиции вставок с условиями страниц; ручное сохранение и все редакции истории; восстановление конкретной интеграции; независимый выпуск всех сохранённых изменений раздела; диагностика конфигурации и ручная проверка в браузере.

За пределами этапа: API Метрики/OAuth/синхронизация целей/встроенные отчёты; несколько счётчиков; редактирование ID готовых событий; произвольные пользовательские события и конструктор триггеров по CSS; PHP/серверные snippets; расписания/A-B распределение; размещение внутри CMS-блоков и отдельный конструктор кнопок запуска виджета; consent manager/баннер и ожидание согласия на загрузку Метрики; системная отсрочка вставок до DOM ready/idle/первого клика; автосохранение; отдельные права интеграций; автоматическая очистка редакций; мгновенное отключение уже выпущенного JS без новой активации; приёмка произвольного будущего сервиса одним универсальным тестом.

| Вопрос | Согласованное решение |
| --- | --- |

| Q13 — параметры событий | Разрешённый контекст без персональных данных: форма, вид обращения, город страницы, тариф, положение действия/назначение телефона, результат адресной проверки |
| Q14 — восстановление | Конкретная интеграция копируется из истории в новый черновик, остальные текущие настройки сохраняются; эффект после общего выпуска |
| Q15 — число счётчиков | Один счётчик на сайт, одна готовая запись Метрики |

Привязка остаётся к явно настроенному единственному контексту Дом.ру, без нового выбора сайта и без выбора первой произвольной записи. Продуктовые вопросы закрыты; конкретные версии parser, технические лимиты и гранулярность CSP уточняются при реализации в рамках этого контракта. Само согласование поведения не разрешает исполнение кода или внешний выпуск.

## 3. Экраны админки и основные сценарии

Один пункт навигации «Интеграции» открывает общий список. В нём одна готовая запись «Яндекс Метрика» и произвольные вставки с типом «Код». У Метрики редактор настроек и событий, у кода — редактор фрагмента. Общие review/история доступны из этого же раздела и не создают ещё одну систему публикации.

Предлагаемые маршруты админки: `/integrations` (общий список), `/integrations/metrika` (настройки/события/сформированный код для просмотра), `/integrations/snippets/new`, `/integrations/snippets/edit?id=...`, `/integrations/history`. Отдельного списка `/integrations/snippets` и самостоятельного пункта «Метрика» в sidebar не требуется. Публичный route inventory и sitemap эти admin URL не затрагивают.

### 3.1. Яндекс Метрика

- Показать рабочую и действующую редакции, номер счётчика и включение. ID хранить десятичной строкой, проверять формат/границы; не преобразовывать произвольную строку в JS.
- Один счётчик на всех публичных HTML-страницах, включая legal и 404; в первом этапе Вебвизор выключен, остальные текущие опции вынесены в настройки. Пустая новая конфигурация с незаданным ID не запускает счётчик; готовые четыре события включены и начнут отправляться только при включённой опубликованной Метрике.
- Опубликованная включённая Метрика загружается сразу асинхронно. Полей ожидания согласия/DOM ready/idle нет. Тестовый и рабочий контуры не используют общий счётчик по умолчанию.
- Сформированный код доступен для просмотра как текст; правки выполняются через настройки. Запись Метрики не дублируется отдельным пользовательским snippet, её нельзя размножить кнопкой создания кода.
- «Сохранить», «Проверить и опубликовать», «История», «Открыть Метрику». Внешняя ссылка строится из валидированного ID, не произвольного URL.
- Состояния установки: «Не настроена», «Выключена», «Изменения не опубликованы», «Конфигурация опубликована», «Ошибка проверки». Не показывать «Данные поступают» на основании одного ID или успешной сборки.
- Изменение ID показывает, что история целей и статистика другого счётчика не переносятся. Изменение включения остаётся черновиком до выпуска.

### 3.2. События

Таблица: русское название; точное условие; ID для цели Метрики; включение; допустимые параметры; инструкция настройки/копирование ID. Различать системный ключ события и идентификатор цели Метрики, даже если в v1 они совпадают.

Все четыре события включены по умолчанию; каждый переключатель сохраняется в конфигурации Метрики вручную и вступает в силу после общего выпуска. Системные ID не редактируются. Цель пользователь создаёт в кабинете Метрики вручную по копируемому ID; mapping и автоматическая отправка второго имени в v1 отсутствуют.

Локальное включение означает «сайт настроен отправлять событие», не «цель существует в Яндексе». Показывать инструкцию проверки и статус «В Метрике не проверено». Автопроверки API нет.

### 3.3. Сторонний код

В общем списке: тип, название, позиция, область действия, состояние черновика/публикации и рабочее включение. Для Метрики scope фиксирован: все публичные страницы. Допустимы поиск по названию и простые фильтры; drag-and-drop не обязателен, порядок вставок можно менять числом/кнопками с клавиатуры.

Редактор:

| Поле | Контракт |
| --- | --- |
| Название, примечание | Название обязательно; примечание объясняет сервис и назначение |
| Включена | Только рабочее состояние, не обещание немедленного эффекта |
| Код | HTML-фрагмент с JS/допустимыми ресурсами; моноширинное поле, без исполнения в редакторе |
| Позиция | `HEAD`, `BODY_START`, `BODY_END`; head не допускает произвольную видимую разметку |
| Порядок | Стабильная сортировка по позиции/порядку/ID; native async/defer сохраняются, порядок вставки не гарантирует порядок завершения async-запросов |
| Область | Все HTML-страницы или выбранные типы/точные paths/города; затем исключения |
| Исполнение | В выбранной позиции по исходному коду и стандартной семантике браузера; дополнительных режимов загрузки нет |
| Источники | Раздельные точные HTTPS origins для script/connect/img/frame/style/font; скрыты в расширенных настройках, сводка видна в review |

Новая вставка создаётся выключенной. Дублирование создаёт новый выключенный черновик. Неготовый HTML/JS можно сохранить выключенным с замечаниями: при этом размеры, структура записи, ID и scope всё равно валидируются. Проверка готовности кода применяется при включении/сохранении включённой вставки и повторно перед публикацией; подтверждённые ошибки активного кода блокируют весь пакет. Неготовая выключенная вставка входит в сохранённую историю/снимок как текст, но не исполняется, не даёт CSP permissions и не блокирует выпуск остальных готовых интеграций.

Архивирование убирает вставку из будущей активной конфигурации после выпуска; сохраняет историю. Выключить и опубликовать — основной путь удаления с сайта, физическое удаление историй не входит. Сохранение только кнопкой, без autosave; уход с несохранённым текстом вызывает guard.

Обычный preview показывает название/позицию и предупреждение «Код здесь не выполняется». Кнопки «Запустить в админке» нет. Проверка реального виджета выполняется отдельно на тестовом сайте с синтетическими данными.

### 3.4. Состояния, восстановление и доступность

| Ситуация | Наблюдаемое поведение |
| --- | --- |
| Загрузка/пустой список | Skeleton с доступным статусом; пустое состояние объясняет создание выключенной вставки |
| Невалидное поле | Русская ошибка у поля, summary ведёт к нему; введённый код не теряется |
| Ошибка сохранения | Текст остаётся в форме; «Повторить» не создаёт новую вставку повторно |
| Конфликт редакций | Сохранение отклонено; предложить перечитать серверную версию и скопировать свой текст, без молчаливого overwrite |
| Несохранённые изменения | Существующий navigation guard; код не сохраняется автоматически в localStorage в первом этапе |
| Истекла сессия | Общий механизм admin; никакого выполнения кода, приватного кэша или фоновой публикации |
| Сбой публикации | Действующая версия продолжает обслуживаться; показать ошибку, revision и штатное восстановление |
| `UNCERTAIN` | Не выдавать успех и не создавать новую конкурирующую операцию; продолжать existing recovery |
| Успех | Только после durable receipt и SQL ack: действующая редакция, время и состав |
| Восстановление истории | Выбранная интеграция из старой редакции копируется в новый рабочий aggregate, остальные текущие настройки сохраняются; затем общий review/выпуск |

Экраны используют существующие Card/Table/Field/Input/Checkbox/Button/Alert/Tabs и React Aria dialogs. Недостающий многострочный ввод адаптировать через текущий Field/TextField-паттерн; CodeMirror/Monaco не устанавливать без отдельного обоснования. При узкой ширине формы складываются; таблица допускает локальный scroll или карточки, действия/статусы не теряются. Проверить клавиатуру, фокус после ошибок/диалога, 200% zoom, ширины 1440/834/390/320; код может прокручиваться внутри своего поля. Визуальную приёмку и фактическую доступность фиксировать раздельно.

## 4. Данные, редакции и admin API

### 4.1. Модель

Рекомендуется один aggregate на сайт, чтобы Метрика, события и вставки проходили review и активацию согласованно:

- `SiteIntegrationConfig`: `siteId` unique, `revision`, `content` JSON, `updatedAt`, `updatedById`.
- `SiteIntegrationRevision`: unique `(siteId, revision)`, immutable `content`, digest, автор/время/причина.
- `IntegrationPublicationItem`: unique `publicationId`, выбранные siteId/revision/digest и immutable snapshot. Связь с существующей `SitePublication`.
- Действующая редакция определяется обслуживаемой подтверждённой публикацией, не только максимальной сохранённой/исторически успешной revision. Аудит — существующий `AuditEvent`; отдельная система пользователей/ролей не создаётся.

JSON имеет `version: '1.0.0'`, единственную `metrika`, `events`, `snippets`. В UI это один список, хранение не требует преобразовывать готовую Метрику в свободный код. У Метрики стабильный системный ключ `metrika`, у вставки — серверный стабильный ID, поля раздела 3 и archive marker. Общий размер ограничен; предлагаемые начальные технические лимиты: 50 вставок, 100 KiB UTF-8 на одну и 1 MiB на весь документ. Лимиты применять до дорогостоящего разбора и согласовать с Fastify body limit; ошибки адресуют конкретное поле.

Ручное сохранение с `expectedRevision` выполняется транзакционно, создаёт следующую immutable revision и audit. No-op не создаёт новую revision. Все редакции сохраняются без автоматического удаления, история пагинируется. Отдельный `clientMutationId` для создания/сохранения либо равноценная идемпотентная операция устраняет дубли при потере ответа.

Восстановление принимает `integrationKey` и source revision, читает текущий aggregate под CAS и заменяет только выбранную интеграцию. Для `metrika` это настройки счётчика и его четырёх переключателей событий; для snippet — запись со стабильным ID. Остальные вставки/настройки остаются текущими; неизменённый результат не создаёт редакцию. Восстановление ранее архивированной вставки не создаёт второй ID. Автоматического отката всего раздела этой кнопкой нет.

### 4.2. Предлагаемый HTTP-контракт

Все пути ниже относительно `/api/v1`; admin cookie/session и штатные machine credentials используют существующую проверенную границу доступа. Отдельная роль/permission интеграций не создаётся. Общедоступного API чтения рабочих вставок нет. Ответы с кодом — `Cache-Control: no-store`; не включать исходники в общие audit summary/ошибки/телеметрию.

| Метод/путь | Назначение и обязательные данные |
| --- | --- |
| `GET /admin/sites/:siteId/integrations` | Рабочая конфигурация, revision, краткая сводка действующей версии/операции |
| `PUT /admin/sites/:siteId/integrations` | Весь aggregate + `expectedRevision`, `clientMutationId`; строгий whitelist полей |
| `POST .../integrations/validate` | Сохранённая `expectedRevision`; ошибки/ресурсы/конфликты/число затронутых страниц, без исполнения и сетевой загрузки vendor JS |
| `POST .../integrations/review` | `expectedRevision`; serving baseline, digest, diff, разрешения CSP и области страниц |
| `POST .../integrations/publish` | `expectedRevision`, `reviewDigest`, `operationId`; точный проверенный пакет |
| `GET .../integrations/operations/:operationId` | Восстановление после потери ответа: операция/публикация/rebuild, без повторного эффекта |
| `GET .../integrations/history` | Пагинированные метаданные редакций без всего кода |
| `GET .../integrations/history/:revision` | Код только запрошенной редакции |
| `POST .../integrations/restore` | `integrationKey`, `revision`, `expectedRevision`, `clientMutationId`; заменяет только выбранную интеграцию в новом черновике |

Коды: 400 — структура/синтаксис/недопустимый ресурс; 401 — сессия; 404 — сайт/редакция; 409 — stale revision/baseline или конкурирующий выпуск; 413 — размер; 429 — штатное ограничение. Ошибки нельзя рендерить через HTML. Проверить отсутствие доступа к чужому siteId и корректность сессии/Origin/CORS на новой границе без самостоятельной переработки всей аутентификации.

## 5. Готовые события: точный смысл и качество сигнала

| Системное событие / ID цели v1 | Триггер | Минимальный разрешённый контекст | Для какого решения |
| --- | --- | --- | --- |
| `lead_created` | Любая подтверждённая API запись из callback-dialog, встроенной помощи или адресной формы, включая консультацию без выбранного тарифа; валидный контракт ответа | `form`, `lead_kind`, `page_type`, нормализованный path без query/hash, `source_city`, `tariff_slug` при наличии | Конверсия сайта во все сохранённые обращения |
| `phone_click` | Активация `tel:` пользователем | `phone_purpose: connection/support/other`, `placement`, `page_type`, `source_city` | Разделить интерес к подключению и поддержку |
| `lead_form_open` | Реальный переход закрытой формы в открытую; для встроенной формы — первое содержательное взаимодействие, не загрузка страницы | `form`, `placement`, `page_type`, `source_city`, `tariff_slug` | Где теряется переход к отправке |
| `address_check_completed` | Валидный актуальный бизнес-результат address API, показанный пользователю | `outcome: TARGET_AVAILABLE/ALTERNATIVES_AVAILABLE/NO_PROVIDERS`, `page_type`, `source_city` | Доля результатов проверки и переход к заявке |

Значения outcome соответствуют [действующему контракту](../../apps/api/src/address-check-result.ts). Ошибка/таймаут/422/отменённый или устаревший ответ не становятся бизнес-результатом «нет покрытия». Не собирать адрес ради сегментации. Source-город и фактический город адреса не смешивать.

Основная конверсия — `lead_created`, без фильтра «только продажи», обязательного выбранного тарифа или ожидания последующей квалификации. Остальные события диагностические; клик по телефону не доказывает звонок, запись обращения не доказывает доставку провайдеру или подключение. Значение/доход цели не приравнивать к абонентской плате тарифа.

### Правила отправки

1. Единый небольшой адаптер `trackSiteEvent(key, context, internalDedupKey?)`; бизнес-код не вызывает `ym` напрямую. Системный реестр проверяет ключ и context по allowlist.
2. ID/телефон/адрес/комментарий/текст полей/сырые API-ответы/внутренние submission keys не отправляются. Внутренний lead ID допускается только локально для дедупликации; не попадает в params/debug logs. Query/hash и referrer не копировать в параметры события.
3. `lead_created` дедуплицируется по подтверждённой заявке в пределах вкладки/сессии с bounded memory и sessionStorage при доступности. При отказе storage остаётся память; межбраузерная exactly-once гарантия не заявляется. Не блокировать отправку заявки ожиданием Метрики.
4. У `lead_form_open` один сигнал на один цикл открытия; для встроенной формы один на её жизненный цикл документа. Телефонный клик — каждое осмысленное действие пользователя, без двойной подписки обработчиков. Результат адреса — один на актуальную проверку, не на перерисовку.
5. При выключенном событии/счётчике или неверном контексте — no-op. Включённая опубликованная Метрика начинает загружаться сразу; очередь SDK на время асинхронной загрузки ограничена по размеру/времени, блокировщик не приводит к бесконечному росту памяти. Отключённые события не накапливаются для будущей отправки.
6. Ошибка SDK не распространяется в пользовательский flow. Успешный вызов `ym`/callback не доказывает появления цели в отчёте.
7. В тесте использовать отдельный ID/подменённый адаптер. Не отправлять синтетические события в рабочий счётчик.
8. Проверить honeypot/rate-limit ветки public lead API: в текущем `public-leads.controller.ts` заполненный `website` отклоняется с ошибкой; такой ответ не создаёт событие. Не менять защиту ради аналитики. При будущем изменении контракта повторно проверить, что успешный ответ всё ещё подтверждает запись, а не маскирует отказ.

Готовность измерений оценивается по фактической настройке счётчика/целям/проверкам перед использованием в рекламе. Числовой индекс качества для ещё не реализованной и непроверенной интеграции не выдумывается. Источник количества сохранённых заявок — API/БД; браузерная аналитика имеет пропуски и не заменяет этот учёт.

## 6. Сторонние вставки, компиляция и CSP

### 6.1. Область и совместимость

Scope сопоставляется с authoritative route inventory опубликованного baseline, не со списком произвольных URL. Предлагаемая формула: `(все либо совпадение любого include) И НЕ совпадение любого exclude`. City-фильтр действует на маршруты с city context; общие страницы не получают случайный город из localStorage. Точные paths нормализуются без query/hash; redirect-источники не являются HTML-страницами. Wildcard/regex/произвольные JS-условия не входят в v1. Review показывает точное число/список совпадений с пагинацией и нулевые совпадения.

404 — отдельная системная поверхность: по умолчанию сторонние вставки на ней выключены, встроенная Метрика может учитывать ошибочную страницу с корректным HTTP404. Явное включение snippets на 404 должно отдельно учитывать, что Caddy может отдавать один и тот же HTML на разные неизвестные paths; фильтр точных неизвестных URL не обещается. Admin, API, preview, sitemap/robots/XML и redirects никогда не входят в scope. Контекст среды задаётся deployment policy, не только проверкой имени hostname в браузере.

Поддержать common vendor snippets: inline/external scripts, ограниченную разметку контейнеров, HTTPS iframe/img, noscript и stylesheet по declared sources. Сохранять исходное поведение и native `async`/`defer`; собственных режимов отсрочки и переноса исполнения через динамический loader нет. Неподдерживаемые конструкции активной вставки отклонять с объяснением, не переписывать молча. В выключенном черновике они сохраняются как текст с замечаниями. Элементам внешних ссылок/iframe применить согласованные ограничения; не обещать sandbox-изоляцию обычному JS документа.

### 6.2. Проверки и исполнение

- Разбор HTML структурным parser; никакого выполнения через `eval`, `new Function`, jsdom с JS или shell/PHP. Никаких запросов к произвольному vendor URL с сервера при validation — это также исключает SSRF в диагностике. Разделить structural validation сохранения и readiness активного кода: замечания выключенной вставки не блокируют сохранение/общую публикацию и не расширяют CSP.
- Проверять границы фрагмента, позиции, скрипты и URL. Не допускать `<html>/<head>/<body>`, `<base>`, meta refresh/CSP, object/embed, inline event attributes и `javascript:` URL; отклонять возможности, для которых нет поддержанного контракта.
- Для `HEAD` — только совместимые metadata/resource/script конструкции; видимую разметку размещать в body. Не менять байты inline JS после вычисления hash. Синтаксис JS проверять parser подходящего языка; parser/dependency зафиксировать перед реализацией, не пытаться доказывать корректность regex.
- Статические inline скрипты/styles получают точные hashes. Внешние источники — отдельные HTTPS origins без credentials/query/path/wildcard; allowlist не равен доверию к поведению загруженного сервиса.
- Не разрешать `unsafe-eval`, `script-src *`, blanket `unsafe-inline` или `strict-dynamic` ради удобства snippets. Виджет с такими требованиями помечается несовместимым; изменение security policy требует отдельного решения.
- Динамические script/connect/frame/img/font/style ресурсы требуют объявленных origins; автоматически извлечённые URL — подсказки, не полный доказанный список. Динамические inline script/style могут быть несовместимы с hashes; общий загрузчик этого не исправляет.
- Активный фрагмент выводится статически в выбранную позицию с исходными атрибутами исполнения. Compiler не превращает обычные scripts в async, не сериализует принудительно async-загрузки и не эмулирует parser через runtime reinsertion. При несопоставимости фрагмента с CSP/позицией выдаётся ошибка совместимости вместо изменения поведения.
- Native порядок обычных scripts и `async`/`defer` сохраняется; отдельно проверить смешанный фрагмент со скриптом, который зависит от предшествующего. Не обещать безопасного автоматического преобразования `document.write`/parser-dependent vendor-кода; поддержка подтверждается fixture либо конструкция отклоняется для активного исполнения.
- Наш адаптер событий изолирует собственные ошибки. Произвольный доверенный JS всё равно способен изменить DOM, читать формы или блокировать main thread; это невозможно гарантированно исправить try/catch. Для нежелательного такого доступа выбирать iframe-совместимый сервис либо не активировать его.
- Общая проверка на повторный известный ID/загрузчик Метрики запрещает очевидный дубль встроенного счётчика. Обфусцированный JS нельзя надёжно распознать статически: review и браузерная проверка остаются обязательными, автоматическую гарантию отсутствия всех дублей не давать.

Разрешения CSP можно брать объединением выбранных активных вставок всего снимка; это проще и предсказуемее, но разрешения действуют шире страницы вставки. Предпочтительно сузить по типу/маршруту там, где сборочная интеграция позволяет без обходных разрешений. Выбор гранулярности зафиксировать измеримым тестом, не обещать per-page изоляцию при фактически общей CSP.

## 7. Публикация и совместимость снимков

Единица выпуска v1 — вся сохранённая конфигурация интеграций одной revision. UI явно показывает все изменения, в том числе сохранённые на другом экране раздела. Несохранённый текст не входит. Выключенная неготовая вставка сохраняется в снимке без активного HTML/CSP permissions и не блокирует готовые изменения. Подтверждённые ошибки включённой вставки блокируют пакет целиком. Старое содержимое сайта продолжает обслуживаться до подтверждённой активации нового артефакта.

Алгоритм независимого выпуска:

1. Прочитать подтверждённый serving source и выбранную integration revision в consistent transaction. При отсутствии baseline запретить независимый выпуск и объяснить необходимость первой штатной публикации; не брать рабочий каталог вместо baseline.
2. Наложить только ветку `integrations` на clone baseline. Не включать рабочие новости/тарифы/города/SEO/контент. Проверить scopes по маршрутам именно этого baseline.
3. Review фиксирует siteId, expectedRevision, digest настроек/кода, baseline publication/releaseSequence и версию валидатора/renderer; показывает полный diff, источники CSP, затронутые страницы и замечания.
4. Publish проверяет те же значения и конкурирующие операции. Если baseline или revision изменились — 409 и новый review; никакого автоматического переноса разрешения на другую редакцию.
5. Создать `SitePublication` со scope интеграций, validation source/catalog, `IntegrationPublicationItem` и одной rebuild job. `operationId` идемпотентен; после потери ответа readback возвращает прежнюю публикацию.
6. Builder берёт точный снимок; settings и CSP участвуют в digest/cache identity/manifest. Ни builder, ни CODE не читают текущую рабочую integration revision.
7. В штатном receipt/SQL ack отметить выпуск выбранной revision. Не продвигать legacy `Site.publishedRevision` как будто опубликован весь каталог. Не применять обработку editorial ledger к scope интеграций.
8. Сбой/неопределённость обслуживаются существующим механизмом retry/recovery той же job. Новый черновик, сохранённый во время сборки, остаётся отдельным.

Матрица обязательной сохранности:

| Операция | Какие интеграции входят |
| --- | --- |
| Независимый выпуск интеграций | Выбранная сохранённая revision поверх serving контента |
| Редакционная публикация новости/404/настроек | Serving integration snapshot без рабочих изменений |
| Общая CMS-публикация | Сохраняет serving integrations; черновики этого раздела не захватываются молча |
| CODE rebuild | Точные интеграции выбранного обслуживаемого snapshot |
| Восстановление интеграции | Новый draft с одной выбранной записью из истории и остальными текущими настройками; эффект только после нового пакетного выпуска |
| Отключение/архивирование | Снимок без активной вставки; эффект после успешной активации |

Текущий code path, где любой `scopeKey !== legacy` интерпретируется как редакционный, требует явного разветвления. Общий serving-source helper можно выделить из существующего editorial helper без изменения его semantics; не дублировать целиком pipeline. Старые снимки без `integrations` получают описанный ниже legacy adapter; явное `{ metrika: { enabled: false } }` никогда не означает fallback на env.

## 8. Согласованная загрузка и границы тестового контура

Для опубликованной включённой Метрики bootstrap и асинхронная загрузка выполняются сразу при открытии любой публичной HTML-страницы, включая legal и 404. Ожидания согласия/клика, таймера и idle нет. Вебвизор выключен в первом этапе. Произвольные активные вставки выполняются в выбранных позициях по исходной семантике браузера, включая их собственные `async`/`defer`. Это зафиксированный выбор владельца Q1/Q2/Q9/Q16; прежние варианты загрузки исключены из требований и тестов.

Новая произвольная вставка выключена. Пустая ненастроенная Метрика не создаёт обращений к vendor; само сохранение настроек ничего не включает в обслуживаемом сайте. Все функции сайта работают при недоступной аналитике, storage и vendor network. Выключение любой интеграции проходит штатную публикацию; универсальной выгрузки уже исполнившегося кода из открытой вкладки не обещаем.

Контекст событий передаётся только по allowlist раздела 5 без персональных данных. Это ограничение относится к нашему адаптеру; свойства автоматического сбора SDK проверяются отдельно в браузере и не выводятся из одного только состава event params. Юридический статус выбранного режима этим техническим планом не устанавливается и не превращается в дополнительный несогласованный gate реализации.

Контуры: admin/preview не запускают код; localhost/CI работают на mock/off; защищённый test — отдельный явно выбранный тестовый счётчик/виджет. Будущая production policy не наследует test ID автоматически. Экран не должен отправлять тестовую цель сам по открытию и не должен предлагать выполнить произвольный код на admin origin.

## 9. Пошаговый инженерный план

Все перечисленные новые имена файлов — предлагаемые; существующие пути проверены. Перед началом уточнить HEAD и инструкции. Реализацию вести последовательно, без автоматического запуска по факту создания этого плана. Для сложных изменений использовать изолированный checkout/worktree; не коммитить чужие рабочие изменения.

Для каждого шага: сначала соответствующий негативный/поведенческий тест и его ожидаемое падение, затем минимальная реализация и профильные проверки. Не добавлять тесты, проверяющие лишь наличие текста/копию implementation. Коммиты — Conventional Commits после обязательных gates; risky блоки требуют `pnpm check` перед коммитом. Не создавать релиз/tag и не делать push без отдельного поручения.

### Этап 0. Зафиксировать согласованный контракт и подготовить реализацию

1. Согласованные Q1–Q20 записаны в разделе 2, [decisions.md](../decisions.md) и задаче #577; заново задавать эти вопросы не требуется.
2. Перед отдельно разрешённой реализацией проверить действующий site context и два синтетических примера: счётчик и iframe/плавающий виджет с native семантикой.

## 10. Переход с env и старой цели

1. До изменения снять read-only inventory по каждому контуру: настроен ли ID, какие текущие опции, существующие цели и использование в рекламе. Не выводить env целиком и не требовать OAuth ради инвентаризации — данные кабинета подтверждает владелец.
2. Новая схема сама ничего не активирует. Команда dry-run строит предлагаемый managed draft из явно переданных ID/опций и показывает diff; apply только после разрешения. Не считать env API-процесса автоматически равным build-env сайта.
3. Managed snapshots имеют явную version и `metrika.enabled`. Для них env не участвует ни в bootstrap, ни в CSP. При выключении нет fallback. Вставки со вторым счётчиком не импортируются автоматически.
4. Для legacy snapshots без ветки `integrations` сохранить документированный legacy adapter, чтобы CODE не выключил существующий счётчик неожиданно. При переходе зафиксировать эффективную legacy-конфигурацию в выбранном migration snapshot/receipt либо явно признать прежнюю зависимость от env; не заявлять историческую воспроизводимость до такого захвата. Повторная managed-сборка должна быть независима от текущего env.
5. `phone_click` сохраняет ID и получает уточнённые параметры; прежняя статистика не обогащается задним числом.
6. Новое `lead_created` получает отдельную фиксированную цель в Метрике и учитывает все подтверждённые сохранённые обращения. По Q4 отправка `lead_form_submit` прекращается полностью: периода двойной отправки и compatibility toggle нет. Старая цель/история в Метрике сохраняются. Общего document submit-listener нет; legacy adapter и восстановление редакции не должны возвращать старую отправку.
7. Проверить новую цель на test, затем владелец отдельно меняет использование в рекламе. Не удалять старую цель/историю и не создавать две равнозначные основные конверсии автоматически.
8. При первом managed выпуске Вебвизор выключен, даже если в прежнем bootstrap он был включён; миграционный diff явно показывает изменение. Перенос legacy ID не создаёт второй счётчик. Совместимость ID/env не является разрешением вернуть старую цель или Вебвизор в новом renderer первого этапа.
9. Возврат — восстановление одной интеграции в managed draft текущего раздела и новый общий выпуск, без отката всей БД и без захвата старого контента/остальных старых настроек. Повторный миграционный запуск идемпотентен. Переменная env остаётся явно помеченной legacy-only до доказанного отказа от исторических снимков.
