# Система управления задачами

Зафиксировано 8 сентября 2026 года, актуализировано 14 сентября 2026 года. Этот документ — единственное полное описание того, как в проекте фиксируются, отслеживаются и закрываются проблемы, задачи и планы. Любой агент (Claude Code, Codex, человек) должен работать по этой схеме, не изобретая параллельную.

## Зачем это существует

До этого документа в проекте было три независимых markdown-реестра (`technical-debt.md`, `decisions.md`, план `plans/*.md`) без механической связи между ними. На практике это дважды приводило к потере синхронизации: решение об упразднении `apps/crm` не попало в план (issue [#23](https://github.com/Celtoman/astro-telekom/issues/23)), а новая находка (TD-21) не попала ни в одну задачу. Причина не в невнимательности, а в том, что ничего не проверяло согласованность — статус хранился в тексте, который никто не обязан был перечитывать целиком.

## Четыре типа записей и где они живут

| Тип | Где живёт | Что это |
| --- | --- | --- |
| **Проблема** (баг, риск, недоделка, подтверждённая кодом) | GitHub Issue, label `tech-debt` + `P0`–`P3` | Атомарная находка. Один issue = одна проблема. |
| **Задача** (спланированный кусок работы, закрывающий одну или несколько проблем) | GitHub Issue, label `task`; milestone `Release 1: минимальный публичный запуск` только если работа входит в этот релиз | Чек-лист шагов (нативные GitHub checkboxes) + sub-issues на закрываемые проблемы. |
| **Продуктовое решение** (согласованный замысел, не факт кода) | [docs/decisions.md](decisions.md) | Не привязано к issue — это не «сделать», а «мы так решили». Issues и Tasks могут на него ссылаться. |
| **Продуктовая/UX/UI-находка** (наблюдение или идея, ещё не согласованная к реализации) | [docs/product-findings.md](product-findings.md) | Входящий реестр для отдельного обсуждения; после решения запись связывается с `decisions.md` и/или issue. |

Не смешивать подтвержденные технические проблемы с продуктовыми гипотезами. Первые сразу оформляются issue, вторые немедленно записываются в `docs/product-findings.md` и не превращаются в работу без отдельного обсуждения. Если идея согласована, результат обсуждения фиксируется в `decisions.md` и/или отдельном task issue, а находка получает статус `CONVERTED` со ссылкой.

## Источник правды и роль markdown-файлов

**GitHub Issue open/closed — единственный механический источник правды.** Markdown-документы существуют не для дублирования статуса, а для контекста, который Issues отражают хуже:

- `docs/technical-debt.md` — компактный **индекс**: ID, ссылка на issue, статус (🟢/✅), одна строка сути. Полное описание проблемы (доказательство, влияние, следующее действие) живёт **только** в issue — не копировать текст в оба места, это и есть источник рассинхронизации, который мы только что чинили.
- `docs/plans/2026-09-07-platform-stabilization-and-mvp.md` — **архитектурное обоснование**: почему Task 3 должен быть раньше Task 4, какие есть зависимости, общая цель релиза. Не содержит пошаговых статусов — они в Task issues.
- `docs/decisions.md` — как и раньше, продуктовый замысел.
- `docs/product-findings.md` — несогласованные продуктовые и UX/UI-наблюдения, которым требуется отдельное обсуждение.

## Как это работает на практике

### Нашёл новую проблему

1. `gh issue create --repo Celtoman/astro-telekom --title "..." --label "P0|P1|P2|P3" --label "tech-debt"` — либо через шаблон `.github/ISSUE_TEMPLATE/tech-debt.yml` (`gh issue create` без флагов предложит выбор шаблона).
2. Если проблема достаточно значима, чтобы попасть в evidence-реестр — добавить строку в `docs/technical-debt.md` (следующий свободный TD-номер, ссылка на issue).
3. Не откладывать оба шага «на потом» — это обязательное правило из `AGENTS.md`, примененное и к issues, не только к docs.

### Нашёл продуктовую, UX/UI или дизайн-проблему либо идею улучшения

1. Сразу добавить следующую запись `PF-NNN` в `docs/product-findings.md`: контекст, наблюдение, возможное влияние, гипотезу улучшения и вопросы для отдельного обсуждения. Это постоянное поручение владельца для всех задач; отдельное разрешение на пополнение реестра не требуется. Область правила включает продукт, интерфейсы, UX/UI, удобство использования, структуру и управление админкой, рабочие процессы и другие идеи улучшения.
2. Не менять продукт или интерфейс по этой находке внутри текущей технической задачи без отдельного согласования.
3. После обсуждения зафиксировать итог: согласованное правило — в `docs/decisions.md`, исполнимую работу — в task issue, отклонение — причиной в исходной записи.
4. Перед завершением каждой задачи проверить, все ли возникшие по ходу работы идеи и находки внесены в реестр.

### Планируешь исполнение

1. Создать issue с label `task` (шаблон `.github/ISSUE_TEMPLATE/task.yml`), чек-лист шагов в теле.
2. Привязать milestone `Release 1: минимальный публичный запуск`, если задача входит в Release 1.
3. Связать с закрываемыми проблемами **дважды**: текстом в теле (`Closes #N`, для читаемости) и нативной sub-issue связью:
   ```bash
   # получить numeric id (не number!) обеих issue
   gh api repos/Celtoman/astro-telekom/issues/<TASK_NUMBER> --jq .id
   gh api repos/Celtoman/astro-telekom/issues/<TD_NUMBER> --jq .id
   # привязать TD как sub-issue Task'а
   gh api repos/Celtoman/astro-telekom/issues/<TASK_NUMBER>/sub_issues -X POST -F sub_issue_id=<TD_ISSUE_NUMERIC_ID>
   ```
   Проверить результат: `gh api repos/Celtoman/astro-telekom/issues/<TASK_NUMBER>/sub_issues --jq '.[].number'`.

### Выполняешь шаг задачи

1. Отметить чекбокс в теле Task issue (`gh issue edit N --body "..."` с обновлённым текстом, либо через веб-интерфейс).
2. Когда все шаги, закрывающие конкретную проблему, сделаны — закрыть соответствующий `tech-debt` issue **в том же коммите**, что и код: `git commit -m "... Closes #N"`.
3. Если проблема решена только частично — не закрывать issue «за компанию». Выделить остаток отдельным issue со ссылкой на родительский (пример — [#4](https://github.com/Celtoman/astro-telekom/issues/4), остаток после закрытия [#3](https://github.com/Celtoman/astro-telekom/issues/3)/TD-03).
4. Когда закрыты все sub-issues Task'а — закрыть сам Task issue.
5. После успешных проверок, обязательных для затронутой области по [AGENTS.md](../AGENTS.md#тестирование-и-проверки), агент создает Conventional Commit и продолжает следующую задачу без отдельного ожидания подтверждения, если владелец явно не запросил review-before-commit. Полный `pnpm check` обязателен перед push кода в `master`, но не повторяется для неизменного состояния; CI запускает его после push. Push остается отдельным внешним действием и требует явного разрешения.

### Проверяешь текущий статус проекта

```bash
gh issue list --repo Celtoman/astro-telekom --state open --label task           # все открытые спланированные задачи
gh issue list --repo Celtoman/astro-telekom --state open --label tech-debt      # все открытые проблемы
gh issue list --repo Celtoman/astro-telekom --state all --milestone "Release 1: минимальный публичный запуск"  # полный состав Release 1 и его прогресс
gh api repos/Celtoman/astro-telekom/issues/<N>/sub_issues                       # что входит в конкретный Task
```

Не нужно читать `docs/technical-debt.md` целиком, чтобы понять, что открыто — таблица там для evidence, не для актуального статуса при быстрой проверке.

## Метки (labels)

| Label | Значение |
| --- | --- |
| `P0` | Блокирует безопасный запуск или ведёт к недостоверным данным |
| `P1` | Нарушает ключевой путь первого релиза |
| `P2` | Существенно ограничивает эксплуатацию |
| `P3` | Улучшение качества и поддерживаемости |
| `tech-debt` | Проблема, подтверждённая кодом — единица evidence-реестра |
| `task` | Спланированная работа с чек-листом, группирует `tech-debt` issues |

## Milestone

`Release 1: минимальный публичный запуск` назначается только элементам, которые входят в приемку этого релиза. Обычно это task issue с чек-листом и sub-issues; отдельную `tech-debt` issue допустимо включить напрямую, если она сама является независимо проверяемым release blocker. Не включать в milestone улучшения следующих релизов только потому, что они открыты.

Состав и прогресс `closed/total` считаются GitHub автоматически: [milestone #1](https://github.com/Celtoman/astro-telekom/milestone/1). Фиксированное количество issues или tasks в Markdown не хранить: для текущего состояния всегда использовать milestone и `gh issue list`.

## Известное ограничение

GitHub Projects v2 (доска/таблица со своими полями поверх issues) сейчас недоступен — токен `gh` не имеет scope `project`. Добавляет он только альтернативное **представление** тех же issues, не новый источник статуса — если понадобится, включается через `gh auth refresh -s project` (интерактивный OAuth, требует ручного действия владельца репозитория) и не меняет ничего из описанного выше.

## Почему не сторонний инструмент

Проверены и сознательно не выбраны: **Taskmaster AI** (task-master, MCP-интеграция для AI-агентов), **GitHub Spec-Kit** (constitution → spec → plan → tasks), **BMAD-METHOD** (полный multi-agent SDLC framework). Все три реальные и активно поддерживаемые, но каждый добавляет собственный стейт (файлы конфигурации, MCP-сервер, свою файловую структуру задач), который пришлось бы отдельно синхронизировать с GitHub Issues — то есть воспроизводит проблему, которую эта система решает. Для одного репозитория с локальным прототипом нативный набор GitHub (Issues + Labels + Milestones + sub-issues) достаточен и не требует установки/поддержки чужого инструмента.
