# Технический долг

Дата фиксации: 7 сентября 2026 года. В реестре только проблемы, подтвержденные текущим исходным кодом, конфигурацией или воспроизводимой проверкой. Идеи из [реестра решений](decisions.md), которым нет реализации, отдельно отмечены как невыполненные возможности, а не как дефекты работающего поведения.

Приоритеты: P0 — блокирует безопасный запуск или ведет к недостоверным данным; P1 — нарушает ключевой путь первого релиза; P2 — существенно ограничивает эксплуатацию; P3 — улучшение качества и поддерживаемости.

## P0

| ID | Проблема и доказательство | Влияние | Следующее действие |
| --- | --- | --- | --- |
| TD-01 | Полный тестовый запуск падает: `node --test tests/*.test.cjs tests/*.test.mjs` дает 34/36. Два теста `lead-check.test.cjs` используют Prisma stub без `lead.findMany`, который вызывает текущий `PublicLeadsController`. В root `package.json` нет `test`-скрипта. | Нельзя использовать тесты как release gate; регрессия в заявках может остаться незамеченной. | Обновить test double, добавить `pnpm test`, запускать build перед тестами либо тестировать TypeScript-source без зависимого `dist`. |
| TD-02 | Email fallback генерирует HMAC-ссылку вида `admin/?lead=...&expires=...&signature=...`, но в admin и CRM нет разбора query-параметров или серверной проверки подписи. | Письмо обещает защищенный переход, которого пользователь фактически не получает; ссылка не дает контролируемого доступа к заявке. | Реализовать серверный endpoint проверки подписи и одноразовую/ограниченную по сроку сессию либо убрать ссылку до реализации. Покрыть expired, подмену и отзыв тестами. |
| TD-03 | Публичный `loadKazanData()` при любой ошибке API собирает витрину с зашитыми демо-тарифами и «Цена уточняется». Astro настроен в `output: 'static'`. | Сбой API или неверный build-контур может опубликовать недостоверный коммерческий контент. | В production сделать API-ошибку сборки блокирующей; отдельно сохранить явный demo-only режим. Добавить smoke-test финального HTML. |

## P1

| ID | Проблема и доказательство | Влияние | Следующее действие |
| --- | --- | --- | --- |
| TD-04 | Публичные маршруты, ссылки и API loader жестко используют `domru-kazan` и `/kazan/`; dynamic route генерирует тарифы только в момент build. | Модель может хранить другие сайты и города, но публичный сайт их не публикует. | Спроектировать маршруты по `Site`/`City`, источник параметров сборки и инкрементальную пересборку. Убрать kazанские fallback-данные из production. |
| TD-05 | API принимает изменения городов, страниц и тарифов, но `RebuildQueueService` лишь делает прямой webhook без хранения задачи, retry, статуса или обратной связи. Worker слушает `site-rebuilds`, однако производитель этой очереди отсутствует. | Редактор не знает, опубликовано ли изменение; статический HTML может отставать от БД. | Выбрать один контур: BullMQ persistent job + worker + delivery status. Отображать результат в API и админке. |
| TD-06 | В `TariffImportService.applyReport()` отсутствующие в новом файле тарифы не снимаются с публикации и не удаляются; `acceptedKeys` допускает частичное применение строк. Это противоречит решению о полном пакете и 404 для отсутствующего тарифа. | Каталог и публичные карточки могут содержать устаревшие предложения; продуктовые правила реализованы не так, как зафиксировано. | До реализации уточнить правило с владельцем продукта, затем сделать import diff, preview, atomic apply, статус/redirect и регрессионные тесты. |
| TD-07 | Модель `Redirect` создана, но controller, public routing, учет хитов и управление редиректами отсутствуют. | Смена slug приведет к потере старого URL вместо обещанного 301. | Реализовать проверку конфликтов, CRUD и edge/public redirect; включить в build и тесты одного hop. |
| TD-08 | В админке большинство счетчиков, таблиц, разделов, уведомлений и кнопок зашиты как demo UI. Рабочие API-вызовы ограничены списками и XLS-import городов/тарифов. | Интерфейс визуально сообщает несуществующие показатели и возможности; им нельзя управлять production-данными. | Заменять экраны по одному: реальные списки/пагинация, then формы, then publishing/SEO. Пока маркировать demo данные явно или не показывать их. |
| TD-09 | CRM и admin получают токен через `window.prompt` и хранят в `sessionStorage`; нет login route, logout, renewal, route protection на уровне приложения. Сервисный `x-admin-token` имеет полный доступ. | Высокий риск ошибочной эксплуатации и утечки высокопривилегированного токена через браузер; неудобный доступ для ролей. | Сделать login UI и короткоживущую HttpOnly-cookie или четко ограниченный token flow; убрать service-token из browser-сценария. |
| TD-10 | В чистом `.env.example` не настроены contract API и Tarifnik. `NOT_CONFIGURED` у проверки договора переводит новую заявку в `MANUAL_CHECK_API`, поэтому delivery не стартует. | Свежий контур принимает заявки, но не передает их в кол-центр. | Добавить явный readiness/status интеграций и release checklist; до запуска с реальными ключами не помечать обработку заявок как готовую. |

## P2

| ID | Проблема и доказательство | Влияние | Следующее действие |
| --- | --- | --- | --- |
| TD-11 | В Prisma и API нет сущностей аудита, версий контента/тарифов, schedule публикации, корзины или rollback. | Нельзя выполнить заявленные контроль, отмену и трассировку изменений. | Сначала утвердить модель audit event и версий, затем внедрять publication workflow. |
| TD-12 | Наследование `content` — только shallow merge JSON верхнего уровня. SEO наследуется от города к странице/тарифу; блоки, шаблоны, источники полей и preview не наследуются. | Нельзя прозрачно управлять контентом на уровнях provider/site/region/city/page, как предполагает продукт. | Описать формальный контракт наследования, поля и конфликты; реализовать resolver с tests. |
| TD-13 | `PageBlock` валидирует и рендерит лишь `hero`, `rich_text`, `tariff_grid`; большинство блоков из исследования не имеет модели, renderer или редактора. | CMS не может создать заявленный набор коммерческих и SEO-блоков. | Согласовать минимальную библиотеку блоков, схему каждого типа и output-contract между API и Astro. |
| TD-14 | В API нет глобального `ValidationPipe`, rate limiting, CAPTCHA/anti-abuse и подтвержденного PII retention/deletion процесса. Полные адреса, телефоны, API responses и активность хранятся в БД. | Риск некорректных данных, abuse публичных форм и несоответствия требованиям обработки персональных данных. | Провести security/legal review; внедрить DTO validation, throttling, anti-bot, policy-driven retention и доступ к PII. |
| TD-15 | Обычное email-уведомление после создания лида выполняется fire-and-forget и результат не сохраняется. | Оператор не видит, что уведомление потеряно; расследование невозможно. | Хранить notification attempt отдельной сущностью или использовать единый delivery outbox. |
| TD-16 | `sitemap.xml` не содержит корневую `/`, а canonical, robots и URL зависят от build-time `PUBLIC_SITE_URL`; нет pre-publication SEO проверки. | Неполная карта сайта и риск публикации URL с локальным origin или устаревшими данными. | Генерировать sitemap из опубликованных сущностей, включить `/`, блокировать build без production origin и проверять raw HTML. |
| TD-17 | Production Dockerfiles используют `pnpm install --no-frozen-lockfile`; миграции и seed запускаются вручную уже после старта Compose. Health API не проверяет подключение к БД. | Поставки не полностью воспроизводимы, новый контейнер может быть healthy при неготовой схеме. | Перейти на `--frozen-lockfile`, добавить migration job/entrypoint и readiness с DB probe. |

## P3

| ID | Проблема и доказательство | Влияние | Следующее действие |
| --- | --- | --- | --- |
| TD-18 | `pnpm lint` не запускает проверку admin и CRM: в их package manifests нет lint-скриптов. | Статические интерфейсы могут регрессировать без CI-сигнала. | Добавить `astro check` для обоих приложений и включить в CI. |

| TD-20 | В документации решений есть открытые вопросы с повторяющейся нумерацией «4». | Труднее ссылаться на решение и отслеживать его закрытие. | Привести открытые вопросы к уникальным IDs и связать с roadmap. |

## Невыполненные, но согласованные возможности

Это не дефекты уже реализованного поведения, а обязательные для следующего релиза направления: полноценный preview и публикации, массовые SEO-операции, история тарифов, редиректы, медиа-библиотека, аналитика, переменные, географическая навигация, роли в UI, интеграционный контракт Tarifnik и юридически утвержденные правила PII. Их порядок и критерии приема есть в [плане реализации](plans/2026-09-07-platform-stabilization-and-mvp.md).
