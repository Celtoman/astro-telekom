# Текущее состояние проекта

Дата среза: 15 сентября 2026 года. Источник этого документа — исходный код, Prisma-схема, Docker-конфигурация, GitHub Issues и результаты локальных проверок на текущей ветке `master`. Состояние внешнего контура приводится только по датированным live-проверкам; наличие более новой миграции или commit в репозитории не доказывает их deployment. Документ описывает фактическое состояние, а не только согласованный продуктовый замысел из [реестра решений](decisions.md).

## Краткий вывод

Репозиторий содержит работоспособный прототип платформы с защищенным внешним test-контуром, но не production-систему для реального трафика. Полностью реализованы базовая инфраструктура, схема данных, API основных сущностей, двухэтапный импорт городов и тарифов, прием заявок и механика их доставки. Публичный сайт строит точный Release 1 для любого числа опубликованных городов; админка работает с реальными тарифами, городами и заявками. Отдельный CRM-frontend удален после переноса его функций в `/leads`.

Целевая структура Release 1 уточнена 14 сентября 2026 года и зафиксирована в [site-structure.md](site-structure.md). API формирует authoritative route inventory, Astro выпускает `/`, пять общих страниц, `/{location}` всех опубликованных городов и `/{location}/{tariffSlug}` каждого опубликованного тарифа такого города. Импорт публикует каждый входящий город вместе с `HOME` и общей канонической композицией из семи блоков; тарифные страницы собираются из тех же CMS-данных, что и карточки. Миграция `0026` заполняет композицией только пустые городские HOME, не перезаписывая Казань или вручную настроенные страницы. Exact-SHA deployment `9q5evkornouucg0k7pwpkeua` на `0a1743f` подтвердил полный live inventory: 207 городов, 3 859 тарифных страниц и шесть общих route, всего 4 072 уникальных URL в API и sitemap. Исходное расхождение зафиксировано в [аудите](research/2026-09-14-release-1-site-structure-gap-audit.md), а возврат тарифных страниц принят в [#149](https://github.com/Celtoman/astro-telekom/issues/149). Post-deploy аудит отдельно обнаружил две опубликованные `HOME` у 206 городов; маршруты не дублируются, но неоднозначность данных отслеживается в [#150](https://github.com/Celtoman/astro-telekom/issues/150).

## Реализованный путь данных

```text
Ручная правка администратора
  -> NestJS API -> рабочая ревизия в PostgreSQL
  -> явная публикация точного snapshot -> persistent SiteRebuild

XLSX-импорт тарифов
  -> NestJS API -> рабочая ревизия + attributed before/after change set
  -> явная публикация точного snapshot -> persistent SiteRebuild

XLSX-импорт городов
  -> NestJS API -> рабочая ревизия PostgreSQL
  -> явная публикация точного snapshot -> persistent SiteRebuild

SiteRebuild -> Redis/BullMQ -> worker
  -> internal start/result API + deployment provider

Публичная Astro-сборка
  -> GET /public/sites/{PUBLIC_SITE_SLUG}/cities во время build
  -> статический HTML для root, пяти global pages и HOME опубликованных City
  -> отдельный detail URL каждого опубликованного Tariff опубликованного города

Посетитель
  -> POST /address-suggestions -> DaData IPLocate (один раз/24 ч) -> DaData suggest с locations_boost
  -> POST /address-checks -> DaData clean -> Tarifnik address/check по фактическому адресу -> AddressCheck
  -> POST /leads -> routing + профиль Дом.ру по данным DaData + contract check -> Lead
  -> только найденный Дом.ру + NOT_FOUND -> очередь lead-deliveries -> Tarifnik или email fallback
```

Это фактический реализованный путь. Обычная форма выполняет проверку под капотом; наличие хотя бы одного провайдера запускает проверку действующего абонента независимо от наличия Дом.ру. Очередь доставки разрешается только при найденном Дом.ру и подтвержденном `NOT_FOUND`. Видимая проверка создает лид с телефоном лишь после обнаружения Дом.ру и отдельного второго шага формы.

Главное следствие статической архитектуры: изменение данных в PostgreSQL не меняет уже опубликованный HTML само по себе. Все текущие content mutators сохраняют новую рабочую ревизию; отдельная публикация фиксирует ее неизменяемый снимок и ставит rebuild-job, worker выполняет его с retry, а статус `SUCCEEDED` появляется только после явного финального ответа deployment provider. Для Coolify реализована цепочка `start → сохранить deployment_uuid → bounded polling → final status`; `queued`/`in_progress` и timeout не публикуют ревизию, а retry продолжает сохраненный deployment. Механика [#57](https://github.com/Celtoman/astro-telekom/issues/57) подтверждена реальным Coolify polling rehearsal и закрыта.

## Реализованные публичные маршруты

Публичный фронтенд генерирует только маршруты Release 1 из authoritative inventory:

- `/`;
- `/{city-slug}` для каждого опубликованного города;
- `/karta-pokrytiya-provaydera` и `/goroda-obsluzhivaniya`;
- `/politika-konfidencialnosti`, `/soglasie-na-obrabotku-personalnyh-dannyh` и `/politika-obrabotki-faylov-kuki`;
- `/robots.txt`, `/sitemap.xml` и общую noindex-404.

Опубликованные service pages остаются данными без самостоятельных URL Release 1. Каждый опубликованный тариф опубликованного города получает `/{location}/{tariffSlug}`; `tariff_grid` одновременно выводит полный snapshot города и не применяет legacy `serviceType`/`limit`, пока отдельные тарифные листинги находятся за границей релиза.

`loadSiteData()` обращается к public catalog API в build-time с таймаутом 5 секунд, отбрасывает draft/archive и проверяет slug/коллизии URL до генерации. Все формируемые public paths, внутренние ссылки, canonical и sitemap используют no-slash contract; Caddy сначала применяет сохраненные точные редиректы, затем одним 301 нормализует slash-варианты HTML с сохранением query string и не трогает `/api/*`, `/_astro/*`, `/assets/*` и файлы. Существующий extensionless route переписывается на его `index.html`, а отсутствующий файл вызывает явную ошибку 404; для обычного HTML path `handle_errors 404` отдает общий `404.html` без смены статуса на 200, а отсутствующие API/assets namespaces не получают HTML-тело. Если API недоступен, сборка по умолчанию падает с ненулевым кодом и явной причиной. До prerender production build требует `PUBLIC_SITE_URL` как чистый HTTPS origin и `PUBLIC_API_URL` как внешний HTTPS URL с path `/api/v1`; нормализованное значение browser API встраивается в форму. После prerender verifier сравнивает весь indexable `*/index.html` с sitemap, отклоняет неизвестные плоские HTML-файлы и проверяет canonical, title, description, единственный H1, robots без глобального `Disallow`, отсутствие loopback-ссылок и `noindex` без canonical у 404. Демо-Казань и loopback URL возвращаются только при явном `ALLOW_DEMO_DATA=true` — это осознанный локальный UX-режим, а не fallback для production-публикации.

Прямой Production Compose принимает отдельный `SITE_DATA_API_URL`, но не оркестрирует первый bootstrap: API нужен уже на стадии Docker build, раньше runtime `depends_on`. Целевой `docker-compose.coolify.yml` устраняет цикл: API и явный initial seed выполняются до runtime Astro publisher, а web стартует только после успешной публикации. Локальная production-подобная проверка полного stack подтвердила ту же последовательность, успешные one-shot контейнеры и устойчивые healthchecks с нулевым restart count. После обновления Coolify до v4.3.19 новый pre-stop `pull --ignore-buildable` ошибочно запросил общий локальный API runtime image от image-only сервиса `bootstrap-seed` из Docker Hub и остановил deployment до миграций; предыдущий stack сохранил `running:healthy`. Добавленный upstream workaround `pull_policy: never` подтвержден deployment `wrozooadortksiftbt7voucn`: Coolify пропустил registry pull общего runtime image, завершил всю цепочку и вернул resource в `running:healthy`.

Внешний test deployment работает в Coolify из GitHub на `tv-internet-dom.ru` и `admin.tv-internet-dom.ru` без дополнительного stage-контура. Схема не публикует API напрямую: оба сайта проксируют `/api/*` same-origin, а Compose Basic Auth закрывает все их маршруты. Перед Basic Auth настроены разные public/admin security middleware, чтобы common headers и frame policy присутствовали и на `401`; внутренние Caddy повторяют их для прямого Compose и авторизованного ответа. Public не выставляет конфликтующий с Webvisor `X-Frame-Options`, admin сочетает `frame-ancestors 'none'`, `X-Frame-Options: DENY` и `X-Robots-Tag: noindex, nofollow, noarchive`.

## Зависимости от окружения

| Переменные | Поведение без них |
| --- | --- |
| Любая из `DADATA_TOKEN`, `DADATA_SECRET`, `DADATA_SUGGEST_API_URL`, `DADATA_CLEAN_API_URL` | Подсказки возвращают честный HTTP 503, нормализация адреса недоступна; проверка не получает разрешающий coverage snapshot. |
| Любая из `TARIFNIK_ADDRESS_CHECK_API_URL`, `TARIFNIK_API_KEY`, `TARIFNIK_TARGET_PROVIDER_ID` | Проверка адреса сохраняется как `MANUAL_CHECK`; автоматическая доставка запрещена. |
| `DOMRU_CONTRACT_API_URL` либо отсутствие подходящего профиля в `apps/api/src/assets/domru-city-profiles.csv` | Новая заявка получает `MANUAL_CHECK_API`; доставка в Tarifnik не запускается. Городские public-параметры не являются секретами окружения. |
| Любая из `TARIFNIK_API_URL`, `TARIFNIK_API_KEY`, `TARIFNIK_UTM_CAMPAIGN` | Pending-заявка остается не переданной; автоматический вызов CRM не выполняется. |
| `LEADS_EMAIL` и `RESEND_API_KEY` либо `LEADS_EMAIL_WEBHOOK_URL` | Обычное оповещение всегда получает outbox-запись. Без transport оно завершается `FAILED/not_configured`; сеть и временные HTTP-ошибки повторяются ограниченно, постоянные — сохраняются без response body. Email fallback delivery завершится отдельной ошибкой и зафиксирует свой outcome. |
| Полная конфигурация выбранного `REBUILD_PROVIDER` | Rebuild-job повторяется и завершается `FAILED`; опубликованная ревизия не изменяется. Для `webhook` нужен `REBUILD_WEBHOOK_URL`, для `coolify` — API URL/token/resource UUID. |
| `REDIS_URL` | Rebuild сохраняется как `PENDING`, но не выполняется до следующего запуска API с Redis. |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Seed не создаст пользователя для входа. |
