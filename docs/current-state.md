# Текущее состояние проекта

Дата среза: 8 сентября 2026 года. Источник этого документа — исходный код, Prisma-схема, Docker-конфигурация и результаты локальных проверок на текущей ветке `master` (HEAD `4e39514`). Он описывает фактическое состояние, а не только согласованный продуктовый замысел из [реестра решений](decisions.md).

## Краткий вывод

Репозиторий содержит работоспособный локальный каркас платформы, но не production-систему. Полностью реализованы базовая инфраструктура, схема данных, API основных сущностей, двухэтапный импорт городов и тарифов, прием заявок и механика их доставки. Публичный сайт статически строит только Казань; админка и CRM частично подключены к API, но значительная часть их экранов показывает демонстрационные данные или не имеет backend-маршрута.

## Реализованный путь данных

```text
Администратор или XLS
  -> NestJS API -> PostgreSQL через Prisma
  -> webhook пересборки или API-очередь доставки

Публичная Astro-сборка
  -> GET /public/sites/domru-kazan/cities/kazan во время build
  -> статический HTML для фиксированных казанских маршрутов

Посетитель
  -> POST /address-checks -> AddressCheck
  -> POST /leads -> Lead -> очередь lead-deliveries -> Tarifnik или email fallback
```

Главное следствие статической архитектуры: изменение данных в PostgreSQL не меняет уже опубликованный HTML само по себе. API вызывает `REBUILD_WEBHOOK_URL` напрямую, но успешный production-процесс пересборки и его обратная связь не реализованы в репозитории.

## Реализованные публичные маршруты

Публичный фронтенд содержит только зашитые маршруты:

- `/`;
- `/kazan/`;
- `/kazan/internet/`, `/kazan/internet-tv/`, `/kazan/tv/`;
- `/kazan/proverka-adresa/`, `/kazan/faq/`;
- `/kazan/:tariff-slug/` для тарифов, известных на момент `astro build`;
- `/robots.txt` и `/sitemap.xml`.

`loadKazanData()` обращается к API в build-time с таймаутом 2 секунды. Если API недоступен, сборка по умолчанию падает с ненулевым кодом и явной причиной. Демо-набор из двух тарифов и текста «Цена уточняется» возвращается только при явном `ALLOW_DEMO_DATA=true` — это осознанный локальный UX-режим, а не молчаливый fallback для production-публикации.

## Зависимости от окружения

| Переменные | Поведение без них |
| --- | --- |
| `DOMRU_COVERAGE_API_URL`, `DOMRU_COVERAGE_API_KEY` | Проверка адреса сохраняется как `MANUAL_CHECK`. |
| `DOMRU_CONTRACT_API_URL` | Новая заявка получает `MANUAL_CHECK_API`; доставка в Tarifnik не запускается. |
| `TARIFNIK_API_KEY` | Pending-заявка остается не переданной; попытка логируется только в server log. |
| `LEADS_EMAIL` и `RESEND_API_KEY` либо `LEADS_EMAIL_WEBHOOK_URL` | Обычное уведомление может тихо не уйти; email fallback завершится ошибкой. |
| `REBUILD_WEBHOOK_URL` | API не инициирует пересборку статического сайта. |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Seed не создаст пользователя для входа. |

## Результаты проверок

На этом срезе выполнены:

| Команда | Результат |
| --- | --- |
| `pnpm lint` | Успешно: TypeScript API, Astro web и syntax check worker. У admin и CRM нет lint-скриптов. |
| `pnpm db:validate` | Успешно: Prisma schema валидна. |
| `pnpm build` | Успешно с `ALLOW_DEMO_DATA=true` (или поднятым API): API, web, admin, CRM и worker собираются. Без флага и без API `apps/web` build осознанно падает — см. TD-03. |
| `pnpm test` | 38/38 успешно, включая дедупликацию лидов по нормализованному телефону и адресу. |
| GitHub Actions CI | `.github/workflows/ci.yml` запускает `pnpm check` на каждый push и pull request в `master`; допустимого красного baseline нет. |
| `docker compose -f docker-compose.prod.yml config --no-interpolate` | YAML и структура Compose читаются. Это не запуск контейнеров и не доказательство готовности production. |
