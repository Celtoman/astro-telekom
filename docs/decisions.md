# Реестр решений по платформе Дом.ру

Статус: живой документ. Обновляется после каждого согласованного решения. Он фиксирует договоренности по продукту и интерфейсам, а не факт поставки функции. Актуальный срез реализации, ограничений и проверок находится в [current-state.md](current-state.md); подтвержденные расхождения и риски — в [technical-debt.md](technical-debt.md).

Последнее обновление: 14 сентября 2026 года.

## 1. Границы продукта

- Первый запуск: партнерский сайт одного провайдера — Дом.ру.
- Дальнейшая цель: платформа для сайтов разных провайдеров. В модели с самого начала разделяются `Provider`, `Site`, `Region`, `City` и `Tariff`; SaaS-мультиарендность пока не строится.
- Казань использовалась как первый тестовый срез. Release 1 не закрепляет один город: `/{city-slug}` создается для каждого и только для опубликованного города.
- Публичная структура первого сайта: один домен с городским префиксом (`site.ru/kazan`). Финальный домен пока не выбран; первый внешний rehearsal проводится на купленном тестовом домене `tv-internet-dom.ru`.
- Полная целевая структура зафиксирована в [site-structure.md](site-structure.md). Страница отдельного тарифа `/{city-slug}/{tariff-slug}` входит в Release 1; остальные строки со статусом «позже» не публикуются автоматически.
- Canonical URL contract: `/` создается один раз; главная каждого опубликованного города имеет URL `/{city-slug}` независимо от служебного slug страницы типа `HOME`; все остальные публичные HTML-URL не имеют завершающего слэша. Slash-варианты приводятся к canonical одним HTTP 301 с сохранением query string; assets, файлы и `/api/*` из правила исключены.
- Минимальный Release 1 включает `/`, по одной странице `/{city-slug}` для каждого города канонического импорта, по одной `/{city-slug}/{tariff-slug}` для каждого опубликованного тарифа опубликованного города, карту покрытия, города обслуживания, три legal-страницы и общий шаблон 404. При `N` опубликованных городов и `T` их опубликованных тарифов это ровно `N + T + 6` обычных HTML-маршрутов; service pages и остальные строки со статусом «позже» не генерируются.
- Применение канонического импорта публикует все входящие города и их единственную `HOME`. Полный тарифный snapshot каждого города отображается на `/{city-slug}`; каждый тариф в `PUBLISHED` получает detail URL, если город и сайт тоже опубликованы.
- Черновые и архивные города не генерируются и не включаются в sitemap. Статус контентной сущности сам по себе не расширяет release scope; конфликт любого допустимого маршрута блокирует сборку с указанием спорного URL, а не разрешается приоритетом шаблона.
- Запись `Redirect` не создает второй HTML-документ и не меняет canonical. Опубликованный source URL входит в build-generated Caddy routing и обслуживается как HTTP 301 на опубликованный target через API resolver; изменение правила требует успешной пересборки, а runtime resolver повторно проверяет статус и учитывает переход.
- Публичный сайт должен отдавать SEO-значимое содержимое в чистом HTML; выбранная архитектура — Astro + NestJS + PostgreSQL + Redis/BullMQ на VPS с Docker, развертывание из GitHub через Coolify.

## 2. Контент, города и публикация

- Наследование: общий шаблон → сайт → регион → город → страница → тариф. В редакторе виден полный источник каждого значения.
- Городская страница строится из библиотеки блоков. Администратор видит структуру и предпросмотр, может менять порядок, скрывать, добавлять и переопределять блоки.
- Минимальная библиотека первого рабочего среза содержит семь типов: `hero`, `rich_text`, `tariff_grid`, `service_grid`, `feature_grid`, `steps`, `faq`. Каждый тип имеет закрытый JSON-контракт с обязательными полями, лимитами и запретом raw HTML; произвольные поля не становятся неявным API.
- Если у страницы есть управляемые блоки, они являются единственным источником ее контентной структуры. Hardcoded-шаблон допустим только как fallback для страницы без блоков и не добавляется поверх них.
- Service landing, включая ранее собранный прототип `/kazan/internet`, относится к следующему релизу и не получает URL в Release 1. Его Page/blocks могут оставаться данными для будущего расширения policy, но не входят в output, sitemap, навигацию или redirects первого запуска.
- `/kazan` — эталонная городская витрина: первый экран объединяет обещание, фактические показатели опубликованных тарифов, оригинальную иллюстрацию оборудования, видимую проверку адреса и консультацию; далее отдельными последовательными секциями идут выбор услуги, полный опубликованный тарифный snapshot города, этапы подключения, оборудование, преимущества и FAQ. В Release 1 legacy `serviceType`/`limit` блока `tariff_grid` не скрывают предложения: отдельные тарифные листинги появятся только в следующих релизах. Нижние смысловые блоки не склеиваются в общую двухколоночную секцию, а рабочая навигация по услугам заменяет неподтвержденный псевдоопрос подбора.
- Любое изменение управляемого контента сначала сохраняется как новая рабочая версия. Публичный сайт продолжает показывать последнюю успешно опубликованную версию и переключается на новую только после успешной сборки, проверок и завершения deployment.
- Полный аудит/версии всех сущностей, публикация по расписанию, rollback и глубокое наследование реализуются поэтапно и не расширяют контракт уже работающего первого прототипа автоматически.
- Предпросмотр доступен на десктопе, планшете и мобильном экране; в первом этапе он личный, без внешних ссылок.
- Изменения страницы: черновик → предпросмотр → публикация сразу или по расписанию.
- Для Release 1 примененный импорт нового города создает опубликованную карточку и одну `HOME` с канонической композицией из семи блоков; API и web блокируют публикацию неполной HOME. Комплект service pages добавляется отдельным шаблоном только в том релизе, где эти URL разрешены policy.
- SEO собирается из шаблонов и переменных города; Title, Description, H1 и canonical можно переопределить вручную.
- Изменение глобального шаблона создает версию и показывает все затронутые города. Конфликт локального переопределения и шаблона решается отдельно для каждого города.
- Массовые SEO-правки и изменение блоков публикуются сразу после обязательного подтверждения. Операция попадает в журнал и отменяется одной командой, пока ни одна затронутая запись не была изменена позже.

## 3. Импорт и каталог городов

- Каталог и управление городами находятся на основной странице раздела, а XLSX-импорт, его отчеты и состояние пересборки — на отдельной вложенной странице «Импорт».
- Городской XLSX проходит полную валидацию до записи; применение возможно только после подтверждения администратора.
- При совпадении `slug` администратор для каждой строки выбирает: обновить, пропустить или создать новую запись.
- Справочник города содержит: субъект РФ, название в именительном, предложном и родительном падежах, legacy URL, slug, адрес офиса и режим работы.
- Legacy URL служит справочным адресом исходного сайта. Публичный URL нового сайта строится из домена `Site` и `City.slug`.
- Основной экран городов — таблица с поиском, фильтрами, массовыми действиями и быстрым состоянием публикации, тарифов, SEO и последней правки.
- Массовые действия: импорт XLSX, публикация/снятие с публикации, назначение шаблона, экспорт, массовое изменение SEO и блоков.

## 4. Тарифы и импорт тарифов

- Каталог, быстрый просмотр и ручное редактирование тарифов находятся на основной странице раздела, а XLSX-импорт, его отчеты и состояние пересборки — на отдельной вложенной странице «Импорт».
- Тариф — отдельная запись для каждого города.
- Первый источник тарифов: локально подготовленный XLSX. Legacy `.xls` не принимается: прямой уязвимый SheetJS-парсер удален, а оба канонических источника проекта уже используют `.xlsx`. В админке не реализуются правила фильтрации и размножение тарифов по городам из старого конвейера; на вход подается готовый файл. В дальнейшем допускаются API, импорт и ручное редактирование. У каждой версии хранится источник.
- Файл сначала проходит полную валидацию. Фактический импорт разрешен только после успешной валидации и подтверждения; неизвестные статусы услуг не должны попасть в пакет.
- Файл тарифов проходит полную валидацию. После успешной валидации администратор запускает импорт кнопкой, и новые/измененные тарифы сразу отображаются на сайте; по строкам пакет не принимается и не отклоняется.
- Ошибки валидации блокируют импорт. Предупреждения показываются в отчете и допускают импорт после явного подтверждения.
- После публикации хранится полная история: кто, когда и каким способом изменил поле, предыдущее и новое значение.
- История предназначена для аудита; кнопка восстановления прежней версии не нужна.
- Пустая ячейка при обновлении не имеет единого автоматического смысла: на экране проверки выбирается правило для поля или строки.
- Ручное изменение опубликованного тарифа после успешной пересборки отражается в карточках городской страницы и на его detail URL.
- После ручной правки запускается существующая полная внешняя пересборка сайта. Точечная пересборка связанных страниц в этой задаче не вводится; новая версия становится видна только после успешного завершения общего deployment.
- Новый XLSX всегда перезаписывает значения, ранее измененные вручную.
- Ошибки длинной формы показываются у неверного поля и в общем списке после сохранения.
- Поле источника «Показывать на сайте» отображается как рекомендация; окончательной публикацией управляет администратор.
- Дата окончания тарифа не меняет публикацию и не участвует в автоматических действиях.
- Если тариф отсутствует в новом импорте, запись, карточка и detail URL исчезают после успешной пересборки полного snapshot. Отдельный redirect для такого массового удаления автоматически не придумывается.
- Каталог тарифов — единая таблица с фильтрами. По умолчанию видны город, название, тип услуги, цена, статус, скорость, ТВ-каналы, акция, дата импорта и источник; дополнительные сервисы находятся в раскрываемых фильтрах.
- Быстрый просмотр тарифа открывается в боковой панели без потери таблицы и фильтров; редактирование открывает отдельную длинную форму.
- Все поля текущего импортного контракта должны храниться в нормализованной модели и быть доступны для проверки и ручного редактирования в одной длинной форме с закрепленной навигацией по секциям и сворачиваемыми группами.
- Длинная форма тарифа сохраняется только кнопкой «Сохранить изменения» вверху и внизу формы; кнопка активна при наличии несохраненных изменений.
- Текущий бизнес-ключ импорта: `{city_slug}-{post_title_lat}-{tariff_type}`.
- При смене тарифного slug сохраняется provenance-aware запись 301. Она эффективна после успешной пересборки, если тариф, его город и сайт опубликованы; draft/archive оставляют правило неэффективным.
- Раздел «Редиректы» включает автоматические и ручные 301-редиректы, редактирование, отключение, число переходов, последние обращения и предложения из найденных 404.
- Если старый URL занят опубликованной страницей, изменение slug и создание редиректа блокируются до разрешения конфликта.
- 301-редирект начинает действовать только после включения новой цели в текущий release route inventory и успешной публикации.
- `connection_cost` выводится как стоимость подключения.
- При `connection_cost = 0` публичная карточка показывает «Бесплатное подключение».
- При пустом `connection_cost` строка не показывается.
- Обычная цена, акционная цена, название, описание и срок акции импортируются раздельно; значение `-1` для акционной цены означает отсутствие акции.

## 5. Заявки, кол-центр и аналитика

- Раздел называется «Заявки». Это журнал контроля, а не рабочее место оператора кол-центра.
- В заявке хранятся: реферер, время на сайте, страница и форма, контакты и адрес, выбранный тариф, данные API Дом.ру о клиенте, полный результат проверки адреса, найденные провайдеры, попытки и статус передачи во внешнюю CRM.
- Дополнительно сохраняются UTM, устройство, просмотренные страницы и события до отправки; краткая сводка показывается в карточке, полная — во вкладке активности.
- Передача в кол-центр: основной канал API, после исчерпания автоматических попыток — email-резерв. В журнале видны все попытки, ответы и время.
- `Tarifnik` — отдельный партнерский сервис. Платформа использует два независимых его API: `address/check` получает список провайдеров по адресу, а `appeal/create` принимает разрешенные нашей системой заявки в CRM кол-центра Tarifnik. Сам Tarifnik не является частью платформы.
- Текущий `domru_smart_bot` используется как источник фактов об интеграциях и проверенного порядка маршрутизации, а не как компонент новой платформы. DaData нормализует адрес, Tarifnik возвращает провайдеров, а запрос к API Дом.ру проверяет наличие действующего контракта по городу и телефону. Подробности и ссылки на исходный код: [исследование API бота](./research/domru-smart-bot-api.md).
- Любое поле ввода адреса использует подсказки DaData. DaData отвечает за корректный структурированный адрес, а не за доступность провайдера; нормализованный адрес передается в Tarifnik `address/check`. Подсказки и проверка не ограничиваются городом открытой страницы: пользователь может проверить и отправить свой фактический адрес в любом городе с любой страницы сайта.
- Адресные подсказки используют только мягкий географический приоритет `locations_boost`, но никогда не жесткий `locations`. При первом вводе API один раз определяет примерный город через DaData IPLocate и хранит 24 часа только КЛАДР-код города либо маркер отсутствия результата в HttpOnly-cookie; IP, определенный город и cookie не сохраняются в заявке, PostgreSQL или Redis. Ошибка, таймаут или `location: null` незаметно переключают ранжирование на пару «регион + город страницы». Явный текст запроса и выбранная пользователем подсказка остаются источником фактического адреса; геолокация по IP не валидирует и не подменяет его.
- Город страницы сохраняется как контекст и источник заявки, а не как фактический город подключения. В интерфейсе администратора и уведомлениях эти понятия должны быть явно разделены: «Город страницы» и «Адрес подключения».
- Поддерживаются два разных пользовательских сценария формы. Обычная форма сразу принимает адрес и телефон, после отправки всегда показывает только короткое подтверждение «Спасибо! Заявка отправлена», а все проверки и решение о передаче выполняет под капотом. Видимая проверка подключения сначала принимает только адрес и показывает результат до запроса телефона.
- Для обычной формы заявка сначала сохраняется локально. Если Tarifnik не нашел ни одного провайдера, проверка действующего абонента не запускается, заявка получает причину непередачи и не уходит в CRM.
- Если Tarifnik нашел по адресу хотя бы одного провайдера, API Дом.ру проверяет телефон на действующий договор независимо от того, присутствует ли Дом.ру в списке найденных провайдеров. Это фильтр обращений действующих абонентов в форму нового подключения.
- Городской профиль запроса Дом.ру определяется по нормализованным DaData городу и региону, а не по slug формы. Источник профилей — версионированный несекретный справочник рабочего бота: 555 исходных строк сведены к 551 уникальной паре «регион + населенный пункт» и 37 явным региональным fallback-профилям. Одинаковые названия городов в разных регионах не смешиваются; неизвестный профиль дает ручную проверку. В окружении хранится только общий URL endpoint, а не отдельный профиль одного города.
- Передать заявку в CRM Tarifnik можно только при одновременном выполнении двух условий: среди найденных провайдеров есть Дом.ру, а API Дом.ру вернул однозначный успешный ответ ожидаемой структуры с пустым массивом `contacts`. Непустой `contacts` означает действующего абонента; отсутствие Дом.ру означает неподходящую заявку на подключение Дом.ру. В обоих случаях заявка сохраняется с причиной непередачи и в CRM не уходит.
- Timeout, сетевая или HTTP-ошибка, HTML вместо JSON, неразбираемый JSON, отсутствие `contacts`, неверный тип `contacts`, неизвестная структура, неопределенный город или отсутствующая конфигурация не считаются ответом «абонент не найден». Заявка сохраняется как «Ручная проверка API» и автоматически в CRM не передается.
- В видимой проверке подключения при найденном Дом.ру появляется второй этап с телефоном; после его отправки действует тот же фильтр действующего абонента. Если Дом.ру не найден, но доступны другие провайдеры, форма показывает их и ведет на партнерский сайт `tarifnik.ru`, не создавая заявку с телефоном. Если провайдеров нет вообще, форма показывает номер технической поддержки и рекомендацию оставить заявку на подключение дома.
- После однозначного ответа Дом.ру о действующем абоненте публичный UI сразу заменяет номера подключения на отдельный управляемый номер техподдержки и сохраняет этот вид на 30 дней. Это некритичная browser-персонализация: ее можно хранить unsigned, поскольку сервер никогда не доверяет ей при проверке абонента и решении о передаче заявки.
- В карточке заявки раздельно показываются «провайдеры по адресу», «действующий абонент Дом.ру», решение маршрутизации и реальные попытки передачи. Для отфильтрованной заявки фиксируется решение и причина, но не создается фиктивная попытка отправки в CRM.
- Новый адаптер кол-центра реализуется самостоятельно и использует Tarifnik `appeal/create`; существующий бот служит примером маршрута и не переносится в код новой платформы. Адаптер обязан иметь персистентный журнал реальных попыток и повторную отправку; у текущего бота этого нет.
- Карточка интеграции Tarifnik содержит URL, API-ключ, тест подключения, email-резерв, журнал последних запросов и редактируемый профиль сопоставления полей заявки с payload API.
- Профиль сопоставления задается на уровне сайта и по умолчанию наследует общую настройку провайдера.
- Профиль сопоставления полей выпускается по схеме: черновик → тест на примере заявки → ручная активация.
- Тест профиля использует только синтетическую заявку: он показывает будущий JSON и ошибки сопоставления, но не передает лид во внешнюю CRM.
- Tarifnik не предоставляет callback/webhook о дальнейшей обработке заявки; локально фиксируется только непосредственный результат `appeal/create`. `created` и `created_duplicate` с непустым `appeal_id` считаются успешной передачей, причем `created_duplicate` означает, что партнер сохранил заявку как дубль.
- При исчерпании API-попыток email-резерв получает контакты, адрес и защищенную ссылку на полную карточку заявки.
- Транспорт email-резерва — Resend. Ключ хранится только в `.env`/Coolify, а синтетическое письмо с настроенным отправителем принято API и получено владельцем 10 сентября 2026 года. Обычное уведомление создается атомарно с лидом как persistent outbox: HTTP/contract failure не откатывает сохранение лида, временные ошибки повторяются ограниченно, outcome виден оператору, а Resend success подтверждается непустым `id` ответа. Outbox не копирует PII и удаляется каскадно вместе с лидом; доставка имеет at-least-once семантику с idempotency header.
- Защищенная ссылка в email-резерве действует 24 часа.
- Первая API-отправка выполняется сразу. Повтор через 5 и затем 30 минут разрешен только после сетевой ошибки/таймаута либо HTTP 408, 425, 429 и 5xx. Для 429 учитывается корректный `Retry-After` с верхней границей 24 часа.
- Постоянный 4xx и неоднозначный успешный ответ (невалидный JSON, неизвестный `result`, отсутствие `appeal_id`) не повторяются автоматически: заявка сразу переходит в email-резерв. После исчерпания трех попыток временной ошибки действует тот же fallback и статус «Ошибка передачи: email отправлен» либо явная ошибка email.
- Все попытки одной заявки используют единый внутренний ключ журнала. Официальный контракт Tarifnik не принимает отдельный idempotency key; дубли определяются ответом `created_duplicate`, поэтому автоматические повторы ограничены только временными ошибками.
- Статус «Ручная проверка» администратор завершает вручную или повторным запуском API-проверок из карточки заявки.
- Дубликат определяется по совпадению телефона **или** нормализованного адреса в течение 24 часов. Он сохраняется со статусом «Дубликат: не передана», ссылкой на исходную заявку и причиной; в кол-центр автоматически не уходит.
- При подавлении дубликата посетитель видит обычное успешное подтверждение без причины блокировки.
- Дашборд отдельно показывает отправки формы и клики по телефону, а также их конверсию от визитов. Источник: собственные события для заявок/телефонов и Яндекс Метрика для посещаемости и маркетинговых срезов.
- Период по умолчанию: 30 дней со сравнением с предыдущими 30 днями. Быстрые переключатели: 7, 30 и 90 дней.
- Фильтры аналитики: период, город/регион, тип страницы, услуга, тариф, источник и UTM. Они действуют только до перезагрузки, не сохраняются в URL или именованные представления; на экране всегда доступна кнопка «Сбросить фильтры».
- «Требует внимания» включает: новые заявки, сбои передачи, ошибки импорта, тарифы без цены, черновики, падение конверсии, проблемы телефона и отсутствие данных Метрики.
- Проверка телефонов совмещает внешний сервис и ручную отметку администратора.

## 6. Админка, навигация и доступ

- Решение от 7 сентября 2026: отдельного приложения `apps/crm` не будет. Список заявок, карточка и смена статуса перенесены в раздел «Заявки» (`/leads`) внутри `apps/admin`; 9 сентября 2026 года временный `apps/crm` удален из workspace и production-контура. Префикс `/crm/leads` пока остается внутренним именем API-контракта и не означает наличие отдельного приложения или роли.
- В первом релизе системой пользуется один администратор. Ролей, разграничения прав и разрешения конфликтов одновременного редактирования нет; все технически созданные учетные записи, если они понадобятся для замены доступа, имеют одинаковые права. Будущая ролевая модель не входит в согласованный план и потребует отдельного решения.
- Главный экран администратора: сводка по сайтам, городам, тарифам и заявкам, блок «Требует внимания» и динамика заявок/конверсии.
- Левое меню сохраняет состояние и может сворачиваться:
  - Обзор
  - Контент: Города, Страницы и шаблоны, Блоки
  - SEO
  - Редиректы
  - Переменные
  - Тарифы: Каталог, Импорты, История изменений
  - Заявки
  - Аналитика
  - Система: Интеграции, Журнал действий, Настройки
- Журнал действий фиксирует изменения данных, входы, интеграционные запросы, отправки заявок и автоматические действия; обычные просмотры не логируются.
- Медиатека поддерживает загрузку и внешние URL. Для изображения обязательны alt-текст и оптимизированные варианты.
- Таблицы используют сбалансированную плотность: читаемые строки, а детали раскрываются по действию пользователя.
- Светлая тема включена по умолчанию, доступен переключатель темной темы.
- Полноценная рабочая версия админки рассчитана на десктоп.
- Визуальная основа интерфейса нейтральная, с небольшими акцентами бренда Дом.ру.
- Левое меню широко по умолчанию и переключается в компактный режим с иконками.
- Поверхности следуют характеру Studio Admin CRM: светлый фон, белые блоки, тонкие границы и почти отсутствующие тени.
- Фирменный цвет Дом.ру используется для действий, активной навигации, ссылок и ключевых показателей.
- Каждая карточка показателя на дашборде открывает готовый отфильтрованный список.
- Глобальный поиск находит города, тарифы, заявки и страницы по всей админке; он также запускает быстрые команды: импорт тарифов, создание города и открытие редиректов.
- Фильтры в таблицах действуют только до перезагрузки страницы; доступна постоянная кнопка «Сбросить фильтры». Адрес страницы и именованные сохраненные представления их не хранят.
- Массовые операции включаются отдельным режимом выбора. После выбора строк снизу появляется панель действий с числом затронутых объектов.
- Клик по строке или названию открывает быструю боковую карточку. Отдельная кнопка в строке открывает полное редактирование.
- Уведомления: краткие сообщения об успехе и ошибке, центр уведомлений для импорта, публикаций и интеграций, email для критических сбоев.
- В верхней панели видны только глобальный поиск, уведомления и профиль. Переключатели сайта и города отсутствуют; нужный контекст задается фильтрами внутри разделов.
- Редактор города: дерево блоков закреплено слева, предпросмотр находится по центру, свойства выбранного блока открываются выезжающей правой панелью.
- Импорт тарифов ведется на отдельном экране: файл, валидация, отчет изменений, подтверждение. История отчетов хранится, а отчет ошибок можно скачать.
- Быстрая карточка заявки использует вкладки «Сводка», «Проверки API», «Передача», «Активность» и закрепленную шапку с телефоном, статусом и временем создания.
- Каждый статус передается одновременно цветом, иконкой и текстом.
- Ручное удаление города, тарифа, страницы или редиректа перемещает объект в корзину с возможностью восстановления.
- Обычная ручная правка опубликованного тарифа сохраняется и публикуется сразу. Подтверждение требуется при изменении цены, URL, статуса публикации или SEO.
- У админки один уровень пользовательского доступа — администратор. Ролевого разграничения нет и не планируется: все активные пользователи имеют одинаковые права во всех разделах. Сервисный `x-admin-token` — отдельный машинный credential, а не пользовательская роль.
- В первом релизе одновременно работает только один администратор; разрешение конфликтов и блокировки одновременного редактирования не нужны.
- Пустой список содержит понятное сообщение, уместное действие и небольшую нейтральную иллюстрацию.
- Уведомление можно отметить прочитанным, архивировать или открыть связанный журнал события.

## 7. Правовые и технические ограничения

- Три legal-документа Release 1 адаптируются для `tv-internet-dom.ru` по материалам [согласия](https://tarify-dom.ru/soglasie), [политики обработки персональных данных](https://tarify-dom.ru/policy) и [политики cookie](https://tarify-dom.ru/politika-obrabotki-faylov-kuki). Реквизиты оператора и получателей сохранены по прямому указанию владельца; перед реальным трафиком их соответствие владельцу нового домена проверяется отдельно.
- Сырые заявки и связанные PII хранятся 180 дней — этот срок согласован владельцем 10 сентября 2026 года и задан в `PII_RETENTION_DAYS`. Юридическое основание, тексты согласия, оператор данных и порядок отзыва будут согласованы отдельно до приема реальных заявок. Сроки технической активности и обезличенной аналитики остаются отдельным решением.
- В карточке заявки сохраняется полный необработанный ответ API проверки адреса; краткая сводка используется в основном интерфейсе.
- Первый внешний тестовый контур разворачивается в Coolify непосредственно из GitHub на `tv-internet-dom.ru`; дополнительный `stage`-контур или `stage.*` hostname не создается.
- До отдельного решения о публичном запуске все web/admin страницы тестового контура закрываются общей парольной защитой на edge proxy. Пароль и его открытое значение не хранятся в Git.
- Browser API должен оставаться работоспособным под парольной защитой; routing проектируется так, чтобы формы и админка не требовали неявной повторной HTTP-аутентификации на другом origin.

## 8. Подтвержденные факты существующего конвейера `D:\01 vibecode\Tarifs`

- Входной файл содержит 1 818 строк и 94 колонки; после фильтрации, исключения ТВ и размножения сформировано 3 859 городских тарифов для 207 городов и 41 региона.
- Статус услуг уже имеет семантику: `-1` — включена в тариф, `1` — доступна за доплату, `0` — недоступна.
- Региональные тарифы без города сейчас размножаются на города справочника, которых нет среди исходных городских тарифов.
- В текущем WordPress-генераторе поля акции не попадают в `staraia_stoimost` и `opisanie_aktsii`. Новый контракт не должен наследовать это ограничение.
- В текущем источнике `Акция абон. плата` равна `-1` во всех строках, а название и описание акции пусты. Это описывает конкретный файл, не правило будущей модели.
- Ключ `{город_slug}-{post_title_lat}` в реальном последнем импорте не уникален: есть одинаковые `post_title_lat` у разных `tarif_type` в одном городе. Это учтено в принятом ключе с `tarif_type`.
