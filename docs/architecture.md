# Архитектура платформы

Сверка с кодом и Compose: 6 октября 2026 года. Действующий [контракт публикации](publication.md) описывает static builder/controller, exact serving snapshot, CODE и восстановление. Датированные результаты внешних проверок — в [приёмках](research/README.md), актуальные ограничения — в [current-state.md](current-state.md).

## Статус архитектуры

В репозитории реализован прототип статической витрины Дом.ру с защищенным внешним test-контуром в Coolify. Архитектура разделяет public web, admin, backoffice API и worker. Публичная маршрутизация строит static paths из отдельного Release 1 route inventory: корень, пять site-global страниц, HOME каждого опубликованного города и detail каждого опубликованного тарифа такого города. Канонический импорт переводит весь входящий каталог городов в `PUBLISHED` и создает новым городам единую композицию HOME.

## Контуры и потоки

Coolify Compose и direct prod Compose запускают one-shot `migrate` из отдельного migration target после PostgreSQL healthcheck. Packaging direct Compose исправлен в #236 и проверен migration rehearsal; полный direct stack отдельно не проверен. `api` стартует только после успешного `prisma migrate deploy` и готового Redis; его `/health/ready` проверяет обе зависимости, а `/health/live` — только процесс. Seed остается отдельной операторской операцией, поскольку создает или обновляет продуктовые данные и администратора.

Целевой внешний deployment provider — Coolify с Git-based `docker-compose.coolify.yml` из GitHub. Первый rehearsal использует `tv-internet-dom.ru` и `admin.tv-internet-dom.ru` без дополнительного stage-контура; Coolify edge применяет один password middleware к обоим human-facing сервисам. API не получает внешний hostname: внутренние Caddy в web/admin проксируют same-origin `/api/*` в `api:3000`, поэтому Basic Auth не ломает browser fetch. Прямой `docker-compose.prod.yml` с внешним Caddy и портами 80/443 остается только локальной production-like конфигурацией.

В Coolify images собираются без каталога. После migrations/API/явного bootstrap seed постоянный Node builder/controller и Caddy используют прежний RW volume. API/worker закреплены на private static provider. Startup принимает проверенный/sealed actual legacy baseline либо возобновляет protocol autosave; CODE после latest terminal exact deployment пересобирает serving snapshot и сохраняет его ID/revision/hash. CMS создаёт immutable snapshot рабочей ревизии, выполняет настоящие Astro/SEO gates и атомарно меняет HTML/redirects/proxy context одной Caddy config. Durable receipt и независимая SQL-сверка подтверждают rebuild/publication/site одной транзакцией. Старые assets сохраняются, HTML автономен при отказе API. Прямой prod Compose сохраняет прежнюю build-time/external-provider схему; внешний rollout и ручные публикации подтверждены [приёмками 6 октября](research/2026-10-06-publication-progress-and-recovery.md).

Coolify CMS worker использует static provider и durable receipts; SQL acknowledgment подтверждается одной транзакцией. Для legacy external-provider режима сохранён Coolify adapter: worker сохраняет deployment UUID и ждёт finished, при ошибке не продвигает processing snapshot. Requested/processing/published IDs остаются раздельными в обоих режимах. Сам CODE-deployment не запускает публикацию working snapshot; после terminal provider status выпускается renderer уже обслуживаемой версии.

Готовность инфраструктуры не смешивается с готовностью бизнеса: защищенный `/admin/readiness` отдельно проверяет наличие конфигурации coverage, contract, Tarifnik, fallback email, deployment provider и валидного PII retention period. Он возвращает только статусы и имена пропущенных переменных; реальная доступность, договорный статус интеграций и legal basis подтверждаются sandbox/rehearsal, а не наличием строки в environment.

```text
Браузер публичного сайта
  -> Caddy -> static web
  -> /api/v1/address-suggestions -> API -> DaData IPLocate (один раз/24 ч) -> DaData suggest с locations_boost
  -> /api/v1/address-checks -> API -> DaData clean -> Tarifnik address/check -> PostgreSQL
  -> /api/v1/leads -> API -> routing/контракт Дом.ру -> PostgreSQL
                    -> persistent LeadNotification -> Redis/BullMQ -> worker -> Resend/webhook
                    -> только разрешенный лид -> Redis/BullMQ -> worker -> Tarifnik/email
                    -> ошибка producer -> QUEUE attempt + DELIVERY_QUEUE_ERROR -> безопасный admin retry

Старый публичный URL
  -> build-generated Caddy matcher -> public redirect resolver API
  -> atomic hitCount/lastHitAt -> HTTP 301 на опубликованный target

Браузер admin
  -> Caddy -> static admin
  -> HttpOnly admin cookie -> API -> PostgreSQL
  -> GET working preview catalog -> sandboxed personal desktop/tablet/mobile render

Ручное изменение города/страницы/блока/тарифа/редиректа в API
  -> рабочая ревизия + before/after audit в PostgreSQL
  -> ручная публикация проверенной ожидаемой ревизии -> неизменяемый SitePublication
  -> PostgreSQL SiteRebuild -> Redis/BullMQ -> worker
  -> private static controller -> Astro/SEO -> atomic Caddy activation
  -> durable receipt + независимый SQL acknowledgment -> SUCCEEDED
  -> legacy webhook/Coolify provider только в альтернативном режиме

PII retention scheduler в worker
  -> worker-only API -> serializable bounded delete в PostgreSQL
  -> cascade history/activity/delivery/tokens + orphan AddressCheck cleanup
```

FLOW 2 сначала сохраняет `AddressCheck`, затем показывает поле телефона только при подтверждённой доступности Дом.ру. FLOW 1 отдельно сохраняет консультацию оператору без адреса. DaData ищет адрес глобально: IPLocate даёт только мягкий КЛАДР-приоритет в HttpOnly-cookie, а город страницы остаётся source-контекстом. `POST /leads` атомарно сохраняет заявку и outbox, сразу возвращает подтверждение и ставит только sales-заявку в `lead-decisions`. Worker последовательно проверяет снимок причины/комментария, телефон через DaData Phone (`qc=0`), договор Дом.ру по профилю фактического города/региона и разрешает `lead-deliveries` только при явном `contacts: []`. Действующий абонент, ошибочная проверка телефона/договора и нецелевой coverage блокируют доставку. Минутный reconciler восстанавливает незавершённые решения. Browser с высокоэнтропийным `submissionKey` кратко опрашивает endpoint для некритичной 30-дневной персонализации действующего абонента; server-side routing этой отметке не доверяет.

Публичный layout собирает ограниченный маршрут текущей вкладки в `sessionStorage` и передает first/last touch в общем компоненте заявки. API проверяет вложенный DTO, очищает URL до разрешенных UTM, добавляет исходный User-Agent и IP только из серверного request и атомарно сохраняет один `Lead.attributionSnapshot`; поля не участвуют в решении о передаче. В Coolify цепочка Traefik → внутренний Caddy → Fastify очищает `X-Forwarded-For` до одного проверенного `{client_ip}` перед API. Hard-delete Lead удаляет снимок по общей 180-дневной policy.

В build-time `apps/web` вызывает `GET /public/sites/:siteSlug/cities` через server-only `SITE_DATA_API_URL` (с совместимым fallback на `PUBLIC_API_URL`). API возвращает `globalPages`, регион каждого города, контент опубликованных городов, тарифы, authoritative `routes` и `sitemap.excludedPaths`. Чистая policy-функция запрещает отсутствие/избыток общих страниц, неверный slug, дубли и коллизии; API требует ровно одну HOME с пустым slug и канонической последовательностью из двух блоков (первый экран и тарифы) у каждого опубликованного города. Web повторно сверяет route/block contract, проверяет каждое исключение против inventory и строит `/sitemap.xml` как индекс `sitemap-pages.xml`, `sitemap-cities.xml`, `sitemap-tariffs.xml`. Группа определяется типом route, а исключение не удаляет HTML и не меняет robots/canonical. Опубликованные service pages остаются данными без detail URL Release 1. Отдельный `PUBLIC_API_URL` встраивается в `data-*` browser-форм. `redirects.caddy` получает только правила с target из inventory; runtime resolver в Coolify использует exact обслуживаемый snapshot из доверенного serving context, а legacy provider — последний успешный SQL snapshot, перед HTTP 301 и hit tracking. Все HTML paths кроме `/` нормализуются без завершающего слэша. `PUBLIC_SITE_SLUG` по умолчанию `domru-site`; Казань остается городом, а не частью идентичности сайта. Любое изменение данных становится видимым только после успешной пересборки соответствующего снимка.

Телефоны подключения и техподдержки являются глобальными типизированными значениями `Site`. Раздел `/variables` изменяет только рабочую ревизию; publication snapshot фиксирует номера вместе с каталогом, а header, формы и result UI читают опубликованное значение. City телефонных копий больше не хранит. Публикация и initial build без обоих валидных номеров блокируются.

`variable-registry.ts` задает закрытый список системных кодов, тип, один источник, нужный контекст и операторское описание; `catalog-variables.ts` разрешает только редакционные текстовые поля после сборки рабочего каталога и до сохранения `SitePublication`. Глобальные Page получают Site/Provider, городские Page — также City, а Tariff — дополнительно собственный Tariff. Рабочий preview использует тот же путь; публичный каталог и Astro читают уже разрешенный неизменяемый снимок. Неизвестные коды, скобочная ошибка и подстановка в URL/служебные поля блокируют формирование каталога, а известное пустое или отсутствующий контекст дают пустую строку и предупреждение с путем к полю. Защищенный read-only каталог V2 сравнивает рабочие и опубликованные значения в выбранном городе/тарифе. Рабочие usage читаются также из черновых и скрытых строк; опубликованные usage и source evidence сохраняются в новых снимках. Публичный DTO удаляет эти операторские метаданные и исходные шаблоны. Исторический снимок без usage evidence остается явно неизвестным, до новой публикации его не пересчитывают из текущих строк.

## API-модули и их ответственность

SEO-поток: `SeoTemplate` хранит по одному Title/Description/index-state для восьми типов маршрута Release 1. API разрешает шаблоны по конкретным URL при построении рабочего каталога, блокирует пустые/неразрешённые значения и фиксирует `seoByPath` в неизменяемом publication snapshot. Astro берёт SEO из этого снимка; исторические записи `SitePublication` не переписываются, а локальные JSON Page/Tariff не используются. `NOINDEX` автоматически исключает URL из sitemap того же снимка, сохраняя HTML. Ручное sitemap-исключение само по себе не меняет robots.

CMS-поток городской HOME: `PageTemplate(CITY_HOME)` принадлежит Site и хранит общий редакционный заголовок и два видимых `PageTemplateBlock` (Hero и тарифы); City содержит факты и формы названия. `Page.templateId` временно связывает старую shell-запись с шаблоном для сохранения ссылок Lead/AddressCheck и маршрута. `SiteCatalogService` собирает эффективную HOME из шаблона, затем разрешает `{CITY_NAME_PREPOSITIONAL}` в контексте конкретного города. `SitePublication` сохраняет результат только по явной публикации рабочей ревизии. Защищённый PATCH общего шаблона создаёт `PAGE_TEMPLATE` revision/audit; прежний `/admin/pages` и mutators PageBlock не меняют городские HOME. Старые строки PageBlock сохраняются до C6, исторические снимки не меняются.

| `rebuild-queue` | Persistent rebuild/outbox, дедупликация по сайту, BullMQ producer, start/progress/result API, сохранение provider deployment UUID и фиксация только финального результата deployment. |
| `redirects` | Admin CRUD с архивированием, проверкой конфликтов/петель/цепочек, рабочими ревизиями без автоматической публикации, public resolver HTTP 301 и атомарным `hitCount`/`lastHitAt`. |
| `audit-events` | Read-only журнал одного сайта: bounded cursor-list с фильтрами и легким DTO, отдельная detail-загрузка field-level before/after, actor и site context. |
| `trash` | Bounded read-only агрегация архивных City/Page/Tariff/Redirect/PageBlock одного сайта; восстановление выполняют профильные versioned mutators, а блок использует guarded soft-delete/restore родительской Page. |

## Границы модулей

`apps/api` — единственный слой, который пишет доменные данные. Admin, worker и web не обращаются к PostgreSQL напрямую. `CoverageService`, `DomruContractService`, `LeadDeliveryService` и `NotificationsService` выступают адаптерами внешних интеграций; их URLs и ключи задаются окружением. Префикс `/crm/leads` сохранен только в HTTP-контракте API; отдельного CRM-приложения или домена больше нет.

`LeadDeliveryService`, `LeadNotificationOutboxService` и `RebuildQueueService` создают доменные очереди в API; worker владеет maintenance scheduler и вызывает защищенные внутренние endpoints. Только API пишет в PostgreSQL. Для обычного оповещения worker передает номер попытки и revision, а API отправляет сообщение и сохраняет outcome; для rebuild worker отдельно вызывает deployment provider и возвращает его success/error в API; для retention повторяет bounded batches до полного результата. `tariff-imports` остается listener без producer и не участвует в текущем import-flow.

## Модель публикации

Перед фиксацией нового или повторного снимка API в одной serializable-транзакции сохраняет `SitePublicationValidation`: точный исходный source snapshot, версию приложения, автора, рабочую ревизию, проверенные URL, адресные blocking/warning issues и итог. Блокирующий результат не создает `SitePublication` и не запускает rebuild; прежний public snapshot остается активным. Успешная публикация ссылается на свой отчет через `validationId`. Админка показывает последний отчет и позволяет скачать полный JSON; история доступна в защищенном API. Первый bootstrap проходит ту же проверку. Исторические публикации до миграции `0050` остаются без ссылки на отчет.

1. Сущности `Site`, `City`, `Page`, `Tariff` имеют статус `DRAFT`, `PUBLISHED` или `ARCHIVED`.
2. Public API возвращает опубликованные данные, но отдельно применяет release policy к URL.
3. Astro получает authoritative inventory и выпускает `N + T + 6` indexable HTML для `N` опубликованных городов и `T` опубликованных тарифов этих городов плюс общую 404. Страница тарифа создаётся только из route с `kind = CITY_TARIFF_DETAIL`; service pages остаются вне Release 1.
4. Ручные изменения cities/pages/blocks/tariffs/redirects и full-snapshot импорт тарифов сохраняют рабочую ревизию и before/after audit в одной транзакции; явные publication endpoints проверяют ожидаемый номер и фиксируют неизменяемый полный снимок для ручного запуска.
5. Общий `/publication` через read-only review показывает все сохранения и проверку URL; только актуальная успешная проверка разрешает явный запуск. Публикации по времени отсутствуют.
6. `SiteRebuild` получает ID именно этого снимка и ставит BullMQ job; изменения одного сайта дедуплицируются, но запрошенный и обрабатываемый snapshots не подменяют друг друга.
7. Worker получает попытку через internal API. В Coolify Compose он вызывает private static controller, строящий exact snapshot и атомарно переключающий Caddy без deployment приложений. Независимая сверка durable receipt и SQL snapshot подтверждает `publishedRevision` транзакционно. Прямой prod Compose сохраняет legacy external provider.

Статус rebuild доступен через admin API. Компактный publication state возвращает рабочую/опубликованную ревизии, последний snapshot, rebuild и фильтрованный `progress`, исключая raw provider response. События реальных этапов/счётчиков сохраняются в существующем JSON по publication/revision/runId и монотонному sequence через CAS; telemetry не влияет на activation authority. ETA использует минимум три успешных запуска того же renderer с числом страниц в пределах ±20%, исключает recovery и ожидание CODE. Карточки редакторов ведут на общий `/publication`; запуск требует актуального review той же ревизии. Runtime после deployment автоматически выполняет CODE для обслуживаемого snapshot по `SOURCE_COMMIT`; проверяет latest exact finished/healthy до и после сборки и продолжает ожидающую CMS job. Защищённый preview строит рабочий catalog без записи snapshot. Внешняя static CODE/CMS-приёмка завершена, #238 закрыта ([доказательства](research/2026-10-06-static-publication-live-acceptance.md)). Guarded undo реализован для новых change set тарифного и городского импортов; корзина объединяет status-архивы и мягко удаленные PageBlock.

## Что не является частью текущей реализации

- Одновременная эксплуатационная публикация нескольких сайтов: route policy поддерживает любое число опубликованных городов одного выбранного сайта, но импорт пока односайтовый. Общие страницы одного сайта включены в датированный live inventory из `current-state.md`.
- SSR и runtime data fetching на публичных SEO-страницах.
- Полная CMS с глубоким наследованием блоков и восстановлением произвольной версии; immutable revisions, личный preview рабочей версии, audit, ручная общая публикация, общий read-only журнал и корзина уже есть.
- Универсальный undo остальных массовых операций и аналитический контур; для двух XLSX-импортов реализован guarded undo, а для ручного удаления — архив и восстановление в новую рабочую ревизию.
- Сертифицированный production-контур с реальным трафиком: внешний защищенный test deployment и sandbox/test-контракты уже подтверждены, но успешный test deployment сам по себе не означает допуск реального трафика. Только владелец определяет готовность к реальному трафику. Дополнительная legal-проверка #144 имеет P3, вне milestone Release 1 и не является gate.

Детальный статус находится в [current-state.md](current-state.md). Стабилизационный план прототипа сохранен в [плане от 7 сентября](archive/plans/2026-09-07-platform-stabilization-and-mvp.md), целевая модель — в [product-contract.md](product-contract.md), а переход к ней — в [плане от 21 сентября](plans/2026-09-21-target-platform-implementation-plan.md).

## Общая оболочка админки

Рабочие разделы админки используют общий сохраняемый AdminWorkspace React-root. Меню, шапка и publication polling сохраняются, экраны монтируются заново по pathname/query; код выбранного раздела предварительно загружается по hover/focus ссылки. Совпадающие одновременные GET объединяются. Для быстрого возврата списки городов/тарифов, справочники, паспорта и read-only каталог подстановок используют ограниченный кэш в памяти сессии (до 30 секунд, до 32 ответов) с обязательной проверкой в фоне и явным состоянием обновления. Доступ проверяется на сервере при каждом запросе; смена пользователя/logout/401 сбрасывают данные. Любая мутация сбрасывает кэш при начале и завершении, завершение публикации — при смене publishedRevision. Поздние ответы прежнего поколения не восстанавливают кэш. Редакторы получают свежие данные и сохраняют expectedWorkingRevision; городская форма фиксирует ревизию прочитанной строки при открытии и недоступна до завершения проверки каталога. Несохранённые формы защищены при внутренних переходах и Back/Forward. `/preview`, login и lead-access сохраняют отдельные документы. [Измерения и границы проверки](research/2026-10-08-admin-navigation-cache.md).

Early history bridge регистрируется до Astro router: window popstate listeners на самом target выполняются в порядке регистрации. При отмене Back/Forward editor останавливает router и восстанавливает history index до выбора пользователя. Полная перезагрузка сохраняет beforeunload.

GET sites?summary=true исключает provider/regions/cities graph. GET sites/values объединяет выбор сайта и чтение телефонов. Variable-catalog читает serializable typed context без рендера Page/SEO/блоков: опубликованные города и ACTIVE/PUBLISHED тарифы только выбранного города. Authoritative usage scan проверяет ту же workingRevision; published evidence читается из прежнего immutable snapshot. UNKNOWN/null сохраняются.

### Тарифный блок и переход композиции 2.0.0
