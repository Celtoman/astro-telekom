# Дизайн-система админки

Зафиксировано: 7 сентября 2026 года. Это обязательный источник истины для интерфейса `apps/admin` — не рекомендация, а жёсткое ограничение.

## Правило

Интерфейс `apps/admin` строится на обязательной дизайн-системе, источником которой служат:

- Репозиторий: [github.com/arhamkhnz/next-shadcn-admin-dashboard](https://github.com/arhamkhnz/next-shadcn-admin-dashboard)
- Живой пример: [next-shadcn-admin-dashboard.vercel.app/dashboard/default](https://next-shadcn-admin-dashboard.vercel.app/dashboard/default)

Это Next.js (App Router) + shadcn/ui + Radix UI + Tailwind CSS. Референс обязателен для layout, визуального языка, состояний и готовых UI-паттернов; он не требует превращать `apps/admin` в Next.js-приложение или буквально копировать неподходящий код.

Если в референсе есть подходящий компонент или блок, его код переносят обычным для shadcn/ui способом: копированием в проект и адаптацией к нашим данным и API. Next.js-специфичные части, включая `next/link`, `next/navigation`, Server Components и серверную загрузку данных, не переносятся как есть. Если прямого блока нет, экран собирают из совместимых shadcn/ui-примитивов в стилистике референса. Новый компонент допустим только при документированном отсутствии подходящего паттерна; он не должен создавать параллельную дизайн-систему на ad-hoc CSS.

## Что это означает технически

Целевая архитектура — Astro как static-оболочка и маршрутизация, React-root для каждой интерактивной страницы или крупного раздела, Tailwind и shadcn/ui внутри React. Данные админка получает и изменяет во время работы через HTTP API; она не зависит от данных, зафиксированных во время `astro build`.

`apps/admin` сейчас — Astro 7 static output без React, без Tailwind, без какой-либо компонентной библиотеки (`apps/admin/src/pages/index.astro`, один файл, ~200 строк plain HTML/CSS/vanilla JS). Чтобы перейти к целевой архитектуре, необходимо:

1. Добавить в `apps/admin` React-интеграцию Astro (`@astrojs/react`), чтобы рендерить перенесённые компоненты как React-острова внутри static output.
2. Добавить Tailwind CSS в `apps/admin` (shadcn/ui-компоненты написаны на Tailwind-классах и Radix-примитивах; без Tailwind они не будут работать как задумано).
3. Переносить подходящие компоненты и паттерны из референса либо собирать отсутствующие экраны из shadcn/ui-примитивов в его визуальном языке; получать данные только через существующий HTTP API.

Ни один из этих трёх пунктов пока не сделан — на дату фиксации правило описывает **обязательное направление будущей работы**, а не текущее состояние стека.

## Область действия

Правило касается только `apps/admin`. `apps/web` (публичная витрина) и `apps/crm` (журнал заявок) им не связаны — для них ограничения на дизайн-систему нет.

## Текущий `index.astro` — legacy, не образец

`apps/admin/src/pages/index.astro` написан до этого правила: plain HTML/CSS, никакой компонентной библиотеки, весь интерактив — inline `<script>` с vanilla JS и `document.querySelector`. Это демонстрационный UI (см. [technical-debt.md](technical-debt.md), TD-08) — **не расширять его новыми фичами в старом стиле**. Реальная миграция экрана на React + shadcn/ui — предмет отдельной задачи, не выполняется по ходу текущей работы автоматически.

## DoD-чек для любой новой/переработанной части admin UI

Перед завершением задачи по `apps/admin`:

1. Использован ли подходящий компонент или паттерн из `next-shadcn-admin-dashboard`? Если нет — зафиксировано ли, почему он не подходит или отсутствует?
2. Если готового блока для конкретного экрана нет — собран ли он из существующих shadcn/ui-примитивов (Button, Table, Sidebar, Card, Dialog и т.д.) в стилистике референса, а не с нуля на голом CSS?
3. Соответствует ли визуально макет живому демо (layout, отступы, типографика, состояния — default/hover/focus/disabled, где применимо)?
4. Проверена ли тёмная тема, если референс её поддерживает для затронутого экрана?
5. Не добавлен ли ad-hoc CSS/HTML в стиле старого `index.astro`, создающий параллельный UI-паттерн?
6. Получает ли интерактивный экран данные через API во время работы и проверяет ли API доступ пользователя независимо от того, что скрыто в интерфейсе?
