# План релизов и порядок работы

Актуализировано 7 ноября 2026. Реализация описана в [current-state.md](current-state.md), целевой продукт — в [product-contract.md](product-contract.md), механические статусы — в [GitHub Issues](https://github.com/Celtoman/astro-telekom/issues). Этот документ задаёт границы и правила выбора работы; он не дублирует чек-листы issues и не является разрешением на реализацию.

## Действующий порядок работы

Технический выпуск кода во внешний контур выполняется через GHCR. Правила для коммита, push, exact-SHA CI, образов, Coolify и отката описаны в [runbook выпуска](runbooks/ghcr-release.md). `pnpm release` оформляет версию проекта. Публикация контента из CMS и допуск трафика требуют отдельных решений владельца.

Следующую задачу определяет владелец. **Работа по страницам начинается только по его отдельным поручениям**: наличие страницы в согласованной структуре, плане #348 или Figma не назначает её в реализацию. Очередь от 7 октября больше не описывает актуальную работу.

## Release 0 — историческая граница локального прототипа

Исходная база — monorepo, API, PostgreSQL/Redis, импорты, static web/admin, заявки и worker — реализована. После неё уже появились шаблоны страниц, рабочие ревизии, audit, guarded undo, корзина, preview и immutable публикации. Поэтому прежние этапы Release 0/2/3 нельзя читать как линейный список полностью отсутствующих функций.

## Release 1 — минимальный публичный запуск

Историческая цель — один реальный партнёрский сайт Дом.ру с достоверным статическим HTML опубликованных городов/тарифов, наблюдаемой публикацией и проверенным путём заявки. Казань — контрольный пример, а не отдельное правило маршрутизации.

Первоначальный минимальный inventory `N + T + 6` включал корень, городские HOME, tariff detail и пять обязательных общих страниц; 404 и системные endpoints учитывались отдельно. Позднее отдельно внедрены ADDRESS, ACCOUNT и новости. Их наличие не переписывает задним числом состав старых immutable snapshots и не подтверждает автоматическое включение всего целевого сайта в первый релиз. Текущая модель маршрутов — в [current-state.md](current-state.md), целевые URL — в [site-structure.md](site-structure.md).

Ранее принятые критерии минимального запуска сохраняются по смыслу:

1. HTML, sitemap и redirects соответствуют точному inventory конкретного снимка; неизвестные URL возвращают 404, коллизии блокируются.
2. Все обязательные автоматические проверки проходят в чистом окружении; production build требует живые API-данные, корректный HTTPS origin и успешный SEO gate. Demo допускается только явно для локальных/CI-проверок.
3. Full-snapshot импорт имеет согласованную семантику и не оставляет устаревшие публичные предложения; review и ручная публикация сохраняют достоверные данные; rebuild/progress/receipt/SQL status показывают фактический результат и поддерживают восстановление.
4. Админский доступ и fallback-доступ защищены; обычная форма и видимая проверка подключения разделены. Delivery следует проверенным контрактам DaData/Tarifnik/Дом.ру, обязательным проверкам провайдеров и однозначной трактовке `contacts: []`. Наличие credentials не заменяет sandbox/live-доказательство интеграции.
5. Срок хранения сырых заявок 180 дней согласован; purge выполняется по валидной policy. Перед соответствующим реальным выпуском `TARIFNIK_UTM_CAMPAIGN` должен иметь подтверждённое владельцем production-значение; агент не меняет его без отдельного решения.

Это критерии и ссылки на доказательства, а не новый вердикт «релиз готов». Состав и open/closed — в [milestone Release 1](https://github.com/Celtoman/astro-telekom/milestone/1); конкретные ограничения — в issues и [TEST_COVERAGE.md](TEST_COVERAGE.md).

## Внешние зависимости и решение о трафике

Технический sandbox-путь заявки и email ранее подтверждался [синтетической приёмкой](research/2026-09-25-release-one-synthetic-lead-acceptance.md). Текущие рабочие credentials, production campaign, состав данных и приемлемость ограничений определяются для конкретного выпуска; историческая успешная отправка не подтверждает их неизменность.

Дополнительная перепроверка legal basis/оператора в [#144](https://github.com/Celtoman/astro-telekom/issues/144) оставлена владельцем как P3 вне milestone Release 1 и не является автоматическим условием решения о трафике. Собственные технические требования к согласию, доступу и retention сохраняются.

Общая задача встроенного PostgreSQL backup/restore [#145](https://github.com/Celtoman/astro-telekom/issues/145) отменена владельцем в пользу внешнего решения. Это не отменяет реализованные scoped редакционные backup/restore и архивирование публикационных артефактов; их контракты — в [editorial backup runbook](runbooks/editorial-backup.md) и [publication retention runbook](runbooks/publication-retention.md).
