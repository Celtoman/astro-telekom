Private Node controller нового отдельного Docker target `publication-runtime` имеет машинно защищённые `GET /active`, `GET /renderer`, `POST /publish`, `GET /receipts/:rebuildId/:revision` и отдельный `POST /release-code`. Они не являются публичными Nest routes и подключены только к внутренней сети Coolify Compose; внешний rollout и две ручные CMS-публикации без redeploy подтверждены в [датированной приёмке](research/2026-10-06-static-publication-live-acceptance.md). Это защищённый test-контур; private endpoints наружу не опубликованы. `/renderer` возвращает hash выпущенных исходников/окружения и nonce экземпляра. CODE принимает только deploymentId, exact expectedCommit, rendererId и instanceId: latest deployment обязан быть finished на этом SHA, настроенный ресурс — running:healthy; проверка повторяется после build. CODE сохраняет фактически обслуживаемые publication ID/revision/hash, durable intent и receipt переживают restart; stale nonce/чужой snapshot отклоняются. Незавершённый CMS intent задерживает CODE; cancelled/failed exact snapshot не активируется. Новый CMS job при renderer mismatch получает HTTP 202 UNCERTAIN до выпуска кода. Контроллер ограничивает JSON, закрыт machine token и не принимает команды/пути/activation kind от CMS. Caddy control API остаётся на loopback.

Для static provider API независимо подтверждает receipt у private controller по exact rebuild ID/revision и сверяет его со снимком в SQL. Rebuild, SitePublication и Site.publishedRevision подтверждаются одной serializable-транзакцией; сбой обновления публикации откатывает rebuild success. Восстановление незавершённой QUEUED/RUNNING/RETRYING job удерживает processing snapshot, даже если requested snapshot уже новее. Этот контракт закреплён в Coolify Compose; прямой prod Compose сохраняет прежний provider. Внешняя static-приёмка зафиксирована в [доказательствах 6 октября](research/2026-10-06-static-publication-live-acceptance.md).

Архивная retention добавляет private `GET /retention/plan`, `POST /retention/archive`, `POST /retention/collect` и `POST /retention/restore`. Все требуют тот же machine token и общую очередь с CMS/CODE; public Nest routes не добавляются. Archive принимает только идентификаторы, checksum, размер и подтверждение S3 readback/restore; collect/restore — только artifactId. Collect защищает serving/baseline/две rollback/семь суток/незавершённые операции, удаляет только HTML после полного проверенного архива, сохраняет assets/metadata/receipts. Restore проверяет полное staged дерево и закрепляет его без переключения serving. Исторический receipt архивной версии проверяется по immutable metadata и GC/archive record; activation требует полного release. [Операционный контракт](runbooks/publication-retention.md).

При `REBUILD_PROVIDER=static` глобальный interceptor принимает `X-Site-Publication-Id` только вместе с proxy token — HMAC-SHA256 от `ADMIN_API_TOKEN` с фиксированным сообщением `serving-publication:v1`. Машинный token сам по себе не служит таким подтверждением. Caddy должен заменять оба клиентских заголовка. Контекст изолирован между запросами через AsyncLocalStorage. Без доверенного контекста API читает приватный `${STATIC_PUBLICATION_URL}/active`, передавая machine token, и проверяет site ID/slug/revision/catalog digest по exact SQL publication. Допустим уже обслуживаемый RUNNING снимок до завершения SQL acknowledgment; недоступный controller, чужой или несовпадающий снимок дают ошибку без SQL latest fallback. Каталог/quote/redirects и новые address/lead запросы используют этот снимок, а не текущие working-статусы. Запись AddressCheck/Lead остаётся через API и реальные FK; сохранённые результаты и submission-key replay сохраняют существующий контракт. Локальный сквозной SQL/HTTP/Caddy rehearsal проверяет этот контракт и восстановление acknowledgment; внешний rollout и приёмка остаются в #238; wiring включён в Coolify Compose.

Базовый prefix: `/api/v1`. Сверка маршрутов и ограничений: 6 октября 2026 года, по controllers/module. Private publication controller имеет собственный контракт в [publication.md](publication.md).

## Общие правила

- API работает на NestJS/Fastify и принимает JSON; server body limit — 35 MB.
- Browser CORS использует credentialed requests для `ADMIN_URL` и явно разрешает методы `GET`, `HEAD`, `POST`, `PATCH`, `DELETE`, `OPTIONS`. Не полагаться на default methods Fastify CORS: без явного списка browser preflight блокирует существующие admin mutation routes.
- `POST /auth/login` создает 12-часовую сессию и возвращает только expiry и пользователя; raw token передается браузеру исключительно в `HttpOnly`, `SameSite=Strict` cookie `admin_session`. В PostgreSQL хранится SHA-256 hash.
- Защищенные административные маршруты принимают cookie-сессию или совместимый `Authorization: Bearer <token>`. `x-admin-token`, совпадающий с `ADMIN_API_TOKEN`, предназначен для машинного сценария; `/internal/*` принимает только его и отклоняет пользовательские сессии.
- У пользовательского доступа один уровень — администратор. Любой активный пользователь с действующей сессией имеет одинаковый полный доступ ко всем административным routes, включая `/crm/leads`; ролевой модели нет.
- Глобальный `ValidationPipe` преобразует DTO, не допускает лишние поля (`forbidNonWhitelisted`) и не возвращает значения в validation errors. Строгими class-based DTO покрыты login, `address-checks`, `leads` и `lead-access`; часть admin CRUD пока сохраняет ручную валидацию.
- Глобальный Redis-backed rate limiter по IP возвращает `429`, но хранит отдельные счетчики по назначению route: по умолчанию 5 login-запросов, 60 запросов подсказок, по 10 запросов проверки адреса, создания заявки и lead-access, а также 300 остальных запросов за 60 секунд. Значения настраиваются `RATE_LIMIT_*`; query string не создает новый bucket, а один API-route не расходует лимит другого. При ошибке Redis limiter не пропускает запрос. Production Compose включает `TRUST_PROXY=true`, поскольку API доступен только через Caddy.

### `POST /address-suggestions`

Тело: обязательный `query`; опциональны `siteSlug`, `citySlug` и пустой honeypot `website`. API принимает только published site/city как проверенный контекст страницы, ограничивает query официальным максимумом 300 символов и передает в DaData глобальный запрос с `count: 5`. Первый запрос без валидной `address_city_kladr` cookie вызывает серверный IPLocate по `request.ip`; API сохраняет на 24 часа только 13-значный КЛАДР-код либо `none` в HttpOnly/SameSite=Lax cookie. Полученный код передается исключительно в `locations_boost`; IP и определенная география не сохраняются в БД/Redis/заявке. При ошибке, таймауте, локальном IP или `location: null` используется мягкий boost `{ region, city }` опубликованной страницы. Параметр `locations` не передается, поэтому пользователь может выбрать адрес любого города. Валидный ответ без совпадений возвращает пустой список; настоящий HTTP/сетевой сбой или невалидный ответ `suggest/address` возвращает `503`, а сбой IPLocate не меняет успешность подсказок. Собственный rate limit API возвращает `429` с `Retry-After`.

### `POST /address-checks`

Тело: обязательны `address` и структурированная `suggestion` с `value`, `unrestricted_value`, `data`; опциональны `siteSlug`, `citySlug`, `pageSlug`, `objectType`. Отсутствующий `pageSlug` не отправляется: пустая строка не является slug и строго отклоняется. Поля ограничены по типу и длине, неизвестные поля возвращают 400. Публичная форма также отправляет пустое honeypot-поле `website`; непустое значение отклоняется до БД и внешних интеграций. После `clean/address` требуется непустой `data.house`: адрес без номера дома возвращает HTTP 422, не вызывает Tarifnik и не создает `AddressCheck`.

Перед Tarifnik API выбранная подсказка проходит серверный DaData `clean/address`; результат преобразуется в тот же envelope, что в рабочем боте: `value=source`, `unrestricted_value=source`, `data=<clean result>`. География нормализованного адреса не сравнивается с городом страницы: `citySlug` определяет опубликованный контекст и источник обращения, а Tarifnik получает фактический адрес пользователя. `POST /address/check` получает ровно `{ suggestion }` с Bearer token. HTTP 200 обязан содержать непустой словарь `providerId: providerName`; HTTP 404 — однозначный пустой список провайдеров; 403/422, сеть, невалидный JSON или неверная структура дают внутренний `ERROR`. Без полного DaData/Tarifnik набора переменных либо без нормализованной подсказки внутренний статус будет `MANUAL_CHECK`; ни один из этих исходов не интерпретируется как разрешение delivery.

Публичный ответ является discriminated union и не раскрывает внутренние coverage-статусы. Бизнес-ветка имеет `type: "business"`, `checkId`, `address`, `citySlug` и ровно один из трех `outcome`: `TARGET_AVAILABLE`, `ALTERNATIVES_AVAILABLE`, `NO_PROVIDERS`. Только `ALTERNATIVES_AVAILABLE` дополнительно содержит безопасный список `providers: [{ id, name }]` и единый `actionUrl` на Tarifnik. `AMBIGUOUS`, `MANUAL_CHECK`, `ERROR`, сетевой сбой клиента или невалидный ответ не становятся четвертым бизнес-исходом: API/клиент показывают отдельный восстановимый `type: "technical_error"` с `retryable: true`, кодом и безопасным сообщением.

В persisted snapshot раздельно сохраняются `providers`, `targetProviderId`, `hasAnyProvider` и `hasTargetProvider`. Наличие хотя бы одного провайдера запускает проверку действующего абонента независимо от наличия Дом.ру, но delivery дополнительно требует присутствия Дом.ру. Публичные embedded/modal entry points используют один client state machine: собственный autocomplete блокирует проверку до выбора подсказки с домом, ручное изменение сбрасывает подтверждение, а generation token и `AbortController` не дают позднему ответу заменить более новое состояние. Городская HOME сохраняет встроенную форму; tariff/service CTA и карточки городов на карте покрытия открывают общий native dialog. Карточка карты передает выбранный `citySlug` в тот же компонент без дублирования формы на каждый город. Три business outcomes открываются в доступном native dialog; technical error имеет отдельные действия повторения и изменения адреса.

### `POST /leads`

Новая browser-форма передаёт ограниченный `session` с `firstTouch`/`lastTouch` (URL, referrer, allowlisted UTM), ISO-временем начала и максимум 50 уникальными путями текущей вкладки. `sessionStorage` не связывает вкладки и сеансы; URL очищается от fragment, credentials и всех query-параметров кроме разрешённых UTM. DTO ограничивает снимок 20 KB, запрещает неизвестные вложенные поля, а сервер сохраняет единый `attributionSnapshot` версии 1 вместе с лидом: начало/отправку, маршрут, код формы, длительность, вычисленный тип устройства, исходный User-Agent и IP из Fastify `request.ip`. IP и User-Agent не принимаются из JSON-тела и не участвуют в маршрутизации. Для старого клиента без `session` создаётся помеченный `api_fallback` с доступными legacy-полями; исторические лиды до миграции `0051` сохраняют `null`. Прежние `utm`, `referrer`, `pageUrl`, `viewedPages`, `timeOnSiteSeconds` и `deviceType` заполняются из того же нормализованного снимка для совместимости.

Обязательны `phone`, `citySlug`, UUID `submissionKey` и точная техническая версия текста согласия `consentVersion=lead-form-v1-2026-09-22`. Для автоматического sales-пути обязателен `addressCheckId` с положительным снимком. Необязательный `reasonCode` принимает только пять кодов закрытого справочника: `callback_consultation`, `new_connection`, `existing_subscriber_support`, `billing`, `relocation`, `other`; Домофон не допускается. Код, русская подпись, маршрут и версия справочника сохраняются сервером в неизменяемом снимке. Текущая адресная форма явно передает `new_connection`; старый запрос без причины остается совместимым. `new_connection` идет по прежнему sales-пути, `existing_subscriber_support` и `billing` сохраняются без sales-проверок и Tarifnik, `relocation` и `other` направляются на ручное решение. Для этих несбытовых/ручных веток положительный `addressCheckId` не требуется. Read-only `GET /crm/leads/reasons` возвращает справочник для фильтра админки; `GET /crm/leads` принимает `reasonCode` из справочника либо `NONE` для исторических записей без снимка.

Необязательный пользовательский `comment` — строка до 2 000 символов; сервер сохраняет trimmed исходный текст. Правила анализа версии 1 распознают шесть ограниченных категорий по целым словам и фразам с границами и отрицаниями, сохраняют результат, категорию, точные фрагменты с позициями и объяснение в nullable полях `Lead`. Комментарий сам по себе не отклоняет заявку: противоречие причине или несбытовой сигнал без причины дает `MANUAL_CHECK` до проверки абонента и передачи; жалоба при совпадающей несбытовой причине дает предупреждение. Отсутствующий комментарий не анализируется, история автоматически не переоценивается при изменении правил. Админка показывает исходный комментарий, снимок анализа, фрагменты и версию.

Телефон принимает только полный российский мобильный номер: `+7`/`7`/внутрироссийская `8` и затем `9` плюс еще девять цифр; десятизначная национальная запись обязана начинаться с `9`. Значение сохраняется только как `79XXXXXXXXX`; неполный номер, не-мобильный префикс и международная запись `+8` возвращают 400. `submissionKey` создается один раз для показанного положительного результата FLOW 2 либо отправки консультации FLOW 1 и повторно используется при сетевом retry. Существующий лид ищется до проверки текущего каталога: тот же ключ с теми же site/city/check/page/tariff/service/phone/reason/comment, адресом и отпечатком расчёта возвращает ранее созданный результат без нового notification/delivery даже после архивации рабочей страницы/тарифа или смены публикации. Повторное использование с другим контекстом отклоняется; новая заявка по устаревшему тарифному расчёту по-прежнему требует актуального опубликованного snapshot. Также допускаются slug страницы/тарифа, контакты, адрес, service type, UTM, referrer, URL, form name, time on site, device, до 50 viewed pages и до 100 activity events. Браузерные numeric IDs и неизвестные поля не принимаются: API разрешает только slug. UTM допускает только стандартные `utm_id`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `utm_source_platform`, `utm_creative_format` и `utm_marketing_tactic` со строками до 256 символов. `viewedPages` ограничен 16 KB JSON, весь `activity` — 64 KB, а `activity[].data` — 4 KB, 20 ключами, короткими безопасными именами, строками до 500 символов и не более одним уровнем вложенных containers. Непустое honeypot-поле `website` отклоняется до сохранения.

`citySlug` и сохраняемый `Lead.cityId` обозначают город страницы-источника, а не обязаны совпадать с географией адреса подключения. Для sales-пути фактический нормализованный адрес и DaData city/settlement/region берутся только из связанного persisted snapshot; check обязан принадлежать тому же сайту и контексту страницы, иметь статус `AVAILABLE` и `hasTargetProvider=true`. Отсутствующая, техническая, альтернативная либо пустая проверка отклоняется до contract check и создания sales-лида. Несбытовая/ручная ветка сохраняется без address check и не вызывает проверку абонента или доставку; обычное оповещение оператора сохраняется.

Для тарифной заявки форма передаёт `configuration: { selection: { router, tvbox, services }, fingerprint }` из опубликованного quote. Сервер повторно считает комбинацию по последнему `SUCCEEDED` каталогу, сравнивает отпечаток и отклоняет устаревшую цену или недопустимый вариант до создания лида. Выбранный опубликованный тариф определяется по снимку, даже если его рабочая строка уже архивирована; связь остаётся с тем же `tariffId` и городом. В `Lead.configurationSnapshot` фиксируются выбор, названия и коды компонентов, все строки цен, итоги и время; админка показывает этот снимок прежде текущей изменяемой строки тарифа. Повтор `submissionKey` требует того же отпечатка, не создавая второй лид. Старые клиенты без `configuration` и исторические лиды с `null` остаются совместимыми.

Контроллер сначала ищет совпадение нормализованного телефона среди лидов того же сайта за последние 24 часа. Только если телефон не совпал, он сопоставляет нормализованный адрес при явно сохраненном одинаковом номере квартиры или комнаты в обеих DaData-подсказках; совпадение одного дома не подавляет новую заявку. Выбранный ID и причина дубликата фиксируются в событии решения. Новая sales-заявка сначала сохраняется как `DECISION_PENDING` и сразу возвращает подтверждение. Фоновая очередь последовательно выполняет проверку DaData Phone, проверку договора и решение о передаче. Дополнительные состояния: `DECISION_RUNNING`, `PHONE_CHECK_RETRY`, `PHONE_CHECK_FAILED`, `PHONE_INVALID_NOT_SENT`; только `qc=0` и совпадающий номер позволяют продолжить. Технические ошибки повторяются через 5 и 30 минут; финальный ответ кешируется на 24 часа. В `PENDING` для доставки заявка переходит только после отрицательной проверки договора. Также сохраняются `DELIVERED`, `DUPLICATE_SUPPRESSED`, `ACTIVE_SUBSCRIBER_NOT_SENT`, `PROVIDER_NOT_AVAILABLE_NOT_SENT`, `NO_PROVIDERS_NOT_SENT`, `NON_SALES_NOT_SENT`, `MANUAL_CHECK`, `ADDRESS_CLARIFICATION`, `MANUAL_CHECK_API` и delivery-error статусы. Сбой постановки decision job оставляет persisted pending для минутного восстановления; сбой постановки delivery job фиксирует failed attempt канала `QUEUE` и `DELIVERY_QUEUE_ERROR`.

Проверка действующего абонента использует фактическую схему рабочего бота: общий публичный endpoint Дом.ру `contract-asterisked`, телефон `7XXXXXXXXXX` в query-параметре `contact`, `isActive=1` и городской профиль `origin/providerid/referer`. Профиль выбирается по нормализованным DaData городу и региону из встроенного UTF-8 справочника: 555 исходных строк, 551 уникальная пара «регион + населенный пункт» и 37 явных региональных fallback-профилей. В окружении требуется только `DOMRU_CONTRACT_API_URL`; отдельного API key нет. Неопределенный город или отсутствующий профиль дает `NOT_CONFIGURED`.

Только валидный JSON с явно присутствующим `contacts: []` означает `NOT_FOUND` и разрешает дальнейшее решение о delivery. Непустой массив означает `ACTIVE`. HTML, пустое тело, невалидный JSON, отсутствие массива `contacts`, неверный телефон, HTTP- или сетевая ошибка дают `ERROR`; лид остается на ручной проверке через `MANUAL_CHECK_API`, и автоматическая передача в Tarifnik не запускается.

Worker повторно проверяет persisted coverage snapshot и однозначный `contractResult.status=NOT_FOUND`/`active=false` перед внешним вызовом. До обращения в Tarifnik атомарно записываются `DELIVERY_API_OUTCOME_UNKNOWN` и API-попытка `OUTCOME_UNKNOWN`; если запись не удалась, внешний вызов не выполняется. Подтвержденный ответ `created | created_duplicate` вместе с `appeal_id` переводит лид и попытку в успешные состояния одной транзакцией. Если после принятого ответа транзакция не удалась, неопределенный статус остается для оператора: автоматические retry и fallback не запускаются. Административный retry разрешен после ошибки очереди, после исчерпанной доставки либо для старого orphan `PENDING` без единой API-попытки; ручные/ошибочные решения coverage или проверки абонента обойти нельзя. Перед email/webhook fallback записывается `DELIVERY_EMAIL_OUTCOME_UNKNOWN`; сбой записи блокирует внешний вызов, сбой после принятого письма оставляет видимый неопределённый статус и не вызывает автоматическую переотправку. Для любого неопределенного исхода и старого orphan `PENDING` после терминальной API-ошибки `POST /crm/leads/:id/retry-delivery` требует тело `{ "confirmUnknownOutcome": true }` и двухминутную паузу с последнего изменения заявки: оператор сначала проверяет внешний канал, потому что повтор может создать дубль. Новый ручной цикл начинается со следующего свободного глобального номера API-attempt, но получает собственный retry budget. Официальный `appeal/create` payload содержит только `utm_campaign` из runtime-конфигурации, нормализованный `phone`, допустимый `belong_type`, исходный нормализованный `suggestion` и опциональное имя. HTTP 200 считается успехом только при `result: created | created_duplicate` и непустом `appeal_id`. Автоматические повторы через 5 и 30 минут выполняются только для сети/таймаута, HTTP 408, 425, 429 и 5xx; `Retry-After` для 429 учитывает верхнюю границу 24 часа. Постоянный 4xx, невалидный JSON или неожиданный 2xx сразу переводят доставку в email/webhook fallback.

FLOW 2 сначала создаёт AddressCheck без телефона; только результат с Дом.ру открывает телефон и явное согласие consentAccepted: true. Комментария в этом сценарии нет. Поля блокируются во время отправки, ошибочный ответ сохраняет форму для retry с тем же submissionKey. Альтернативы ведут на Tarifnik, отсутствие предложений позволяет изменить адрес; телефон не собирается. Юридические документы открываются внутри той же модалки с возвратом к форме. FLOW 1 использует POST /leads с reasonCode: callback_consultation, обязательными phone, consentAccepted: true, consentVersion и submissionKey; citySlug необязателен только для этой причины, comment необязателен. Передавать для консультации address/addressCheckId, tariffSlug/configuration, pageSlug, objectType или serviceType запрещено. Сервер сохраняет MANUAL_CHECK, SKIPPED для проверки телефона и один notification outbox; фоновые sales-проверки и автоматическая доставка не запускаются. Городская форма передаёт свой опубликованный citySlug, общая главная оставляет его отсутствующим.

`POST /leads` теперь возвращает `subscriberMode: false`, поскольку договор проверяется после ответа формы. Browser до 30 секунд опрашивает `POST /leads/:id/decision-status` с UUID `submissionKey` в JSON-теле; ответ содержит только `complete` и `subscriberMode`, без PII и внутренних результатов проверок. `subscriberMode: true` возможен лишь после persisted-решения `ACTIVE_SUBSCRIBER_NOT_SENT` и включает некритичную UI-персонализацию. Это не credential: API не принимает browser-флаг в решении о доставке.

Общая программная `TariffView` (не новое поле HTTP catalog) содержит числовое `tvChannelsTotal: number | null`: для `INTERNET_TV` используется уже проверенный `tv_channels_total`, для `INTERNET` — `null`. Городской Hero агрегирует цену, скорость и каналы только доступных предложений; форматированный `baseComponents[].value` не парсится обратно в число.

Системные подстановки V1 обрабатываются сервером при построении рабочего каталога и фиксации `SitePublication`, а не при публичном чтении. Реестр закрыт кодами `{CONNECTION_PHONE}`, `{SUPPORT_PHONE}`, `{PROVIDER_NAME}`, `{CITY_NAME}`, `{CITY_NAME_GENITIVE}`, `{CITY_NAME_PREPOSITIONAL}`, `{TARIFF_NAME}`, `{TARIFF_SPEED}`, `{TARIFF_PRICE}`, `{TARIFF_CHANNELS}`, `{YEAR}`. Источники соответственно: два поля Site, `Provider.name`, три формы City, имя/скорость/эффективная цена (`promoPrice ?? standardPrice`)/`attributes.tv_channels_total` тарифа и UTC-год фиксации каталога. Числа выдаются без единиц, телефоны форматируются; подстановки допускаются только в редакционных полях Page title/content.text/SEO title/description, текстовых полях PageBlock и Tariff promoText/SEO title/description. Неизвестный или некорректный код блокирует каталог и публикацию; известное пустое значение или отсутствие City/Tariff-контекста удаляет только код и добавляет `variableWarnings` с `code`, `path`, `reason`. В URL, slug, идентификаторы и другие служебные поля подстановка запрещена; вложенные коды, HTML и URL-интерполяция также отклоняются. ### Контракт `PageBlock`

Корневой объект допускает только `blockType`, `position`, `visible`, `data`, `source`. При создании обязательны `blockType`, неотрицательный целый `position` до `2147483647` и объект `data`; `visible`, если передан, должен быть boolean, а `source` — `null` либо непустая строка до 200 символов без HTML-разметки. Неизвестные корневые поля отклоняются. Строки внутри `data` должны быть непустыми после trim и не могут содержать `<` или `>`.

| `blockType` | Точный объект `data` |
| --- | --- |
| `hero` | Обязательные `title` (до 120) и `text` (до 1000); опциональный CTA задается парой `ctaText` (до 80) + `ctaHref` (до 2048), отдельно они не принимаются; `eyebrow` (до 80) также опционален. CTA принимает локальный path без завершающего слэша, простой `#fragment` или внешний HTTPS URL без credentials; whitespace, backslash, protocol-relative и executable schemes отклоняются. |
| `rich_text` | Обязательные `title` до 120 и `text` до 4000 символов. |
| `tariff_grid` | Обязательный `title` до 120 символов, необязательный `text` до 1000, три обязательные подписи кнопок до 80, `initialCount` 1–100 и `sort` PRICE_ASC/PRICE_DESC. Тарифы берутся из доступного каталога города: сначала закреплённые, внутри групп — по текущей месячной цене. «Показать ещё» раскрывает весь остаток одним нажатием. Фильтров, ручных карточек и отдельной страницы списка нет. Действия карточки фиксированы: detail URL и встроенная проверка адреса. |
| `service_grid` | `title` до 120 и `items` из 1–8 объектов с точными полями `pageType`, `title`, `text`; разрешены page types `INTERNET`, `INTERNET_TV`, `TV`, `ADDRESS_CHECK`, `FAQ`, строки ограничены 120/1000 символами. В Release 1 `pageType` сохраняется как будущая семантика, а действие карточки ведет к `#address-check`. |
| `feature_grid` | `title` до 120 и `items` из 1–8 объектов `{ title, text }` с лимитами 120/1000. |
| `steps` | `title` до 120 и `items` из 2–8 объектов `{ title, text }` с лимитами 120/1000. |
| `faq` | `title` до 120 и `items` из 1–12 объектов `{ question, answer }` с лимитами 240/4000. |

Во всех `data` и элементах массивов действует exact allowlist ключей. Admin list и public catalog стабильно сортируют активные блоки по `position`, затем по `id`; `archivedAt IS NOT NULL` исключает блок из обоих списков. PATCH, меняющий discriminator или `data`, валидирует полный объединенный блок и условно записывает его только при неизменном сохраненном `blockType`; архивный блок нельзя менять до восстановления, конкурентная смена типа дает 409. Public catalog возвращает только `visible` и неархивные blocks, повторно валидирует каждый сохраненный блок и fail-closed требует ровно один видимый `hero` у любой непустой блочной страницы. Для опубликованного города до рендера дополнительно требуется ровно одна `HOME` с пустым slug и точной последовательностью `hero,tariff_grid`. В Release 1 Astro рендерит блоки городской `HOME`; остальные опубликованные Page могут оставаться в каталоге как данные будущих релизов, но маршрутов не получают. Адресная форма остается системным компонентом и не входит в `PageBlock`.

`SiteRebuild` дедуплицируется по сайту; `affectedPaths` сейчас всегда `["/*"]`, потому что пересобирается весь static artifact. BullMQ делает до трех попыток с exponential backoff 30 секунд. Legacy webhook получает `rebuildId`, `siteId`, `dedupeKey`, `affectedPaths`, `revision` и idempotency header `<rebuildId>:<revision>` и обязан вернуть финальный `SUCCEEDED`. Coolify adapter запускает resource, сохраняет `deployment_uuid`, опрашивает deployment и преобразует только `finished` в `SUCCEEDED`; pending/failure/timeout опубликованную ревизию не меняют.

### Import contracts

Тарифный import читает первый лист и требует точный 38-колоночный состав из `CANONICAL_IMPORT_COLUMNS`; `external_id`, `show_on_site`, производные тексты оборудования, отдельное название игры и игровой флаг запрещены. Поддерживаются только типы `Интернет` и `Интернет+ТВ`; `post_title` после очистки обязан совпасть с `nazvanie_tarifa`. Цены, скорость, каналы и сроки принимаются только как целые значения: текст с единицами, дроби, отрицательные значения и недопустимый ноль блокируют строку. Для `Интернет` TV-поля пусты, для `Интернет+ТВ` общее число каналов положительно, а HD при наличии также положительно и не больше общего. Import и ручное создание рассчитывают один обязательный `identityKey` из города, нормализованного канонического названия и типа; slug, цена и скорость в ключ не входят. Ручная правка не может изменить бизнес-ключ существующей записи: для такого изменения создается новый тариф. Full-snapshot lifecycle использует `ACTIVE/ARCHIVED`; архивный тариф исключается из public catalog, route inventory, sitemap, redirect targets и выбора для новой заявки.

Все source-specific поля закрыты единым реестром `TARIFF_ATTRIBUTE_FIELDS`: очищенный одно- и многострочный текст, booleans, положительные/неотрицательные integers, TV-счетчики, закрытые коды онлайн-кинотеатров и игр, оборудование/цены и внутренние статусы услуг. Импорт и PATCH используют один нормализатор типов и отклоняют неизвестные ключи; пустые значения не создают JSON-ключ. Пара рассрочки `price/months` либо целиком отсутствует (`0/0` и пустые значения нормализуются совместно), либо содержит две положительные величины. `UNAVAILABLE` несовместим с зависимыми ценами или `game_code`; доступное игровое предложение требует известный код. Реестр возвращается detail endpoint как схема формы. `connection_cost` нормализуется отдельно в nullable `Tariff.connectionFee` и входит в public catalog для build-time отображения.

Городской import принимает русские и латинские aliases для субъекта, грамматических форм, slug, legacy URL и офиса, включая фактические комбинированные заголовки канонического `data/imports/cities.xlsx`. Apply блокируется при errors, а при warnings требует явного `confirmWarnings: true`. Регионы и города предварительно загружаются в transaction-local maps, одинаковый нормализованный slug объединяет «Республика Татарстан» из seed и «Татарстан» из XLSX. Каждый примененный город получает `PUBLISHED`; новый город создается с одной `PUBLISHED` страницей `HOME`. Полный пакет выполняется с transaction timeout 30 секунд.

Тарифный preview проверяет `subekt_rf` по точному имени региона города или по тому же slug субъекта, который использует городской import. Поэтому `Татарстан` из канонического справочника принимается для seed-региона `Республика Татарстан` со slug `tatarstan`; другой субъект по-прежнему дает ошибку до apply.

Apply тарифа трактует файл как полный snapshot провайдера: partial apply через `acceptedKeys` отклоняется, перед записью повторно сверяются exact tariff snapshot и конфликты slug, а legacy report требует новой проверки файла. Все строки и условный переход run `VALIDATED -> APPLIED` применяются в одной serializable-транзакции с timeout 120 секунд; отсутствующие в новом файле активные тарифы архивируются с provenance, но не удаляются. Apply сохраняет только рабочую версию, а пересборка начинается после отдельной явной публикации нужного сайта. Ручная смена city/slug тарифа сохраняет provenance-aware redirect; он становится эффективным только после успешной публикации снимка, в котором новая tariff detail-цель входит в актуальный route inventory. Public catalog и runtime resolver fail-closed пропускают только активные target.

| POST | `/internal/pii-retention` | Worker-only bounded purge: требует service `x-admin-token` и валидный `PII_RETENTION_DAYS`, удаляет один batch просроченных лидов с cascade-данными, истекшие fallback tokens и осиротевшие старые AddressCheck; возвращает только cutoff и счетчики. |

Cursor-list endpoints используют стабильную сортировку по timestamp и `id`, `limit=25` по умолчанию и жесткий максимум 100. `cursor` — непрозрачная base64url-позиция; неверное значение дает HTTP 400. Ответ имеет вид `{ items, pageInfo: { limit, total, hasNextPage, nextCursor } }`, где `total` относится ко всему текущему фильтру, а не только к остатку после cursor. `/crm/leads` дополнительно возвращает глобальную `summary` для карточек `total/new/pending/attention`. List DTO заявки содержит только поля журнала, город и безопасный статус notification; история, delivery attempts, activity, результаты проверок и остальные PII загружаются через `/crm/leads/:id` после явного открытия карточки. Audit list аналогично откладывает `changes` до detail-запроса.

Retention endpoint физически удаляет весь `Lead`, чтобы PII не осталось в `contractResult`, `apiResult`, UTM или delivery JSON. Cascade удаляет `LeadDeliveryAttempt`, `LeadNotification`, `LeadActivityEvent`, `LeadStatusHistory` и `LeadAccessToken`; старые `AddressCheck` удаляются только после исчезновения всех ссылок. Свежий duplicate, ссылающийся на удаляемый лид, предварительно отвязывается. Один вызов ограничен `PII_RETENTION_BATCH_SIZE` (default 500, максимум 5000); worker повторяет batches и запускает scheduler ежедневно. Согласованный срок для сырых заявок — 180 дней. Без валидного `PII_RETENTION_DAYS` endpoint возвращает 503, scheduler отключен, а release readiness остается `blocked`.

## Отсутствующие routes

В коде нет admin endpoints для media, analytics, per-entity rollback, самостоятельного SEO-аудита вне публикации, редакторов остальных page templates и отдельного режима структуры и предложений редиректов из 404. Узкий `GET/PATCH /admin/sites/:siteId/values` управляет только двумя типизированными телефонными значениями Site; он не является API произвольных переменных. Read-only каталог V2 не создает пользовательские коды, не вставляет их в редакторы и не мигрирует legacy-содержимое: это отдельный V3. Общий `/preview` read-only собирает текущий рабочий Release 1 catalog, использует действующие public-компоненты для поддержанных блоков после #235; `/templates` показывает два шаблона главных страниц и вторичную ссылку на программную тарифную страницу и защищённый preview без редактора кода. Ни один не является отдельным deployment-артефактом или публичной ссылкой. Общий read-only audit журнал показывает сохраненные действия и field-level diff, но не является редактором истории или механизмом восстановления. Защищенный build endpoint publication snapshot также не заменяет эти пользовательские функции. Callback от Tarifnik не реализован, поскольку партнерский API его не предоставляет.


Подготовка ручной публикации (`POST /admin/sites/:siteId/publications`) читает источник, проверяет все URL и сохраняет immutable catalog/report в одной Serializable-транзакции с bounded timeout 60 секунд. Стандартные 5 секунд Prisma недостаточны для полного городского/тарифного каталога (#250). Проверка expectedWorkingRevision и idempotent PENDING retry сохраняются; увеличение бюджета не меняет опубликованную версию и не отменяет serving/receipt gates.

## Чтения и защита после #259/#260

- GET `/admin/sites/values` защищён AdminTokenGuard и возвращает список с теми же нормализованными/форматированными телефонами, ревизиями и readiness errors, что одиночный GET values. Пустой/множественный список не выбирает сайт автоматически. PATCH сохраняет прежний контракт: точная expectedWorkingRevision, отдельное сохранение и публикация.
- Variable-catalog получает serializable typed source context без рендера всего public catalog. Authoritative usage scan сверяет workingRevision; варианты тарифов ограничены выбранным опубликованным городом и ACTIVE/PUBLISHED статусом. Published evidence берётся из immutable snapshot; отсутствие evidence сохраняет null/UNKNOWN.
- Rate-limit max и key используют единый raw path classifier для origin-form и HTTP(S) absolute-form target: login 5/min, suggestions 60/min, address-check/lead/lead-access 10/min. Dot/percent segments не нормализуются в другой route; AuthGuard и CORS остаются обязательными.

Клиентский кэш касается только отображения согласованных списков и справочников в текущей сессии; обычный requestJson, editorial reads и серверные разрешения остаются свежими. ## Редактор ADDRESS

`GET /admin/sites/:siteId/page-templates/address-composition` возвращает восемь блоков, version/implementationVersion, missingFields, рабочую/опубликованную ревизии, собственную опубликованную композицию либо null и общие системные значения. `PATCH` того же URL принимает только `{expectedWorkingRevision, blocks:[{blockType,data}]}`. ## Рабочее место новостей — T5 (#534)

- `GET /api/v1/admin/sites/:siteId/news/related-options`: только serving-проекция опубликованных статей. Query `currentId`, `categoryId`, `ids` (до трёх через запятую), `search`, `page`; 25 результатов, `selected` с available=false для исчезнувших материалов и auto `recommended`. Незавершённые заголовки других черновиков не подставляются.
- Workspace возвращает необязательный `publicUrl` из фактически опубликованного slug и настроенного public origin. Для черновика, скрытой пустой категории и 404 отдельной ссылки нет. Operation read включает source `siteRevision`; progress админки привязан к тому же publication ID.
- ARTICLE clientId не может занимать namespaces `media`, `categories`, `publications`, `related-options`; отказ 400 до записи (TD-220/#538). Стабильные client UUID и импортные ID сохраняются.
- No-op save с `checkpoint=true` закрепляет существующую редакцию в истории без дублирующей revision. Безопасный draft может содержать незаполненное имя автора/URL источника; missingFields блокируют публикацию, небезопасный URL отклоняется.
- UI перед review/history/preview сохраняет точный checkpoint. Локальная recovery-копия не является опубликованной или подтверждённой серверной редакцией.

T6: история статьи возвращает `restoreCategory.required/options`. Если исходная категория архивирована, POST ARTICLE restore требует явно выбранный `categoryId`; другие restore scopes его не принимают. Текст остаётся draft, CAS и действующая категория проверяются сервером. CATEGORY PUBLISH блокируется при незавершённом retirement даже после смены serving baseline. ## Новости: точный preview — T8

POST `/:id/preview` под news, news/categories и POST `/editorial/:kind/preview` принимают только `{expectedRevision,mode:"draft"|"published"}`. Сначала клиент сохраняет черновик; несовпадающая ревизия даёт409. Payload содержит kind/entityId/revision/selectedRevision/publicationId, проверенный catalog и editorial projection. Публичная версия читается из обслуживаемого baseline, не из pending snapshot. Только выбранный saved draft и необходимая новая категория перекрывают baseline; остальные рабочие изменения не включаются. Отсутствующая публичная версия возвращает available=false. Приватные mediaRequests остаются авторизованными; `file?kind=...&variant=<sha256>` выбирает только собственную проверенную производную, чужой или неизвестный hash отклоняется. Preview ничего не публикует.

## Импорт новостей WordPress — T9

POST `/admin/sites/:siteId/news/imports/wordpress` защищён AdminTokenGuard и принимает только `{sourceId,sourceHash,sourceUrl,category:{sourceId,content},content}`. Источник ограничен HTTPS tarify-dom.ru, slug исходного path совпадает с content.slug. Новый материал возвращает IMPORTED_DRAFT, revision1, categoryId, missingFields и pendingRedirect(active=false); статья/категория не публикуются. Повтор того же sourceHash возвращает SKIPPED_IDENTICAL/SKIPPED_ARCHIVED и текущую revision без перезаписи ручных правок; изменившийся источник, занятый slug и архивная/удаляемая категория дают409. Media проверяются до commit; сбой откатывает также новую категорию и историю. ID и sourceId уникальны внутри своего site. Импорт не создаёт SitePublication/Redirect и не меняет legacy revisions.
