## Редакционная модель и границы опубликованного состояния

Статьи, категории, настройки списка/404, медиа и история имеют отдельные рабочие и опубликованные редакции. Первый перенос в DRAFT зафиксирован в [T11](research/2026-11-07-news-external-release.md); последующий [протокол CSP/CHANGED](research/2026-11-07-csp-manifest-and-changed-batch.md) уже проверял опубликованные версии с рабочими изменениями. Числа и ревизии, приведённые в этих протоколах, относятся к датированным срезам, а не к постоянному состоянию модели. CODE не публикует рабочие изменения.

T4 (#534): `0069_editorial_redirect_ownership` добавляет nullable `Redirect.managedEditorialKey` и индекс site/owner. Прежние ручные записи получают null без изменения адресов; новые `ARTICLE:id`, `CATEGORY:id`, `NEWS_SETTINGS` защищают автоматические aliases от отдельной правки. Активность определяется immutable catalog, а не этим признаком или working status DB. [Контракт и локальные проверки](research/2026-11-06-news-scoped-backend.md).

`PublishStatus` принимает `DRAFT`, `PUBLISHED`, `ARCHIVED`. `PageType` дополнительно содержит пять типов Release 1: `COVERAGE`, `CITIES`, `PRIVACY`, `PERSONAL_DATA_CONSENT`, `COOKIE_POLICY`. DB constraint разрешает этим пяти типам и дополнительным ACCOUNT/OFFICIAL_SITE/SPEED_TEST только `cityId IS NULL`; остальные типы имеют городской scope. ACCOUNT добавлен миграциями 0066/0067 и имеет отдельный canonical/unique contract; admin API до записи также проверяет scope и точный slug общей страницы. Для `HOME` база и API независимо требуют пустой slug и не допускают вторую HOME того же города независимо от статуса. Город, Page, Tariff и Redirect используют `ARCHIVED` как корзину, а PageBlock — nullable `archivedAt`; общий admin endpoint группирует их по сайту. `SitemapExclusion` хранит уникальную пару `(siteId, path)`, обязательную причину, автора и timestamps; тип карты не дублируется в БД, а выводится из authoritative route kind. `0033` добавляет эту таблицу без изменения существующих публикаций. Рабочий preview уже реализован: защищенный endpoint собирает текущий каталог без создания публикации или rebuild, а `/preview` показывает его в sandboxed iframe; отсутствует только отдельный внешний preview token/link.

JSON `data` не является произвольным хранилищем. API применяет закрытый discriminated contract по `blockType`: hero содержит заголовок, текст и опциональные eyebrow/CTA; rich text — заголовок и текст; tariff grid — заголовок, необязательное описание, три подписи кнопок, initialCount 1–100 и PRICE_ASC/PRICE_DESC, без фильтров и ручных карточек; service grid — заголовок и ссылки по допустимому типу опубликованной страницы; feature grid и steps — заголовок и массив пар «заголовок + текст»; FAQ — заголовок и массив пар «вопрос + ответ». Неизвестные ключи, raw HTML, пустые обязательные строки, превышение лимитов и небезопасные CTA отклоняются. Массивы ограничены по числу элементов. При PATCH новое `data` валидируется как полная замена контракта вместе с сохраненным `blockType`, а не как свободный частичный JSON; условная запись блокирует конкурентную смену discriminator. Public catalog повторно валидирует сохраненный JSON и требует ровно один видимый hero у непустой блочной страницы. Для новой городской HOME версии 3.0.0 действует фиксированная последовательность десяти блоков. Точный порядок `hero,tariff_grid` относится к v2; известная историческая семиблочная композиция проецируется по совместимости 0058. Специализированные HOME/CITY/ADDRESS-схемы не заменяются произвольным legacy PageBlock JSON.

Форма заявки остается отдельным системным компонентом публичной страницы и в `PageBlock` не моделируется. Для городской HOME именно упорядоченный набор блоков определяет контентную структуру; отдельный hardcoded fallback удален. Внутренние `hero.data.ctaHref` хранятся без завершающего слэша; migration `0018_page_block_cta_paths` идемпотентно нормализует legacy-значения. `0019` и `0020` фиксируют снимки Казани и отдельный номер техподдержки. Миграции `0021`–`0023` добавляют первые четыре global-типа и nullable scope. `0024` отдельно добавляет `COOKIE_POLICY`, а `0025` обновляет scope constraint, создает пятую global page, публикует обязательные общие страницы, все существующие города и их `HOME`, не изменяя тарифы и заявки. `0026` добавляет канонические блоки только в пустые опубликованные городские HOME, используя `namePrepositional`, и сохраняет любые уже существующие композиции. `0030` только добавляет nullable `archivedAt` и индекс, поэтому существующие блоки остаются активными. `0031` аддитивно расширяет жизненный цикл публикации состояниями `SCHEDULED`/`CANCELLED`, добавляет `scheduledFor`/`cancelledAt` и индекс выборки наступивших расписаний; существующие снимки и публикации не меняются. `0032` fail-closed принимает только единственную каноническую HOME либо известную пару `slug=''` + `slug='home'` с одинаковыми status/SEO/content/блоками; во втором случае переводит `Lead.pageId` и `AddressCheck.pageId`, удаляет legacy-строку, добавляет DB-инварианты и системную рабочую ревизию. Исторические `SitePublication.catalog` не переписываются. Исторические `PageBlock` сохранены для ссылок и C6; seed и city import теперь связывают новую HOME с одним `PageTemplate` и не создают семь локальных блоков.

Миграция `0035` переносит единственные непротиворечивые городские номера на `Site`, нормализует их в `7XXXXXXXXXX` и удаляет поля City. Несколько разных значений или неверный российский номер останавливают миграцию с ошибкой; скрытого выбора и подстановки нет. Nullable-схема позволяет развернуть миграцию на пустой базе, но readiness gate запрещает публикацию и build без обоих телефонов.

Forward-only migration `0039` восстанавливает только пропущенный revision trail после `0034`–`0035`. Она выбирает Site, у которого последний `SUCCEEDED` snapshot не совпадает с live name/slug/телефонами, `workingRevision = publishedRevision` и нет уже подготовленной более новой `ContentRevision`. Для такого сайта `workingRevision` увеличивается ровно на один и добавляются согласованные `ContentRevision`/`AuditEvent`. Исторические `SitePublication` не меняются, автоматической публикации нет; повторный запуск не создает вторую revision.

Миграция `0036` вводит `HAS_OFFICE`/`NO_OFFICE`, runtime-ссылку на проверенный профиль абонента и timestamps города; удаляет неиспользуемый творительный падеж, City SEO/content и Region phone/content. Она fail-closed отклоняет частично заполненный офис и непустые удаляемые JSON override, чтобы deployment не потерял редакционные данные молча. Readiness города отдельно проверяет регион, название и обе используемые формы, slug, согласованность офиса, каноническую HOME и хотя бы один опубликованный тариф; отсутствие профиля остается предупреждением с отдельным подтверждением.

## Тарифы и импорты

`Tariff` хранит provider/city, name, slug, service type, standard/promo price, speed, promo text, nullable connection fee, enum `availability`, legacy external key, обязательный внутренний identity key, source, attributes и publication status. Нулевой `connectionFee` означает бесплатное подключение, положительный — его стоимость, а `NULL` — отсутствие публичной строки. Канонический import принимает ровно 38 колонок в фиксированном порядке. Source-specific поля не дублируются в верхнем уровне: единый закрытый реестр `TARIFF_ATTRIBUTE_FIELDS` нормализует очищенный текст, целые значения, booleans, коды и статусы услуг для import и ручного PATCH; пустые значения не сохраняются, неизвестные ключи отклоняются. Импортные `-1/0/1` сохраняются внутри JSON как `INCLUDED/UNAVAILABLE/OPTIONAL`; `show_on_site`, внешние/производные поля оборудования и отдельное название игры в новом контракте отсутствуют. Ограничения модели: unique `(cityId, slug)` и `(cityId, identityKey)`; `identityKey = cityId:normalized(name):serviceType`, где пробелы нормализуются и регистр игнорируется, а пунктуация и `е/ё` сохраняются. `0037_tariff_business_identity` fail-closed проверяет дубликаты, пересчитывает ключи и делает поле обязательным. `0038_tariff_archive_lifecycle` заменяет boolean на `ACTIVE/ARCHIVED`, хранит причину, время и import run архива и DB constraint-ом запрещает несогласованные lifecycle-состояния.

Миграция `0016_admin_list_pagination_indexes` добавляет составные индексы `Tariff(updatedAt, id)` и `Lead(createdAt, id)` для стабильного keyset/cursor обхода административных журналов. Фильтр статуса заявок использует существующий `Lead(status, createdAt)`, а тарифные city/service/status-фильтры — `Tariff(cityId, serviceType, status)`. Подстроковый `q` остается bounded-поиском по текущему каталогу и не подменяется неутвержденным полнотекстовым индексом.

`TariffImportRun` и `CityImportRun` сохраняют метаданные файла, счетчики, JSON report, `VALIDATED`/`APPLIED`/`UNDONE`/`FAILED`, время и автора apply/undo, JSON change set и номера undo-ревизий. Tariff report версии 3 содержит нормализованные candidates, exact catalog snapshot, счетчики `create/update/archive/unchanged` и field-level diff по каждому тарифу. Apply с transaction timeout 120 секунд атомарно архивирует отсутствующие в snapshot активные тарифы, не удаляя строки и не меняя их `Lead.tariffId`. Change set версии 3 содержит exact before/after catalog вместе с archive provenance, контентный снимок redirects, карту сайтов/городов и созданные рабочие ревизии. Guarded undo требует совпадения текущего post-import каталога и отсутствия более поздних затрагивающих `ContentRevision`, затем восстанавливает бизнес-поля и lifecycle, создает `UNDO` revisions и условно переводит run из `APPLIED` в `UNDONE` в той же serializable-транзакции. Версия 2 остается undo-совместимой через нормализацию бывшего boolean availability; версия 1 намеренно не отменяется. Счетчики переходов редиректа не входят в content guard. City change set версии 1 фиксирует выбранные действия, before/after cities, созданные regions/pages и рабочую ревизию. City undo требует точного совпадения этих снимков, отсутствия последующих ревизий и зависимых данных у новых городов; затем восстанавливает прежние города, удаляет только сохраненные новые записи и создает attributed `UNDO` revision в той же serializable-транзакции. Сырые файлы не сохраняются; отдельной построчной import history нет.

Проверка импорта использует индексы по `(cityId, identityKey)` для сопоставления тарифов и по `(cityId, slug)` для проверки владельца URL. Применение сверяет снимок и опубликованные маршруты перед записью. Вставки и обновления пишутся партиями до 256 строк внутри одной serializable-транзакции. Для отмены v3 пакетное обновление используется, когда все восстанавливаемые строки присутствуют в подтверждённом каталоге. Исторический v2 и восстановление отсутствующей строки проходят через прежний upsert с сохранением ID и `createdAt`. Архивирование, привязки заявок, версия отчёта и аудиторские снимки следуют описанному выше контракту. [Сравнение и SQL-профиль](research/2026-11-20-tariff-import-performance.md).

`LeadProcessingStatus` отделяет delivery flow от операторского `LeadStatus`. Помимо технических/доставочных исходов, миграция `0013_lead_provider_outcomes` добавила две исторические однозначные причины непередачи: `PROVIDER_NOT_AVAILABLE_NOT_SENT` и `NO_PROVIDERS_NOT_SENT`. FLOW 2 не создаёт sales-лид для этих результатов: телефон запрашивается и принимается только при persisted AVAILABLE с Дом.ру. FLOW 1 отдельно сохраняет консультацию без адресной проверки и автоматической sales-доставки. Миграция `0014_delivery_queue_status` добавляет `DELIVERY_QUEUE_ERROR` и канал `QUEUE`, чтобы сбой producer не оставался ложным `PENDING` и был виден отдельно от ответа Tarifnik/email.

Дедупликация новой заявки выбирает совпадение нормализованного телефона за 24 часа прежде адресного совпадения. Адресный путь допускается только при одинаковом явно сохраненном номере квартиры или комнаты в DaData-снимках обеих заявок и одинаковом нормализованном адресе; дом без помещения не блокирует другого жильца. `Lead.duplicateOfId` и `duplicateReason` фиксируют выбор, а `LeadDecisionEvent` сохраняет те же ID и причину в evidence. В окне от `createdAt >= cutoff` выбирается самая поздняя строка по `createdAt DESC, id DESC`. Телефон сравнивается прежним нормализатором по компактным полям. Когда у новой заявки есть адрес и номер помещения, обе фазы чтения используют один RepeatableRead-снимок. `Lead.apiResult` читается только для кандидатов с тем же нормализованным адресом, по 500 ключей за запрос. Прежний parser обрабатывает историческую форму ответа проверки адреса. Новые столбцы и индексы для ПДн не требуются. [Протокол проверки на синтетических данных](research/2026-11-20-lead-duplicate-read-performance.md).

Миграция `0015_lead_notification_outbox` добавляет `LeadNotification` и статусы `PENDING/QUEUED/RUNNING/RETRYING/SUCCEEDED/FAILED`. Запись создается в одной транзакции с `Lead`; revision отделяет ручные циклы, а persisted attempts сохраняют общий лимит после потери Redis. Каждый queue job имеет revision+attempt в ID и удаляется после terminal BullMQ outcome. Свежий `RUNNING` защищен lease, ручной retry — compare-and-swap. Доставка имеет at-least-once семантику, а idempotency header `lead-notification-<leadId>-revision-<revision>` снижает риск дубля внутри автоматических попыток и не блокирует новый ручной цикл.

Согласованная маршрутизация требует хранить отдельно исходные ответы проверок, нормализованное решение и реальные delivery attempts. Отсутствие Дом.ру, подтвержденный действующий абонент и неоднозначный ответ API — разные причины непередачи. API Dom.ru вызывается после обнаружения хотя бы одного провайдера; только успешный ответ ожидаемой структуры с явным `contacts: []` означает `NOT_FOUND`, но delivery дополнительно требует наличия Дом.ру. Отсутствие или неверный тип `contacts` является ошибкой контракта и должно приводить к `MANUAL_CHECK_API`. Для видимой проверки подключения `AddressCheck` может существовать без `Lead`; лид появляется только после найденного Дом.ру и ввода телефона.

Для retention не добавлена отдельная policy-таблица: согласованный срок 180 дней задается обязательной production-переменной `PII_RETENTION_DAYS=180`. Миграция `0012_pii_retention_indexes` добавила индексы по времени; `0016` расширяет индекс `Lead.createdAt` полем `id`, сохраняя тот же ведущий столбец для purge-запроса. `AddressCheck.createdAt` остается отдельным индексом. Bounded hard-delete старого `Lead` каскадно удаляет history, delivery attempts, notification evidence, activity и access tokens; свежие duplicates предварительно отвязываются, старый `AddressCheck` удаляется только без оставшихся ссылок. Это исключает частичную «анонимизацию», при которой PII мог бы остаться в JSON.

Миграция `0040_lead_positive_submission` аддитивно добавляет `Lead.submissionKey`, `consentVersion` и `consentAcceptedAt`, а также unique index для server-side idempotency. Старые записи не переписываются; для каждой новой публичной заявки поля обязательны на уровне DTO/controller, телефон сохраняется нормализованным, а положительный `AddressCheck` и выбранный `tariffId` остаются отдельными неизменяемыми ссылками факта отправки. Миграция `0041_lead_configuration_snapshot` добавляет nullable JSONB без переписывания исторических лидов. Новая тарифная заявка сохраняет нормализованный выбор, ID/название тарифа, выбранные компоненты, строки ежемесячных и разовых платежей, итоги, отпечаток серверного расчёта и время фиксации; снимок не зависит от последующих правок тарифа.

Миграция `0043_lead_reason_snapshot` аддитивно добавляет четыре nullable поля снимка причины, индекс `(siteId, reasonCode, createdAt)` для фильтра журнала и `NON_SALES_NOT_SENT` в processing enum. Закрытый справочник имеет версию `1`: `new_connection` проходит sales-проверки, `existing_subscriber_support`/`billing` сохраняются без внешней sales-доставки, `relocation`/`other` остаются на ручном решении. Код и подпись берутся из серверного реестра при создании и не обновляются при последующих изменениях справочника.

Миграция `0044_lead_comment_analysis` аддитивно добавляет nullable исходный пользовательский `Lead.comment` и снимок результата анализа: `commentAnalysisVersion`, `commentAnalysisOutcome`, `commentAnalysisCategory`, `commentAnalysisEvidence` (JSONB-массив точных фрагментов и позиций) и `commentAnalysisExplanation`. Отсутствующий комментарий не анализируется и сохраняет `null`, исторические лиды не переписываются. Правила версии 1 находятся в коде; результат не переоценивается автоматически при будущей смене правил. Ручной исход блокирует sales-доставку, но не отклоняет заявку.

`0045_lead_phone_decision` добавляет статусы фонового решения и nullable evidence DaData Phone: status, `qc`, нормализованный номер, время, попытку, источник `API`/`CACHE`, безопасный технический код, срок следующего повтора и lease решения. Полный ответ DaData не хранится; исторические лиды остаются с `null`. Индексы поддерживают 24-часовое повторное использование финального результата и восстановление незавершенной обработки.

`0046_lead_decision_events` аддитивно добавляет `LeadDecisionEvent` и nullable `Lead.decisionAttemptNumber`. События сохраняются в той же транзакции, что и итог каждого шага фонового решения; ручной повтор после финальной технической ошибки и переанализ комментария также фиксируют автора и прежний результат до изменения текущего снимка. Историческим заявкам таблица не заполняется задним числом. `decisionAttemptNumber` позволяет после истечения lease восстановить именно выполнявшуюся попытку, не выдавая ее за предыдущую.

## Доступ и технические записи

`User` содержит email, `passwordHash`, name, active и timestamps. Ролевой модели нет: любая активная учетная запись имеет единый уровень доступа администратора. `Session` хранит не raw token, а его SHA-256 hash и expiry. При reset password или deactivate API удаляет sessions пользователя. `LeadAccessToken` также хранит только hash: raw token существует лишь в одноразовой email-ссылке и не возвращается административными CRM routes.

`Redirect` хранит site/city, no-slash source/target path, status, `hitCount`, `lastHitAt`, опциональный `managedTariffId` и timestamps. `managedTariffId` — provenance автоматического правила без foreign key: это позволяет сохранить redirect history после удаления тарифа. Только управляемое тарифом правило синхронизирует status с его публикацией; совместимое ручное правило не захватывается. Admin API создает, изменяет и архивирует записи; published-правило проходит проверку конфликтов, запрета цепочек и принадлежности target к Release 1 route inventory. Каждая ручная мутация в той же транзакции создает рабочую ревизию и before/after audit, но не запускает публикацию. Во время Astro build эффективные записи превращаются в точные Caddy matchers, а runtime resolver проверяет exact serving snapshot при static provider либо последний успешный SQL snapshot в legacy режиме, атомарно учитывает переход и отдает HTTP 301. Удаление реализовано как `ARCHIVED`, а общий экран корзины позволяет вернуть редирект в рабочий `DRAFT`; предложения редиректа из 404 пока отсутствуют.

`SiteRebuild` — одна актуальная outbox/status-запись на `dedupeKey` сайта. Она хранит affected paths, последнюю причину, `requestedRevision`, `processingRevision`, `publishedRevision`, число попыток, ошибку и финальный ответ deployment provider. Три nullable-ссылки `requestedPublicationId`, `processingPublicationId`, `publishedPublicationId` не дают новой правке заменить снимок уже идущей сборки. Ревизия считается опубликованной только при статусе `SUCCEEDED`; новая мутация во время активной сборки увеличивает requested revision и создает следующий job после завершения текущего.

`Site.workingRevision` — монотонный номер сохраненного состояния CMS, `Site.publishedRevision` — подтверждённая ревизия legacy CMS-source; редакционные выпуски не продвигают её как общий watermark. `ContentRevision` хранит неизменяемые JSON-снимки сущности до и после изменения, ее собственный номер версии, общую ревизию сайта, источник, автора и измененные поля. Номер `entityRevision` глобален для пары `(entityType, entityId)`, даже если общий Provider затрагивает несколько сайтов; изменение Provider создает отдельную запись и site revision для каждого такого сайта. `AuditEvent` — отдельная append-only запись действия с явными значениями `before`/`after` для каждого верхнеуровневого измененного поля. `SitePublication` хранит полный денормализованный каталог точного выпуска и состояния `PENDING`/`RUNNING`/`SUCCEEDED`/`FAILED`/`CANCELLED` и безопасное evidence deployment provider. Уникальность `(siteId, siteRevision, scopeKey)` разделяет legacy и редакционные операции. `releaseSequence` задаёт порядок выпусков, `basePublicationId` и `changeSetDigest` связывают редакционный candidate с serving baseline; ledger подтверждает только выбранные entity revisions. Миграция `0057` отменяет ещё не запущенные расписания, переносит их даты в историческое providerResponse.retiredSchedule и удаляет прежние поля/индекс/enum-значение. Наличие уже переданного в сборку отложенного снимка блокирует миграцию до завершения; catalog и опубликованная ревизия не меняются. Общие legacy CMS mutators, включая программный import тарифов и apply/undo обоих XLSX-импортов, создают рабочие ревизии без автоматической публикации; создание Provider до появления Site не имеет public site scope и потому не создает ревизию. Защищенные publication endpoints фиксируют точную ожидаемую ревизию для ручного запуска.

`SitePublicationValidation` добавлена миграцией `0050_publication_validation_report` без backfill исторических публикаций. Она хранит `sourceSnapshot` и `report` как JSONB, site revision, версию приложения, автора, число URL, итог `BLOCKED`/`PASSED_WITH_WARNINGS`/`PASSED` и время проверки. Неуспешный отчет сохраняется отдельно от публикации; успешный `SitePublication` содержит nullable `validationId`. API не редактирует сохраненный отчет. Изолированный PostgreSQL 18 rehearsal применил все 50 миграций и проверил, что ошибочный отчет переживает HTTP 409, публичная ревизия не меняется, повторная проверка того же snapshot воспроизводима, а исправленный snapshot создаёт связанную публикацию. Внешний one-shot `migrate` завершился до запуска здорового API на exact-SHA `71fac3e5cee30906bc4e1171d7244cc6feb4d657`; отдельного live отчета пока нет.

Public catalog разрешает уровни `content` в таком порядке:

```text
Provider.settings.content -> Site.settings.content -> Page.content
```

Для site-global Page цепочка сокращается до `Provider.settings.content -> Site.settings.content -> Page.content`. В публичное наследование из настроек Provider/Site входит только явный namespace `content`; соседние credentials, integration settings и другие приватные ключи не участвуют.

Контракт разрешения `content` сохраняет переходную цепочку Provider → Site → Page для общих страниц и Provider → Site → PageTemplate для городской HOME: вложенные JSON-объекты объединяются рекурсивно, а массив, строка, число, boolean и `null` целиком заменяют родительское значение. Город и регион больше не участвуют в наследовании. Новые публикации используют site-scoped SEO-шаблоны в `seoByPath`; исторические `SitePublication` не переписываются. Локальных SEO-полей города, страницы, шаблона страницы и тарифа больше нет.

`PageBlock` не участвует в JSON-наследовании. Для городской HOME редакционный заголовок, content и фиксированный состав текущей композиции принадлежат `PageTemplate`; у CITY3 это десять блоков, у исторической v2 — два, а SEO — `SeoTemplate(CITY_HOME)`; город даёт только структурированные факты и форму названия для `{CITY_NAME_PREPOSITIONAL}`. Исторические `PageBlock` остаются до C6, но не управляют рабочим рендером и недоступны для редактирования HOME.

## Переход городской HOME к PageTemplate

`0052_page_template_schema` добавляет типизированные сущности и nullable связь `Page.templateId`; `0053_page_template_home_backfill` проверяет нормализованные заголовки и видимые блоки всех опубликованных HOME одного сайта, затем привязывает их к одному шаблону. Различие `null` и `{}` в пустых `content`/`seo` и служебный `source` старой Казани не считаются редакционными вариантами. Любой другой вариант или неполная семиблочная композиция останавливает миграцию до записи. Создаются `PAGE_TEMPLATE/CREATE` revision и audit, `Site.workingRevision` увеличивается на один; публичный `SitePublication` не переписывается и не обновляется автоматически.

Существующие `Page` остаются как временные shell-записи для `Lead.pageId`, `AddressCheck.pageId`, статуса и уникального маршрута; API блокирует их ручное редактирование и редактирование их старых `PageBlock`. Рабочий каталог берёт контент из site-scoped шаблона и структурированных полей City. При построении нового снимка он сохраняет legacy ID/source блоков в выходном DTO до C6, чтобы публичный результат миграции остался эквивалентным; новый город использует ID/source блоков шаблона. Отсутствующая или черновая привязка блокирует публикацию. C3 завершена в согласованном scope; универсальные функциональные/юридические редакторы C4/C5 и удаление старых строк C6 остаются отдельным остатком #167. Готовность каждого последующего паспорта/редактора проверяется отдельно.

## Очистка legacy SEO

`0054_drop_legacy_seo_overrides` в одной транзакции блокирует `Page`, `Tariff` и `PageTemplate`, отказывает при любом `seo` кроме SQL `NULL`, JSON `null` и `{}`, затем удаляет три колонки. PostgreSQL 18 rehearsal проверяет отказ для каждой таблицы, сохранение колонок после отказа и успешное удаление. Исторические `SitePublication`, `ContentRevision`, `AuditEvent` и импортные change sets не переписываются. Новые импортные снимки не содержат `seo`; guarded undo старого снимка допускается только при пустом legacy SEO и явно блокируется при непустом значении.

`0055_tariff_purge_guards` добавляет действие `PURGE` в enum истории и меняет FK `Lead.tariffId` с `ON DELETE SET NULL` на `ON DELETE RESTRICT`, не отвязывая существующие заявки. Физическая очистка допускает только `Tariff` с `status=ARCHIVED` и `availability=ARCHIVED`, без `Lead.tariffId`, связанного `Redirect`, упоминания в `SitePublication.catalog`/`triggerEntityId`, `SitePublicationValidation.sourceSnapshot` или `TariffImportRun.changeSet`; `archivedByImportRunId` тоже блокирует удаление. Исторические `ContentRevision` и `AuditEvent` не имеют FK на `Tariff`, сохраняют собственные снимки и получают заключительное `PURGE`-событие. Сайт и пакет тарифов блокируются в serializable-транзакции; изменение связей отменяет весь пакет.

## Чего в модели нет

Редакционные MediaAsset и NewsCategory реализованы отдельно; универсальных media library/category/collection, analytics aggregates, универсального variable registry, equipment, channel package, review, persisted legal retention policy и provider integration profile нет. Модели версий/аудита, ручная публикация точного snapshot, защищенный рабочий preview, общий read-only admin-журнал, корзина status-сущностей/PageBlock и guarded undo двух XLSX-импортов уже добавлены, но внешняя preview-ссылка и универсальный per-entity rollback поверх них еще не реализованы.
