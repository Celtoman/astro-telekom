# Модель данных текущего прототипа

Источник правды: `prisma/schema.prisma` и 36 последовательных миграций от `0001_initial` до `0036_city_contract`. Этот документ отличает существующие таблицы от объектов, которые фигурируют только в продуктовом плане; примененность конкретной миграции во внешнем контуре подтверждается отдельно, а не выводится из репозитория.

## Сущности контента и географии

| Сущность | Реальные ключевые поля | Связи и статус |
| --- | --- | --- |
| `Provider` | `name`, unique `slug`, `legalData`, `settings` | Имеет sites и tariffs. |
| `Site` | `providerId`, `name`, unique `slug`, `domain`, нормализованные `connectionPhone` и `supportPhone`, `settings`, `status`, `workingRevision`, `publishedRevision` | Имеет regions, cities, pages, leads, checks, redirects, sitemap exclusions, revisions, publications, audit events и rebuild status. |
| `Region` | `siteId`, `name`, `slug` | Unique `(siteId, slug)`, содержит cities. Телефон и произвольный content региону не принадлежат. |
| `City` | site/region, название и используемые родительный/предложный варианты, slug, legacy URL, явное состояние офиса, адрес/режим, проверенный `subscriberProfileKey`, `status`, timestamps | Unique `(siteId, slug)`, имеет pages, tariffs, leads, checks, redirects. Телефоны, SEO и произвольный content городу не принадлежат. |
| `Page` | `siteId`, nullable `cityId`, `type`, `title`, `slug`, `status`, `seo`, `content` | City pages имеют unique `(cityId, slug)`; site-global pages — partial unique `(siteId, slug) WHERE cityId IS NULL`; городская `HOME` дополнительно имеет пустой slug и partial unique `(cityId) WHERE type = HOME`; имеет ordered blocks. |
| `PageBlock` | `blockType`, `position`, `visible`, JSON `data`, optional `source`, nullable `archivedAt` | Cascade delete только вместе с parent Page. Ручной DELETE выставляет `archivedAt`, а restore очищает его; API разрешает `hero`, `rich_text`, `tariff_grid`, `service_grid`, `feature_grid`, `steps` и `faq`; `position` задает порядок активных visible-блоков. |

`PublishStatus` принимает `DRAFT`, `PUBLISHED`, `ARCHIVED`. `PageType` дополнительно содержит пять типов Release 1: `COVERAGE`, `CITIES`, `PRIVACY`, `PERSONAL_DATA_CONSENT`, `COOKIE_POLICY`. DB constraint разрешает им только `cityId IS NULL`, а всем остальным типам — только непустой `cityId`; admin API до записи также проверяет scope и точный slug общей страницы. Для `HOME` база и API независимо требуют пустой slug и не допускают вторую HOME того же города независимо от статуса. Город, Page, Tariff и Redirect используют `ARCHIVED` как корзину, а PageBlock — nullable `archivedAt`; общий admin endpoint группирует их по сайту. `SitemapExclusion` хранит уникальную пару `(siteId, path)`, обязательную причину, автора и timestamps; тип карты не дублируется в БД, а выводится из authoritative route kind. `0033` добавляет эту таблицу без изменения существующих публикаций. Дата отложенного запуска хранится не на content-сущностях, а в зафиксированном `SitePublication`; отдельного preview token пока нет.

JSON `data` не является произвольным хранилищем. API применяет закрытый discriminated contract по `blockType`: hero содержит заголовок, текст и опциональные eyebrow/CTA; rich text — заголовок и текст; tariff grid — заголовок и опциональные фильтр услуги, лимит 1–12 и тип страницы для ссылки на полный каталог; service grid — заголовок и ссылки по допустимому типу опубликованной страницы; feature grid и steps — заголовок и массив пар «заголовок + текст»; FAQ — заголовок и массив пар «вопрос + ответ». Неизвестные ключи, raw HTML, пустые обязательные строки, превышение лимитов и небезопасные CTA отклоняются. Массивы ограничены по числу элементов. При PATCH новое `data` валидируется как полная замена контракта вместе с сохраненным `blockType`, а не как свободный частичный JSON; условная запись блокирует конкурентную смену discriminator. Public catalog повторно валидирует сохраненный JSON и требует ровно один видимый hero у непустой блочной страницы. Для опубликованной городской `HOME` контракт строже: обязателен точный порядок семи видимых блоков `hero`, `service_grid`, `tariff_grid`, `steps`, двух `feature_grid` и `faq`.

Форма заявки остается отдельным системным компонентом публичной страницы и в `PageBlock` не моделируется. Для городской HOME именно упорядоченный набор блоков определяет контентную структуру; отдельный hardcoded fallback удален. Внутренние `hero.data.ctaHref` хранятся без завершающего слэша; migration `0018_page_block_cta_paths` идемпотентно нормализует legacy-значения. `0019` и `0020` фиксируют снимки Казани и отдельный номер техподдержки. Миграции `0021`–`0023` добавляют первые четыре global-типа и nullable scope. `0024` отдельно добавляет `COOKIE_POLICY`, а `0025` обновляет scope constraint, создает пятую global page, публикует обязательные общие страницы, все существующие города и их `HOME`, не изменяя тарифы и заявки. `0026` добавляет канонические блоки только в пустые опубликованные городские HOME, используя `namePrepositional`, и сохраняет любые уже существующие композиции. `0030` только добавляет nullable `archivedAt` и индекс, поэтому существующие блоки остаются активными. `0031` аддитивно расширяет жизненный цикл публикации состояниями `SCHEDULED`/`CANCELLED`, добавляет `scheduledFor`/`cancelledAt` и индекс выборки наступивших расписаний; существующие снимки и публикации не меняются. `0032` fail-closed принимает только единственную каноническую HOME либо известную пару `slug=''` + `slug='home'` с одинаковыми status/SEO/content/блоками; во втором случае переводит `Lead.pageId` и `AddressCheck.pageId`, удаляет legacy-строку, добавляет DB-инварианты и системную рабочую ревизию. Исторические `SitePublication.catalog` не переписываются. Seed и city import используют общий application-level factory `template:city-home:v1`; отдельной сущности шаблона в БД пока нет.

Миграция `0035` переносит единственные непротиворечивые городские номера на `Site`, нормализует их в `7XXXXXXXXXX` и удаляет поля City. Несколько разных значений или неверный российский номер останавливают миграцию с ошибкой; скрытого выбора и подстановки нет. Nullable-схема позволяет развернуть миграцию на пустой базе, но readiness gate запрещает публикацию и build без обоих телефонов.

Миграция `0036` вводит `HAS_OFFICE`/`NO_OFFICE`, runtime-ссылку на проверенный профиль абонента и timestamps города; удаляет неиспользуемый творительный падеж, City SEO/content и Region phone/content. Она fail-closed отклоняет частично заполненный офис и непустые удаляемые JSON override, чтобы deployment не потерял редакционные данные молча. Readiness города отдельно проверяет регион, название и обе используемые формы, slug, согласованность офиса, каноническую HOME и хотя бы один опубликованный тариф; отсутствие профиля остается предупреждением с отдельным подтверждением.

## Тарифы и импорты

`Tariff` хранит provider/city, name, slug, service type, standard/promo price, speed, promo text, nullable connection fee, availability, external/identity keys, source, attributes, seo и publication status. Нулевой `connectionFee` означает бесплатное подключение, положительный — его стоимость, а `NULL` — отсутствие публичной строки. Канонический import принимает ровно 37 колонок в фиксированном порядке. Source-specific поля не дублируются в верхнем уровне: единый закрытый реестр `TARIFF_ATTRIBUTE_FIELDS` нормализует очищенный текст, целые значения, booleans, коды и статусы услуг для import и ручного PATCH; пустые значения не сохраняются, неизвестные ключи отклоняются. Импортные `-1/0/1` сохраняются внутри JSON как `INCLUDED/UNAVAILABLE/OPTIONAL`; `show_on_site`, внешние/производные поля оборудования и отдельное название игры в новом контракте отсутствуют. Ограничения модели пока прежние: unique `(cityId, slug)` и `(cityId, identityKey)`; identity key для ручной правки и импорта одинаков — `cityId:slug:serviceType`, а публичный slug остается уникальным в городе независимо от типа услуги. Переход identity и lifecycle на целевую модель выполняют отдельные T2/T3, поэтому T1 не добавляет Prisma migration.

Миграция `0016_admin_list_pagination_indexes` добавляет составные индексы `Tariff(updatedAt, id)` и `Lead(createdAt, id)` для стабильного keyset/cursor обхода административных журналов. Фильтр статуса заявок использует существующий `Lead(status, createdAt)`, а тарифные city/service/status-фильтры — `Tariff(cityId, serviceType, status)`. Подстроковый `q` остается bounded-поиском по текущему каталогу и не подменяется неутвержденным полнотекстовым индексом.

`TariffImportRun` и `CityImportRun` сохраняют метаданные файла, счетчики, JSON report, `VALIDATED`/`APPLIED`/`UNDONE`/`FAILED`, время и автора apply/undo, JSON change set и номера undo-ревизий. Эти поля введены единой миграцией. Tariff change set версии 2 содержит exact before/after catalog, контентный снимок redirects, связи заявок с удаляемыми тарифами, карту сайтов/городов и созданные рабочие ревизии. Tariff undo требует совпадения текущего post-import каталога, отсутствия более поздних затрагивающих `ContentRevision` и неизменных lead links; затем восстанавливает бизнес-поля тарифов и связи, не откатывая системные `updatedAt`, создает `UNDO` revisions с аудитом обоих видов данных и условно переводит run из `APPLIED` в `UNDONE` в той же serializable-транзакции. Счетчики переходов редиректа не входят в content guard. Старый tariff change set версии 1 намеренно не отменяется, потому что не содержит связей заявок. City change set версии 1 фиксирует выбранные действия, before/after cities, созданные regions/pages и рабочую ревизию. City undo требует точного совпадения этих снимков, отсутствия последующих ревизий и зависимых данных у новых городов; затем восстанавливает прежние города, удаляет только сохраненные новые записи и создает attributed `UNDO` revision в той же serializable-транзакции. Tariff report содержит нормализованные candidates и preview diff полного provider snapshot; apply с transaction timeout 120 секунд атомарно удаляет отсутствующие в snapshot тарифы. City report имеет явную версию и хранит номер строки, normalized candidate, snapshot найденного города и field-level diff; report прежней версии требует повторной валидации. City apply требует полный `create/update/skip` map, сверяет snapshot и сохраняет attributed ревизию в serializable-транзакции. Сырые файлы не сохраняются; отдельной построчной import history нет.

## Проверки и заявки

| Сущность | Назначение |
| --- | --- |
| `AddressCheck` | Фактический нормализованный адрес, object type, status, raw provider response и site/city/page source-контекст. `cityId` обозначает город страницы и не ограничивает географию адреса. |
| `Lead` | Контакты, фактический адрес, allowlisted и bounded UTM, URL/form/device/visited pages с лимитом 16 KB JSON, address/contract results, processing status, external lead data, operator status. `cityId` обозначает город страницы-источника. |
| `LeadDeliveryAttempt` | Каждый queue/API/email attempt, idempotency key, payload/response/error, next retry time. |
| `LeadNotification` | Одна persistent outbox/status-запись обычного оповещения на лид: revision, attempts, transport, безопасный error code/HTTP status и provider message ID без копии телефона, адреса или текста письма. |
| `LeadActivityEvent` | События браузера до формы: allowlisted оболочка `type/data`, до 100 событий и 64 KB JSON суммарно; `data` ограничен 4 KB, 20 ключами и глубиной. |
| `LeadStatusHistory` | Операторские переходы NEW/IN_PROGRESS/CALL_LATER/CONNECTED/REJECTED. |
| `LeadAccessToken` | SHA-256 hash одноразовой fallback-ссылки, срок действия, отметки использования и отзыва; связан ровно с одной заявкой и удаляется каскадно. |

`LeadProcessingStatus` отделяет delivery flow от операторского `LeadStatus`. Помимо технических/доставочных исходов, миграция `0013_lead_provider_outcomes` добавляет две однозначные причины непередачи: `PROVIDER_NOT_AVAILABLE_NOT_SENT` (провайдеры есть, Дом.ру среди них нет) и `NO_PROVIDERS_NOT_SENT` (Tarifnik вернул пустой список). Они не подменяются ручной проверкой, потому что отрицательный ответ уже однозначен. Миграция `0014_delivery_queue_status` добавляет `DELIVERY_QUEUE_ERROR` и канал `QUEUE`, чтобы сбой producer не оставался ложным `PENDING` и был виден отдельно от ответа Tarifnik/email.

Миграция `0015_lead_notification_outbox` добавляет `LeadNotification` и статусы `PENDING/QUEUED/RUNNING/RETRYING/SUCCEEDED/FAILED`. Запись создается в одной транзакции с `Lead`; revision отделяет ручные циклы, а persisted attempts сохраняют общий лимит после потери Redis. Каждый queue job имеет revision+attempt в ID и удаляется после terminal BullMQ outcome. Свежий `RUNNING` защищен lease, ручной retry — compare-and-swap. Доставка имеет at-least-once семантику, а idempotency header `lead-notification-<leadId>-revision-<revision>` снижает риск дубля внутри автоматических попыток и не блокирует новый ручной цикл.

Согласованная маршрутизация требует хранить отдельно исходные ответы проверок, нормализованное решение и реальные delivery attempts. Отсутствие Дом.ру, подтвержденный действующий абонент и неоднозначный ответ API — разные причины непередачи. API Dom.ru вызывается после обнаружения хотя бы одного провайдера; только успешный ответ ожидаемой структуры с явным `contacts: []` означает `NOT_FOUND`, но delivery дополнительно требует наличия Дом.ру. Отсутствие или неверный тип `contacts` является ошибкой контракта и должно приводить к `MANUAL_CHECK_API`. Для видимой проверки подключения `AddressCheck` может существовать без `Lead`; лид появляется только после найденного Дом.ру и ввода телефона.

Для retention не добавлена отдельная policy-таблица: юридически утвержденный срок приходит только из обязательной production-переменной `PII_RETENTION_DAYS`. Миграция `0012_pii_retention_indexes` добавила индексы по времени; `0016` расширяет индекс `Lead.createdAt` полем `id`, сохраняя тот же ведущий столбец для purge-запроса. `AddressCheck.createdAt` остается отдельным индексом. Bounded hard-delete старого `Lead` каскадно удаляет history, delivery attempts, notification evidence, activity и access tokens; свежие duplicates предварительно отвязываются, старый `AddressCheck` удаляется только без оставшихся ссылок. Это исключает частичную «анонимизацию», при которой PII мог бы остаться в JSON.

## Доступ и технические записи

`User` содержит email, `passwordHash`, name, active и timestamps. Ролевой модели нет: любая активная учетная запись имеет единый уровень доступа администратора. `Session` хранит не raw token, а его SHA-256 hash и expiry. При reset password или deactivate API удаляет sessions пользователя. `LeadAccessToken` также хранит только hash: raw token существует лишь в одноразовой email-ссылке и не возвращается административными CRM routes.

`Redirect` хранит site/city, no-slash source/target path, status, `hitCount`, `lastHitAt`, опциональный `managedTariffId` и timestamps. `managedTariffId` — provenance автоматического правила без foreign key: это позволяет сохранить redirect history после удаления тарифа. Только управляемое тарифом правило синхронизирует status с его публикацией; совместимое ручное правило не захватывается. Admin API создает, изменяет и архивирует записи; published-правило проходит проверку конфликтов, запрета цепочек и принадлежности target к Release 1 route inventory. Каждая ручная мутация в той же транзакции создает рабочую ревизию и before/after audit, но не запускает публикацию. Во время Astro build эффективные записи превращаются в точные Caddy matchers, а runtime resolver повторно проверяет последний успешный publication snapshot, атомарно учитывает переход и отдает HTTP 301. Удаление реализовано как `ARCHIVED`, а общий экран корзины позволяет вернуть редирект в рабочий `DRAFT`; предложения редиректа из 404 пока отсутствуют.

`SiteRebuild` — одна актуальная outbox/status-запись на `dedupeKey` сайта. Она хранит affected paths, последнюю причину, `requestedRevision`, `processingRevision`, `publishedRevision`, число попыток, ошибку и финальный ответ deployment provider. Три nullable-ссылки `requestedPublicationId`, `processingPublicationId`, `publishedPublicationId` не дают новой правке заменить снимок уже идущей сборки. Ревизия считается опубликованной только при статусе `SUCCEEDED`; новая мутация во время активной сборки увеличивает requested revision и создает следующий job после завершения текущего.

`Site.workingRevision` — монотонный номер сохраненного состояния CMS, `Site.publishedRevision` — номер последнего успешно развернутого снимка. `ContentRevision` хранит неизменяемые JSON-снимки сущности до и после изменения, ее собственный номер версии, общую ревизию сайта, источник, автора и измененные поля. Номер `entityRevision` глобален для пары `(entityType, entityId)`, даже если общий Provider затрагивает несколько сайтов; изменение Provider создает отдельную запись и site revision для каждого такого сайта. `AuditEvent` — отдельная append-only запись действия с явными значениями `before`/`after` для каждого верхнеуровневого измененного поля. `SitePublication` хранит полный денормализованный Release 1 каталог одной рабочей ревизии и состояния `SCHEDULED`/`PENDING`/`RUNNING`/`SUCCEEDED`/`FAILED`/`CANCELLED`, включая `scheduledFor`, `cancelledAt` и безопасное evidence deployment provider. Уникальность `(siteId, siteRevision)` не допускает два разных публикационных снимка одной рабочей версии. Расписание фиксирует каталог сразу, поэтому последующие рабочие изменения не входят в запланированный выпуск; более старый наступивший снимок отменяется, если уже существует более новая активная или опубликованная версия. Все текущие content mutators, включая программный import тарифов и apply/undo обоих XLSX-импортов, создают рабочие ревизии без автоматической публикации; создание Provider до появления Site не имеет public site scope и потому не создает ревизию. Защищенные publication endpoints фиксируют точную ожидаемую ревизию для немедленного или отложенного запуска.

## Реальное наследование

Public catalog разрешает уровни `content` в таком порядке:

```text
Provider.settings.content -> Site.settings.content -> Page.content
```

Для site-global Page цепочка сокращается до `Provider.settings.content -> Site.settings.content -> Page.content`. В публичное наследование из настроек Provider/Site входит только явный namespace `content`; соседние credentials, integration settings и другие приватные ключи не участвуют.

Контракт разрешения `content` пока сохраняет переходную цепочку Provider → Site → Page: вложенные JSON-объекты объединяются рекурсивно, а массив, строка, число, boolean и `null` целиком заменяют родительское значение. Город и регион больше не участвуют в наследовании. SEO страницы или тарифа читается только из соответствующей записи до перехода на общие SEO-шаблоны; локального SEO города нет.

`PageBlock` не участвует в JSON-наследовании и не объединяется как массив: city HOME получает снимок общего application-level шаблона при создании или backfill, после чего блоки остаются самостоятельной упорядоченной композицией Page. Отдельной версионируемой сущности шаблона и UI с происхождением каждого эффективного поля пока нет; их нельзя подменять неявным merge-механизмом.

## Чего в модели нет

Нет сущностей для media library, page template, analytics aggregates, SEO validation, variable registry, category/collection, equipment, channel package, review, persisted legal retention policy и provider integration profile. Модели версий/аудита, отложенная публикация точного snapshot, общий read-only admin-журнал, корзина status-сущностей/PageBlock и guarded undo двух XLSX-импортов уже добавлены, но preview и универсальный per-entity rollback поверх них еще не реализованы. Retention mechanism существует, но конкретный срок остается внешним legal decision. Перед добавлением новых сущностей нужно утвердить их interface и ownership, а не использовать неструктурированный JSON как постоянную замену.
