# Модель данных текущего прототипа

Источник правды: `prisma/schema.prisma` и 46 последовательных миграций от `0001_initial` до `0046_lead_decision_events`. Этот документ отличает существующие таблицы от объектов, которые фигурируют только в продуктовом плане; примененность конкретной миграции во внешнем контуре подтверждается отдельно, а не выводится из репозитория.

## Сущности контента и географии

| Сущность | Реальные ключевые поля | Связи и статус |
| --- | --- | --- |
| `Provider` | `name`, unique `slug`, `legalData`, `settings` | Имеет sites и tariffs. |
| `Site` | `providerId`, `name`, unique `slug`, `domain`, нормализованные `connectionPhone` и `supportPhone`, `settings`, `status`, `workingRevision`, `publishedRevision` | Имеет regions, cities, pages, leads, checks, redirects, sitemap exclusions, SEO templates, revisions, publications, audit events и rebuild status. |
| `SeoTemplate` | `siteId`, enum `kind`, обязательные `titleTemplate`/`descriptionTemplate`, enum `indexState`, nullable `ogTitleTemplate`/`ogDescriptionTemplate`/`ogImageUrl` | Unique `(siteId, kind)` для восьми типов Release 1. `0047_seo_templates` создаёт значения по умолчанию, `0048_seo_open_graph` аддитивно добавляет необязательные OG-поля; старые `Page.seo` и `Tariff.seo` не удаляются до отдельной сверки. Разрешённые SEO и OG-значения и предупреждения фиксируются в publication catalog как `seoByPath`/`seoWarnings`. |
| `Region` | `siteId`, `name`, `slug` | Unique `(siteId, slug)`, содержит cities. Телефон и произвольный content региону не принадлежат. |
| `City` | site/region, название и используемые родительный/предложный варианты, slug, legacy URL, явное состояние офиса, адрес/режим, проверенный `subscriberProfileKey`, `status`, timestamps | Unique `(siteId, slug)`, имеет pages, tariffs, leads, checks, redirects. Телефоны, SEO и произвольный content городу не принадлежат. |
| `Page` | `siteId`, nullable `cityId`, `type`, `title`, `slug`, `status`, `seo`, `content` | City pages имеют unique `(cityId, slug)`; site-global pages — partial unique `(siteId, slug) WHERE cityId IS NULL`; городская `HOME` дополнительно имеет пустой slug и partial unique `(cityId) WHERE type = HOME`; имеет ordered blocks. |
| `PageBlock` | `blockType`, `position`, `visible`, JSON `data`, optional `source`, nullable `archivedAt` | Cascade delete только вместе с parent Page. Ручной DELETE выставляет `archivedAt`, а restore очищает его; API разрешает `hero`, `rich_text`, `tariff_grid`, `service_grid`, `feature_grid`, `steps` и `faq`; `position` задает порядок активных visible-блоков. |

`PublishStatus` принимает `DRAFT`, `PUBLISHED`, `ARCHIVED`. `PageType` дополнительно содержит пять типов Release 1: `COVERAGE`, `CITIES`, `PRIVACY`, `PERSONAL_DATA_CONSENT`, `COOKIE_POLICY`. DB constraint разрешает им только `cityId IS NULL`, а всем остальным типам — только непустой `cityId`; admin API до записи также проверяет scope и точный slug общей страницы. Для `HOME` база и API независимо требуют пустой slug и не допускают вторую HOME того же города независимо от статуса. Город, Page, Tariff и Redirect используют `ARCHIVED` как корзину, а PageBlock — nullable `archivedAt`; общий admin endpoint группирует их по сайту. `SitemapExclusion` хранит уникальную пару `(siteId, path)`, обязательную причину, автора и timestamps; тип карты не дублируется в БД, а выводится из authoritative route kind. `0033` добавляет эту таблицу без изменения существующих публикаций. Дата отложенного запуска хранится не на content-сущностях, а в зафиксированном `SitePublication`. Рабочий preview уже реализован: защищенный endpoint собирает текущий каталог без создания публикации или rebuild, а `/preview` показывает его в sandboxed iframe; отсутствует только отдельный внешний preview token/link.

JSON `data` не является произвольным хранилищем. API применяет закрытый discriminated contract по `blockType`: hero содержит заголовок, текст и опциональные eyebrow/CTA; rich text — заголовок и текст; tariff grid — заголовок и опциональные фильтр услуги, лимит 1–12 и тип страницы для ссылки на полный каталог; service grid — заголовок и ссылки по допустимому типу опубликованной страницы; feature grid и steps — заголовок и массив пар «заголовок + текст»; FAQ — заголовок и массив пар «вопрос + ответ». Неизвестные ключи, raw HTML, пустые обязательные строки, превышение лимитов и небезопасные CTA отклоняются. Массивы ограничены по числу элементов. При PATCH новое `data` валидируется как полная замена контракта вместе с сохраненным `blockType`, а не как свободный частичный JSON; условная запись блокирует конкурентную смену discriminator. Public catalog повторно валидирует сохраненный JSON и требует ровно один видимый hero у непустой блочной страницы. Для опубликованной городской `HOME` контракт строже: обязателен точный порядок семи видимых блоков `hero`, `service_grid`, `tariff_grid`, `steps`, двух `feature_grid` и `faq`.

Форма заявки остается отдельным системным компонентом публичной страницы и в `PageBlock` не моделируется. Для городской HOME именно упорядоченный набор блоков определяет контентную структуру; отдельный hardcoded fallback удален. Внутренние `hero.data.ctaHref` хранятся без завершающего слэша; migration `0018_page_block_cta_paths` идемпотентно нормализует legacy-значения. `0019` и `0020` фиксируют снимки Казани и отдельный номер техподдержки. Миграции `0021`–`0023` добавляют первые четыре global-типа и nullable scope. `0024` отдельно добавляет `COOKIE_POLICY`, а `0025` обновляет scope constraint, создает пятую global page, публикует обязательные общие страницы, все существующие города и их `HOME`, не изменяя тарифы и заявки. `0026` добавляет канонические блоки только в пустые опубликованные городские HOME, используя `namePrepositional`, и сохраняет любые уже существующие композиции. `0030` только добавляет nullable `archivedAt` и индекс, поэтому существующие блоки остаются активными. `0031` аддитивно расширяет жизненный цикл публикации состояниями `SCHEDULED`/`CANCELLED`, добавляет `scheduledFor`/`cancelledAt` и индекс выборки наступивших расписаний; существующие снимки и публикации не меняются. `0032` fail-closed принимает только единственную каноническую HOME либо известную пару `slug=''` + `slug='home'` с одинаковыми status/SEO/content/блоками; во втором случае переводит `Lead.pageId` и `AddressCheck.pageId`, удаляет legacy-строку, добавляет DB-инварианты и системную рабочую ревизию. Исторические `SitePublication.catalog` не переписываются. Seed и city import используют общий application-level factory `template:city-home:v1`; отдельной сущности шаблона в БД пока нет.

Миграция `0035` переносит единственные непротиворечивые городские номера на `Site`, нормализует их в `7XXXXXXXXXX` и удаляет поля City. Несколько разных значений или неверный российский номер останавливают миграцию с ошибкой; скрытого выбора и подстановки нет. Nullable-схема позволяет развернуть миграцию на пустой базе, но readiness gate запрещает публикацию и build без обоих телефонов.

Forward-only migration `0039` восстанавливает только пропущенный revision trail после `0034`–`0035`. Она выбирает Site, у которого последний `SUCCEEDED` snapshot не совпадает с live name/slug/телефонами, `workingRevision = publishedRevision` и нет уже подготовленной более новой `ContentRevision`. Для такого сайта `workingRevision` увеличивается ровно на один и добавляются согласованные `ContentRevision`/`AuditEvent`. Исторические `SitePublication` не меняются, автоматической публикации нет; повторный запуск не создает вторую revision.

Миграция `0036` вводит `HAS_OFFICE`/`NO_OFFICE`, runtime-ссылку на проверенный профиль абонента и timestamps города; удаляет неиспользуемый творительный падеж, City SEO/content и Region phone/content. Она fail-closed отклоняет частично заполненный офис и непустые удаляемые JSON override, чтобы deployment не потерял редакционные данные молча. Readiness города отдельно проверяет регион, название и обе используемые формы, slug, согласованность офиса, каноническую HOME и хотя бы один опубликованный тариф; отсутствие профиля остается предупреждением с отдельным подтверждением.

## Тарифы и импорты

`Tariff` хранит provider/city, name, slug, service type, standard/promo price, speed, promo text, nullable connection fee, enum `availability`, legacy external key, обязательный внутренний identity key, source, attributes, seo и publication status. Нулевой `connectionFee` означает бесплатное подключение, положительный — его стоимость, а `NULL` — отсутствие публичной строки. Канонический import принимает ровно 37 колонок в фиксированном порядке. Source-specific поля не дублируются в верхнем уровне: единый закрытый реестр `TARIFF_ATTRIBUTE_FIELDS` нормализует очищенный текст, целые значения, booleans, коды и статусы услуг для import и ручного PATCH; пустые значения не сохраняются, неизвестные ключи отклоняются. Импортные `-1/0/1` сохраняются внутри JSON как `INCLUDED/UNAVAILABLE/OPTIONAL`; `show_on_site`, внешние/производные поля оборудования и отдельное название игры в новом контракте отсутствуют. Ограничения модели: unique `(cityId, slug)` и `(cityId, identityKey)`; `identityKey = cityId:normalized(name):serviceType`, где пробелы нормализуются и регистр игнорируется, а пунктуация и `е/ё` сохраняются. `0037_tariff_business_identity` fail-closed проверяет дубликаты, пересчитывает ключи и делает поле обязательным. `0038_tariff_archive_lifecycle` заменяет boolean на `ACTIVE/ARCHIVED`, хранит причину, время и import run архива и DB constraint-ом запрещает несогласованные lifecycle-состояния.

Миграция `0016_admin_list_pagination_indexes` добавляет составные индексы `Tariff(updatedAt, id)` и `Lead(createdAt, id)` для стабильного keyset/cursor обхода административных журналов. Фильтр статуса заявок использует существующий `Lead(status, createdAt)`, а тарифные city/service/status-фильтры — `Tariff(cityId, serviceType, status)`. Подстроковый `q` остается bounded-поиском по текущему каталогу и не подменяется неутвержденным полнотекстовым индексом.

`TariffImportRun` и `CityImportRun` сохраняют метаданные файла, счетчики, JSON report, `VALIDATED`/`APPLIED`/`UNDONE`/`FAILED`, время и автора apply/undo, JSON change set и номера undo-ревизий. Tariff report версии 3 содержит нормализованные candidates, exact catalog snapshot, счетчики `create/update/archive/unchanged` и field-level diff по каждому тарифу. Apply с transaction timeout 120 секунд атомарно архивирует отсутствующие в snapshot активные тарифы, не удаляя строки и не меняя их `Lead.tariffId`. Change set версии 3 содержит exact before/after catalog вместе с archive provenance, контентный снимок redirects, карту сайтов/городов и созданные рабочие ревизии. Guarded undo требует совпадения текущего post-import каталога и отсутствия более поздних затрагивающих `ContentRevision`, затем восстанавливает бизнес-поля и lifecycle, создает `UNDO` revisions и условно переводит run из `APPLIED` в `UNDONE` в той же serializable-транзакции. Версия 2 остается undo-совместимой через нормализацию бывшего boolean availability; версия 1 намеренно не отменяется. Счетчики переходов редиректа не входят в content guard. City change set версии 1 фиксирует выбранные действия, before/after cities, созданные regions/pages и рабочую ревизию. City undo требует точного совпадения этих снимков, отсутствия последующих ревизий и зависимых данных у новых городов; затем восстанавливает прежние города, удаляет только сохраненные новые записи и создает attributed `UNDO` revision в той же serializable-транзакции. Сырые файлы не сохраняются; отдельной построчной import history нет.

## Проверки и заявки

| Сущность | Назначение |
| --- | --- |
| `AddressCheck` | Фактический нормализованный адрес, object type, status, raw provider response и site/city/page source-контекст. `cityId` обозначает город страницы и не ограничивает географию адреса. |
| `Lead` | Контакты, фактический адрес, allowlisted и bounded UTM, URL/form/device/visited pages с лимитом 16 KB JSON, address/contract results, processing status, external lead data, operator status. `cityId` обозначает город страницы-источника; nullable unique `submissionKey`, `consentVersion` и `consentAcceptedAt` сохраняют идемпотентность новой публичной отправки и техническое evidence согласия, оставаясь nullable для исторических лидов. Nullable `configurationSnapshot` хранит неизменяемые выбор, компоненты, цены и итоги новых тарифных заявок. Nullable `reasonCode`, `reasonLabel`, `reasonRoute`, `reasonRegistryVersion` — серверный неизменяемый снимок причины; исторические лиды остаются с `null`. |
| `LeadDeliveryAttempt` | Каждый queue/API/email attempt, idempotency key, payload/response/error, next retry time. |
| `LeadNotification` | Одна persistent outbox/status-запись обычного оповещения на лид: revision, attempts, transport, безопасный error code/HTTP status и provider message ID без копии телефона, адреса или текста письма. |
| `LeadActivityEvent` | События браузера до формы: allowlisted оболочка `type/data`, до 100 событий и 64 KB JSON суммарно; `data` ограничен 4 KB, 20 ключами и глубиной. |
| `LeadStatusHistory` | Операторские переходы NEW/IN_PROGRESS/CALL_LATER/CONNECTED/REJECTED. |
| `LeadDecisionEvent` | Append-only события проверки телефона, проверки абонента, выбора маршрута, ручного повтора и переанализа комментария: тип, исход, глобальный номер попытки, автор, ограниченное evidence и время. Удаляется каскадно вместе с Lead при PII purge. |
| `LeadAccessToken` | SHA-256 hash одноразовой fallback-ссылки, срок действия, отметки использования и отзыва; связан ровно с одной заявкой и удаляется каскадно. |

`LeadProcessingStatus` отделяет delivery flow от операторского `LeadStatus`. Помимо технических/доставочных исходов, миграция `0013_lead_provider_outcomes` добавила две исторические однозначные причины непередачи: `PROVIDER_NOT_AVAILABLE_NOT_SENT` и `NO_PROVIDERS_NOT_SENT`. После F2 публичный `/leads` вообще не создает лид для этих результатов: телефон запрашивается и принимается только при persisted `AVAILABLE` с Дом.ру. Миграция `0014_delivery_queue_status` добавляет `DELIVERY_QUEUE_ERROR` и канал `QUEUE`, чтобы сбой producer не оставался ложным `PENDING` и был виден отдельно от ответа Tarifnik/email.

Миграция `0015_lead_notification_outbox` добавляет `LeadNotification` и статусы `PENDING/QUEUED/RUNNING/RETRYING/SUCCEEDED/FAILED`. Запись создается в одной транзакции с `Lead`; revision отделяет ручные циклы, а persisted attempts сохраняют общий лимит после потери Redis. Каждый queue job имеет revision+attempt в ID и удаляется после terminal BullMQ outcome. Свежий `RUNNING` защищен lease, ручной retry — compare-and-swap. Доставка имеет at-least-once семантику, а idempotency header `lead-notification-<leadId>-revision-<revision>` снижает риск дубля внутри автоматических попыток и не блокирует новый ручной цикл.

Согласованная маршрутизация требует хранить отдельно исходные ответы проверок, нормализованное решение и реальные delivery attempts. Отсутствие Дом.ру, подтвержденный действующий абонент и неоднозначный ответ API — разные причины непередачи. API Dom.ru вызывается после обнаружения хотя бы одного провайдера; только успешный ответ ожидаемой структуры с явным `contacts: []` означает `NOT_FOUND`, но delivery дополнительно требует наличия Дом.ру. Отсутствие или неверный тип `contacts` является ошибкой контракта и должно приводить к `MANUAL_CHECK_API`. Для видимой проверки подключения `AddressCheck` может существовать без `Lead`; лид появляется только после найденного Дом.ру и ввода телефона.

Для retention не добавлена отдельная policy-таблица: согласованный срок 180 дней задается обязательной production-переменной `PII_RETENTION_DAYS=180`. Миграция `0012_pii_retention_indexes` добавила индексы по времени; `0016` расширяет индекс `Lead.createdAt` полем `id`, сохраняя тот же ведущий столбец для purge-запроса. `AddressCheck.createdAt` остается отдельным индексом. Bounded hard-delete старого `Lead` каскадно удаляет history, delivery attempts, notification evidence, activity и access tokens; свежие duplicates предварительно отвязываются, старый `AddressCheck` удаляется только без оставшихся ссылок. Это исключает частичную «анонимизацию», при которой PII мог бы остаться в JSON.

Миграция `0040_lead_positive_submission` аддитивно добавляет `Lead.submissionKey`, `consentVersion` и `consentAcceptedAt`, а также unique index для server-side idempotency. Старые записи не переписываются; для каждой новой публичной заявки поля обязательны на уровне DTO/controller, телефон сохраняется нормализованным, а положительный `AddressCheck` и выбранный `tariffId` остаются отдельными неизменяемыми ссылками факта отправки. Миграция `0041_lead_configuration_snapshot` добавляет nullable JSONB без переписывания исторических лидов. Новая тарифная заявка сохраняет нормализованный выбор, ID/название тарифа, выбранные компоненты, строки ежемесячных и разовых платежей, итоги, отпечаток серверного расчёта и время фиксации; снимок не зависит от последующих правок тарифа.

Миграция `0043_lead_reason_snapshot` аддитивно добавляет четыре nullable поля снимка причины, индекс `(siteId, reasonCode, createdAt)` для фильтра журнала и `NON_SALES_NOT_SENT` в processing enum. Закрытый справочник имеет версию `1`: `new_connection` проходит sales-проверки, `existing_subscriber_support`/`billing` сохраняются без внешней sales-доставки, `relocation`/`other` остаются на ручном решении. Код и подпись берутся из серверного реестра при создании и не обновляются при последующих изменениях справочника.

Миграция `0044_lead_comment_analysis` аддитивно добавляет nullable исходный пользовательский `Lead.comment` и снимок результата анализа: `commentAnalysisVersion`, `commentAnalysisOutcome`, `commentAnalysisCategory`, `commentAnalysisEvidence` (JSONB-массив точных фрагментов и позиций) и `commentAnalysisExplanation`. Отсутствующий комментарий не анализируется и сохраняет `null`, исторические лиды не переписываются. Правила версии 1 находятся в коде; результат не переоценивается автоматически при будущей смене правил. Ручной исход блокирует sales-доставку, но не отклоняет заявку.

`0045_lead_phone_decision` добавляет статусы фонового решения и nullable evidence DaData Phone: status, `qc`, нормализованный номер, время, попытку, источник `API`/`CACHE`, безопасный технический код, срок следующего повтора и lease решения. Полный ответ DaData не хранится; исторические лиды остаются с `null`. Индексы поддерживают 24-часовое повторное использование финального результата и восстановление незавершенной обработки.

`0046_lead_decision_events` аддитивно добавляет `LeadDecisionEvent` и nullable `Lead.decisionAttemptNumber`. События сохраняются в той же транзакции, что и итог каждого шага фонового решения; ручной повтор после финальной технической ошибки и переанализ комментария также фиксируют автора и прежний результат до изменения текущего снимка. Историческим заявкам таблица не заполняется задним числом. `decisionAttemptNumber` позволяет после истечения lease восстановить именно выполнявшуюся попытку, не выдавая ее за предыдущую.

## Доступ и технические записи

`User` содержит email, `passwordHash`, name, active и timestamps. Ролевой модели нет: любая активная учетная запись имеет единый уровень доступа администратора. `Session` хранит не raw token, а его SHA-256 hash и expiry. При reset password или deactivate API удаляет sessions пользователя. `LeadAccessToken` также хранит только hash: raw token существует лишь в одноразовой email-ссылке и не возвращается административными CRM routes.

`Redirect` хранит site/city, no-slash source/target path, status, `hitCount`, `lastHitAt`, опциональный `managedTariffId` и timestamps. `managedTariffId` — provenance автоматического правила без foreign key: это позволяет сохранить redirect history после удаления тарифа. Только управляемое тарифом правило синхронизирует status с его публикацией; совместимое ручное правило не захватывается. Admin API создает, изменяет и архивирует записи; published-правило проходит проверку конфликтов, запрета цепочек и принадлежности target к Release 1 route inventory. Каждая ручная мутация в той же транзакции создает рабочую ревизию и before/after audit, но не запускает публикацию. Во время Astro build эффективные записи превращаются в точные Caddy matchers, а runtime resolver повторно проверяет последний успешный publication snapshot, атомарно учитывает переход и отдает HTTP 301. Удаление реализовано как `ARCHIVED`, а общий экран корзины позволяет вернуть редирект в рабочий `DRAFT`; предложения редиректа из 404 пока отсутствуют.

`SiteRebuild` — одна актуальная outbox/status-запись на `dedupeKey` сайта. Она хранит affected paths, последнюю причину, `requestedRevision`, `processingRevision`, `publishedRevision`, число попыток, ошибку и финальный ответ deployment provider. Три nullable-ссылки `requestedPublicationId`, `processingPublicationId`, `publishedPublicationId` не дают новой правке заменить снимок уже идущей сборки. Ревизия считается опубликованной только при статусе `SUCCEEDED`; новая мутация во время активной сборки увеличивает requested revision и создает следующий job после завершения текущего.

`Site.workingRevision` — монотонный номер сохраненного состояния CMS, `Site.publishedRevision` — номер последнего успешно развернутого снимка. `ContentRevision` хранит неизменяемые JSON-снимки сущности до и после изменения, ее собственный номер версии, общую ревизию сайта, источник, автора и измененные поля. Номер `entityRevision` глобален для пары `(entityType, entityId)`, даже если общий Provider затрагивает несколько сайтов; изменение Provider создает отдельную запись и site revision для каждого такого сайта. `AuditEvent` — отдельная append-only запись действия с явными значениями `before`/`after` для каждого верхнеуровневого измененного поля. `SitePublication` хранит полный денормализованный Release 1 каталог одной рабочей ревизии и состояния `SCHEDULED`/`PENDING`/`RUNNING`/`SUCCEEDED`/`FAILED`/`CANCELLED`, включая `scheduledFor`, `cancelledAt` и безопасное evidence deployment provider. Уникальность `(siteId, siteRevision)` не допускает два разных публикационных снимка одной рабочей версии. Расписание фиксирует каталог сразу, поэтому последующие рабочие изменения не входят в запланированный выпуск; более старый наступивший снимок отменяется, если уже существует более новая активная или опубликованная версия. Все текущие content mutators, включая программный import тарифов и apply/undo обоих XLSX-импортов, создают рабочие ревизии без автоматической публикации; создание Provider до появления Site не имеет public site scope и потому не создает ревизию. Защищенные publication endpoints фиксируют точную ожидаемую ревизию для немедленного или отложенного запуска.

## Реальное наследование

Public catalog разрешает уровни `content` в таком порядке:

```text
Provider.settings.content -> Site.settings.content -> Page.content
```

Для site-global Page цепочка сокращается до `Provider.settings.content -> Site.settings.content -> Page.content`. В публичное наследование из настроек Provider/Site входит только явный namespace `content`; соседние credentials, integration settings и другие приватные ключи не участвуют.

Контракт разрешения `content` пока сохраняет переходную цепочку Provider → Site → Page: вложенные JSON-объекты объединяются рекурсивно, а массив, строка, число, boolean и `null` целиком заменяют родительское значение. Город и регион больше не участвуют в наследовании. Новые публикации используют site-scoped SEO-шаблоны в `seoByPath`; исторические снимки без `seoByPath` остаются совместимы с прежними Page/Tariff SEO-значениями. Локального SEO города нет.

`PageBlock` не участвует в JSON-наследовании и не объединяется как массив: city HOME получает снимок общего application-level шаблона при создании или backfill, после чего блоки остаются самостоятельной упорядоченной композицией Page. Отдельной версионируемой сущности шаблона и UI с происхождением каждого эффективного поля пока нет; их нельзя подменять неявным merge-механизмом.

## Чего в модели нет

Нет сущностей для media library, page template, analytics aggregates, SEO validation, универсального variable registry, category/collection, equipment, channel package, review, persisted legal retention policy и provider integration profile. Модели версий/аудита, отложенная публикация точного snapshot, защищенный рабочий preview, общий read-only admin-журнал, корзина status-сущностей/PageBlock и guarded undo двух XLSX-импортов уже добавлены, но внешняя preview-ссылка и универсальный per-entity rollback поверх них еще не реализованы. Retention mechanism работает с согласованным сроком 180 дней из обязательной runtime-конфигурации; юридическое основание обработки остается отдельным решением владельца. Перед добавлением новых сущностей нужно утвердить их interface и ownership, а не использовать неструктурированный JSON как постоянную замену.
