# Применение и отмена импорта тарифов

Локальная проверка [#643](https://github.com/Celtoman/astro-telekom/issues/643) от 20 ноября 2026 года. До изменения валидация искала тарифы и владельцев slug последовательными проходами по массиву. Номер строки также проверялся по всему накопленному списку предупреждений и ошибок. При применении один обновлённый или новый тариф создавал один SQL-вызов. При отмене приходился один upsert на каждый тариф из исходного каталога.

Сопоставление использует индексы по существующим парам ключей. Вставка применяет Prisma `createMany`, обновление использует параметризованный PostgreSQL `UPDATE` с типом строки таблицы `Tariff`. Batch ограничен 256 строками. Сохранённый diff, статус импорта и аудит проходят через прежнюю serializable-транзакцию. Отмена v3 использует пакетный путь для строк, присутствие которых подтверждено снимком после импорта. При отмене v2 и восстановлении отсутствующего тарифа используется прежний upsert.

## Корпус и CPU-проверка

Исходная сборка `05903e64`, Node.js 24.22.3. Синтетический пакет содержит 6 210 входных строк для 207 городов на двух сайтах одного провайдера. В базе 5 796 тарифов перед импортом. Diff включает 1 242 новых, 2 484 изменённых, 828 архивируемых и 2 484 совпадающих тарифа.

В CPU-прогоне чтения городов и тарифов возвращали одну фиксированную выборку в памяти. На каждую сборку выполнены два прогрева и семь замеров с чередованием порядка. Проверены обычный вход и вход с предупреждением в каждой строке. Полный отчёт, включая дифф, порядок диагностик и снимок каталога, совпал после исключения генерируемого времени его создания.

| Вход | Медиана CPU, мс | Медиана времени, мс |
| --- | ---: | ---: |
| Обычный | 4 281 → 1 079 | 6 415 → 1 753 |
| 6 210 предупреждений | 5 484 → 1 281 | 8 154 → 1 685 |

## PostgreSQL-профиль большого пакета

Использованы PostgreSQL 18.6, полная цепочка миграций и новые синтетические базы для каждой сборки. Применение и отмена вызваны через настоящий сервис и Prisma. Число SQL-вызовов и серверное время выполнения собраны через `pg_stat_statements`. Время сервиса включает ожидание между запросами, обмен данными, преобразование JSON и запись аудита.

| Этап | SQL-вызовы | Время сервиса, мс | Выполнение SQL, мс |
| --- | ---: | ---: | ---: |
| Проверка | 4 → 4 | 2 331 → 3 534 | 91 → 315 |
| Применение | 3 744 → 33 | 26 681 → 19 447 | 1 920 → 2 905 |
| Отмена | 5 815 → 42 | 43 693 → 16 450 | 3 271 → 3 826 |

В старом применении 2 484 отдельных обновления и 1 242 вставки составляли основную часть вызовов. В старой отмене 5 796 upsert составляли почти весь запросный объём. В новой версии эти операции требуют соответственно 10 обновлений и 5 вставок при apply и 23 обновления при undo. Архивирование по-прежнему выполняется одним запросом.

Времена большого пакета взяты из двух успешных локальных запусков при разной нагрузке на машину. Повтор старой отмены прервался на штатном лимите транзакции 120 секунд. Число вызовов и совпадение состояния воспроизводятся по фиксированному входу. Серверное время SQL и полное время запроса следует оценивать отдельно.

Парный контроль на одной локальной PostgreSQL с 720 строками и 672 существующими тарифами подтвердил сокращение времени применения с 6 751 до 2 307 мс и отмены с 6 504 до 2 384 мс. Число запросов составило 450 → 21 и 691 → 22 соответственно. Для этого контрольного пакета также совпали SHA отчёта, состояния и аудита.

## Проверка состояния и конфликтов

Для каждой сборки сохранённый change set v3 совпал с данными PostgreSQL до и после применения, включая реальные ID и timestamps. При сравнении сборок из SHA-256 бизнес-состояний исключены времена отдельных запусков и вновь сгенерированные ID. Отчёт, исходное состояние, результат применения, восстановленный каталог и содержание аудита каждого сайта совпали. Каталог после undo совпал по бизнес-полям с исходным. Архивированная строка сохранила связь с заявкой. Заявка на созданный тариф блокировала отмену до удаления синтетической зависимости.

В отдельных транзакционных сценариях проверены откат после конфликта уникальности, единственный успешный apply одного запуска при конкуренции, восстановление JSON null, дробной цены, `externalId` и исходной даты архивации при отмене v3. Сценарий исторического v2 восстановил удалённый тариф с прежним ID и заново привязал его к заявке. Локально прошли сборка и проверка типов API и 101 профильный тест.
