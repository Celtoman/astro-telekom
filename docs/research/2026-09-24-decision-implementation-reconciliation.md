## Расхождения с принятым замыслом и риски

1. **`LEAD-015` / #186:** принятое правило не позволяет одному дому без квартиры блокировать заявки других жильцов. В `apps/api/src/public-leads.controller.ts` адресный дубль сейчас определяется и без номера помещения; тест `tests/lead-check.test.cjs` закрепляет этот результат. #186 открыта как `P2` вне Release 1. Это подтвержденное расхождение реализации с контрактом, а не новый продуктовый вопрос.
2. **Доставка / #210:** `apps/api/src/lead-delivery.service.ts` может классифицировать успешную передачу в Tarifnik как failed, если последующая запись результата в БД упала. #210 открыта как `P1` без milestone. Закрытая #205 исправляла отдельный EMAIL fallback и не закрывает этот сценарий.
3. **Публикация / #179:** опубликованный catalog не содержит требуемого полного сохраненного отчета валидации всех затронутых URL. Это остающийся пункт Release 1, а не формальность закрытия Issue.
4. **Порядок исполнения:** исходный критический путь ставил внешний XLSX перед тарифными T1–T8, но эти локальные задачи уже закрыты при открытом [Celtoman/tarifs#1](https://github.com/Celtoman/tarifs/issues/1). Реализация могла развиваться на контракте из 37 колонок; полнота внешнего преобразования этим не доказана. Также L2–L5/L7, V1–V2 и S1–S3 выполнены раньше завершения P1 и остальных CMS задач. Это изменение фактического порядка, а не отмена зависимостей приемки.
5. **Проверка внешнего контура:** комментарий к #190 сообщает об успешном CI и завершенном deployment точного HEAD `28617b55aee001669428274bfeab670b34e48472`, а также о read-only проверках admin. Это свидетельство команды в Issue; независимая сквозная проверка заявки, production публикация новых SEO-правил и решение владельца о трафике не следуют из этого комментария.

## Насколько решения привязаны к работе

Реестр сохраняет происхождение всех 295 ID и статус «принято/отменено», а план связывает **группы** решений с атомарными Issues. Полной построчной матрицы `каждый ID → Issue → участок кода/тест → приемка` пока нет. Поэтому закрытие групповой задачи нельзя считать автоматической отметкой выполнения каждого отдельного ID. В частности, CMS-019–CMS-023 и CITY-001/002/007/011/019 не имеют индивидуальной ссылки на Issue в плане; их покрытие следует проверять по контракту и конкретному коду при выполнении профильных задач. `OPEN-005` и `OPEN-012` остаются вопросами; отмененные `TAR-009` и `TAR-073` не должны превращаться в задачи.

Для следующего цикла: завершить #179 и внешнюю проверку XLSX, исправить #186 и #210 по их собственным критериям, закончить #190/#200 и CMS backlog, затем сверить оставшиеся ID построчно при приемке соответствующих областей. Приоритет #186 и включение #210 в Release 1 требуют отдельного решения владельца; этот аудит их не меняет.
