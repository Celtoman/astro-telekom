Настройки обоих экранов открываются отдельным чтением без расчёта каталога. SEO показывает проверенный список и SEO/OG выбранного URL после действия «Проверить маршруты». ## Эквивалентность

- Полный список Sitemap совпал по всем строкам и диагностике. Совпали все страницы группы городов и крайние страницы остальных групп. XML использует тот же origin, порядок и набор URL после применения `noindex` и ручных исключений. Независимое чтение трёх дочерних XML подтвердило все 3527 абсолютных адресов без дублей. Тест публичной сборки отдельно проверяет один canonical на точный URL у индексируемой страницы и отсутствие canonical у `noindex`.
- SEO-проверка вернула те же канонические пути, SEO/OG, `noindex` и предупреждения для выбранного из списка URL. Исторический снимок без `seoByPath` сохранил `null` для опубликованной детали.
- Точная рабочая ревизия обязательна для проверки. При продолжении SEO-проверки можно закрепить ID опубликованного снимка. Локальный контроллер `/active` успешно указал на уже обслуживаемый `RUNNING`, хотя в SQL существовал другой `SUCCEEDED`. Неверный digest вернул 503, несовпадающий ожидаемый ID — 409.
- Полная проверка находит ошибки вне выбранного URL. Переход в `NOINDEX` требует подтверждения точного числа маршрутов, сохранение ручных исключений повторно проверяет рабочую ревизию и полный каталог.

После добавления неизвестной SEO-переменной в шаблон тарифов выборка вернула прежние строки, а полная проверка заблокировала и SEO главной, и Sitemap. Этот быстрый результат пока не используется для проверки готовности.

Запрос каждой точной страницы всё ещё собирает рабочий каталог. Редактор Sitemap получает проверенный список целиком, чтобы мгновенно искать по изменённым в форме причинам и строить XML из того же набора. Дополнительная страничная выдача API ограничивает JSON, а её запрос пока тоже проходит полную проверку. Для дешёвых повторных страниц нужен проверенный результат фонового расчёта с доказанной актуальностью по рабочему источнику, опубликованному основанию и версии правил. Это пересекается с [#633](https://github.com/Celtoman/astro-telekom/issues/633). Узкое чтение опубликованных SEO при сохранении доказательства digest связано с [#635](https://github.com/Celtoman/astro-telekom/issues/635). Использование одной рабочей ревизии как ключа требует учесть seed и другие технические записи вне редакторского CAS.

## Стенд общего результата для предпросмотра, SEO и Sitemap

Кандидат `8ea62bbc` проверен на PostgreSQL с 207 городами, 3 933 тарифами и 207 страницами поддержки. Режимы включённого и выключенного `WORKING_PREVIEW_REUSE_ENABLED` чередовались. Выключенный режим уже использовал компактное чтение тарифов. Для каждого сценария проверено по 20 пар при пустом и заполненном кэше. ### Подготовленная проекция SEO

Изолированный стенд сравнил три варианта первого отчёта `CITY_TARIFF_DETAIL`. В 24 чередующихся тройках p50/p95 полного HTTP составили 591/762 мс у штатного компактного расчёта, 741/801 мс у чтения полного готового JSON и 288/331 мс у готовой проекции SEO. Размер JSON, возвращённого из БД, сократился с 25,46 до 2,51 МБ, p95 чтения, SHA и разбора — с 504 до 39 мс. Проверка рабочих данных отдельным отпечатком занимала около 103 мс по p95.

Поля ответов и продолжение по `reviewId` совпали. При отсутствии READY чтение записи занимало 0,6 мс по медиане. Затем выполнялся штатный строгий расчёт без дополнительного отпечатка. Покрыты изменение города без повышения ревизии, устаревшая попытка и смена обслуживаемого снимка до SQL ACK. В дополнительном локальном прогоне PostgreSQL 18.6 смена сайта между чтением готового результата и финальной сверкой `/active` вернула 409 во всех трёх вариантах. Полезная нагрузка старого снимка ни разу не ушла клиенту. SHA-256 локального результата `4e3638c70695f0b6da9c07975c65f5cfc97b116deb4ccf08693a4f3632164227`.

Готовый артефакт создавался тестовой обвязкой. Результат измеряет чтение и проверку проекции. Ресурсный допуск реального фонового расчёта остаётся в #633. [Стенд и сырые замеры](https://github.com/Celtoman/astro-telekom/actions/runs/44932162269/artifacts/14717329351).

## Сравнение с админкой Туркурса

Проверен исходный код `Celtoman/turagent-currency` на `d5e62b434bd6927f9a976b772090b1226d9c78b9`. Он совпал с последним завершённым deployment `tour-kurs-prod`. Во встроенном браузере открылся экран входа. Время авторизованных переходов и размеры живых ответов в этом сравнении не измерялись.

Туркурс использует Next.js App Router и React. В меню стоят ссылки `next/link`. Для формы SEO после проверки cookie выполняется один внутренний GET `/api/admin/page-seo` с `no-store`. Express читает девять полей таблицы SQLite, упорядоченной по ключу маршрута, без JOIN. На встроенных исходных данных это три строки и 2 809 байт JSON. Форма не проверяет все URL при открытии. [Навигация](https://github.com/Celtoman/turagent-currency/blob/d5e62b434bd6927f9a976b772090b1226d9c78b9/web/components/admin-sidebar-nav.tsx#L33), [страница SEO](https://github.com/Celtoman/turagent-currency/blob/d5e62b434bd6927f9a976b772090b1226d9c78b9/web/app/mellon-page/seo/page.tsx#L44), [чтение SQLite](https://github.com/Celtoman/turagent-currency/blob/d5e62b434bd6927f9a976b772090b1226d9c78b9/src/repositories/pageSeoRepository.ts#L18).

Сбор курсов и прогноз по расписанию отделены от открытия формы. Ручная синхронизация и предпросмотр прогноза выполняют дополнительные расчёты. В Astro известные маршруты уже переключаются внутри общего React workspace. Принцип, применимый к #630, состоит в отдельной выдаче данных формы, выбранного маршрута и результатов тяжёлой проверки. Результат этапа определяется замерами каждого из этих действий. [Расписание в API](https://github.com/Celtoman/turagent-currency/blob/d5e62b434bd6927f9a976b772090b1226d9c78b9/src/server.ts#L2004), [навигация Astro](2026-11-20-admin-client-navigation.md).
