# Открытие SEO-шаблонов и Sitemap · #630, этап 3.4

Настройки обоих экранов открываются отдельным чтением без расчёта каталога. SEO показывает проверенный список и SEO/OG выбранного URL после действия «Проверить маршруты». Sitemap загружает проверенные строки после действия «Проверить маршруты Sitemap» и строит XML по кнопке с учётом несохранённых исключений. Полные маршруты API и условия сохранения поддерживаются для прежних клиентов.

## Сравнение на PostgreSQL

Локальная PostgreSQL 18.6, все 78 миграций, данные штатного bootstrap и синтетическое дополнение до 207 городов и 3105 опубликованных тарифов. Проверочное состояние содержало 3735 публичных URL, 3737 строк Sitemap, 207 автоматических `noindex`, одно ручное и одно устаревшее исключение. Исторический снимок без `seoByPath` также исключал отдельные поздние опциональные типы. База старой сборки — `05903e64`.

Замерялся прямой вызов сервисного метода с Prisma и сериализацией результата в Node.js. На операцию выполнялось одно прогревочное чтение, затем пять измерений для старых входов и полной проверки, 12 измерений для настроек и восемь для экспериментальной выборки полей маршрутов. ## Эквивалентность

- Полный список Sitemap совпал по всем строкам и диагностике. Совпали все страницы группы городов и крайние страницы остальных групп. XML использует тот же origin, порядок и набор URL после применения `noindex` и ручных исключений. Независимое чтение трёх дочерних XML подтвердило все 3527 абсолютных адресов без дублей. Тест публичной сборки отдельно проверяет один canonical на точный URL у индексируемой страницы и отсутствие canonical у `noindex`.
- SEO-проверка вернула те же канонические пути, SEO/OG, `noindex` и предупреждения для выбранного из списка URL. Исторический снимок без `seoByPath` сохранил `null` для опубликованной детали.
- Точная рабочая ревизия обязательна для проверки. При продолжении SEO-проверки можно закрепить ID опубликованного снимка. Локальный контроллер `/active` успешно указал на уже обслуживаемый `RUNNING`, хотя в SQL существовал другой `SUCCEEDED`. Неверный digest вернул 503, несовпадающий ожидаемый ID — 409.
- Полная проверка находит ошибки вне выбранного URL. Переход в `NOINDEX` требует подтверждения точного числа маршрутов, сохранение ручных исключений повторно проверяет рабочую ревизию и полный каталог.

## Точечное чтение обслуживаемого основания

Кандидат `5d014c36` переиспользует точечную выборку редакционных данных из обслуживаемого снимка при проверке Sitemap с заданной рабочей ревизией. Используются имеющийся флаг проекций и static provider. Валидация, построение рабочего каталога, поиск, пагинация, черновые исключения и полный XML проходят прежний путь. Для исторического снимка без полного seal сохранено чтение с проверкой полного каталога. При неверном или недоступном `/active` редактор получает прежнюю диагностику внутри `inventory`.

В каждой паре работали тот же PostgreSQL 18.6, 207 городов и 3 933 тарифа. `/active` указывал на B в статусе `RUNNING` до SQL ACK, пока последним `SUCCEEDED` в БД был A. Сравнение чередовало порядок двух сборок.

## Оставшаяся работа

Экспериментальная выборка только типов, slug, статусов и состояния индексации дала p95 44,3 мс и 6 SQL-чтений. На валидном каталоге она совпала по 3735 маршрутам и 207 `noindex`. После добавления неизвестной SEO-переменной в шаблон тарифов выборка вернула прежние строки, а полная проверка заблокировала и SEO главной, и Sitemap. Этот быстрый результат пока не используется для проверки готовности.

Запрос каждой точной страницы всё ещё собирает рабочий каталог. Редактор Sitemap получает проверенный список целиком, чтобы мгновенно искать по изменённым в форме причинам и строить XML из того же набора. Дополнительная страничная выдача API ограничивает JSON, а её запрос пока тоже проходит полную проверку. Для дешёвых повторных страниц нужен проверенный результат фонового расчёта с доказанной актуальностью по рабочему источнику, опубликованному основанию и версии правил. Это пересекается с [#633](https://github.com/Celtoman/astro-telekom/issues/633). Узкое чтение опубликованных SEO при сохранении доказательства digest связано с [#635](https://github.com/Celtoman/astro-telekom/issues/635). Использование одной рабочей ревизии как ключа требует учесть seed и другие технические записи вне редакторского CAS.
