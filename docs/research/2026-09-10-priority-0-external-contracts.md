# Priority 0: проверка внешних контрактов и секретов

Дата проверки: 10 сентября 2026 года.

## Область и правила безопасности

- Значения ключей и токенов не записываются в Git, документацию, GitHub Issues или логи проверки.
- Единый локальный источник значений — корневой `.env`, исключенный правилами `.gitignore`.
- Единственный production runtime-источник значений — Coolify Environment Variables. Перенос выполняется после проверки каждого контракта.
- Для probes использованы публичные адреса без квартиры и предоставленный владельцем тестовый номер. Значения номера и `appeal_id` не записаны в Git или отчет.
- `Tarifnik appeal/create` вызван только с согласованной меткой `utm_campaign=test`; владелец подтвердил, что такие заявки не обрабатываются кол-центром.

## Что уже собрано локально

Без вывода значений в корневой `.env` перенесены существующие:

- `DADATA_TOKEN` и `DADATA_SECRET` из рабочего бота;
- актуальный `TARIFNIK_API_KEY`, установленный владельцем вместо отклоненного старого token;
- локальные Basic Auth credentials;
- email и пароль администратора;
- `COOLIFY_SETUP_TOKEN` и действующий `COOLIFY_API_TOKEN`;
- найденный через Coolify API UUID приложения `astro-telekom`;
- городской профиль Казани для публичной проверки договора Дом.ру из рабочего бота.

Исходные файлы пока сохранены: старый бот продолжает использовать собственный `.env`, а локальные Coolify-файлы можно удалить только после подтверждения нового runtime-контура.

## Официальный контракт Tarifnik v3.0

Источник: [«Открытое API для дилеров»](https://dealers-api.tarifnik.ru/open_api.html#/), предоставленный владельцем проекта.

- Base URL: `https://dealers-api.tarifnik.ru/api/v3.0`.
- Все запросы используют Bearer API token; token создается в личном кабинете партнера.
- `POST /address/check` принимает обязательный объект `suggestion` с полями `value`, `unrestricted_value` и `data` из DaData.
- Успешный ответ `address/check` — JSON-словарь `providerId: providerName`, например `{"8":"Дом.ру"}`. HTTP 404 означает, что провайдеры не найдены; HTTP 403 — token не найден или истек; HTTP 422 — ошибка валидации адреса.
- `POST /appeal/create` требует `utm_campaign`, `phone` в формате `7XXXXXXXXXX` и `suggestion`. Допустимые `belong_type`: `apartments`, `house`, `b2b`.
- Для `belong_type != b2b` Tarifnik дополнительно валидирует, что по адресу найден хотя бы один провайдер. Для `b2b` эта проверка не выполняется.
- Успешный ответ `appeal/create` содержит `result: created | created_duplicate` и `appeal_id` UUID. HTTP 403 означает отсутствующий/истекший token; HTTP 422 возвращает `message` и словарь `errors`.
- Дополнительные необязательные поля обращения: имя, фамилия, отчество, комментарий, этаж, квартира, подъезд, `region_fias`, `house_fias`, `is_prepend`.
- `GET /regions` с тем же Bearer token возвращает список регионов с `name` и `fias_id`.

Для всех текущих probes и sandbox-заявок владелец проекта указал `utm_campaign=test`. Заявки с этой меткой не обрабатываются кол-центром. Production campaign остается отдельным обязательным значением перед запуском реального трафика.

Следствие для платформы на момент аудита: прежний generic-контракт `available/coverage/alternatives` не соответствовал официальному API. В текущем коде он заменен адаптером словаря провайдеров: HTTP 404 — однозначный пустой список, 403/422/сеть/невалидный JSON — ошибка без разрешения delivery.

На момент аудита `LeadDeliveryService` также не соответствовал официальному контракту `appeal/create`: отправлял `contact`, `private_houses`, самостоятельно собранный `suggestion`, недокументированные поля и жестко заданную кампанию. В текущем коде mapper исправлен: отправляет только официальный набор полей, берет кампанию из защищенной переменной, повторно проверяет persisted target coverage и признает успехом только `created|created_duplicate` с `appeal_id`.

API key не требуется. Положительная ветка требует отдельного тестового действующего абонента. |

После исправления кода выполнен повторный сквозной sandbox-прогон: DaData вернула 5 подсказок, `clean/address` нормализовал выбранный адрес, Tarifnik `address/check` вернул 5 провайдеров с target ID `8`, а новый `LeadDeliveryService` с `utm_campaign=test` получил валидный `created_duplicate`. Телефон, token и `appeal_id` не записаны в репозиторий.

## Что еще требуется от владельца

### Доступы и окружение

- production-значение `utm_campaign`, созданное в личном кабинете партнера; до запуска используется подтвержденная тестовая метка `test`;
- email fallback transport: Resend key либо webhook URL;
- решение: сохранить существующие внутренние credentials или выполнить согласованную ротацию.

### Тестовые данные и внешние контракты

- безопасный адрес только с альтернативными провайдерами;
- тестовый телефон действующего абонента;
- правила rate limit, retry и допустимой идемпотентности Tarifnik, которые не описаны в публичной спецификации.

### Продуктовые и legal-решения

- телефон технической поддержки;
- получатель и отправитель email fallback;
- допустимые поля для DaData, Дом.ру, Tarifnik и email;
- срок хранения заявок и телеметрии;
- legal basis передачи PII;
- оператор персональных данных и ссылка на политику;
- текст и способ фиксации согласия пользователя.

## Критерий завершения Priority 0

Priority 0 завершен только когда для каждой интеграции сохранен обезличенный контракт success/error, test credentials находятся в защищенном источнике, read-only проверки воспроизводимы, `appeal/create` проверен в sandbox без попадания теста в рабочий кол-центр, legal/retention решения записаны в `docs/decisions.md`, а production secrets перенесены в Coolify без Git и логов.
