# Хранение публикаций по бюджету — подготовка 7 ноября 2026

Задача [#580](https://github.com/Celtoman/astro-telekom/issues/580), согласованная находка PF-155. Новая политика пока не объявлена внедрённой: старый runtime и прежний timer сохранены. Push требует отдельного явного разрешения по AGENTS.md.

## Согласованный объём

Постоянно защищать active, все serving/fallback roots, baseline, две последние подтверждённые rollback, неподтверждённые артефакты и candidate/previous незавершённых операций. Восстановленные версии сохраняют pin. До двух дополнительных подтверждённых версий за 24 часа допускаются только в бюджете 8 ГиБ всего оставшегося тома. Assets, manifests, receipts и legacy current сохраняются.

Владелец выбрал существующий Backblaze B2 для новых архивов. Старые Timeweb-архивы не перемещаются и не удаляются; их storageId остаётся частью immutable proof. До любого GC весь выбранный пакет должен пройти upload, download, SHA-256 и полное изолированное восстановление.

## Что использовано из «Мониторинга и бэкапа»

Изучены AGENTS, README/CURRENT_STATE, CONTEXT, INVENTORY, DECISIONS, BACKUP_POLICY, RESTORE_RUNBOOK, MONITORING, scripts/README и действующие host backup/bridge/watchdog исходники.

Проверено 7 ноября: Coolify DB+config и TourKurs DB имеют отдельные systemd workflows; основной storage — B2 id 2. Native jobs и расписания «Мониторинга и бэкапа» не менялись. Новая publication retention остаётся отдельным workflow: это не native backup всей Astro-базы или VPS и не новое расписание для тех же Coolify/TourKurs dumps.

Заимствованы разделение статуса запуска и результата, атомарная запись собственного status.json, scope по точному namespace, preflight, полное восстановление и запрет ротации после неуспешной проверки. Telegram config не копируется, тестовые сообщения не отправляются. Подключение новых уведомлений этой задачей не заявлено.

## Изменения кода

- private controller рассчитывает консервативный физический бюджет всего тома; legacy current учитывается без следования по ссылке. Перед каждым GC актуальная защита пересчитывается под serial queue.
- builder допускает новую сборку только при свободных 8 ГиБ; существующий sealed артефакт можно использовать без создания новых файлов.
- host helper сохраняет original storageId старого архива, проверяет весь выбранный пакет до первого удаления и пишет атомарный root-only статус без credentials.
- bridge ограничен известными UUID/endpoint/bucket Timeweb и B2; S3 delete/lifecycle операций нет.
- подготовлены hourly timer (:30 UTC с jitter до пяти минут), событийный path и штатная партия двух версий. Установка расписания — только после фактической приёмки.

## Проверки и предварительная опись

Read-only исполнение нового planner на реальном томе: 16 кандидатов, 8 сохраняемых версий, projectedBytes=7 997 157 376 при budgetBytes=8 589 934 592. Это оценка после GC, а не уже освобождённое место.

Профильные регрессии проверяют частые сборки, точную границу бюджета, обязательную защиту сверх лимита, незавершённые операции, отсутствие следования по legacy link, S3/restore failure, сохранение старого storage и архивирование всей партии до первого GC. Linux filesystem и archive/restore проверки выполнены отдельно без пропусков. PHP lint выполнен внутри существующего Coolify.

Первый полный gate встретил CRLF в старом checkout scripts/pnpm-install-retry.sh: та же причина сломала форматную проверку и Docker rehearsal. Файл приведён точно к LF-байтам Git HEAD по действующему .gitattributes; лог первого прогона сохранён. Повторный gate выявил нехватку локального места на C: — новая защита 8 ГиБ отклонила реальные сборки. Подготовлено отдельное рабочее дерево на D: с проверкой равенства изменённых исходников по SHA и собственными frozen-lockfile dependencies. Полный gate там завершён успешно; все проверки прошли, один Windows symlink skip покрыт отдельным Linux-прогоном. Точный результат хранится только в [TEST_COVERAGE](../TEST_COVERAGE.md). Код/config/связанные тесты проверочного дерева сверены с рабочими по SHA.

## Контрольная точка B2 и лимит скачивания

До уведомления о cap в B2 были полностью восстановлены и подтверждены восемь архивов, суммарно 1 320 726 069 байт скачанных проверенных объектов. Дополнительные неуспешные попытки могли также расходовать трафик. Эти данные не объявляются полным объёмом account-wide egress.

При обработке следующего объекта получен HTTP 403. Владелец передал уведомление о достижении Daily Download Bandwidth Cap. Это заменило предварительную гипотезу о правах; credentials, bucket policy и caps не менялись. На этой контрольной точке дальнейшие скачивания были остановлены; HTML не удалялся, runtime/timer не обновлялись. Существующие backup watchdogs после исчерпания общего лимита также начали сообщать B2 unavailable; их конфигурации не менялись.

Владелец выбрал продолжение сегодня и запросил ограниченный платный cap. Предложено $0.10/day только для Download Bandwidth, без No Cap и без изменения остальных лимитов. После сообщения владельца «Готово» подтверждено чтение одного байта по Native API и S3 из Coolify; архивирование продолжилось с контрольной точки. Все 16 исходных кандидатов загружены в B2 и полностью восстановлены, суммарный размер проверенных объектов 2 681 403 599 байт. Оба существующих backup watchdog после применения cap вновь healthy/без issues. HTML, runtime и расписания по-прежнему не менялись.

[Backblaze Caps & Alerts](https://www.backblaze.com/docs/en/cloud-storage-data-caps-and-alerts?highlight=cap) описывает суточный сброс в 00:00 GMT и категории caps. [Backblaze API](https://www.backblaze.com/apidocs/b2-download-file-by-id) указывает HTTP 403 для download_cap_exceeded. Опубликованная [цена egress](https://help.backblaze.com/hc/en-us/articles/217667478-Understanding-B2-Pricing-Structure) сверх бесплатного объёма — $0.01/GB; фактическое применение бесплатного объёма определяется аккаунтом.
