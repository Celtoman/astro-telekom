# Продолжение проверки SEO-маршрутов

Ручная кнопка «Проверить маршруты» вычисляет рабочий каталог для выбранного типа SEO-шаблона и привязывает отчёт к рабочей ревизии, сайту и точному обслуживаемому снимку. Переключение страницы и открытие URL используют этот отчёт и проверяют, что ревизия и снимок по-прежнему действуют. Смена ревизии возвращает HTTP 409 и убирает прежний отчёт с экрана. При старом API или недоступном лимите хранения продолжает работать совместимый путь расчёта. При истечении отчёта или обращении на другой экземпляр API интерфейс предлагает запустить проверку заново.

## Результаты во встроенном браузере

Проверено на `d44e99b34e612784c565158adfc5004c1a668ec8`, 30 проходов на вариант, одна прогревочная пара. Обе ветки использовали одну сборку Astro и React. Стенд A выбирал совместимый API-путь без идентификатора отчёта, B использовал обычный revision-bound запрос. В каталоге 207 городов и 20 тарифов на город. На каждый API-запрос добавлено 120 мс. Обе ветки получают одинаковый синтетический рабочий расчёт с задержкой 180 мс и копированием каталога. Измерение охватывает HTTP и появление нужного состояния DOM.

| Действие | p50, A → B, мс | p95, A → B, мс | Рабочих расчётов A → B |
| --- | ---: | ---: | ---: |
| Открытие до настроек | 691,2 → 690,7 | 729,0 → 771,7 | 0 → 0 |
| Явный расчёт до первого результата | 351,8 → 341,6 | 364,8 → 353,9 | 1 → 1 |
| Следующая страница маршрутов | 352,5 → 133,8 | 364,8 → 140,9 | 1 → 0 |
| Деталь выбранного URL | 351,2 → 137,3 | 366,2 → 139,9 | 1 → 0 |
| Смена рабочей ревизии и предупреждение | 138,2 → 134,7 | 142,6 → 137,3 | 0 → 0 |

Обе ветки получили HTTP 409 после смены рабочей ревизии и убрали устаревший результат. Ошибок измерения и сообщений в консоли не наблюдалось. Каждый из четырёх действий с отчётом сделал один API-запрос. Первый ответ содержит 1 813 → 1 863 байта JSON и 417 → около 459 байт gzip. Разница включает идентификатор отчёта. Объём страницы 2 составляет 1 833 → 1 883 байта JSON, детали 1 897 → 1 947. Целевой бюджет 1,5 с для первой страницы на стенде соблюдён. Подтверждённый выигрыш связан с отсутствием повторного рабочего расчёта при продолжении. Первый явный расчёт сохраняет полную проверку и требует отдельного профиля на рабочих данных.

Проверка с изолированным PostgreSQL отдельно покрывает точную активированную публикацию до SQL ACK, чтение исторического снимка, проверку digest и хранение поколения каталога. Синтетический браузерный профиль показывает разницу при заданных задержках. Длительность SQL, время внешней сети и производственный SLO измеряются отдельно. ## Воспроизведение

Из корня проекта в PowerShell:

```powershell
pnpm --filter @provider/api run build
$env:ADMIN_URL = 'http://127.0.0.1:43055'
$env:PUBLIC_API_URL = 'http://127.0.0.1:43055/api/v1'
pnpm --filter @provider/admin run build
node scripts/rehearse-seo-route-review-ui.mjs
```

Во встроенном браузере откройте `http://127.0.0.1:43055/seo-review-benchmark` и выберите «Запустить 30 пар». Новый документ загружается на каждый проход, порядок вариантов чередуется. Скрипт измеряет время от открытия или DOM-события до готовности нужного элемента, число завершившихся API-запросов и их размеры по Resource Timing. PostgreSQL и авторизация имитируются в процессе стенда. POST на служебный адрес меняет только хранимую в памяти фиктивную ревизию и восстанавливает её между проходами. Сам API fixture доступен только на loopback и не выполняет внешних операций.

Для отдельного теста реального PostgreSQL после сборки API запустите `node --test tests/admin-read-projections.test.cjs`. Тест создаёт и останавливает собственный контейнер.
