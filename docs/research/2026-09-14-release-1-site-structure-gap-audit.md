# Аудит расхождений с канонической структурой Release 1

> Исторический снимок до уточнения владельца 14 сентября 2026 года. Текущий канон добавляет cookie policy и формулу `N + 6`; примененный импорт публикует все города. Актуальные требования находятся в [site-structure.md](../site-structure.md).

Дата: 14 сентября 2026 года.

Статус: read-only снимок реализации до перехода. В рамках аудита код, схема БД и production-данные не менялись.

Канон: [site-structure.md](../site-structure.md). Исполнимый план: [2026-09-14-release-1-site-structure-transition.md](../plans/2026-09-14-release-1-site-structure-transition.md). Главная задача: [#136](https://github.com/Celtoman/astro-telekom/issues/136).

## Итог

Текущая реализация **не соответствует** Release 1. Она умеет строить несколько опубликованных городов, но продолжает использовать прежнюю модель «опубликовано все, что имеет статус `PUBLISHED`»: городские service pages и detail каждого тарифа автоматически становятся HTML-маршрутами, ссылками и sitemap URL.

Одновременно четыре обязательные общие страницы Release 1 невозможно представить в текущей `Page`: каждая запись обязательно принадлежит городу. `/goroda-obsluzhivaniya` отсутствует, а список городов встроен в `/`. Импорт после apply дополнительно возвращает каталог к одной опубликованной Казани.

Это системное расхождение. Локальное добавление пяти Astro-файлов не исправит API redirect contract, модель данных, импорт и утечки будущих URL.

## Точный маршрутный разрыв

Пусть:

- `N` — число опубликованных городов;
- `P` — число опубликованных городских страниц, кроме `HOME` и `TARIFF`;
- `T` — число опубликованных тарифов.

Сейчас обычный output равен `1 + N + P + T`. Release 1 должен содержать ровно `N + 5` обычных HTML-маршрутов и один общий шаблон 404.

| Элемент Release 1 | Канон | Текущее состояние | Вывод |
| --- | --- | --- | --- |
| Главная | `/` | Есть, но основным содержанием служит список городов | Маршрут есть; назначение требует уточнения относительно отдельной страницы городов |
| Страница города | `/{location}` для каждого опубликованного города | Генерируется из всех `City.status = PUBLISHED` | Основа подходит; Казань уже не hardcoded в route pattern |
| Карта покрытия | `/karta-pokrytiya-provaydera` | Нет общего маршрута/страницы | Отсутствует |
| Города обслуживания | `/goroda-obsluzhivaniya` | Нет; список находится на `/` | Отсутствует |
| Политика конфиденциальности | `/politika-konfidencialnosti` | Нет общего маршрута/страницы | Отсутствует |
| Согласие на обработку ПД | `/soglasie-na-obrabotku-personalnyh-dannyh` | Нет общего маршрута/страницы | Отсутствует |
| 404 | неизвестный URL → HTTP 404 | `apps/web/src/pages/404.astro` существует, получает `noindex` и не получает canonical | Соответствует по шаблону; HTTP-поведение сохраняется edge/static server |
| Будущие страницы | Не входят в Release 1 | Все опубликованные Page/Tariff генерируются и попадают в sitemap | Критическое расхождение |

## Подтвержденные причины

### 1. Нет release-aware реестра допустимых URL

- `apps/web/src/pages/[city]/[slug].astro` возвращает static paths для каждой опубликованной городской страницы и каждого опубликованного тарифа.
- `apps/web/src/pages/sitemap.xml.ts` повторяет этот набор.
- `apps/web/src/components/BlockRenderer.astro` строит ссылки на тарифные detail и service pages.
- `apps/web/src/layouts/BaseLayout.astro` формирует городскую навигацию из старых типов `INTERNET`, `INTERNET_TV`, `TV`, `ADDRESS_CHECK`, а footer — ссылку на городской FAQ.
- `apps/api/src/cities.controller.ts` отдает весь опубликованный контент и считает все его URL допустимыми target для redirects.
- `apps/api/src/redirect.service.ts` использует ту же широкую трактовку публикации.

Следствие: фильтр только в Astro создал бы рассинхронизацию — runtime API разрешал бы редирект на страницу, которой нет в static output.

Issue: [#133](https://github.com/Celtoman/astro-telekom/issues/133).

### 2. `Page` допускает только городскую область

- `prisma/schema.prisma`: `Page.cityId String` и `Page.city City` обязательны.
- `PageType` содержит только `HOME`, `INTERNET`, `INTERNET_TV`, `TV`, `TARIFF`, `ADDRESS_CHECK`, `FAQ`.
- `apps/api/src/cities.controller.ts` возвращает pages только вложенными в города.
- `apps/api/src/admin-pages.controller.ts` требует `cityId`; отдельного site-global API нет.

Следствие: карта покрытия, города и legal pages могут появиться только как hardcoded Astro-контент или через фиктивный город. Оба решения создают второй источник контента и не подходят как основа полной структуры.

Issue: [#134](https://github.com/Celtoman/astro-telekom/issues/134).

### 3. Bootstrap данных закрепляет старую тестовую схему

- `scripts/import-cities.mjs` после apply переводит в `DRAFT` все города, кроме `CITY_IMPORT_PUBLISHED_SLUG`, который по умолчанию равен `kazan`, и проверяет ровно один опубликованный город.
- `apps/api/src/city-import.service.ts` создает каждому новому городу шесть legacy-страниц: `HOME`, `INTERNET`, `INTERNET_TV`, `TV`, `ADDRESS_CHECK`, `FAQ`.
- `apps/api/src/seed.ts` публикует тот же старый комплект для Казани и два demo-тарифа при пустом каталоге.
- HOME имеет разные служебные slug: пустой в seed и `home` в city import.

Следствие: новый каталог получает неверную структуру еще до сборки, а повторный служебный импорт может снять с публикации корректно опубликованные города.

Issue: [#135](https://github.com/Celtoman/astro-telekom/issues/135).

### 4. Тесты закрепляют прежнее поведение

- `tests/web-build-data.test.mjs` ожидает HTML и sitemap для service pages и tariff detail двух опубликованных городов.
- `tests/city-import.test.cjs` ожидает старый комплект из шести draft pages.
- `tests/redirects.test.cjs` считает опубликованные Page/Tariff URL допустимыми targets.
- `tests/public-city-catalog.test.cjs` проверяет только вложенные в город страницы; site-global pages в контракте отсутствуют.

Это полезные regression-тесты текущей системы, но перед изменением кода их нужно перевести на новый контракт, чтобы красный тест точно показывал требуемое отличие.

## Проверенные смежные зоны

| Зона | Текущее поведение | Что потребуется |
| --- | --- | --- |
| Каталог городов admin | Позволяет вручную менять статус любого города | Сохранить; добавить release-readiness перед публикацией отдельно, не возвращать invariant одной Казани |
| Rebuild | Любая затронутая сущность ставит полную пересборку `/*` | Для первого перехода достаточно; оптимизация affected paths не обязательна |
| Robots/404/SEO gate | Уже проверяет robots, canonical, sitemap и noindex 404 | Расширить exact inventory, не переписывать рабочий gate |
| Тарифы | Нужны на `/{location}` как данные/карточки | Отделить доступность предложения от наличия отдельного tariff URL |
| Redirects | Проверяют существование опубликованного target | Перевести на release route inventory, иначе возможен target вне output |
| Текущие данные | Содержат страницы/тарифы прежнего прототипа | Мигрировать без удаления тарифов, блоков, лидов и истории |

## Рассмотренные варианты

### Вариант A — добавить пять hardcoded Astro-страниц

Плюс: минимальный объем кода. Минусы: общие страницы обходят CMS/API, future URL продолжают утекать, redirect resolver остается несовместимым. Вариант отклонен.

### Вариант B — управлять Release 1 только статусами БД

Плюс: не нужен отдельный release policy. Минусы: опубликованные тарифы нужны как предложения на городской странице, но их detail URL пока запрещены; один `PUBLISHED` не может выразить это различие. Ошибка редактора снова расширит output. Вариант отклонен.

### Вариант C — site-global `Page` и authoritative route inventory API

API хранит общие и городские страницы, а отдельная release policy строит точный список разрешенных маршрутов. Web генерирует только полученный inventory; sitemap, внутренние ссылки и redirect resolver используют тот же контракт. Тариф может оставаться опубликованным предложением, но не получать detail URL до следующего релиза.

Это предпочтительный вариант: он устраняет все три причины, не создает параллельную CMS и позволяет расширять полную структуру осознанно по релизам.

## Безопасный порядок перехода

1. Зафиксировать тестами новый exact inventory и новые общие типы страниц.
2. Расширить Prisma/API для site-global pages с DB-ограничением уникальности.
3. Создать четыре общие записи Release 1 миграцией/явным bootstrap, не удаляя существующий контент.
4. Убрать из импорта single-city post-pass и legacy page pack.
5. Ввести API route inventory и перевести на него redirects.
6. Перевести Astro static paths, sitemap, navigation и link renderer.
7. Выполнить data audit, затем production-like build и exact сверку `N + 5`.

Такой порядок сначала делает данные представимыми, затем переключает потребителей. Он не оставляет промежуточную ревизию, в которой обязательные global URL отсутствуют, а старые URL уже отключены.

## Открытые продуктовые решения

Техническая схема не определяет:

- чем содержательно отличаются `/` и `/goroda-obsluzhivaniya`;
- куда ведет тарифная карточка, пока tariff detail отсутствует;
- какие общие страницы входят в header, footer и breadcrumbs;
- какие утвержденные тексты и реквизиты публикуются на legal pages.

Они зафиксированы как [PF-015](../product-findings.md#pf-015--определить-навигационную-роль-общих-страниц-release-1). До ответа можно реализовать модель, маршрутизацию и проверки, но нельзя считать страницы готовыми к реальному трафику.

## Граница этого аудита

Live production-данные и внешний сайт не изменялись. Аудит основан на текущем checkout `master`, схеме, исходниках, тестах и живом состоянии GitHub Issues на дату документа. Фактический production inventory нужно повторно получить непосредственно перед data migration и deployment.
