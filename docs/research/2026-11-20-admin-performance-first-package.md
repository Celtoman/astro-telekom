# Первый пакет ускорения админки

20 ноября 2026. Локальная реализация от SHA `ec7be550213fa1471490f8d818be00f9fd65e86a`. Архитектура, варианты и условия выпуска собраны в [плане ускорения](../plans/2026-11-20-admin-backend-performance.md). Связанные задачи и этапы ведутся в [#644](https://github.com/Celtoman/astro-telekom/issues/644).

## Изменения

- `first-screen`, `general-home` и `tariff-collection` читают область переменной по индексу реестра. Список определений для API по-прежнему формирует отдельные DTO. Числовые подстановки и денежные подписи тарифов переиспользуют по одному форматтеру для своих настроек. Правила округления и замены разделителей сохранены. [#632](https://github.com/Celtoman/astro-telekom/issues/632)
- При открытии `/publication` админка показывает сохранённые изменения и состояние через `publication-state`. Действие «Проверить изменения» вызывает `publication-review`. Полный состав выпуска с последними 100 сохранениями и диагностикой появляется после проверки. Возврат фокуса, события сохранения и обновление состояния проходят по лёгкому пути. После проверки заново читается состояние. Выпуск в интерфейсе доступен только после успеха на совпадающих siteId, рабочей и опубликованной ревизиях. Финальный POST выполняет штатную серверную проверку. [#631](https://github.com/Celtoman/astro-telekom/issues/631)
- Применяется текущий [контракт публикации](../publication.md#экран-публикации-и-запуск-проверки). У пакета нет миграций, изменений статического builder или форматов ответов. Для возврата подходят предыдущие образы API/admin по [runbook выпуска](../runbooks/ghcr-release.md#откат).

## Контрольные измерения

В одном процессе Node.js 24.22.3 загрузили baseline и новый собранный API, затем прогнали один сохранённый исходник ревизии 36 с фиксированным временем отчёта. Исходник содержит 207 городов, 3 805 тарифов и 4 451 проверяемый URL. Порядок — baseline, новый код, новый код, baseline. Локально мерили время рендера и проверки отдельно от HTTP и PostgreSQL.

| Операция | Baseline, мс | Первый пакет, мс |
| --- | ---: | ---: |
| Рендер каталога | 3 255 / 3 936 | 782 / 718 |
| Полная валидация | 8 313 / 8 918 | 1 776 / 1 928 |

Во всех четырёх прогонах совпали SHA-256 JSON каталога, отчёта и каталога после валидации. Все 4 451 URL прошли проверку. Эксперимент не измеряет внешнее время до первого байта, SQL или задержку при одновременной работе клиентов. Сохранённый исходник получен штатным read-only GET и обработан в памяти. В репозиторий входят агрегаты замера.

## Браузер и проверка поведения

Локальная production-сборка админки из рабочей ветки и HTTP fixture с синтетической сессией, двумя ревизиями и управляемыми ответами. Проверка выполнена во встроенном Chromium Codex.

| Сценарий | Наблюдение |
| --- | --- |
| Прямой вход и перезагрузка | Сводка появилась с доступной кнопкой «Проверить изменения» и заблокированной кнопкой выпуска. Сервер зарегистрировал ноль вызовов `publication-review` по этим действиям |
| Явная проверка | Один вызов от одного клика. После ответа для версии 9 отображаются состав, отчёт и доступная кнопка выпуска |
| Новая рабочая ревизия после проверки | Обновление состояния показало версию 10, пометило отчёт устаревшим и заблокировало выпуск. Повторного вызова ревью не появилось |
| Блокирующая проверка и отказ запроса | Контрольная ошибка видна, кнопка выпуска заблокирована. При отказе запроса доступен повтор |
| Отказ и восстановление статуса | На финальной сборке контрольный HTTP 503 скрывает отчёт и блокирует выпуск. После восстановления той же ревизии прежний отчёт доступен без дополнительного запроса ревью |
| Console и запросы | Ошибок и предупреждений консоли не зарегистрировано. В первом прогоне три запроса ревью соответствуют трём явным кликам. На финальной сборке был один запрос по кнопке. POST публикации не запрашивался |

Профильный прогон Node — 45 из 45. Сборка админки — 33 страницы. Полный `pnpm check --test-concurrency=2` на Node 24.22.3 и Docker Desktop — 1 160 успешных тестов, 0 падений, 1 пропуск из-за отсутствия права на symlink в Windows, exit 0. Пройдены проверка типов, валидация Prisma, сборка и интеграционные сценарии PostgreSQL/Redis/Caddy. Сквозной базовый замер SQL и event loop на внешнем контуре остаётся работой этапа наблюдаемости. Два параллельных источника статуса ещё отслеживаются в [#641](https://github.com/Celtoman/astro-telekom/issues/641).

## Что проверять после согласованного выпуска

1. Войти в «Публикацию сайта» и проверить Network. Должны быть лёгкие чтения состояния, а `publication-review` появляется по кнопке.
2. Выполнить обычное чтение отчёта с актуальной ревизией. Сверить длительность, число URL и блокировку на устаревшем состоянии. Для проверки выпуска состояния и восстановления использовать синтетический стенд.
3. Повторить замеры по [#633](https://github.com/Celtoman/astro-telekom/issues/633) после изоляции расчёта. Явное ревью пока синхронно, полная валидация выполняется в текущем HTTP-процессе. Сравнение отчёта в UI опирается на siteId и две ревизии. Привязка к фактически обслуживаемому publicationId, версия правил и короткая транзакция относятся к следующему этапу. [#634](https://github.com/Celtoman/astro-telekom/issues/634)

Внешнее приложение для этого пакета не выпускалось.
