# Каталог переменных админки · проверка #640

Замер проведён 20 ноября 2026 года на изолированной PostgreSQL 18.6 со всеми 78 миграциями. В синтетической базе 207 городов, 621 страница, 3105 блоков и 3105 тарифов. Рабочий скан нашёл 18 013 мест использования. Полный опубликованный индекс содержал 12 000 мест и занимал 3,95 МБ JSON.

Замеряли вызов контроллера и сериализацию ответа в Node.js. Старый путь собран с базы `4e4e1162`. Новый путь измерен на том же наборе данных после первого чтения значений, счётчиков и деталей. Для каждого состояния снимка выполнены два прогревочных и 12 измеряемых переключений с чередованием четырёх городов и тарифов. Размер — несжатый JSON ответа. p50 и p95 рассчитаны отдельно для каждой серии. Время браузера, сеть до внешнего контура и продовая загрузка в замер не входят.

| Опубликованный снимок | p50 до → после | p95 до → после | JSON до → после | SQL SELECT до → после |
| --- | --- | --- | --- | --- |
| Полный индекс | 827,9 → 206,4 мс | 1078,3 → 300,6 мс | 10 821 439 → 270 891 Б | 12 → 5 |
| Исторический неполный индекс | 1027,7 → 189,5 мс | 1411,2 → 270,4 мс | 10 821 440 → 270 892 Б | 12 → 5 |
| Исторический снимок без индекса | 728,5 → 135,1 мс | 967,7 → 585,6 мс | 6 873 953 → 270 893 Б | 12 → 5 |

Для полного снимка опубликованная проекция старого пути занимала p50 611,7 мс с сериализацией и возвращала 3,98 МБ. Отдельный рабочий скан занимал p50 291,9 мс и возвращал 6,60 МБ. В новом пути переключение контекста пропускает скан и получает только признак наличия опубликованных мест использования. Отдельная серия по восемь чтений после прогрева дала 819 Б и p95 685,3 мс для счётчиков, до 33 458 Б и p95 375,9 мс для страницы деталей полного снимка. Рабочий usage собирается из авторитетных строк при новом запросе `/usages`. В админке селекторы города и тарифа не меняют ключ этого запроса.

Полная и компактная выдачи совпали по кодам, городам, тарифам, значениям, признакам изменений и обеим ревизиям. Отдельный ответ совпал с полным DTO по счётчикам всех кодов и проверенным срезам ссылок. Неполный исторический индекс отдаёт известные использования и признак неполноты. Снимок без индекса возвращает `null` для опубликованных счётчиков и деталей.

Для двух выпусков с одинаковой исходной ревизией админка выбрала последний `SUCCEEDED` по `releaseSequence`. Стендовый контроллер `/active` указал на уже обслуживаемый `RUNNING` с другой ценой и другим usage. Публичный код получил обслуживаемый снимок, а чтение админки сохранило последний подтверждённый. После SQL ACK значения и использования одновременно перешли на новый точный ID. Запрос usages со старым ID получил `409`.

## Повторное чтение опубликованных значений после выпуска

На точном исходном коде `e8f62274` внешний запрос `/variable-catalog/values` показал 2,828 с в Network, а готовность интерфейса заняла 3,146 с. В ответе было 19 кодов и около 275 КБ JSON (15,6 КБ в сжатом виде). Счётчики использований загружались отдельным запросом за 1,962 с.

Для локального сравнения использовали PostgreSQL 18.6 и Node.js 24.22.3. Синтетический каталог содержал 207 рабочих городов, 3105 тарифов и 12 000 опубликованных использований. Полный опубликованный JSON занимал 22,60 МБ, хранимое значение после сжатия PostgreSQL — 2,03 МБ. Сравнили исходный запрос и собранный кандидат с теми же контроллером и Prisma-клиентом. После двух прогревов на каждый вариант провели 30 чередующихся измерений с девятью комбинациями выбора города и тарифа. Сетевая задержка до внешнего контура и браузерный рендер в локальный профиль не входят.

| Фаза | p50 до → после, мс | p95 до → после, мс |
| --- | ---: | ---: |
| Обработчик | 257,71 → 186,81 | 409,75 → 313,36 |
| Чтение опубликованного контекста | 238,97 → 164,63 | 387,68 → 282,67 |
| Чтение рабочего контекста | 20,81 → 20,05 | 64,85 → 33,39 |
| Сериализация ответа | 0,95 → 0,95 | 1,87 → 1,57 |

Отдельные обращения к пяти полям `p.catalog` повторно открывали одно большое значение. Замеры `EXPLAIN (ANALYZE, BUFFERS)` на прогретом сервере по девять повторов на вариант показали 1556 обращений к страницам в кэше у исходного запроса, 520 у `jsonb_to_record` с проверкой типа и 261 у `JSON_TABLE`. Физических чтений в этих сериях не было. В первой серии p95 SQL составил 258,50, 211,16 и 190,76 мс соответственно. В повторной серии исходный SQL дал p95 507,35 мс, а `JSON_TABLE` дал 368,69 мс при тех же 1556 и 261 обращении. Комбинация с конкатенацией JSON была медленнее исходного запроса.

Одна проекция через `JSON_TABLE` читает перечисленные поля. `LEFT JOIN` сохраняет запись об опубликованном снимке при историческом корне JSON другого типа. Полные ответы совпали побайтово в 21 проверенном сравнении, включая варианты выбора опубликованного города и тарифа, которых уже нет в рабочем каталоге. Совпали и шесть форм прежней полной выдачи с историческими, отсутствующими и неполными данными. При одинаковой исходной ревизии новый SQL выбрал `SUCCEEDED` с большим `releaseSequence`. При стендовом ответе `/active`, имитирующем уже выполненную активацию Caddy, публичное чтение получило `RUNNING`, а админка увидела этот снимок после SQL ACK. Старый ID публикации или рабочей ревизии после перехода получил `409` при запросе использований.

Размер ответа сохранился. В основной серии медиана составила 281 518 Б JSON и 10 653 Б после gzip. Сокращение `allowedFields` и `allowedContexts` в отдельной диагностической копии уменьшило бы ответ до 30 751 Б JSON и 3829 Б gzip. Эти поля нужны существующим потребителям, а p95 сериализации, сжатия и обратного разбора на стенде составили около 1,9, 3,9 и 1,1 мс соответственно. Изменение DTO требует отдельного профиля клиентской загрузки. SQL счётчиков и деталей использований сохранился, контрольные ответы совпали. Повторный p95 во внешнем контуре измеряется после выпуска.
