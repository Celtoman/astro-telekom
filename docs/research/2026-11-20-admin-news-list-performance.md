# Чтение списков новостей и категорий, #629

20 ноября 2026. [Исходный инцидент](https://github.com/Celtoman/astro-telekom/issues/629).

На внешнем контуре после выпуска каталога городов один вход во встроенном браузере Codex показал 4 522 мс до заголовков ответа списка новостей и 4 119 мс для запроса категорий. Оба запроса завершились HTTP 200. Для выпадающего фильтра использовался полный ответ категорий с подсчётом опубликованных статей. Обработчик списка загружал тексты всех подходящих новостей, дважды читал сведения о публикации вместе с запросом категорий и вычислял статусы до выбора страницы.

## Изменение

- `GET /admin/sites/:siteId/news/categories?view=options` возвращает `{items:[{id,name}]}` для рабочих неперенесённых в архив категорий сайта. Список и редактор новостей пользуются этим ответом. Прежний API игнорирует параметр и отдаёт совместимые поля.
- Без фильтра состояния список считает записи и читает до 25 строк в одном снимке PostgreSQL через Repeatable Read. При фильтре состояния сравнение текста идёт до подсчёта и пагинации. Новая сохранённая ревизия с содержимым прежней публикации сохраняет состояние `PUBLISHED`.
- У источника статусов сохраняется полная проверка фактически обслуживаемого каталога. По его точному `validationId` из `sourceSnapshot` выбираются опубликованные тексты нужных статей, поля категорий со счётчиками или поля списка связанных новостей. Копирование всего исходника остаётся у процессов, которые собирают новый кандидат или формируют предпросмотр. При недоступности сводки активной публикации список показывает `UNKNOWN`, а счётчик публикации категории остаётся `null`. Валидный исторический снимок без новостей читается как пустая опубликованная редакция.

## Приёмка на стенде

PostgreSQL 18.6 с 78 миграциями, 207 городов, 3 933 тарифа, 180 рабочих новостей и 12 категорий. В активном снимке 144 опубликованных новости, размер JSON исходника 3 195 124 байта. Сравнены 106 ответов, включая 25 вариантов запроса списка при каждом из четырёх состояний источника. Проверены активный RUNNING при более новом SQL SUCCEEDED, несовпадение digest, 503 от контроллера и исторический SUCCEEDED без редакционной части. Совпали полные JSON первой страницы, фильтров, `total`, категорий и связанных новостей. HTTP-тест проверил guard справочника и совместимость старого режима. Профильный прогон прошёл 20 тестов.

30 повторных переходов для каждого обработчика во встроенном Chromium. Одна сборка админки, одни и те же данные и HTML, режим API выбирался на локальном сервере. Измерены первый DOM списка и появление вариантов фильтра. Переходы совершались через ссылку меню.

| До события | p50 до → после, мс | p95 до → после, мс |
| --- | ---: | ---: |
| Первые строки новостей | 983 → 255 | 2 121 → 459 |
| Заполнение фильтра категорий | 684 → 55 | 1 482 → 84 |

По одному входу из свежеоткрытого обзора дали 903 и 951 мс до первой строки и 745 и 477 мс до фильтра. По одиночному входу нельзя утверждать, что первая загрузка списка ускорилась. В серии до и после браузерная консоль чистая. Проверены вторая страница, фильтрация по рабочей категории и состояние CHANGED.

Отдельный прогон обработчиков без HTTP на той же базе показал для обычного списка 177 → 29 строк, возвращаемых PostgreSQL на один ответ. Для полного справочника категорий редакционный ответ сохранил поля и размер JSON, а справочник выбора отдаёт только 555 байт против 3 069 байт полного справочника на этих данных. p95 обработки запроса справочника выбора составил 8,9 мс. Серверное время PostgreSQL и длительности адаптера измерены отдельно. PostgreSQL продолжает выполнять разбор JSONB исходника, а API подтверждает digest полного каталога. Таблица браузерных измерений относится к синтетическому стенду. Внешняя производительность проверяется отдельными проходами после выпуска.
