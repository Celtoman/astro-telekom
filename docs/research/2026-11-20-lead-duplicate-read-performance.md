# Проверка дублей заявок на синтетических данных · #642

В PostgreSQL 18.6 применили все 78 миграций и создали отдельные синтетические сайты с 100, 1000 и 10 000 строк для основного сценария. В каждом окне добавили ещё 17 граничных и исторических записей. Bulk-снимки занимают около 6,6 КБ JSON каждый. Контрольные данные, формы, ключи и outbox созданы только в изолированной базе. В ходе проверки отправки работали заглушки очередей, а сетевые обращения из контроллера блокировались.

Для каждого сценария сравнили прежний алгоритм с новой реализацией последовательно на одной базе. После прогрева сделали семь вызовов на вариант и чередовали порядок. Таймер охватывал Prisma и выбор дубля, объём JSON результата запросов подсчитывался после остановки таймера. Абсолютные задержки отражают нагрузку испытательного хоста, где часть серии совпала с lint. Они не характеризуют скорость production.

В полной группе прежний путь считал все 10 017 строк с JSON кандидатов. Новый путь при совпадении телефона или неизвестном помещении не читает ни одного снимка. При совпадении адреса проверяет снимки девяти адресных кандидатов. Оба варианта удерживают прежний порядок `createdAt DESC, id DESC` и ту же включительную нижнюю границу 24-часового окна. Область поиска по-прежнему ограничена сайтом.

## Совместимость и варианты

- Исторические `8…`, десятизначный телефон, `+7…`, Unicode-пробелы и BOM сопоставляются прежней функцией. `+8…` сохраняет другую ветвь нормализации. При равной дате выбирается первый ID по действующей сортировке.
- Адресная ветка использует те же регистр, `ё`, знаки и Unicode-категории. Строковые квартира и комната различаются, непустая квартира имеет приоритет. Числовой номер, лишние ведущие нули, сломанный snapshot, неверная integration или несогласованные признаки провайдера обрабатываются как прежде. Подтверждены включительная граница, строка сроком на 1 мс старше окна, изоляция сайта и прежнее отношение к времени строки позже момента запроса.
- Запрос по существующему точному `phone` с индексом находит только совпадение сохранённой строки. На стенде он выбрал более старую canonical-запись и пропустил более новый исторический формат. SQL-выражение по ASCII-цифрам можно применить как отбор кандидатов с обязательной проверкой текущим JS. В эксперименте план нашёл две строки. Индекс-выражение сократил чтение с 587 до пяти shared buffers, время SQL-плана с 8,57 до 0,12 мс. Этот подход ускоряет телефонную ветку и оставляет отдельный вопрос адреса.
- Типовое SQL-сочетание `lower` и POSIX `[[:alnum:]]` дало `ia` для `İA` и `a b` для `A²B`. Node.js с текущими правилами дал `i a` и `a²b`. Точный адресный индекс потребовал бы той же версии нормализации на записи. Аддитивный ключ, dual-write, сравнение результатов, backfill и удаление производного ключа по политике ПДн потребуют отдельного решения. Текущая правка использует существующие поля.

## Параллельная отправка

На стенде оба запроса проходили барьер после чтения дублей перед записью. Для одинакового `submissionKey` и одинакового payload создались одна запись и один outbox, оба ответа указали на один ID. Для одинакового ключа с разным payload создались одна запись и один outbox, второй ответ вернул 400. Для разных ключей при том же телефоне или помещении оба запроса могут пройти до записи и создать две заявки. Эта уже существовавшая гонка сохранена и зарегистрирована отдельно.
