# #633 · вклад SQL-захвата и расчёта фонового отчёта

На базе `9254430f` завершены 72 парных сравнения с 98–100 пробами на чтение. Linux, два общих CPU, 1 CPU / 768 МиБ на подготовку, PostgreSQL 18.6 и Redis 8.10.1. Синтетический набор содержит 207 городов, 3105 тарифов и 3735 маршрутов. У каждого режима собственный idle. Во всех случаях тот же serving seal, durable очередь и HTTP readback. Интервал 40 мс, одинаковое окно 4 с от claim. [Повторяемая проверка и сырые артефакты](https://github.com/Celtoman/astro-telekom/actions/runs/44837074567).

| Медиана роста p95 сводки по 12 парам | Полный отчёт | Только SQL-захват | Только расчёт |
| --- | ---: | ---: | ---: |
| В покое | +80,45% | +1,99% | +59,20% |
| С CPU-конкурентом 0,75 CPU | +55,50% | +4,77% | +50,25% |

Для `compute-only` оба лёгких HTTP-маршрута уложились в +20% в 0/12 раундов в каждом сценарии. Для `capture-only` этот критерий выполнен в 10/12 и 7/12, для полного отчёта в 1/12 и 2/12. В точном окне чистого расчёта p95 сводки вырос с 3,16 до 5,94 мс в покое и с 4,23 до 8,31 мс под нагрузкой. Прямой SQL в том же режиме замедлился с 1,46 до 2,91 и с 2,13 до 4,54 мс. Медиана compute составила 1,38–1,49 с. Медиана реальной capture-транзакции составила 55–89 мс в зависимости от группы. Короткие capture-окна дали 18–27 проб на сторону, поэтому отдельный p95 этой фазы не публикуется.

Совпали SHA-256 отчёта, порядка маршрутов, SQL-захвата, валидации и каталога там, где он рендерится. Каталог обслуживаемого выпуска и его поколение сохранены. Все задачи завершились `READY` с первой попытки. Первый диагностический стенд завершился V8 OOM после 36 пар. После освобождения захваченных графов между измерениями медиана heapUsed в первой и последней четвертях серии составила 59,56 и 56,15 МиБ, RSS 181,32 и 183,18 МиБ. Ресурсы и исходник API в повторе совпадают с первым стендом. [Первый запуск и журнал V8](https://github.com/Celtoman/astro-telekom/actions/runs/44834823349).

Основной длительный вклад в p95 создаёт CPU-расчёт. Замедление отдельного SQL-пробника при обходе capture указывает на конкуренцию за общие ресурсы. Для включения фонового отчёта требуется отдельный полный парный gate после интеграции #638. Тестовая граница остатков — повторная материализация городского каталога между preflight и доверенным рендером. Сравнивать нужно точный JSON, порядок diagnostics и маршрутов, исторические v2/v3, редиректы и RUNNING serving baseline.
