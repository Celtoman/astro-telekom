## Что проверили

Для прежних типов сравнили HTML полного и компактного входа. Проверили общую оболочку, HOME, CITY_HOME, ADDRESS, тариф и конфигуратор, FAQ, ACCOUNT, OFFICIAL_SITE, города, покрытие, юридические страницы, поддержку, скорость и пустой каталог. Невалидные данные другого города дают выбранному URL прежнюю полную ошибку. Локальная HTTP-проверка сохранила `/faq` в меню после перехода с рабочей ревизии 7 на 8. Устаревшая рабочая ревизия и сменившаяся редакционная база дали 409, неизвестный URL исправного каталога — 404. Документ новой ревизии совпал с исходным HTML при неизменном содержимом fixture.

В исходном общем preview список новостей, пагинация, категория и статья присутствовали в меню. Общий рендерер завершался ошибкой «Маршрут не отрисован», потому что поддерживал только прежние типы. Новый путь использует общие публичные новостные renderers. Точное сравнение полного и компактного входа включает оболочку, видимые карточки, изображение со `srcset`, типизированное тело и связанные новости. В документе отключены формы, ссылки и скрипты.

Встроенный браузер не был доступен при проверке из этой сессии. Точное сравнение HTML, проверка кода клавиатурных элементов и HTTP воспроизведение не подтверждают браузерный фокус или скриншоты. Внешний выпуск и полный gate этой итерации ещё не выполнялись.

## Следующий этап

Проверили два прототипа на уже считанном входе того же PostgreSQL fixture. Для выбранного тарифа HTML совпал точно. Медиана 11 прогретых замеров на рендер и сериализацию выбранного ответа — 246,86 мс для полной проверки 207 городов. При сокращении входа до города тарифа и Москвы она составила 9,52 мс. Выбор и сериализация из уже проверенного результата той же ревизии заняли 0,16 мс. SQL, проверка идентичности снимка и хранение результата в эти значения не входят.

1. **Загрузка по маршруту.** Читать один город или общую страницу, точный опубликованный редакционный источник и минимальные данные меню. Повторно использовать существующие materialize, route policy и правила подстановки. Для HOME и каталога городов остаётся общая выборка компактных справочных данных. Такой путь ускоряет первый просмотр после сохранения. Изолированный рендер выбранного тарифа пропускает ошибку в другом городе, которую текущий контракт показывает. Такой режим требует отдельного решения о границе проверки.
2. **Готовый результат полной проверки рабочей ревизии.** Использовать механизм фоновой подготовки из #633 для произведённого один раз проверенного результата или точной прежней ошибки. Нынешний результат #633 хранит отчёт проверки. Опубликованные проекции #635 относятся к конкретной обслуживаемой версии. Для рабочего preview нужен сохраняемый производный снимок с данными оболочки, группами городов/тарифов и отдельными редакционными данными. Полные копии оболочки на каждый из 4 399 URL здесь не нужны. Быстрое чтение допускается только при совпадении сайта, рабочей ревизии, подтверждённого ID и `validationId` редакционной базы, digest или generation, версии рендерера и контекста разрешения переменных и медиа. Смена базы, в том числе retry с тем же ID, должна атомарно инвалидировать результат. Необходимы сценарии `/active` fail-closed, `RUNNING` до ACK, rollback и смена даты для календарных переменных. При отсутствии готового результата можно выполнить существующую строгую проверку или показать её фактический статус. Захват согласованного входа и тяжёлая проверка не должны удерживать Site lock.

Вариант с готовой полной проверкой сохраняет прежний контракт. Перед его приёмкой нужно измерить холодный запрос после сохранения, повторные выборы в рамках ревизии и конкурирующие запросы. Для сравнения нужны одинаковые HTML, снимки и ошибки, объём хранения, I/O по маршрутам, проверка фокуса и визуальное сравнение во встроенном браузере.

## Строгий повтор выбора и холодный вход

Первое продолжение применило только к общему предпросмотру компактное чтение `editorial` и замороженных redirects из `validation.sourceSnapshot`. Для нетипичной исторической структуры сохранилось точное прежнее чтение. В legacy-ветке разрешение редакционной базы выбирало только ID, site ID, sequence и `validationId`. Static на этом этапе проверял полный обслуживаемый каталог.

На нагрузке в 207 городов и 3 933 тарифа архив работающей публикации занимал 28 372 420 байт, а её source snapshot — 19 110 863 байта. Шесть пар чтений без кэша показали медиану серверного detail 2 077 → 1 138 мс и максимум 2 370 → 1 582 мс. Для menu медиана 689 → 235 мс. Объекты совпали. Это измерение legacy metadata на локальном PostgreSQL 18.

Рабочая ревизия одна недостаточна для ускоренного чтения. Изменение состояния и деривативов медиа, как и часть операций bootstrap, выполняется без увеличения `workingRevision`. Сравнили SQL SHA фактического содержимого и компактный ключ из физических версий строк. На fixture их медианы составили 347 и 29 мс. Выбрано сравнение содержимого. Физический ключ потребовал бы дополнительных гарантий при freeze, повторном использовании адресов строк и замене таблиц. Для редиректов фиксируются только поля, которые участвуют в чтении рабочего каталога. Обновление hit counter не инвалидирует результат.

Опциональный `WORKING_PREVIEW_REUSE_ENABLED` проверяет вход каждого запроса в одном Serializable snapshot. Ключ включает рабочую и опубликованную ревизии, версию правил, UTC-день, семантический SHA эффективных рабочих строк и Site media `ready`/derivatives, ID/sequence/`validationId` редакционной базы и её реально использованное содержимое. В static-режиме ключ также включает SHA подтверждённого обслуживаемого каталога. Попадание в кэш не обходит `/active` и проверку состояния выпуска. Встроенная проверка `YEAR` работает от даты того же захвата.

Один процесс допускает к повторному использованию один успешно проверенный результат в течение 60 секунд размером до 32 МиБ сериализованного JSON. Параллельный запрос сначала независимо сверяет тот же вход, затем ждёт результат общей проверки вне SQL-транзакции. При другом входе проверка выполняется отдельно. Экземпляры API не передают друг другу результат. Они самостоятельно считывают зафиксированное содержимое перед использованием своих результатов, поэтому изменение на другом экземпляре отражается при первом запросе после commit. Ошибки не переиспользуются. Декодирование и рендер полного набора остались на холодном запросе. Цепочки публикации и #633/#634 этот режим не используют.

| Локальный HTTP через NestJS/Fastify | Вызовы на вариант | p50 до → после, мс | p95 до → после, мс |
| --- | ---: | ---: | ---: |
| Холодный detail, чистый экземпляр кэша | 7 | 2 301 → 1 531 | 3 499 → 2 612 |
| Повторный выбор URL | 30 | 1 898 → 445 | 2 499 → 618 |

В HTTP-профиле ответы целиком совпали на HOME, CITY_HOME, тарифе, ADDRESS, FAQ, списке новостей и статье. Максимальный ответ составил 154 041 байт. В 37 запросах кандидат захватил рабочий каталог 8 раз. Для прямого `/active` с точным RUNNING снимком и без #635 один запрос новости занял 2 629 мс на холодном и 1 430 мс на прогретом пути. Неверный digest получил 503 даже при прогретом результате. Новый `validationId` с прежним ID заставил повторить проверку.

На PostgreSQL два отдельных экземпляра API вернули ширину варианта изображения поддержки 600, 620 и 640 пикселей после последовательных изменений `derivatives`. Рабочая ревизия оставалась 7. Обновление счётчика и времени перехода по редиректу сохраняло ключ и готовый результат. После commit `ready=false` новый запрос FAQ на обоих экземплярах возвращал прежнюю строгую ошибку `ASSET_SOURCE` с HTTP-статусом 400, хотя проблемный ресурс находится на другой странице. Уже начатый запрос удержал ранее захваченный Serializable snapshot и завершился с его вариантом 640. Следующий запрос также увидел 400. После возврата `ready=true` оба экземпляра отдали текущий вариант.

На этом этапе флаг оставили выключенным. Холодный p95 с флагом был выше бюджета 2 с. Для дальнейшего сокращения холодного времени пригодна отдельная рабочая подготовка по тому же ключу, с сохранением готового результата и повторной проверкой входа при чтении. Статус или отчёт подготовки выпуска сам по себе готовой страницы не подтверждает.

## Совмещение с проверенной проекцией #635

Кандидат построен от `27bf937b69d1b00f4a57d9aa23ce6070e4ad0481`. Оба чтения общей редакционной базы используют `readEditorialView` и проверку #635. В одном SQL snapshot совпадают подтверждённое поколение, digest и `validationId`. Уже проверенный digest входит в ключ повторного результата без повторной сериализации полного JSON. При неполном seal тот же захваченный `/active` ID проверяется полным чтением. Исторический source fallback привязан к тому же `validationId`. В legacy-ветке используем метаданные последнего успешного SQL-выпуска.

На отдельной копии репетиционного PostgreSQL 18 применена миграция 0080. Активный синтетический снимок находился в `RUNNING` до ACK. Он содержит 207 городов, 3 933 тарифа и 4 399 URL. Каталог занимает 28 372 420 байт, архив источника — 19 110 863 байта. Петля сравнения чередовала исходный кандидат `9f67af91db550e5edd188fdc7575a6be7f73b260` и совмещённый код через два локальных NestJS/Fastify HTTP-сервера. Для каждой холодной пары оба экземпляра начинали без готового результата. Отдельный локальный HTTP-сервер отдавал точную идентичность из `/active`. Ниже значения до конца JSON-ответа.

| Сценарий | Вызовов на вариант | p50 исходный → совмещённый, мс | p95 исходный → совмещённый, мс |
| --- | ---: | ---: | ---: |
| Меню маршрутов | 7 | 1 098 → 195 | 1 677 → 309 |
| Холодный выбор с переиспользованием | 7 | 2 747 → 1 437 | 4 390 → 2 972 |
| Повторный выбор с переиспользованием | 30 | 1 466 → 490 | 2 357 → 994 |

В отдельной серии из семи холодных выборов с проекцией и выключенным переиспользованием p50 составил 1 179 мс, p95 — 1 225 мс. Два HTTP-сервера вернули одинаковый JSON для всех пар. Типовые detail-ответы занимали до 154 041 байта, первая страница меню — 5 412 байт. В парных сериях фиксировались полные SQL-чтения `SitePublication.catalog`. Исходный путь выполнил 45, совмещённый при комплектной проекции — 0.

После замера отдельно проверили исторический обслуживаемый ID при более новом успешном SQL-выпуске. Удаление одной строки города оставило точные меню и detail через полный fallback с одним чтением `/active` на запрос. В legacy-режиме более новый успешный выпуск выбирался без `/active`. Устаревшая рабочая ревизия получила 409. Неверный digest при готовом seal получил 503 в обоих маршрутах без чтения полного каталога. При замене каталога и `validationId` под тем же ID PostgreSQL повысил поколение. Старый digest получил 503 до и после прогрева. С новым точным digest вернулась новая редакция статьи.

Результаты относятся к локальному HTTP на синтетических данных. Повторный выбор с кэшем уложился в цель, холодный p95 с ним остаётся выше 2 с. Без кэша холодная серия на готовом seal уложилась в цель в этом запуске. Перед внешней приёмкой нужны замеры на репрезентативном сохранении, конкурентной нагрузке и проверка во встроенном браузере. `WORKING_PREVIEW_REUSE_ENABLED` остаётся выключенным по умолчанию.
