# Изолированный прототип первого открытия Preview · #630

Базовое дерево `38cc75b80e665ae27d5cb76652ec3af718421a42`. Прототип остаётся в отдельном worktree `codex/preview-cold-bootstrap-630`. Для отката достаточно вернуться к базовой сборке. Миграций, новых зависимостей и env-флагов продукта нет.

Первое открытие получает пользователя, компактную сводку сайтов и первые options одним `GET /api/v1/admin/sites/preview-bootstrap`. Guard тот же, что у остальных admin routes. Ответ требует пользовательскую сессию как `/auth/me` и имеет `Cache-Control: private, no-store`. Сервер использует прежнюю сводку, правило выбора явного или единственного сайта и прежний расчёт маршрутов. Если options недоступны, клиент получает оболочку и выполняет прежнее чтение списка с прежним отображением ошибки. Ревизия и ID обслуживаемого основания по-прежнему передаются в отдельный `preview-page`; 409 сохраняется при смене каждого из них.

Для первой подписки на состояние публикации оболочка Preview передаёт свежую сводку сайтов из bootstrap. `publication-state` читается параллельно с выбранной страницей. Ручное обновление и обычные подписки других экранов не меняются. По 401 Preview убирает кадр, отменяет свои активные чтения, очищает кэш сессии и переводит на вход. Отдельный документ, sandbox и CSP остаются прежними.

Проверяются точный порядок guard → сводка → options → независимый page, отсутствие доступа до guard, machine token, 401, 409 при обеих сменах stamp, nullable base, явный/единственный сайт, fallback ошибки options и завершение bootstrap + page до разблокировки `publication-state`.

Локально прошли 28 профильных backend/Preview-тестов, 42 теста навигации, кэша, renderer и индикатора, Astro check и статическая production-проверка CSP. Системный Node 22.23.2 подходит для Nest build; Astro check и проверки проводились на поддерживаемом Node 24.22.3. Первый прогон preview UI без установленных зависимостей не нашёл шрифты. После штатной установки профильный набор прошёл.

В десяти чередующихся парах с искусственными 15 мс на каждый HTTP-запрос и удержанным `publication-state` p50/p95 до готового HTML снизились с 92,27/96,91 до 61,33/62,71 мс. Совпали DTO и HTML всех десяти пар. Число проверок сессии до завершения кадра на HTTP fixture снизилось с четырёх до двух. Измерение фиксирует сетевую очередность и работу renderer в Node; browser timing и production latency на этом этапе не измерялись.

## Встроенный браузер · парное сравнение готовых сборок

1. Подготовить отдельное дерево на базовом SHA. В базовом и экспериментальном worktree выполнить `pnpm install --frozen-lockfile` и собрать каждую админку с одинаковыми `PUBLIC_API_URL=http://localhost:43057/api/v1` и `ADMIN_URL=http://localhost:43057` через `pnpm --filter @provider/admin build`. Для экспериментального worktree потребуется также `pnpm --filter @provider/api build`.
2. Из экспериментального worktree запустить `node scripts/rehearse-preview-bootstrap-ui.mjs <absolute-baseline-dist> <absolute-candidate-dist>`. Это только локальный сервер. PostgreSQL, Redis и внешний контур не требуются. `PREVIEW_FIXTURE_WIRE_MS=100` задаёт одинаковую задержку каждого запроса, `PREVIEW_FIXTURE_PAGE_MS=130` добавляет задержку выбранной странице, `PREVIEW_FIXTURE_PUBLICATION_MS=15000` удерживает состояние публикации. Эти значения действуют по умолчанию.
3. Для прямого входа открывать `http://localhost:43057/fixture/session?arm=baseline` и `http://localhost:43057/fixture/session?arm=candidate` в чередующемся порядке. Для входа из меню добавить `&menu=true`, дождаться готовности обзора, затем выбрать «Предпросмотр». Сбрасывать браузерный ресурсный кэш для отдельной холодной серии и сохранять его для прогретой. Выполнить по 30 пар на серию. Ожидаемый кадр в обоих вариантах — «Политика» со штатным юридическим renderer.
4. В Network проверить, что кандидат отправляет один bootstrap до `preview-page`, не ждёт отложенный `publication-state`, и что `preview-options` используется после явного обновления. Для 401 при входе добавить `&expired=true`. Для 401 во время загрузки кадра установить `PREVIEW_FIXTURE_PUBLICATION_MS=10`, `PREVIEW_FIXTURE_PAGE_MS=500` и добавить `&expired=publication`. В первом случае запрос страницы отсутствует, во втором видимость кадра блокируется после 401 и поздний ответ не применяется. Оба сценария переводят на вход. Задержки стенда заданы искусственно для измерения сетевой очередности.
5. Сохранять начало навигации, старт и завершение bootstrap/options, заголовки и тело выбранной страницы, появление и загрузку iframe. Измерять отдельно отложенное состояние публикации. Сопоставлять ошибки CSP и сетевые ошибки в двух вариантах. Для полного сравнения продовых сценариев с защищёнными изображениями потребуется отдельная репрезентативная DB fixture.
6. Для обратной совместимости открыть `http://localhost:43057/fixture/session?arm=candidate&legacyApi=true`. Bootstrap должен вернуть 404. После прежних `/auth/me`, `sites`, `preview-options` и проверенного `preview-page` отображается тот же кадр. При 401 и 503 bootstrap запасной путь не запускается.

### Результат браузерного A/B

В Codex IAB сравнили готовые статические сборки `38cc75b8` и `a596382c`. Основной сценарий — прямое открытие `/preview` страницы `/politika`. По 30 чередующихся пар AB/BA выполнены с отключённым ресурсным кэшем и с одинаковым прогревом обеих сборок. Chrome Network подтвердил 0 из 28 попаданий в кэш в холодной серии и 28 из 28 в прогретой. Время до кадра измерялось от вызова прямого перехода через fixture-редирект до видимости заголовка «Политика» внутри `iframe` с пустым атрибутом `sandbox`. Время старта запроса отсчитывалось от начала загрузки конечного документа `/preview`.

| Прямой вход | p50 до кадра, мс | p95 до кадра, мс | p95 до старта `preview-page`, мс | Кандидат быстрее |
| --- | ---: | ---: | ---: | ---: |
| Холодный ресурсный кэш | 1 008 → 855 | 1 090 → 956 | 535 → 387 | 30/30 |
| Прогретый ресурсный кэш | 904 → 748 | 1 055 → 937 | 444 → 317 | 27/30 |

Во всех 120 измерениях кадр появился при ещё незавершённом `publication-state`. В консоли нормальных серий 0 ошибок и 0 предупреждений. Переход из меню загрузил `preview-bootstrap` и `preview-page`, обновление данных — `preview-options` и `preview-page`. При 401 bootstrap открылся `/login` без отправки запроса страницы. При 401 от `publication-state` уже запущенный `preview-page` был отменён, на `/login` iframe отсутствовал. В первоначальной модели стенда `/auth/me` в этом сценарии продолжал считать сессию действующей, поэтому после перехода на логин возникали повторные перенаправления. Модель истечения сессии исправлена, чтобы следующие защищённые запросы тоже возвращали 401.

Измерения сравнивают клиентскую цепочку на одном backend fixture с одинаковыми искусственными задержками 100/130/15 000 мс. Они не подтверждают внешний бюджет скорости, время PostgreSQL или загрузку защищённых медиа. Сырые пары `paired-network.json`, SHA-256 `ccd3efa673b15921bd4002175966d2f7387eeb379ab4587fc1c12fc99593b967`.

### Проверка совместимости перед выпуском

Во встроенном браузере проверены прежний UI с новым API, новый UI с новым API и новый UI при отсутствии bootstrap. В третьем случае зафиксирован 404 bootstrap, затем параллельный запуск `/auth/me` и `/admin/sites`, успешные `preview-options` и `preview-page`. Во всех трёх сценариях открыт кадр «Политика» с пустым атрибутом `sandbox`. Отсутствие маршрута bootstrap воспроизведено на HTTP fixture. Оно соответствует прежнему контроллеру.

При 401 на входе запрос кадра отсутствует. При 401 от `publication-state` браузер отменяет уже начатый `preview-page` и открывает `/login` без iframe. На экране входа повторная проверка `/auth/me` также вернула 401. После восстановления тестовой сессии кадр появился снова. Консоль браузера не зарегистрировала ошибок и предупреждений в проверенных сценариях.
