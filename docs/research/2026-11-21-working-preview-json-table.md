### Стоимость текстового результата Tariff

Из фактически выполненного запроса повторили тот же SELECT с теми же параметрами на PostgreSQL 18.6. Девять прогретых чередующихся пар дали p50/p95 4,95/5,33 мс без преобразования строк и 107,62/109,58 мс с `SERIALIZE TEXT`. Попарная прибавка p50/p95 102,73/104,25 мс. План одинаковый, сортировка в памяти, 261 попадание в общие буферы, физических чтений и временных файлов нет. PostgreSQL сформировал 17 383 КиБ текста для 3 933 тарифов. Эта операция `EXPLAIN` не отправляет строки клиенту. [CI](https://github.com/Celtoman/astro-telekom/actions/runs/44859397326), [документация PostgreSQL](https://www.postgresql.org/docs/18/sql-explain.html).

В синтетическом наборе каждый тариф содержит длинное описание `attributes.opisanie_tarifa`. Оно участвует в карточке тарифа и проходит проверки каталога. Эти размеры характеризуют тестовую выборку. Рабочую выборку нужно оценивать отдельно. У захваченного запроса совпал SHA-256 HOME. Сводка планов без параметров и содержимого имеет SHA-256 `645de46e8e7456fe31f3ca08fc6c7da8e8a103b66062490a25b36d104b0f3e24`.

На работающем `1051ea96` один агрегат с ограничением времени в транзакции только для чтения подтвердил 3 805 активных опубликованных тарифов в 207 городах. Текстовое представление `attributes` занимает 7 229 036 байт суммарно, p50/p95 на строку 1 931/2 107 байт. У 3 775 тарифов есть описание, суммарно 5 289 197 байт. p50/p95 описания 1 450/1 575 байт. В агрегат входят только тарифы опубликованных городов. Это объём полей до передачи клиенту, а не измерение времени HTTP или размера всего результата SELECT. Описания и идентификаторы тарифов не извлекались.

Отдельный агрегат с теми же фильтрами не нашёл совпадений `(cityId, createdAt)` среди 3 805 тарифов. Пакетный импорт может создать такие совпадения. Штатная выборка сортирует тарифы по `createdAt`, поэтому сужение SQL должно сохранить очередность строгих диагностик. При совпадениях эксперименту нужен штатный путь в той же Serializable-транзакции.

Сравнили два синтетических набора с описаниями 4 092 и 1 452 байта на тариф. Второй размер близок к рабочей медиане. Остальные поля совпали по SHA-256. Текстовый результат SQL сократился с 17 383 до 7 243 КиБ. В девяти прогретых парах на вариант p95 с `SERIALIZE TEXT` составил 137,52 и 29,58 мс. Сокращение сериализации сохранилось при сортировке репрезентативного набора с временным файлом. В 12 запросах на вариант p95 HTTP оказался 747,00 и 464,59 мс. В этих небольших сериях p95 соответствует максимуму. Ответ HOME и строгая ошибка 400 совпали побайтово. Сравнение измеряет влияние ширины данных, программный путь у обоих наборов один. [Прогон](https://github.com/Celtoman/astro-telekom/actions/runs/44860477624).

## Компактное чтение холодного HOME

Кандидат `4018dacc` сокращает только строковое `attributes.opisanie_tarifa` без открывающей фигурной скобки, если запрошен точный `/` и переиспользование выключено. HOME возвращает профили городов и данные общей страницы. Описания со скобкой остаются в полном виде для строгой диагностики. При совпадениях `(cityId, createdAt)` исходные тарифы захватываются через штатное чтение Prisma в том же Serializable-снимке.
